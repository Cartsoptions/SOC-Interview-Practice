# SOC Interview Practice — 2026-08-28

## Question 28

### Interview Question

What is Kusto Query Language (KQL), and how would you use it in Microsoft Sentinel during a Tier 1 SOC investigation rather than just saying that it is a query language?

### Interview-Ready Answer

Kusto Query Language, or KQL, is the query language Microsoft uses to analyse log and telemetry data in services such as Microsoft Sentinel and Log Analytics. Microsoft’s current Sentinel training explicitly describes KQL as the language used to query log data for detections, analysis, reporting, workbooks and hunting.

In a SOC environment, I would use KQL to move from an alert summary to the underlying evidence. My goal would not be to write the most complicated query possible; it would be to answer specific investigation questions such as: Which user or host triggered the alert? What happened immediately before and after? Is the behaviour isolated or widespread? Are there related authentication, endpoint or network events?

I would start with the relevant table and time window, then filter to the entities involved, project only the useful fields, sort by time and expand the search when the evidence requires it. Operators such as `where`, `project`, `extend`, `summarize`, `order by` and `join` can help structure that analysis, but exact table and field names depend on the connected data source and schema. I would therefore inspect the actual table schema instead of inventing fields.

As a Tier 1 analyst, I would normally use existing queries, analytics and hunting content as a starting point, modify them carefully to answer the case at hand, document what I found and escalate when the evidence meets the playbook criteria. Building production detection rules or making broad changes to shared analytics would normally require the relevant authority or detection-engineering process.

### Real-World SOC Scenario

Microsoft Sentinel raises an alert for repeated failed sign-ins followed by a successful sign-in for one user. I would use KQL to retrieve the relevant authentication events for that account around the alert timeframe, order them chronologically, compare source IPs and applications, and then expand the investigation to related endpoint or network telemetry if available. If the successful sign-in is followed by unusual access or endpoint activity, the combined evidence would strengthen the case for escalation.

The alert is the observation. Account compromise is a hypothesis. KQL helps me retrieve and correlate the evidence needed to support or reject that hypothesis.

### What I Would Check as a Tier 1 Analyst

- The alert entities and exact timeframe
- Which Sentinel/Log Analytics table contains the relevant telemetry
- Actual field names and schema before writing filters
- User, host, IP, process, application or resource involved
- Events immediately before and after the alert
- Frequency and prevalence across other users or hosts
- Authentication, endpoint, firewall, DNS or proxy evidence that can be correlated
- Whether joins or summaries are actually necessary for the question
- Whether the query returns expected data or is missing telemetry because of connector/retention coverage
- Observation versus hypothesis versus confirmed evidence
- Whether the case meets documented escalation criteria

### Relevant Tools / Logs

Microsoft Sentinel; Log Analytics; KQL; Microsoft Defender XDR/Endpoint telemetry where connected; Microsoft Entra sign-in data; Windows/Linux logs; firewall, DNS and proxy telemetry; incident/ticketing records.

### Key Interview Takeaway

KQL is the query language used to analyse telemetry in Microsoft Sentinel. As a Tier 1 analyst, I would use it to filter, correlate and timeline the evidence behind an alert, using the real table schema and keeping the query focused on the investigation question rather than writing complex queries for their own sake.

## Question 29

### Interview Question

What is LDAP, and how would you investigate suspicious LDAP activity or possible Active Directory enumeration as a Tier 1 SOC analyst?

### Interview-Ready Answer

LDAP, or Lightweight Directory Access Protocol, is a protocol for accessing and working with directory services. RFC 4511 defines LDAP as providing access to distributed directory services. In Microsoft Active Directory environments, LDAP is commonly used by applications and administrators to query directory information such as users, groups, computers and other directory objects.

In Windows Server environments, Microsoft documents LDAP on TCP/UDP port 389 and LDAP over SSL/TLS on TCP port 636. Global Catalog queries commonly use TCP 3268, or 3269 when protected with SSL/TLS. Those port numbers are useful context, but seeing LDAP traffic is not automatically suspicious because legitimate applications, domain-joined systems and administrators rely on directory queries every day.

During a SOC investigation, I would look for abnormal context: an unusual workstation or non-admin endpoint issuing large numbers of directory searches, a process that is not normally associated with directory administration, rapid enumeration of many users or groups, or LDAP discovery followed by credential access, lateral movement or privilege-related activity.

MITRE ATT&CK’s current detection guidance for Domain Account Discovery specifically includes LDAP queries from non-domain controllers or non-admin endpoints as a signal defenders can monitor, and its Domain Groups technique includes LDAP-based group enumeration. This means LDAP can be part of legitimate administration or adversary discovery; the surrounding process, account, source host, query pattern and follow-on behaviour determine the risk.

### Real-World SOC Scenario

EDR and network telemetry show a normal user workstation making repeated LDAP queries to a domain controller and enumerating many domain users and privileged groups. The activity begins shortly after an unusual executable starts on the host.

I would identify the process responsible for the LDAP connections, review the user context, timing and source host, determine whether the behaviour matches approved administrative or inventory software, and correlate the activity with process creation, PowerShell, authentication and network evidence. If the LDAP enumeration is followed by attempts to access privileged systems or credential-related activity, I would escalate the case as suspected adversary discovery with supporting evidence.

### What I Would Check as a Tier 1 Analyst

- Source host/IP and whether it normally performs directory queries
- User/account context and privilege level
- Destination domain controller or directory service
- TCP/UDP 389, TCP 636, or Global Catalog ports where relevant
- Process responsible for the LDAP connection
- Process path, signer, hash and parent/child relationships where available
- Volume and timing of directory queries
- Whether users, groups or privileged-group membership are being enumerated
- Windows 4688/Sysmon or EDR process telemetry
- PowerShell or command-line activity around the same time
- Related authentication, SMB/RDP or lateral-movement evidence
- Approved inventory, identity-management or administration tools that could explain the activity
- Similar LDAP behaviour on other endpoints
- Escalation criteria and containment authority

### Relevant Tools / Logs

EDR/Defender for Endpoint; Microsoft Sentinel, Splunk or Wazuh; Windows Security and Sysmon telemetry where configured; domain-controller/network telemetry; firewall/NSM data; PowerShell logs; Active Directory auditing; change-management and software-inventory records.

### Key Interview Takeaway

LDAP is a directory-access protocol and is heavily used in Active Directory environments. I would not treat LDAP traffic itself as malicious; I would investigate who or what is querying the directory, from which host, at what volume, for which objects, and what behaviour follows the enumeration.

## Question 30

### Interview Question

What is SMTP, and how would you use mail-flow evidence such as message trace during a phishing or suspicious-email investigation?

### Interview-Ready Answer

SMTP, or Simple Mail Transfer Protocol, is the protocol used to transfer email between mail systems. RFC 5321 describes an SMTP client establishing a two-way channel to an SMTP server and transferring a message through one or more mail servers or relays. A normal SMTP mail transaction includes commands that identify the sender and recipient and then transfer the message data.

In a SOC environment, SMTP knowledge helps me understand the difference between the message envelope, routing path and what the user sees in the visible From or Reply-To fields. That distinction matters because an attacker can manipulate visible message content while the underlying mail-routing evidence tells a different story.

In Microsoft 365, Exchange Online message trace can follow a message through the service and show whether it was received, rejected, deferred, delivered or otherwise acted on before reaching its final status. Microsoft also documents that message trace uses the SMTP `MAIL FROM` value as the sender for trace searches even when the visible From or Reply-To values differ. That makes message trace useful for confirming delivery and routing, but it should be correlated with full message headers and the Defender for Office 365 email investigation evidence where available.

As Tier 1, I would use message trace to establish whether the service received and delivered the message, who the sender and recipients were, what events occurred in transit, and whether the same message reached other users. I would then correlate that with headers, SPF/DKIM/DMARC results, URLs/attachments, user interaction, identity activity and endpoint evidence. Delivery alone does not prove the message was safe, and a suspicious visible From address alone does not prove which SMTP system actually sent the message.

### Real-World SOC Scenario

A user reports an urgent payment email that appears to come from a senior executive. The visible From name looks legitimate, but the Reply-To is external.

I would preserve the message, inspect the headers and authentication results, then use message trace to confirm when Exchange Online received the message, which recipients received it and what delivery actions occurred. If multiple finance users received the same message, I would scope the campaign, check whether anyone clicked or replied, and correlate identity and endpoint telemetry for affected users. If the message was delivered from unexpected infrastructure and contains a malicious link or fraudulent payment request, I would escalate according to the phishing/BEC playbook.

### What I Would Check as a Tier 1 Analyst

- Visible From, Sender, Reply-To and Return-Path values
- SMTP `MAIL FROM`/envelope sender where available
- Message-ID and Network Message ID where available
- Received/routing headers and timestamps
- SPF, DKIM and DMARC results and alignment
- Message-trace status: received, delivered, failed, pending, quarantined or other recorded action
- Sender, recipient and direction in message trace
- Whether the same message reached additional recipients
- Mail-flow or transport-rule actions where trace details expose them
- URLs, attachments and security verdicts
- User actions: clicked, replied, submitted credentials, approved MFA or made payment
- Identity and endpoint evidence after interaction
- Approved business explanation or known internal sender workflow
- Escalation/remediation authority

### Relevant Tools / Logs

Exchange Online message trace; Microsoft Defender for Office 365 Email entity and Threat Explorer/Real-time detections where licensed; message headers; Exchange/mail-flow data; Microsoft Sentinel/Splunk/Wazuh; Entra sign-in logs; EDR; DNS/proxy/firewall telemetry; Proofpoint or Abnormal Security where deployed.

### Key Interview Takeaway

SMTP is the protocol used to transfer email between mail systems. In a SOC investigation, I would use message trace and headers to reconstruct delivery and routing, then correlate that evidence with authentication results, URLs, attachments, user actions, identity and endpoint telemetry before deciding whether the email is malicious.
