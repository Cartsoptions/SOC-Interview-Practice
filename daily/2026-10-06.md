# SOC Interview Practice — 2026-10-06

## Question 113

### Interview Question
What is DNS, and why is DNS telemetry valuable to a SOC analyst?

### Interview-Ready Answer
DNS is the distributed naming system that lets systems locate Internet resources using domain names rather than requiring users and applications to know IP addresses directly. NIST SP 800-81 Rev. 3, published in March 2026, notes that DNS translates domain names into IP addresses and can serve both as a security-policy enforcement point and as an indicator of potentially malicious network activity.

In a SOC environment, I would use DNS telemetry to help answer which host queried which domain, when it happened, how frequently it happened, and whether the domain/query pattern fits normal business activity. DNS evidence can help connect a suspicious process or endpoint to infrastructure used for phishing, malware command-and-control, or tunneling. It is evidence, not a verdict: a newly seen or unusual domain is not automatically malicious.

As Tier 1, I investigate and correlate the DNS evidence with endpoint, proxy, firewall, identity and threat-intelligence data. I would not normally change enterprise DNS architecture or filtering policy unless my role explicitly authorised that.

### Real-World SOC Scenario
An EDR alert shows an unusual process on a workstation, and DNS telemetry shows the same host repeatedly resolving a domain not normally seen in the environment. I would correlate process timing, DNS requests, network connections, domain context and activity on other hosts before deciding whether the pattern supports malicious command-and-control.

**Observation:** The endpoint generated DNS activity involving an unusual domain.
**Hypothesis:** The domain may be associated with malicious infrastructure or command-and-control.
**Confirmed Evidence:** Requires corroborating endpoint/network evidence or validated threat intelligence; unusual DNS alone is insufficient.

### What I Would Check as a Tier 1 Analyst
- Source device/user and timestamp
- Queried domain/FQDN and query pattern where available
- Frequency, recurrence and other affected hosts
- Process responsible for related network activity where endpoint telemetry supports attribution
- DNS response/resolved IPs and subsequent connections where available
- Proxy/firewall/EDR evidence and reputable threat intelligence
- Whether the domain/service is expected for that host or application

### Tools / Logs
Enterprise DNS/resolver logs, Microsoft Defender XDR/EDR, Microsoft Sentinel, Splunk, Wazuh, Sysmon where deployed, firewall/proxy logs, Wireshark/NSM where authorised, threat intelligence.

### Interview Takeaway
"DNS translates names into information systems need to reach network resources. In a SOC I use DNS telemetry as an investigation pivot, correlating domain activity with the host, process and subsequent network behaviour rather than treating an unusual domain as proof of compromise."

## Question 114

### Interview Question
What is DNS tunneling, and what evidence would make you suspect it?

### Interview-Ready Answer
DNS tunneling is abuse of DNS traffic to carry information that DNS was not intended to transport in that way, often to support command-and-control or, depending on the technique, data exfiltration. MITRE ATT&CK maps DNS used for command-and-control to T1071.004. MITRE's current DET0400 detection strategy highlights behaviours such as high-frequency or anomalous DNS queries, long/encoded-looking subdomains and DNS activity initiated by unusual processes such as PowerShell, rundll32 or Python.

I would not label every long DNS name or burst of DNS traffic as tunneling. CDNs, security products and legitimate applications can create unusual-looking DNS patterns. I would establish a baseline and correlate query characteristics, process attribution, destination/domain context, timing and data volume.

### Real-World SOC Scenario
A workstation begins making hundreds of DNS queries containing long, changing subdomain labels to the same parent domain. Endpoint evidence associates the activity with an unexpected scripting process. That combination is more suspicious than either signal alone and warrants investigation for DNS-based command-and-control or tunneling.

**Observation:** Repetitive DNS traffic with unusual subdomain characteristics is occurring.
**Hypothesis:** DNS may be carrying command-and-control or encoded data.
**Confirmed Evidence:** Requires protocol/query inspection and corroborating endpoint/network evidence showing the DNS channel is being used maliciously.

### What I Would Check as a Tier 1 Analyst
- Query rate, timing and periodicity
- Length and entropy/variability of subdomains
- Record types and parent domain
- Process generating or associated with the traffic where telemetry permits
- Whether other hosts show the same pattern
- Domain age/reputation and organisational allowlists
- DNS response behaviour and related endpoint/process events
- Outbound data volume and evidence of staged data if exfiltration is suspected

### Tools / Logs
DNS resolver logs, Defender for Endpoint/XDR, Sentinel, Splunk, Wazuh, Sysmon Event 22 where configured, network sensor/packet capture where authorised, firewall/proxy and threat intelligence.

### Interview Takeaway
"DNS tunneling is abuse of DNS as a covert communications channel. I look for behavioural patterns such as unusual query frequency, long or changing subdomains and unexpected processes, then correlate them before reaching a verdict."

## Question 115

### Interview Question
Explain what this Defender XDR Advanced Hunting query tells you and what it does not prove.

```kusto
DeviceNetworkEvents
| where Timestamp > ago(24h)
| where RemotePort == 53
| summarize Connections=count(),
            RemoteIPs=dcount(RemoteIP)
            by DeviceName, InitiatingProcessFileName
| order by Connections desc
```

### Interview-Ready Answer
This query searches Microsoft Defender XDR's DeviceNetworkEvents table for recorded network events in the previous 24 hours where RemotePort equals 53. It groups results by device and initiating process, counts matching records, estimates the number of distinct remote IPs, and sorts the highest event counts first.

Microsoft documents DeviceNetworkEvents fields including Timestamp, DeviceName, RemoteIP, RemotePort, Protocol, RemoteUrl and InitiatingProcessFileName.

The query is useful for surfacing processes associated with network connections to remote port 53, but it does not by itself prove DNS tunneling, does not inspect DNS payload/query contents, and should not be described as a complete DNS detector. Port 53 traffic may be legitimate, and DNS can also be transported in ways this simple filter does not comprehensively cover.

### Real-World SOC Scenario
The results show a scripting process with a much higher number of port-53 network events than expected. I would pivot into the raw events, inspect process context, protocol and destination, then correlate with resolver/network telemetry that exposes actual DNS queries before deciding whether DNS abuse is occurring.

**Observation:** A device/process has many network events to remote port 53.
**Hypothesis:** The process may be generating unusual DNS traffic.
**Confirmed Evidence:** Requires raw event validation plus DNS/query and endpoint evidence supporting malicious use.

### What I Would Check as a Tier 1 Analyst
- Raw DeviceNetworkEvents and ActionType
- InitiatingProcessFileName, path/hash/command line through related endpoint telemetry
- RemoteIP, RemoteUrl where populated, Protocol and timing
- Enterprise DNS/resolver logs containing query details
- Baseline for that process/device
- Other hosts contacting the same infrastructure
- Related EDR alerts and process activity

### Tools / Logs
Defender XDR DeviceNetworkEvents, Defender for Endpoint, DNS/resolver telemetry, Sentinel, Splunk, Wazuh, Sysmon/network sensors where deployed.

### Interview Takeaway
"This hunt identifies endpoint processes associated with connections to remote port 53. It is a lead, not proof of DNS tunneling; I need DNS query content/patterns and endpoint context to validate the hypothesis."

## Question 116

### Interview Question
Your SOC detects a PowerShell process on a finance workstation generating high-frequency DNS queries with long, changing subdomains to one unfamiliar parent domain. Shortly before this, the same host created a large archive file. How would you triage it?

### Interview-Ready Answer
I would treat this as high priority because the signals form a potentially meaningful chain: unusual process activity, anomalous DNS behaviour and possible data staging. I would not immediately call it exfiltration.

First I would build the timeline: archive creation -> PowerShell activity -> DNS queries -> any related outbound network behaviour. I would identify what created the archive, its path/size and what files were included if authorised telemetry allows that determination. I would inspect the PowerShell process tree and command line, user context, parent process, hash/signature information where relevant and related alerts.

Then I would investigate the DNS pattern: query frequency, subdomain length/variability, record types, parent domain, responses, process attribution and whether other hosts show the same activity. MITRE ATT&CK T1071.004 covers DNS for command-and-control, while T1048/its sub-techniques cover exfiltration over alternative protocols. MITRE DET0400 specifically highlights high-frequency/anomalous DNS queries from non-standard processes as a DNS-tunneling signal.

The archive plus DNS behaviour raises an exfiltration hypothesis, but archive creation alone is not proof of staging and DNS anomalies alone are not proof data left the network. I would seek evidence connecting the archive/data to the DNS channel or other outbound transfer.

If evidence supports active malicious command-and-control or exfiltration, I would urgently escalate and follow the organisation's containment playbook. If my Tier 1 authority allows endpoint isolation, I would isolate according to that playbook; otherwise I would request immediate isolation while preserving the evidence needed for investigation.

### Real-World SOC Scenario
The archive was created by an unexpected process in the user's profile, PowerShell then launched with a suspicious command line, and DNS telemetry shows repeated long subdomains to an unapproved domain. Packet/network or resolver evidence further demonstrates encoded data being carried in the DNS queries. At that point, the exfiltration assessment is far stronger and requires urgent containment and scoping.

**Observation:** Archive creation, PowerShell execution and anomalous DNS activity occurred on the same host.
**Hypothesis:** Data may have been staged and DNS may be used for C2 or exfiltration.
**Confirmed Evidence:** Requires corroboration connecting malicious process behaviour and the DNS channel to unauthorised communication/data transfer.

### What I Would Check as a Tier 1 Analyst
- Full timeline and affected user/device
- Archive creator, path, size and relevant file evidence
- PowerShell parent/child processes and command line
- DNS query frequency, names, record types, responses and destination/domain context
- Other hosts querying the same parent domain
- Network/packet evidence where available and authorised
- EDR file/process/network telemetry
- Whether finance data or sensitive files were accessed before the archive was created
- Related identity, email or initial-access alerts
- Scope, evidence preservation and immediate escalation/containment authority

### Tools / Logs
Defender for Endpoint/XDR, Sentinel, Splunk, Wazuh, PowerShell/Windows logs, DNS resolver logs, Sysmon where deployed, firewall/network sensors, Wireshark/packet capture where authorised, threat intelligence.

### Interview Takeaway
"I would correlate the whole chain rather than label the DNS anomaly alone as exfiltration. The archive, suspicious PowerShell and abnormal DNS raise the risk sharply; I then look for evidence linking staged data to the DNS channel, scope the environment and escalate for authorised containment."
