# SOC Interview Practice — 2026-09-29

## Question 97

### Interview Question

What is EDR, and how would you use it as a Tier 1 SOC analyst rather than just saying it is “antivirus with more features”?

### Interview-Ready Answer

EDR, or Endpoint Detection and Response, is endpoint security technology that records and analyses endpoint activity so defenders can detect, investigate and respond to suspicious behaviour. Traditional antivirus is primarily associated with preventing or detecting known malicious files and patterns, while EDR gives the SOC richer behavioural telemetry such as process creation, parent-child process relationships, command lines, files, network activity and security alerts, plus response actions depending on the product and permissions.

In a SOC environment, I would use EDR to answer investigation questions such as: What process ran? What launched it? Under which account? What command line was used? Did it create files, spawn child processes or make network connections? Is the behaviour isolated to one endpoint or seen elsewhere? In Microsoft Defender for Endpoint, for example, the device page exposes investigation context and response actions such as collecting an investigation package, running an antivirus scan, initiating Live Response where permitted, and isolating a device. I would not assume that every Tier 1 analyst is authorised to perform those actions. My responsibility is to investigate, document evidence, follow the playbook and execute or request containment only within my assigned authority.

Observation: an EDR alert or telemetry shows endpoint behaviour. Hypothesis: the behaviour may be malicious or may be legitimate administration/software activity. Confirmed malicious activity requires supporting evidence and context.

### Real-World SOC Scenario

An EDR alert reports PowerShell launched from Microsoft Word after a user opened an attachment. I would inspect the process tree, command line, user, file/hash information, subsequent child processes and network activity. Word spawning PowerShell is unusual enough to investigate, but it is not by itself proof of malware. If the PowerShell command downloads content from an untrusted domain and the endpoint then launches an unknown payload, the evidence becomes much stronger and I would escalate promptly, requesting or performing containment according to the playbook and my permissions.

### What I Would Check as a Tier 1 Analyst

- Alert title, severity, detection source and timestamp
- Device and signed-in user
- Process tree and parent-child relationship
- Process/file path and command line
- File hashes and reputation where appropriate
- Digital-signature information where available
- Network connections and remote destinations
- Related file/registry/persistence activity
- Whether the behaviour is expected for that user/device
- Similar activity across other endpoints
- Previous alerts on the device/user
- Containment/escalation authority and playbook steps

### Relevant Tools / Logs

Microsoft Defender for Endpoint/Defender XDR, other EDR/XDR platforms, Microsoft Sentinel, Splunk, Wazuh, Windows Security logs, Sysmon where deployed, DNS/proxy/firewall logs and threat-intelligence sources.

### Key Interview Takeaway

“EDR gives the SOC behavioural endpoint telemetry and response capability. As Tier 1, I would use it to reconstruct what happened on the endpoint, correlate process, user, file and network evidence, then follow the playbook for escalation or authorised containment rather than treating an alert as automatic proof of compromise.”

## Question 98

### Interview Question

What does Windows Security Event ID 4688 tell you, and what are its limitations during a SOC investigation?

### Interview-Ready Answer

Microsoft documents Security Event ID 4688 as “A new process has been created.” It is valuable because process creation is central to many endpoint investigations. Depending on Windows version and audit configuration, the event can provide the new process ID/name, creator information and process command line. Microsoft specifically notes that the Process Command Line field is empty by default unless the policy to include command lines in process creation events is enabled.

In a SOC environment, I would use 4688 to help reconstruct execution: which executable started, who launched it, what parent/creator context is available and, if command-line auditing is enabled, what arguments were supplied. I would correlate the event with EDR/Sysmon, authentication, file, network and PowerShell telemetry rather than using one event in isolation.

A common interview mistake is to say that Event 4688 proves malware execution. It does not. Legitimate administrators, software installers and business applications create processes constantly. The event is evidence of process creation; maliciousness depends on context such as unusual parent-child relationships, suspicious paths or arguments, unexpected accounts, network activity, reputation and follow-on behaviour.

Observation: a process was created. Hypothesis: the process may be suspicious based on context. Confirmed malicious execution requires corroborating evidence.

### Real-World SOC Scenario

You see 4688 for `powershell.exe` on a finance workstation. I would inspect the creator/parent process, account, path and command line if available. PowerShell launched interactively by an authorised administrator during a documented maintenance window may be legitimate. PowerShell spawned by Word with encoded or download-oriented arguments, followed by an outbound connection and unknown child process, would justify urgent investigation and likely escalation.

### What I Would Check as a Tier 1 Analyst

- Event timestamp and affected host
- New process name/path and process ID
- Creator/parent process information
- Account/security context
- Process command line, if auditing is enabled
- Whether the path and parent-child relationship are expected
- File hash/signature/reputation where available
- Related EDR/Sysmon process and network telemetry
- PowerShell operational/script-block logs if relevant and enabled
- User activity/change window
- Follow-on child processes, persistence or network connections

### Relevant Tools / Logs

Windows Security Event 4688, Microsoft Defender for Endpoint/Defender XDR, Microsoft Sentinel, Splunk, Wazuh, Sysmon Event ID 1 where deployed, PowerShell logs, DNS/proxy/firewall telemetry.

### Key Interview Takeaway

“4688 records process creation. It is excellent execution evidence, but it does not tell me by itself that a process is malicious. I would correlate the process, parent, user, command line and follow-on endpoint/network activity before reaching a verdict.”

### Verification Notes

- Microsoft Learn Event 4688: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4688
- Microsoft documents that command-line data in 4688 requires the relevant process-creation auditing policy; otherwise the field is empty.

## Question 99

### Interview Question

You are hunting in Microsoft Defender XDR and see this KQL. Explain what it does, what it does not prove, and what you would investigate next:

```kusto
DeviceProcessEvents
| where FileName =~ "powershell.exe"
| project Timestamp, DeviceName, AccountName, FileName,
          ProcessCommandLine, InitiatingProcessFileName, SHA1
| order by Timestamp desc
```

### Interview-Ready Answer

The query searches the Defender XDR `DeviceProcessEvents` table for process events where `FileName` case-insensitively equals `powershell.exe`. It then returns selected investigation fields: time, device, account, process name, the PowerShell command line, initiating process name and SHA1, ordered newest first.

The field choices are useful because Microsoft documents `ProcessCommandLine` as the command line used to create the new process and `InitiatingProcessFileName` as the process file that initiated the event. `SHA1` identifies the file involved in the recorded action when populated. However, the query does not prove malicious PowerShell. PowerShell is a legitimate administrative and automation tool, and MITRE ATT&CK T1059.001 describes how adversaries may abuse it for execution. The analyst must distinguish normal administration from abuse using context.

I would inspect unusual parents such as Office applications or script hosts, suspicious arguments such as encoded/obfuscated commands, the user and device role, execution time, child processes and subsequent network activity. I would also remember that attackers can use PowerShell through underlying .NET interfaces without directly launching `powershell.exe`, so this exact query is useful but not a complete PowerShell-abuse detector.

Observation: `powershell.exe` process events are present. Hypothesis: one or more executions may represent PowerShell abuse. Confirmed malicious activity requires command/context and correlated endpoint/network evidence.

### Real-World SOC Scenario

The result shows `WINWORD.EXE` initiating `powershell.exe` for a standard user, followed shortly by network activity to a newly observed external domain. I would inspect the complete command line, originating document/email context, child processes, file changes and related `DeviceNetworkEvents`. If the command retrieves and executes attacker-controlled content, that becomes strong evidence of malicious execution and should be escalated under the incident playbook.

### What I Would Check as a Tier 1 Analyst

- `Timestamp`, `DeviceName` and `AccountName`
- `ProcessCommandLine`
- `InitiatingProcessFileName` and broader process tree
- File path and SHA1/reputation
- Whether the activity matches approved administration
- Child processes and file writes
- Network connections, `RemoteIP`/`RemoteUrl` where correlated
- Related email/document if Office was the parent
- PowerShell logging where enabled
- Other devices/users showing the same command or indicators
- Relevant MITRE ATT&CK mapping only after behaviour is understood

### Relevant Tools / Logs

Microsoft Defender XDR Advanced Hunting (`DeviceProcessEvents`, `DeviceNetworkEvents`), Microsoft Sentinel, Defender for Endpoint device timeline, PowerShell logs, Windows Security/Sysmon, DNS/proxy/firewall logs, email-security telemetry and threat intelligence.

### Key Interview Takeaway

“This query finds direct `powershell.exe` process events and exposes useful context, but PowerShell is dual-use. I would investigate the parent process, command line, user, child processes and network activity, and I would not call it malicious simply because PowerShell appears.”

### Verification Notes

- Microsoft Defender XDR DeviceProcessEvents schema: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table
- Microsoft Defender XDR DeviceNetworkEvents schema: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-devicenetworkevents-table
- MITRE ATT&CK T1059.001 PowerShell: https://attack.mitre.org/techniques/T1059/001/
- MITRE detection strategy DET0455 notes suspicious PowerShell behavioural chains such as encoded commands, unusual parents, network connections and child processes: https://attack.mitre.org/detectionstrategies/DET0455/

## Question 100

### Interview Question

A Microsoft Defender alert shows `WINWORD.EXE` spawning `powershell.exe` on a user's laptop. The command line is encoded, and minutes later the endpoint connects to an unfamiliar external IP. As a Tier 1 analyst, how would you triage this and decide whether to isolate the device?

### Interview-Ready Answer

I would treat this as high-priority suspicious behaviour because the evidence forms a chain rather than a single weak indicator: an Office process launches PowerShell, the command is encoded, and related outbound network activity follows. MITRE's current PowerShell detection guidance specifically highlights encoded commands, unusual parent processes, network connections and child-process activity as useful behavioural signals. Even so, I would separate observation from conclusion and rapidly validate the context.

First, I would confirm the alert entities, timestamps, user and device. I would inspect the process tree and full PowerShell command line, decode or safely analyse the encoded content using approved tooling/processes, and determine whether it attempts to download, execute or persist content. I would correlate the network connection with the initiating process, inspect the destination's reputation/context, and look for child processes, dropped files, persistence, credential-access indicators or similar activity elsewhere. If the activity came from an email attachment, I would also pivot into the email-security evidence to identify the message, sender, recipients, URL/attachment verdicts and whether other users received it.

For containment, I would follow the organisation's playbook and my permissions. Microsoft Defender for Endpoint supports device isolation as a response action; Microsoft states that isolation disconnects the device from the organisation's network while maintaining Defender service connectivity, subject to platform/configuration considerations. As Tier 1, I would isolate the endpoint myself only if the playbook and my role authorise it. Otherwise I would escalate/request isolation immediately when the evidence indicates likely compromise or there is significant risk of command-and-control, lateral movement or data loss.

Observation: Word spawned encoded PowerShell and outbound communication followed. Hypothesis: malicious document or phishing-led PowerShell execution with possible command-and-control/payload retrieval. Confirmed evidence would include decoded malicious instructions, a validated malicious destination/payload, unauthorised execution or other corroborating post-exploitation telemetry.

### Real-World SOC Scenario

A user opens an emailed Word document. Defender shows Word spawning PowerShell, whose decoded command retrieves a script from an external domain and starts another executable. `DeviceNetworkEvents` ties the PowerShell/descendant activity to the destination, and the user confirms they were not performing administrative work. I would document the timeline and indicators, check whether the same email or indicators affected other users/devices, and follow the incident playbook for urgent containment and escalation. If authorised, device isolation can reduce further network activity while Defender continues monitoring; if not authorised, I would request it immediately from the responder who holds that permission.

### What I Would Check as a Tier 1 Analyst

- Alert severity, entities and timeline
- User/device role and expected activity
- Full process tree: Word → PowerShell → descendants
- PowerShell command line and safely decoded content
- File paths, hashes, signatures and reputation
- Network connections tied to the suspicious process
- Remote IP/domain reputation and organisational history
- Downloaded/dropped files and persistence activity
- Related PowerShell/Windows/Sysmon telemetry where available
- Originating email, sender, attachment/URL and other recipients
- Similar indicators across the environment
- Signs of credential access, lateral movement or data exfiltration
- Whether containment is authorised for Tier 1
- Evidence preservation, ticket updates and escalation details

### Relevant Tools / Logs

Microsoft Defender for Endpoint/Defender XDR, Advanced Hunting `DeviceProcessEvents` and `DeviceNetworkEvents`, Microsoft Sentinel, Windows Security Event 4688, Sysmon where deployed, PowerShell logs, Microsoft Defender for Office 365 or equivalent email security such as Proofpoint/Abnormal Security, DNS/proxy/firewall logs and threat-intelligence sources.

### Key Interview Takeaway

“I would triage the whole behaviour chain, not one indicator. Word spawning encoded PowerShell followed by outbound traffic is highly suspicious, but I would validate the command, process tree and network evidence. If compromise is likely, I would follow the playbook to isolate or immediately request isolation, while preserving evidence and scoping other affected users/devices.”

- Microsoft Defender XDR DeviceProcessEvents: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table
