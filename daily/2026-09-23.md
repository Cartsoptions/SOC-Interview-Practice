# SOC Interview Practice — 2026-09-23

## Question 82

### Interview Question

Windows Security Event ID 4688 shows a new process on an endpoint. What does 4688 tell you, and how would you investigate a suspicious process without assuming that an unfamiliar executable is malware?

### Interview-Ready Answer

Event ID 4688 is generated when Audit Process Creation is enabled and records that a new process was created. Microsoft documents 4688 as “A new process has been created.” Process command-line data is not guaranteed merely because 4688 exists: expanded command-line auditing must also be enabled for the Process Command Line field to be populated.

In a SOC environment, I would use 4688 as process-execution evidence and correlate it with EDR and surrounding telemetry. I would check the executable name/path, account, parent/creator process, command line when available, timestamp, hash/signature/prevalence where EDR provides them, and what the process did next. Defender XDR DeviceProcessEvents provides process telemetry including FileName, FolderPath, ProcessCommandLine and initiating-process fields; Microsoft cautions that initiating-process signature fields describe the initiating process, not the newly created process.

Observation: a process was created. Hypotheses: legitimate OS/application/admin activity, unwanted software, or malicious execution. Confirmation requires contextual evidence such as suspicious lineage/command line, malicious file reputation or analysis, persistence, credential access, or abnormal network behaviour.

### Real-World SOC Scenario

A user opens an email attachment. Minutes later, 4688/EDR telemetry shows an unfamiliar executable launched from a user-writable directory, with a scripting process in its lineage. The executable then creates persistence and contacts an unusual external destination.

I would build the timeline: user/email activity -> process creation -> parent/child lineage -> file/hash/signature context -> persistence -> network activity. An unusual filename alone is not enough; the combined execution chain and follow-on behaviour determine whether the malicious-execution hypothesis is supported.

### What I Would Check as a Tier 1 Analyst

- Host, user and timestamp
- New process name and executable path
- Creator/parent process and process tree
- Process command line when auditing/EDR provides it
- Account, integrity/elevation context where available
- Hash, signer/certificate and organisational prevalence
- File origin and creation/download evidence
- Child processes and persistence activity
- DNS/proxy/firewall/network connections
- Related email/browser activity
- Whether the software is approved
- Tier 1 containment/escalation authority

### Tools / Logs

Windows Security Event 4688 where Audit Process Creation is enabled; Defender for Endpoint/Defender XDR DeviceProcessEvents or another EDR; Microsoft Sentinel, Splunk or Wazuh; Sysmon where configured; DNS/proxy/firewall and email telemetry.

### Interview Takeaway

“4688 tells me a process was created. I would not call it malware from the process name alone. I would validate the path, parent-child lineage, command line, hash/signature and follow-on file, persistence and network behaviour, then escalate or contain within my authority.”

- Microsoft command-line process auditing: https://learn.microsoft.com/windows-server/identity/ad-ds/manage/component-updates/command-line-process-auditing
- Microsoft Defender XDR DeviceProcessEvents schema: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table

## Question 83

### Interview Question

Your SIEM shows authentication failures across many user accounts, with only a small number of attempts per account. How would you distinguish password spraying from ordinary failed logons, and what would you do if one account later succeeds?

### Interview-Ready Answer

Password spraying is a brute-force technique that tries one or a small set of common passwords across many accounts, rather than making many guesses against one account. MITRE ATT&CK maps it to T1110.003 and its current detection strategy looks for authentication failures distributed across multiple accounts within a time window.

I would therefore focus on the pattern, not one failed logon. A few failures for one user may be a typo, stale credential, service or application issue. A single source or coordinated sources attempting many different identities with low attempts per identity is more consistent with spraying.

For Microsoft Entra ID Protection, there is an important nuance: Microsoft states that its Password spray risk detection is triggered only when the attacker successfully validates a user’s password. That means the detection indicates the password was correctly identified, but Microsoft explicitly says this does not by itself prove that the attacker accessed a resource.

Observation: distributed authentication failures occurred. Hypothesis: password spraying. Stronger evidence: the multi-account pattern, suspicious source/infrastructure, and a subsequent successful credential validation or sign-in. Confirmed account compromise still requires checking whether authentication completed and what the identity did afterwards.

### Real-World SOC Scenario

Over ten minutes, the SIEM shows failed authentication against 40 employee accounts from the same external infrastructure, with only one or two attempts per account. One targeted identity later records a successful authentication from the same source context.

I would immediately pivot from “spray attempt” to possible credential compromise. I would investigate the successful identity’s sign-ins, MFA result, device/session context and post-authentication activity, scope other targeted accounts, and escalate/contain according to the identity-response playbook.

### What I Would Check as a Tier 1 Analyst

- Number of distinct accounts targeted
- Attempts per account and time window
- Source IP/infrastructure and geography as contextual signals
- Failure/error reasons
- Successful authentication after failures
- MFA and Conditional Access results where applicable
- Normal user/device/location baseline
- Entra risk detections where licensed
- Mailbox/cloud/endpoint activity after successful authentication
- Other targeted or successfully validated accounts
- Known scanners/tests or authorised security activity
- Tier 1 identity containment/escalation authority

### Tools / Logs

Microsoft Entra sign-in/risk evidence where available, Windows authentication logs where applicable, Microsoft Sentinel, Splunk or Wazuh, VPN/identity-provider logs, Defender XDR and relevant SaaS/cloud audit telemetry.

### Interview Takeaway

“Password spraying is a pattern: a small set of passwords against many identities. I would correlate account count, source and timing, then treat any subsequent successful validation as a priority pivot and investigate whether the identity actually authenticated and performed suspicious activity.”

### Verification Notes

- MITRE ATT&CK T1110.003 Password Spraying / current distributed-spray detection strategy: https://attack.mitre.org/techniques/T1110/003/ and https://attack.mitre.org/detectionstrategies/DET0487/
- Microsoft Entra ID Protection risk detections, including Password spray: https://learn.microsoft.com/en-us/entra/id-protection/concept-identity-protection-risks

## Question 84

### Interview Question

EDR reports that a process attempted to disable antivirus protection or add a broad antivirus exclusion. How would you investigate possible defence impairment, and what does Microsoft Defender Tamper Protection change about your interpretation?

### Interview-Ready Answer

Trying to disable, degrade or modify security tooling is defence impairment. MITRE ATT&CK’s current Enterprise taxonomy maps disabling or modifying security tools to T1685, Disable or Modify Tools. Attackers may stop services/processes, alter configurations or exclusions, interfere with logging, or otherwise reduce defensive visibility.

But an attempted security-setting change is not automatically malicious. Enterprise administrators, troubleshooting workflows and deployment tooling can make authorised changes. I would establish who/what initiated the change, whether it was approved, whether the change succeeded, and what happened before and afterwards.

Microsoft Defender Tamper Protection is relevant because, when enabled on Windows, it protects settings including real-time protection, behaviour monitoring, cloud protection and antivirus exclusions from unauthorised changes. Microsoft also notes that attempts to modify protected Defender Antivirus settings through the Registry are blocked. Therefore, I must distinguish an attempted change from a successful impairment; a command or alert showing an attempt does not prove Defender was actually disabled.

Observation: a process attempted or made a security-control change. Hypotheses: authorised administration/troubleshooting or attacker defence impairment. Confirmation requires validating authorisation, resulting protection state and correlated malicious behaviour.

### Real-World SOC Scenario

EDR alerts that an unfamiliar elevated process attempted to weaken Defender settings shortly after a suspicious download. Tamper Protection is enabled and blocks the protected change, but the endpoint then shows additional suspicious process and network activity.

I would not close the incident because the setting change was blocked. The failed tampering attempt is still valuable intent/context. I would verify Defender/EDR health, inspect the initiating process and user/session, determine whether other controls or exclusions were changed, preserve the timeline and escalate based on the broader compromise evidence.

### What I Would Check as a Tier 1 Analyst

- Device/user and timestamp
- Initiating process, parent, path and command line
- Privilege/elevation context
- Exact security setting/tool targeted
- Whether the action was attempted, blocked or successful
- Tamper Protection/controlled configuration state as applicable
- Defender/EDR sensor and protection health
- Newly added exclusions or changed policies
- Approved troubleshooting/change record
- Process/file/hash/signature context
- Logging gaps or telemetry loss
- Follow-on persistence, credential or network activity
- Similar activity on other devices
- Tier 1 containment/escalation authority

### Tools / Logs

Defender for Endpoint/Defender XDR, Microsoft Sentinel, Windows/Defender telemetry, Intune or other endpoint-management evidence where applicable, Splunk/Wazuh if integrated, Sysmon where configured, and change-management records.

### Interview Takeaway

“An attempt to weaken security controls is a high-value signal, but I would verify whether the change actually succeeded. With Defender Tamper Protection enabled, protected changes can be blocked, so I would investigate the initiating process, authorisation, resulting protection state and surrounding malicious behaviour rather than equating an attempted command with a disabled defence.”

### Verification Notes

- MITRE ATT&CK T1685 Disable or Modify Tools: https://attack.mitre.org/techniques/T1685/
- Microsoft Defender Tamper Protection overview: https://learn.microsoft.com/en-us/defender-endpoint/prevent-changes-to-security-settings-with-tamper-protection
- Microsoft Defender Tamper Protection configuration: https://learn.microsoft.com/en-us/defender-endpoint/tamper-protection-windows-configure
