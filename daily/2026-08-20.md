# SOC Interview Practice — 2026-08-20

## Question 10

### Interview Question

What is Active Directory, and how would you investigate an alert showing that a user was unexpectedly added to a privileged Active Directory group?

### Interview-Ready Answer

Active Directory Domain Services (AD DS) is Microsoft's directory service for centrally managing identities, computers, groups, authentication and access to resources in a Windows domain. In practical SOC work, Active Directory is important because identity changes can alter what a user or computer is authorised to access.

I would distinguish authentication from authorisation. Authentication verifies the identity of a user or host; after authentication, permissions and group membership help determine what that identity is authorised to access. Microsoft documents Kerberos as the default domain authentication protocol in Windows domain environments, while Active Directory security groups are used to assign rights and permissions to resources.

If an alert shows that a user was added to a privileged group, the group-membership change is my observation. My hypothesis might be legitimate administration, an unauthorised privilege change, or attacker-driven privilege escalation. I would verify which account performed the change, which member was added, which group was changed, when it happened, whether there was an approved change or ticket, and what the newly privileged account did afterwards.

Windows auditing distinguishes group types. Event ID 4728 records a member added to a security-enabled global group; 4732 records a member added to a security-enabled local group; and 4756 records a member added to a security-enabled universal group. I would not claim that one specific Event ID applies to every privileged-group change without first confirming the group's type and that the relevant auditing was enabled.

As a Tier 1 analyst, I would normally investigate, preserve the timeline, document evidence and escalate according to the identity/privilege-change playbook. Removing a user from a production privileged group, disabling an account or resetting credentials should only be done if my role and procedure authorise it.

### Real-World SOC Scenario

The SIEM alerts that a standard help-desk account has been added to a high-value administrative group outside the normal change window. I would identify the group type and corresponding Windows Security event, review the Subject/account that made the change and the Member that was added, check whether there is an approved service ticket, and correlate the initiating administrator's logons and endpoint activity. I would then examine what the newly privileged account did after the change, such as remote logons, account-management actions or access to sensitive systems. If the change is unexplained or followed by suspicious activity, I would escalate urgently as a potential privilege-escalation or account-compromise incident.

### What I Would Check as a Tier 1 Analyst

- Exact privileged group, group scope/type and business importance
- Added member and the account that performed the change
- Relevant group-management event: 4728, 4732 or 4756 as applicable
- Timestamp, domain controller/host and surrounding Security events
- Approved change ticket, onboarding request or administrative activity
- Recent authentication activity for the initiating and newly privileged accounts
- Other account-management changes such as account creation, enablement, password reset or modification
- EDR/SIEM evidence from systems used by the initiating account
- Actions performed by the newly privileged account after the change
- Escalation and authorised containment requirements

### Tools / Logs

Windows Security logs on relevant domain controllers/hosts; Active Directory audit events; Microsoft Sentinel, Splunk or Wazuh; EDR; identity logs; ticket/change-management system; Active Directory administrative records.

### Interview Takeaway

Active Directory centrally manages identities and access in a Windows domain. If I saw an unexpected privileged-group addition, I would verify who made the change, who was added, which group type and audit event apply, whether the change was authorised, and what happened afterwards before escalating or supporting authorised containment.

## Question 11

### Interview Question

What is DNS, and why are DNS logs useful during a SOC investigation?

### Interview-Ready Answer

DNS, or the Domain Name System, resolves names such as hostnames and domain names into information systems can use to locate services, most commonly IP addresses. In normal enterprise operations it is fundamental infrastructure; in SOC work, DNS telemetry can also provide valuable evidence about which domains systems attempted to resolve and when.

I would not treat a DNS lookup by itself as proof that a host communicated successfully with a malicious server. A lookup shows name-resolution activity. To determine whether a connection actually occurred, I would correlate DNS evidence with firewall, proxy, EDR and network telemetry.

DNS is valuable because many malicious workflows rely on domain names for phishing destinations, payload delivery or command-and-control infrastructure. During an investigation, I would examine the queried domain, requesting host/client where the telemetry provides it, timestamps, query/response information, prevalence across the environment, threat-intelligence context and related network connections. I would also consider false positives: a security scanner, browser prefetch, email-security product or legitimate application might resolve a domain without the user intentionally visiting it.

Microsoft documents DNS Server audit and analytic logging in Windows Server. Audit events track configuration changes, while analytic events can track DNS server activity such as information sent or received; analytic logging is not enabled by default. Therefore, I would first understand what DNS telemetry the organisation actually collects rather than assume every environment has identical query visibility.

### Real-World SOC Scenario

EDR reports that a workstation attempted to resolve a newly observed domain shortly after a user opened an email attachment. I would correlate the DNS timestamp with the email event, process tree and network telemetry. If the process spawned from the attachment, resolved the domain and then made an outbound connection to the resolved infrastructure, the evidence becomes much stronger than the DNS lookup alone. I would also search the SIEM to see whether other hosts queried the same domain, which could indicate broader exposure.

### What I Would Check as a Tier 1 Analyst

- Queried domain and timestamp
- Requesting host/client where available
- DNS response and resolved IP addresses where captured
- Frequency and prevalence across users/hosts
- Domain age/reputation and threat-intelligence context where appropriate
- Related email, browser or process activity before the lookup
- Firewall/proxy/EDR evidence of a subsequent connection
- Other hosts resolving or connecting to the same infrastructure
- Whether a legitimate application, scanner or security control explains the lookup
- Whether DNS query/analytic logging is actually enabled and retained in the environment

### Tools / Logs

DNS server/resolver telemetry; Microsoft Sentinel, Splunk or Wazuh; EDR; firewall and proxy logs; email-security telemetry; threat-intelligence/reputation sources; Windows DNS Server audit/analytic logs where configured.

### Interview Takeaway

DNS translates names into network information and gives the SOC useful visibility into domain-resolution activity. I would use DNS as one evidence source, then correlate it with endpoint and network logs before claiming that a suspicious connection or compromise occurred.

## Question 12

### Interview Question

A user says, "I opened the attachment, but nothing happened." How would you investigate the possible phishing or malware incident as a Tier 1 SOC analyst?

### Interview-Ready Answer

I would treat the user's statement as useful evidence, but not as proof that nothing executed. Some malicious files produce little or no visible effect while launching a child process, changing files or registry values, or making network connections in the background.

I would first preserve the email and establish exactly what the user did: which message and attachment, when it was opened, whether they clicked any prompts, enabled content, entered credentials, copied and pasted a command, or downloaded another file. I would then use the email-security platform to review the sender, recipients, attachment and URL verdicts, delivery status, related messages and whether other users received or interacted with the same campaign. Microsoft Defender for Office 365 Threat Explorer/Real-time detections can expose malicious-email and URL-click evidence where the organisation has the required licensing and permissions, and the Email entity page provides message, URL and attachment investigation context.

Next I would pivot to endpoint evidence around the user's interaction time. I would examine the process tree, child processes, file writes, registry activity, network connections and related EDR alerts. MITRE ATT&CK maps user execution of a malicious file to T1204.002 and malicious-link execution to T1204.001. Current ATT&CK also includes T1204.004 for malicious copy-and-paste techniques such as ClickFix, so I would explicitly ask whether the user was instructed to paste or run a command rather than limiting the investigation to attachments and links.

The observation is that the user opened the file. A hypothesis is that malicious code executed. Confirmation requires supporting endpoint, network, email or identity evidence. If I find execution, credential theft, persistence, suspicious outbound communication or wider delivery, I would escalate according to the incident playbook and support authorised containment/remediation.

### Real-World SOC Scenario

A finance employee reports opening a ZIP attachment from what appeared to be a supplier. The document displayed an error and seemed to close. Email investigation shows that several users received similar messages. On the affected workstation, EDR shows an unexpected child process shortly after the attachment was opened, followed by a DNS lookup and outbound connection to unfamiliar infrastructure. I would document the email-to-endpoint timeline, identify any files or hashes involved, search for the same indicators across other recipients/endpoints, and escalate the case as a likely malicious execution rather than relying on the user's observation that "nothing happened."

### What I Would Check as a Tier 1 Analyst

- Original message, sender/reply-to, recipients, delivery status and authentication/routing evidence
- Attachment name/type/hash and security verdicts where available
- URLs and user click activity
- Exact user actions, including prompts, credentials, MFA approval or copied/pasted commands
- Other recipients and related messages/campaign evidence
- EDR process tree and timeline around the interaction
- Child processes, files written/modified and registry changes
- DNS, proxy and firewall connections after execution
- Identity/sign-in activity if credentials might have been exposed
- Same indicators or behaviour on other endpoints/users
- Required escalation, isolation or remediation steps and whether I am authorised to perform them

### Tools / Logs

Microsoft Defender for Office 365/Threat Explorer where licensed; Proofpoint or Abnormal Security where deployed; Microsoft Defender for Endpoint or other EDR; Microsoft Sentinel/Splunk/Wazuh; email headers; DNS/proxy/firewall logs; identity logs; approved malware/reputation services.

### Interview Takeaway

If a user says an attachment did nothing, I would not assume the system is safe. I would correlate the email, user actions, endpoint process activity and network/identity evidence to determine whether execution occurred, assess scope, document the timeline and escalate when the evidence supports compromise.

## Verification Notes

- Microsoft Learn documents that Active Directory security groups collect users/computers/groups into manageable units and can be used to assign rights and permissions. Microsoft Windows authentication documentation identifies Kerberos as the Windows domain authentication protocol and distinguishes authentication from subsequent authorised access.
- Microsoft's AD DS events-to-monitor guidance lists 4728 as a member added to a security-enabled global group, 4732 for a security-enabled local group and 4756 for a security-enabled universal group. Event 4732 guidance also recommends monitoring additions to high-value groups such as administrators/domain admins.
- Microsoft Windows Server DNS guidance states that DNS audit logs track server/zone/resource-record changes and that DNS analytic events track DNS server activity; analytic logging is not enabled by default.
- Microsoft Defender for Office 365 documentation states that Threat Explorer/Real-time detections support malicious-email investigation and that Threat Explorer can expose URL-click information. The Email entity page exposes URLs and scanning results; exact availability depends on licensing/permissions.
- MITRE ATT&CK User Execution includes Malicious Link T1204.001, Malicious File T1204.002 and Malicious Copy and Paste T1204.004. The latter includes ClickFix-style social engineering and was last modified 12 May 2026.
