# SOC Interview Practice — 2026-09-09

## Question 52

### Interview Question

What is a Pass-the-Hash attack, and how would you investigate suspected Pass-the-Hash activity in a Windows/Active Directory environment as a Tier 1 SOC analyst?

### Interview-Ready Answer

**Pass-the-Hash, or PtH, is an authentication abuse technique where an attacker uses a stolen password hash, commonly an NTLM hash, to authenticate to a remote Windows service without knowing or recovering the user's plaintext password.** Microsoft describes PtH as authentication to a remote server or service using the underlying NTLM hash of a user's password or another credential derivative. MITRE ATT&CK maps the technique to **Use Alternate Authentication Material: Pass the Hash — T1550.002**.

In a SOC environment, I would not say that one NTLM logon automatically means Pass-the-Hash. NTLM still exists legitimately in Windows environments, especially where Kerberos cannot be used. My observation might be an unusual NTLM network logon or lateral authentication pattern. The PtH hypothesis becomes stronger when that authentication is unusual for the account or source host and is followed by remote-service execution, administrative-share activity, service creation or other lateral movement.

Current MITRE detection guidance for Pass-the-Hash on Windows looks for anomalous NTLM network authentication, especially **Logon Type 3**, and correlates authentication/session events with process and network telemetry. Depending on the environment and audit coverage, useful evidence can include Windows Security events such as **4624**, **4648** and related domain-authentication events, plus Sysmon or EDR process/network telemetry. I would use those Event IDs only when they are actually collected and relevant to the authentication path.

As Tier 1, I would focus on validating the source account and host, the authentication protocol, the destination systems, the pattern across multiple hosts, and what happened after authentication. I would not attempt credential-theft tooling or disruptive response on my own. If the evidence supports credential misuse or lateral movement, I would escalate immediately and follow the authorised identity/endpoint containment playbook.

### Real-World SOC Scenario

A SIEM alert shows a privileged account making **NTLM Logon Type 3** connections from a normal employee workstation to several servers within a short period.

The user normally administers servers from a dedicated admin workstation, not from this device.

EDR then shows the employee workstation launching an unusual process shortly before the authentication burst, and one destination server records follow-on remote-service activity.

My observation is an abnormal NTLM network-authentication pattern from an unexpected source.

My hypothesis is that stolen NTLM credential material may be being used for lateral movement.

I would correlate:

**source process → NTLM authentication → destination hosts → remote-service/process activity**

If the account owner denies the activity, the source device is unexpected, several hosts are accessed in sequence and supporting endpoint/network evidence shows follow-on execution, the Pass-the-Hash hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- User account and privilege level
- Source workstation and normal administrative baseline
- Destination systems contacted
- Authentication protocol, especially NTLM where recorded
- Windows 4624 Logon Type and authentication package where available
- 4648 or other related authentication events where applicable
- Number and timing of systems accessed
- Whether the account normally connects from that source
- EDR/Sysmon process activity on the source host
- SMB, remote-service or administrative-share activity
- Service or scheduled-task creation on destinations
- Firewall/network connections between systems
- Similar NTLM lateral activity involving other accounts
- Approved administration, vulnerability scanning or deployment explanation
- Tier 1 containment and escalation authority

### Tools / Logs

Windows Security logs; Active Directory/domain-controller authentication telemetry; Microsoft Defender for Endpoint or another EDR; Sysmon where deployed; Microsoft Sentinel; Splunk; Wazuh; SMB/remote-service logs; firewall/network telemetry; Microsoft Defender for Identity where deployed.

### Interview Takeaway

Pass-the-Hash abuses stolen NTLM password-hash material to authenticate without knowing the plaintext password. I would not diagnose PtH from NTLM alone; I would correlate the source host, account, Logon Type/authentication context, destination pattern and follow-on endpoint or lateral-movement evidence before escalating.

## Question 53

### Interview Question

What is the difference between hashing and encryption, and how would that difference matter during a SOC investigation?

### Interview-Ready Answer

**Hashing and encryption solve different security problems.**

A cryptographic hash function takes input data and produces a fixed or bounded digest that represents that input. NIST describes hashing as applying a cryptographic hash function to data to calculate a relatively unique output or hash digest. In normal cryptographic use, hashing is designed to be **one-way**: analysts compare hashes rather than decrypting them back to the original file or message.

**Encryption**, by contrast, transforms plaintext into ciphertext to conceal the original meaning. NIST defines encryption as a cryptographic transformation that is reversible through decryption when the appropriate key and algorithm are available.

In a SOC environment, hashing is useful for **integrity checks, file identification, IOC matching and prevalence searches**. For example, I can calculate or retrieve a SHA-256 hash for a suspicious executable and compare that hash with EDR prevalence data or an approved reputation source. If two files have the same cryptographic hash, that strongly supports that the file contents are identical, subject to the properties and security of the hash algorithm used.

Encryption is different. I may encounter encrypted network traffic, encrypted archives, encrypted disks or ransomware-encrypted files. Encryption is intended to protect confidentiality or, in ransomware, deny access. Whether I can inspect encrypted content depends on the keys, architecture and authorised controls. I would not say that 'encrypted traffic is malicious' or that 'hashes can be decrypted.'

Another interview detail is that password systems do not normally need to store a reversibly encrypted password just to verify it. Password-verification designs commonly use password hashing or password-derived values, although the exact implementation depends on the system. In Windows authentication, Microsoft documents that NTLM uses cryptographic password-hash material in its challenge-response process; that hash can itself become valuable credential material to an attacker, which is why Pass-the-Hash is possible.

### Real-World SOC Scenario

EDR alerts on an unknown executable and provides its SHA-256 hash.

I would use the hash to search the environment for the exact file and check approved reputation/threat-intelligence sources. That does **not** mean I am decrypting or opening the file.

Separately, the same endpoint makes an HTTPS connection to an external domain. The traffic is encrypted in transit, so the amount of content visible to the SOC depends on the organisation's proxy/TLS-inspection architecture and endpoint telemetry.

My observation is:

- one exact file can be identified by its hash;
- the network session is encrypted.

My hypotheses about maliciousness still require behavioural context such as the process tree, destination, file activity and subsequent actions.

### What I Would Check as a Tier 1 Analyst

- Hash algorithm used, preferably a modern cryptographic hash such as SHA-256 for file investigation
- File hash and internal prevalence
- File path, signer and process tree
- Whether the hash appears in approved reputation/threat-intelligence sources
- Whether the file content changed between observations
- Whether traffic or files are encrypted
- TLS/proxy visibility and inspection coverage where applicable
- Endpoint behaviour before and after the encrypted connection
- Whether encryption is expected for the application or service
- Whether encrypted archives/files are associated with phishing, staging or ransomware
- Avoiding the false assumption that a cryptographic hash can simply be decrypted

### Tools / Logs

Defender for Endpoint or another EDR; Sentinel/Splunk/Wazuh; file hashes such as SHA-256; VirusTotal or another approved reputation service; proxy/TLS-inspection telemetry where authorised; firewall/DNS logs; file-integrity or malware-analysis tools.

### Interview Takeaway

Hashing produces a one-way digest that is useful for integrity and identification, while encryption converts plaintext to ciphertext and is designed to be reversible with the proper key. In a SOC, I use hashes to identify and correlate artefacts, while encrypted data or traffic requires the appropriate authorised visibility and keys to inspect its content.

## Question 54

### Interview Question

What is the difference between a forward proxy and a reverse proxy, and how would that difference affect a SOC investigation?

### Interview-Ready Answer

A **forward proxy sits in front of clients and makes requests to external services on their behalf.** A **reverse proxy sits in front of one or more origin servers and receives client requests before forwarding them to those servers.** Cloudflare describes the distinction this way: the forward proxy represents clients to the Internet, while the reverse proxy represents origin servers to clients.

In an enterprise SOC, a forward proxy or secure web gateway can provide valuable outbound-web telemetry. Depending on the product and configuration, it may record the user or device, destination domain or URL, HTTP method, action, response, bytes transferred and file/download information. Microsoft Defender for Endpoint also documents a specific investigation challenge with forward proxies: basic connection telemetry can show the proxy as the network destination rather than the true Internet destination. With supported network-protection telemetry, Defender can expose the real destination domain behind the proxy.

A reverse proxy, on the other hand, is commonly used in front of public web applications for functions such as load balancing, TLS termination, caching and security controls. WAFs and CDNs often operate in or alongside this reverse-proxy layer. From the SOC perspective, reverse-proxy logs can be important for understanding inbound requests before they reach the origin server.

The key investigation point is **which side of the connection the proxy is representing**. I would not confuse the proxy IP with the true client or true destination. I would also be careful with source-IP interpretation because reverse proxies, load balancers and CDNs can affect what the origin server sees; trustworthy forwarded-client-IP headers depend on the architecture and configuration.

As Tier 1, I would use the relevant proxy logs to reconstruct the request path and then correlate with DNS, firewall, EDR, WAF and application evidence. Proxy configuration changes or trust-header engineering would normally belong to network/platform/security engineering unless my role explicitly includes them.

### Real-World SOC Scenario

A workstation appears in simple endpoint network telemetry to connect repeatedly to the organisation's forward-proxy IP.

That alone tells me very little about the final Internet destination.

The secure-web-gateway logs show that the user actually requested a newly registered external domain and downloaded a file. EDR then shows the browser writing the file to Downloads and the file executing shortly afterwards.

I would build the timeline:

**client → forward proxy → external domain → download → endpoint execution**

Now consider an inbound case: a reverse proxy/WAF reports repeated exploit-like requests against a public application. I would correlate the reverse-proxy/WAF request data with origin web/application logs to determine whether the requests were blocked, forwarded or produced application-side effects.

### What I Would Check as a Tier 1 Analyst

- Whether the device is using a forward proxy, reverse proxy or both in the relevant path
- Client/user/device identity where available
- True destination domain/URL for forward-proxy traffic
- Proxy action: allowed, blocked, warned or otherwise handled
- HTTP method, status and download metadata where available
- Proxy timestamp and request sequence
- TLS-inspection visibility and limitations
- DNS and firewall evidence
- EDR/browser process responsible for outbound traffic
- For reverse-proxy cases, client/source information as preserved by the architecture
- Reverse-proxy/WAF/CDN action
- Origin-server/application evidence
- Whether proxy/CDN/load-balancer architecture changes the apparent IP
- Approved business/application explanation
- Engineering escalation where proxy configuration or trust settings need changes

### Tools / Logs

Secure web gateway/forward-proxy logs; reverse-proxy/CDN/WAF logs; Microsoft Defender for Endpoint; Microsoft Sentinel; Splunk; Wazuh; DNS/firewall telemetry; web/application logs; browser/endpoint telemetry.

### Interview Takeaway

A forward proxy represents clients when they access external services, while a reverse proxy represents origin servers to incoming clients. In a SOC investigation, I would use that distinction to identify the real client or destination, interpret proxy logs correctly and correlate the request path with endpoint, firewall, WAF and application evidence.
