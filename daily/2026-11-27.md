# SOC Interview Practice — 2026-11-27

**Curriculum:** Questions 253–256 | Firewall evidence, TCP and TLS packet interpretation, Linux SSH compromise, and DDoS incident triage

## Question 253

### Interview Question

A firewall alert shows an allowed outbound TCP/443 connection from a finance laptop to a rare external IP. An IDS also alerted, but the web proxy has no matching record. What does the firewall evidence prove, and how would you decide whether the connection is malicious?

### Interview-Ready Answer

A firewall enforces traffic policy between networks or hosts. In a SOC environment, I would use its logs to establish which source and destination were involved, the protocol and ports, the rule and action, timestamps, address translation and, where the product records them, session state and traffic volume. An **allow** action means the traffic matched a rule that permitted it. It does not prove the destination, process or payload was safe.

I would first validate the time zone, source asset and any NAT mapping. I would review the rule that allowed the traffic, whether the record represents a completed session rather than only an initial packet, and the bytes sent and received if available. Field names and session semantics vary by vendor, so I would use the raw event and that product's documentation rather than inventing a generic schema.

The missing proxy record is useful but not conclusive. The application may have bypassed the proxy, used a non-browser TLS connection, followed a direct-access exception, or produced a logging gap. I would correlate EDR network telemetry to identify the initiating process and user, then check DNS, IDS, proxy, firewall and TLS metadata. Reputation and ownership data for the destination are enrichment, not proof.

If the IDS was detection-only, it did not necessarily block the traffic. I would verify its action and signature context. Tier 1 can establish the evidence, scope similar activity and escalate a supported verdict. Changing firewall rules, proxy routing or network architecture belongs to authorised network or security engineering staff unless the playbook delegates a specific containment action.

### Real-World SOC Scenario

EDR shows an unsigned executable in the user's temporary directory initiating the session seconds after a malicious document ran. DNS logs show the laptop resolved a newly registered domain to the firewall destination, and the firewall recorded bidirectional traffic. The IDS signature describes a protocol anomaly consistent with command-and-control traffic. No approved software or business exception matches the activity.

- **Observation:** The firewall permitted outbound TCP/443, the IDS alerted, and no proxy event exists.
- **Hypothesis:** A process bypassed the proxy and established encrypted command-and-control traffic.
- **Confirmed Evidence:** EDR identifies the suspicious initiating process; DNS ties the domain to the destination; the firewall records bidirectional traffic; and the endpoint timeline links the session to malicious document execution.

The verdict is **confirmed malicious outbound communication from the finance laptop; escalate for authorised endpoint containment, scope the process, domain and destination across the estate, and preserve the correlated timeline**.

### What I Would Check as a Tier 1 Analyst

1. Raw firewall event, device time zone, rule, action, interfaces, protocol, ports and session identifiers.
2. Source asset, user and NAT mapping at the event time.
3. Session completion and bytes sent or received where the firewall provides those fields.
4. IDS signature, confidence, action and whether it blocked or only detected.
5. EDR process tree and the process that opened the connection.
6. DNS query and response for the destination domain.
7. Proxy policy, bypass rules, direct-access exceptions and logging health.
8. Destination ownership, reputation and prevalence as enrichment.
9. Matching domain, IP, process or pattern on other hosts.
10. Approved containment and escalation under the incident playbook.

### Relevant Tools / Logs

Firewall and NAT logs; IDS/IPS events; EDR network and process telemetry; DNS and proxy logs; TLS or packet metadata where lawfully collected; CMDB and asset inventory; threat-intelligence enrichment; incident-management records.

### Key Interview Takeaway

An allowed firewall event proves policy permitted the traffic, not that it was benign. I correlate the network session with process, DNS, proxy and IDS evidence before assigning a verdict.

## Question 254

### Interview Question

In Wireshark you see a client send SYN, receive SYN-ACK and send ACK. A TLS handshake follows, then encrypted application data, and the client later sends a TCP reset. What can you conclude, what remains unknown, and what evidence would you correlate?

### Interview-Ready Answer

The SYN, SYN-ACK and ACK sequence is the normal TCP three-way handshake. It supports that the client reached a listening TCP peer and that both sides established TCP state. It does not prove the application is trusted or that later activity succeeded.

The TLS exchange supports that the peers negotiated a protected session. I would review the observable protocol version, server name where present, certificate chain, endpoints, timing and byte counts. With TLS 1.3, messages after ServerHello are encrypted, so the capture may reveal less handshake detail than an older TLS session. Encrypted application data proves data records were exchanged, but without an approved decryption capability or endpoint evidence it does not reveal the content or prove data theft, command-and-control or a benign business transaction.

A reset terminates a TCP connection abruptly. The capture can show which side sent it, but it may not reveal why. Possibilities include application behaviour, timeout handling, security-control intervention or an error. I would avoid claiming that the reset means the firewall blocked the session unless another control's log confirms that action.

In a SOC environment, I would correlate the packet timestamps and five-tuple with DNS, firewall, proxy, load-balancer and EDR data. The EDR process that opened the socket and the preceding process tree are especially important. Packet capture provides strong transport evidence, but the verdict normally comes from combining it with host, identity and application context.

### Real-World SOC Scenario

The capture shows the laptop connecting to an IP returned for a newly observed domain. EDR attributes the socket to a script interpreter launched by a document reader. The endpoint records the script reading a credential file immediately before the TLS session, while the firewall records a large outbound transfer. The TLS payload remains encrypted.

- **Observation:** TCP and TLS sessions were established, encrypted records flowed, and the client later reset the connection.
- **Hypothesis:** The document-triggered script used TLS to exfiltrate credentials or communicate with command-and-control infrastructure.
- **Confirmed Evidence:** EDR confirms the suspicious process and credential-file access; DNS links the domain to the packet destination; and firewall byte counts confirm substantial outbound transfer. The capture alone does not confirm the exact encrypted content.

The verdict is **confirmed malicious process communication with suspected data access and transfer; the exact payload content remains unconfirmed unless authorised endpoint or decryption evidence establishes it**.

### What I Would Check as a Tier 1 Analyst

1. Capture point, time zone, packet loss and whether the full session is present.
2. Source and destination IPs and ports, TCP flags, sequence and retransmission behaviour.
3. Which peer sent the reset and when it occurred.
4. TLS version and observable handshake metadata.
5. Server name and certificate details when visible.
6. DNS query and response immediately before the connection.
7. Firewall, proxy or load-balancer session action and byte counts.
8. EDR process, parent process, user and file activity associated with the socket.
9. Destination ownership, prevalence and intelligence as enrichment.
10. Similar communications on other endpoints and the approved escalation path.

### Relevant Tools / Logs

Wireshark or approved packet-capture tooling; DNS; firewall, proxy and load-balancer logs; EDR process and network telemetry; TLS inspection logs where authorised; application logs; threat-intelligence enrichment.

### Key Interview Takeaway

The handshake establishes transport and TLS-session evidence, not intent. I state what the packets prove, preserve what encryption leaves unknown and correlate the session with endpoint and control logs.

## Question 255

### Interview Question

Wazuh reports many failed SSH logins to a Linux server, followed by a successful public-key login for a service account from the same external IP. Minutes later, the account uses sudo and the host makes a new outbound connection. How would you investigate without assuming the password was brute-forced?

### Interview-Ready Answer

Wazuh documents that it can identify brute-force activity by correlating multiple authentication failures. That alert supports a brute-force hypothesis, but the raw authentication events and later success need separate interpretation. A successful **public-key** login does not show that the password was guessed. It may reflect a stolen private key, an already-authorised operator, an unauthorised key added for persistence or a different event sequence.

I would validate the Wazuh alert against the underlying SSH logs or system journal for that distribution. I would record the source, account, timestamps and authentication method, then compare the activity with bastion, VPN, maintenance and change records. Log wording and available key details depend on the OpenSSH configuration and platform, so I would not claim a key fingerprint is present unless the raw log actually contains it.

Next I would review file-integrity or audit evidence for changes to the account's `authorized_keys` file, account and group changes, sudo activity, shell history only where reliable and permitted, process execution, persistence and outbound connections. MITRE ATT&CK maps repeated password attempts to Brute Force T1110, abuse of a legitimate account to Valid Accounts T1078, and adding an SSH key for persistence to SSH Authorized Keys T1098.004. These mappings organise evidence; they do not by themselves confirm an incident.

Tier 1 should scope the account and source across other systems, preserve the timeline and escalate quickly if post-authentication activity is unauthorised. Disabling an account, revoking keys, isolating the host or blocking the source should follow delegated permissions and the playbook, with system owners involved where availability may be affected.

### Real-World SOC Scenario

File-integrity monitoring confirms that a new line was added to the service account's `authorized_keys` file from an unauthorised administrator session. The public-key login uses the new access path, sudo starts an unfamiliar process, and firewall logs confirm an outbound TLS session. The service owner confirms no maintenance or vendor access was scheduled.

- **Observation:** Repeated SSH failures were followed by a successful key-based login, sudo use and new outbound traffic.
- **Hypothesis:** An attacker obtained or planted an SSH key and used the service account for persistence and execution.
- **Confirmed Evidence:** An unauthorised `authorized_keys` change, successful subsequent login, unapproved privileged process and outbound session confirm account and host compromise. The failed passwords do not prove the successful login resulted from password guessing.

The verdict is **confirmed Linux host compromise through unauthorised SSH-key access; escalate for authorised key revocation, account and host containment, and estate-wide scoping of the key, account and source**.

### What I Would Check as a Tier 1 Analyst

1. Wazuh alert correlation and the underlying raw events.
2. SSH authentication method, account, source, timestamps and target host.
3. Bastion, VPN, allowlist and maintenance context.
4. `authorized_keys` and SSH configuration changes through FIM, auditd or change records.
5. Account, group and privilege changes.
6. Sudo events and the resulting process tree.
7. New files, persistence mechanisms and scheduled tasks.
8. DNS, firewall and EDR or host network telemetry for the outbound session.
9. Same source, account or key evidence on other systems.
10. Evidence preservation, severity, containment authority and escalation handover.

### Relevant Tools / Logs

Wazuh alerts and raw-event views; OpenSSH authentication logs or system journal; Wazuh file-integrity monitoring where configured; auditd; sudo logs; Linux process and network telemetry; firewall and DNS logs; bastion and VPN logs; CMDB, change and incident records.

### Key Interview Takeaway

I do not equate failed passwords with a later key-based success. I validate the authentication method, look for key or account changes and prove compromise from the post-login evidence.

## Question 256

### Interview Question

A customer portal becomes slow and returns HTTP 503 errors. The CDN and WAF show traffic at twenty times baseline from thousands of IP addresses, concentrated on an expensive search endpoint. How would you distinguish a DDoS attack from a legitimate surge and respond as Tier 1?

### Interview-Ready Answer

A denial-of-service attack targets availability by exhausting network, system or application resources. Distributed denial of service means the traffic or requests come from many sources. In this scenario, the volume and errors justify urgent investigation, but neither a spike nor many source IPs alone proves malicious intent. A product launch, marketing campaign, crawler, faulty client or internal misconfiguration can also create abnormal load.

I would first establish business impact and the layer under stress: bandwidth, connections, CDN origin traffic, WAF requests, application workers, database calls, CPU, memory or another dependency. I would compare the traffic with a known-good baseline and inspect source distribution, autonomous systems and geography; request method and path; user agent; session or cookie behaviour; referrer; request rate; response code; cache hit ratio; and whether clients complete normal journeys. I would ask the business and application teams about releases, campaigns or outages.

NCSC guidance recommends clarifying what is happening, applying the right defences, then continually reviewing, communicating and recovering. Depending on approved architecture and authority, mitigations may include CDN or provider DDoS protection, WAF rules, adaptive rate limits, challenges, caching, load balancing, upstream filtering or temporarily reducing an expensive feature. Tier 1 should not make unapproved production changes or block thousands of individual addresses without considering spoofing, shared infrastructure and legitimate-user impact.

I would maintain monitoring for other security events because a DDoS may distract the team from concurrent intrusion activity. I would document the detection, business impact, decisions, communications, mitigation results and recovery evidence. NIST SP 800-61 Rev. 3 frames incident response across Detect, Respond and Recover, while MITRE ATT&CK distinguishes network saturation under T1498 from endpoint or application resource exhaustion under T1499.

### Real-World SOC Scenario

The business confirms there is no campaign or release. WAF and application logs show nearly identical automated requests with no cookies or normal navigation, extreme concentration on the costly search function and rising origin CPU. The CDN provider classifies the pattern as an application-layer attack. An approved rate-limit and managed challenge sharply reduce malicious requests, restore latency and keep verified customer sessions working.

- **Observation:** Request volume is twenty times baseline, HTTP 503 errors and origin load rise, and traffic is concentrated on one expensive endpoint.
- **Hypothesis:** A distributed application-layer denial-of-service attack is exhausting the portal rather than a legitimate customer surge.
- **Confirmed Evidence:** Automated request behaviour, absence of a business event, provider classification, origin-resource exhaustion and successful targeted mitigation confirm the DDoS incident and its availability impact.

The verdict is **confirmed application-layer DDoS with customer impact; maintain authorised mitigations, monitor for adaptation and parallel threats, communicate status, and validate stable recovery before closure**.

### What I Would Check as a Tier 1 Analyst

1. Customer impact, affected services, start time and severity.
2. Bandwidth, connection, CDN, WAF, application, database and host metrics.
3. Baseline comparison and whether traffic reaches the origin.
4. Source distribution, ASN and geography without treating geography alone as malicious.
5. Request method, URI, user agent, cookies, referrer and session behaviour.
6. Status codes, latency, cache hit ratio and expensive backend operations.
7. Product launches, campaigns, releases, monitoring errors or faulty clients.
8. Provider DDoS classification and available pre-approved mitigations.
9. Concurrent alerts that might indicate distraction or a separate intrusion.
10. Mitigation effect, legitimate-user impact, communications and recovery evidence.

### Relevant Tools / Logs

CDN and managed DDoS dashboards; WAF and reverse-proxy logs; load balancer and network-flow telemetry; firewall and IDS/IPS logs; application, database and infrastructure metrics; synthetic monitoring; cloud-provider telemetry; SIEM; incident and communications records.

### Key Interview Takeaway

I confirm both malicious behaviour and service impact, distinguish network from application exhaustion, coordinate approved upstream or application controls and validate recovery without losing sight of parallel threats.

## Verification Notes

- NIST SP 800-41 Rev. 1 defines firewalls as controls for traffic flow between networks or hosts and explains stateful inspection. An allowed stateful session means policy permitted the traffic; it is not a content-safety verdict: https://csrc.nist.gov/pubs/sp/800/41/r1/final
- RFC 9293 specifies TCP and describes the three-way handshake used to establish a connection. It also defines reset handling; a capture can identify a reset but may not establish the application's reason for it: https://www.rfc-editor.org/rfc/rfc9293.html
- RFC 8446 specifies TLS 1.3. Following ServerHello, later handshake messages are encrypted, and application data uses authenticated encryption. This supports the answer's limits on what an undecrypted capture proves: https://www.rfc-editor.org/rfc/rfc8446.html
- Wazuh's current proof-of-concept guide states that Wazuh identifies brute-force attacks by correlating multiple authentication-failure events. The answer therefore treats the Wazuh alert as correlation evidence and validates it against raw SSH logs: https://documentation.wazuh.com/current/proof-of-concept-guide/detect-brute-force-attack.html
- MITRE ATT&CK defines Brute Force T1110, Valid Accounts T1078 and SSH Authorized Keys T1098.004. The latter documents modification of `authorized_keys` for persistence: https://attack.mitre.org/techniques/T1110/ ; https://attack.mitre.org/techniques/T1078/ ; https://attack.mitre.org/techniques/T1098/004/
- NCSC's DoS response guidance prioritises clarifying what is happening, applying appropriate defences, then monitoring, communicating and recovering. It discusses CDN, WAF, baselining, rate limiting, provider controls, infrastructure changes and temporary application-layer changes: https://www.ncsc.gov.uk/collection/denial-service-dos-guidance-collection/a-minimal-denial-of-service-response-plan
- MITRE ATT&CK distinguishes Network Denial of Service T1498 from Endpoint Denial of Service T1499, including application exhaustion: https://attack.mitre.org/techniques/T1498/ and https://attack.mitre.org/techniques/T1499/
- NIST finalised SP 800-61 Rev. 3 in April 2025. It integrates incident response with CSF 2.0 and emphasises effective detection, response and recovery: https://csrc.nist.gov/pubs/sp/800/61/r3/final
