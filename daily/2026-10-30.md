# SOC Interview Practice — 2026-10-30

**Curriculum:** Questions 173–176 | IDS/IPS verdict interpretation, DNS-tunnelling hunting in Splunk, Windows service-based lateral movement, and ransomware incident response

## Question 173

### Interview Question

A Suricata alert reports an exploit signature against an internal server. The EVE record shows the alert action as `allowed`, while the firewall later records a permitted outbound connection from that server. Explain what an IDS and an IPS do in this situation and how you would decide whether the server was compromised.

### Interview-Ready Answer

An intrusion detection system monitors traffic and generates evidence about suspicious activity. An intrusion prevention system performs similar inspection while operating inline and can enforce actions such as dropping or rejecting traffic. Whether a particular deployment is acting as IDS or IPS depends on its placement, configuration and rules; the product name alone is not enough.

In Suricata EVE JSON, an alert `action` of `allowed` means that the alert itself did not apply a drop action. Suricata's documentation also warns that this is not necessarily the final packet or flow verdict because several signatures or other flow decisions can apply; in IPS mode the separate verdict can still be `drop`. I would therefore review the raw EVE event, deployment mode, rule action, flow identifier and any `verdict` information rather than claiming that the traffic definitely reached the server.

I would then correlate the alert with firewall, server, application and EDR telemetry. The source and destination, ports, protocol, timestamps, request details and flow identifiers should align. I would check whether the server accepted the connection, whether the application returned an error or success response, and whether new processes, files, persistence or outbound communication followed.

As Tier 1, I would not change an inline policy or disable a production service without authority. If host evidence indicates compromise, I would invoke or request containment under the playbook, preserve evidence and escalate. If the signature fired but the packet was blocked and there is no endpoint impact, I would document an attempted attack rather than a successful compromise.

### Real-World SOC Scenario

The sensor is deployed passively as an IDS. The alert's five-tuple matches a request accepted by the server, and EDR records the application process spawning an unexpected shell followed by a rare outbound connection.

- **Observation:** Suricata generated an exploit alert with `action: allowed`; the firewall and EDR show related activity.
- **Hypothesis:** The request may have reached vulnerable code and caused unauthorised execution.
- **Confirmed evidence:** Matching network timing plus unexplained application-child process execution and follow-on egress establish compromise. The alert alone would not have done so.

The verdict is **critical true positive — successful exploitation confirmed by correlated host and network evidence; the IDS detected but was not positioned to block the traffic**.

### What I Would Check as a Tier 1 Analyst

1. Confirm whether Suricata is deployed passively or inline and whether the relevant rule uses `alert`, `drop`, `reject` or another action.
2. Review the EVE timestamp, signature, severity, action, verdict where present, flow ID and five-tuple.
3. Correlate firewall, proxy, packet, server and application evidence for the same connection.
4. Check whether the destination service was listening and whether the request was accepted or blocked downstream.
5. Review EDR process ancestry, command lines, file changes, persistence and outbound connections.
6. Check asset criticality, vulnerability state, change records and legitimate testing activity.
7. Invoke approved host isolation, egress restriction or service protection only under the response playbook.
8. Escalate the evidence, affected scope, containment status and remaining uncertainty to Tier 2/IR.

### Relevant Tools / Logs

Suricata EVE JSON, firewall and proxy logs, packet capture where authorised, server/application logs, EDR/XDR, Microsoft Sentinel or Splunk, asset inventory and change-management records.

### Key Interview Takeaway

An IDS alert and its `allowed` action are not proof that exploitation succeeded. I would establish sensor mode and final enforcement, then correlate the network signal with endpoint or application impact before assigning the verdict.

## Question 174

### Interview Question

A workstation is generating hundreds of unusually long DNS queries to one unfamiliar domain. Write a starting Splunk search using the CIM Network Resolution DNS data model, and explain how you would decide whether this is DNS tunnelling or legitimate software.

### Interview-Ready Answer

Assuming the DNS source is correctly mapped to Splunk's Common Information Model and the `Network_Resolution.DNS` data model is available, I would begin with a bounded candidate search:

```spl
| tstats count min(_time) as firstTime max(_time) as lastTime
    values(DNS.record_type) as recordTypes
  from datamodel=Network_Resolution.DNS
  where earliest=-24h
  by DNS.src DNS.query
| rename DNS.src as src DNS.query as query
| eval queryLength=len(query)
| where queryLength>=50 OR count>=20
| convert ctime(firstTime) ctime(lastTime)
| sort - queryLength count
```

Splunk documents the Network Resolution DNS data model as describing client/server and server/server DNS activity, with fields including `query`, `record_type` and `src`. The `tstats` command can use indexed fields or accelerated data-model summaries for efficient aggregation. This query's 50-character and 20-event thresholds are analyst-selected starting points, not Splunk defaults and not a complete DNS-tunnelling detector.

The results identify long or repeated fully qualified queries by source. They do not prove that the labels contain encoded data, that responses succeeded, or that the traffic is malicious. Grouping by the complete query can also hide a campaign whose subdomain changes every time. I would pivot to raw events and analyse the parent domain, query rate, label length and character distribution, record types, response codes, answers, bytes where available, timing and the process that generated the requests.

I would compare the behaviour with software-update, content-delivery, endpoint-security, telemetry and cloud-service baselines. MITRE ATT&CK T1071.004 describes DNS as a possible command-and-control channel, and its detection guidance focuses on high-frequency or anomalous queries, long or encoded-looking subdomains and unusual initiating processes. These are investigation signals rather than proof.

### Real-World SOC Scenario

Raw DNS events show a new subdomain every ten seconds under the same parent domain. Defender for Endpoint attributes the requests to an unsigned executable in a user's temporary directory. The software owner and user confirm that the program is not approved.

- **Observation:** One workstation generates frequent, long and changing subdomains to an unfamiliar domain.
- **Hypothesis:** The executable may be using DNS for command and control or data transfer.
- **Confirmed evidence:** Endpoint process attribution, unauthorised execution, repeatable DNS behaviour and owner confirmation establish malicious activity. Packet or authoritative-DNS evidence would be needed to state exactly what data was exchanged.

The verdict is **high-severity true positive — confirmed endpoint compromise with DNS activity consistent with tunnelling or DNS-based command and control; the transferred content remains unconfirmed**.

### What I Would Check as a Tier 1 Analyst

1. Validate DNS data coverage, field normalisation, retention, time range and data-model acceleration status.
2. Open raw events and review full queries, parent domain, record type, response code, answer and frequency.
3. Compare query length, changing labels, timing and character patterns with the organisation's baseline.
4. Identify the source device, user and initiating process through EDR, Sysmon DNS events where configured, or local telemetry.
5. Check domain age/reputation and whether approved security, CDN, update or telemetry software explains the traffic.
6. Hunt for the executable, hash, domain, parent process and behaviour across the estate.
7. Invoke authorised endpoint and indicator containment while preserving DNS and process evidence.
8. Escalate the confirmed facts separately from unverified claims about exfiltrated data.

### Relevant Tools / Logs

Splunk and the CIM Network Resolution DNS data model, DNS resolver logs, Defender for Endpoint or another EDR, Sysmon where configured, firewall/proxy logs, passive DNS or threat intelligence, packet capture where authorised and asset/software inventory.

### Key Interview Takeaway

Long DNS queries are a hunting signal, not a verdict. I would correlate the query pattern with the generating process, endpoint impact and environmental baseline before confirming DNS-based malicious activity.

## Question 175

### Interview Question

Wazuh receives Windows Security events showing a successful network logon to a server, followed seconds later by a new service installation. Network telemetry also shows an administrative-share transfer from the same workstation. How would you determine whether this is legitimate administration or service-based lateral movement?

### Interview-Ready Answer

I would correlate the target-server events, source workstation, identity, service details and change records before deciding. Windows Security Event ID 4624 records a successful logon; logon type 3 means a network logon. Event ID 4697 records that a service was installed and can include the subject account, logon ID, service name, service file name, service type, start type and service account. Microsoft notes that the logon ID can help correlate 4697 with a recent 4624 event. Event 4697 requires the relevant audit policy, so absence of the event does not prove that no service was created.

Wazuh agents monitor the Windows System, Application and Security channels by default and can collect specified Windows event channels using the `eventchannel` format. I would use Wazuh as the collection and alerting view, then validate the original Windows event records and endpoint evidence.

The sequence resembles remote service execution, but administrators and deployment tools can legitimately use the same mechanism. I would identify the source address and account, correlate logon IDs where available, inspect the service binary path and hash, check whether the file was written through `ADMIN$` or another share, review process ancestry and verify an approved change. MITRE ATT&CK maps SMB/Windows Admin Shares to T1021.002 and service execution to T1569.002; mapping describes observed behaviour, not malicious intent.

If the account owner denies the activity, the binary is unauthorised or malicious, or the same pattern spreads across hosts, I would request or invoke containment under the playbook and escalate as lateral movement. I would preserve the service and file evidence rather than deleting it during initial triage.

### Real-World SOC Scenario

The target server records 4624 logon type 3 from a finance workstation and 4697 for a randomly named service whose binary resides in `C:\Windows\Temp`. The administrator denies the activity, and EDR identifies the file as malicious on three servers.

- **Observation:** A network logon, administrative-share transfer and new service occur in a tight sequence from one source.
- **Hypothesis:** Compromised credentials are being used for SMB-based lateral movement and remote service execution.
- **Confirmed evidence:** Correlated source/account details, malicious binary evidence, user denial and repetition across servers establish unauthorised lateral movement. The original credential-theft method remains unconfirmed.

The verdict is **critical true positive — confirmed multi-host lateral movement using administrative shares and service execution**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the raw 4624 and 4697 records and confirm that they came from the target system.
2. Review account, source address/workstation, logon type, authentication package, logon ID and timestamp.
3. Inspect service name, binary path, start type, service account, signature and cryptographic hash.
4. Correlate SMB/firewall telemetry, administrative-share access and file creation on the target.
5. Review EDR process ancestry and subsequent service execution, network connections and persistence.
6. Check deployment tools, administrator activity, maintenance windows and approved change records.
7. Hunt for the account, source, service, path and hash across other endpoints and servers.
8. Invoke authorised account/session and host containment; escalate affected scope and evidence to Tier 2/IR.

### Relevant Tools / Logs

Wazuh, Windows Security log Events 4624 and 4697 where auditing is enabled, System log and EDR telemetry, Microsoft Defender for Endpoint, Sysmon where configured, SMB/firewall logs, Active Directory/identity logs, software-deployment records and the incident-management platform.

### Key Interview Takeaway

Network logon plus service creation is a strong correlation, not an automatic verdict. I would connect the events to the source, account, service binary and change context, then distinguish legitimate administration from confirmed lateral movement.

## Question 176

### Interview Question

Microsoft Defender for Endpoint detects rapid encryption behaviour on one file server. A second endpoint shows the same binary hash, several users report inaccessible files and the backup console reports recent deletion attempts. What are your Tier 1 priorities across containment, investigation, recovery and lessons learned?

### Interview-Ready Answer

I would treat this as a critical suspected ransomware incident with potential multi-host and backup impact. The immediate objective is to limit spread while preserving enough evidence to understand scope and support safe recovery.

Within authorised Tier 1 permissions, I would isolate or request isolation of affected endpoints, restrict known malicious indicators and disable or restrict compromised identities or sessions under the playbook. Microsoft documents that Defender for Endpoint device isolation disconnects a device from the organisation's network while retaining connectivity to the Defender service, subject to platform, role and configuration requirements. I would be cautious with infrastructure such as Hyper-V hosts or critical servers because isolation can have wider operational effects; the incident commander and service owner should approve high-impact actions.

I would preserve the alert, device timelines, process trees, hashes, ransom note, file paths, account activity, network connections and backup-console evidence. I would identify the first and last observed activity, affected hosts and shares, privileged or service accounts, remote-management activity, persistence, lateral movement, data staging or exfiltration evidence, and whether the backup system itself is compromised. Encryption does not prove that data was stolen, so extortion or breach claims require separate evidence.

Containment is not eradication or recovery. Specialist teams should remove persistence, rotate exposed credentials, patch the entry path and rebuild or restore from known-good sources. Recovery should use validated backups, prioritised business services, monitored restoration and agreed return-to-service criteria. NIST SP 800-61 Rev. 3 integrates incident response across cybersecurity risk management and emphasises risk-based prioritisation, recorded investigation actions, containment, recovery and continuous improvement. NIST IR 8374 Rev. 1, finalised in June 2026, applies CSF 2.0 outcomes to ransomware risk across Govern, Identify, Protect, Detect, Respond and Recover.

### Real-World SOC Scenario

Defender confirms the same unsigned binary on four endpoints. File-server audit evidence shows one compromised administrative account deleting shadow copies and connecting to the backup-management server. The backup team confirms deletion attempts failed and that offline recovery copies remain available.

- **Observation:** Multiple endpoints show common encryption behaviour, user impact and attempted backup interference.
- **Hypothesis:** An attacker is executing ransomware across the environment and attempting to inhibit recovery.
- **Confirmed evidence:** Correlated process, file, identity and backup-console records establish ransomware execution and recovery-inhibition attempts. Data exfiltration remains unconfirmed.

The verdict is **critical true positive — active multi-host ransomware incident with attempted backup impact, requiring enterprise incident command and immediate coordinated containment**.

### What I Would Check as a Tier 1 Analyst

1. Confirm affected devices, servers, users, shares, business services and the earliest known activity.
2. Preserve Defender alerts, timelines, hashes, ransom notes, file samples, identity events and backup-console records.
3. Isolate or request isolation of affected hosts and restrict indicators under the approved playbook.
4. Identify and contain compromised privileged, service and user identities or active sessions.
5. Hunt for the binary, process chain, persistence, remote-service activity and lateral movement across the estate.
6. Check whether backups, hypervisors, management platforms or security tooling were accessed or modified.
7. Investigate staging, archive creation, unusual egress and cloud activity before making any exfiltration claim.
8. Escalate a UTC-normalised timeline, affected scope, business impact, containment status and evidence gaps to Incident Response and leadership.
9. Support specialist-led eradication, credential rotation, patching, trusted rebuilding and validated restoration.
10. Record actions and feed lessons into detections, segmentation, identity controls, backup protections and the ransomware playbook.

### Relevant Tools / Logs

Microsoft Defender for Endpoint and Defender XDR, Microsoft Sentinel or Splunk, Wazuh where deployed, Windows event and file-server audit logs, Active Directory/Entra identity logs, firewall/DNS/proxy telemetry, backup and hypervisor audit logs, asset inventory and incident-management records.

### Key Interview Takeaway

For ransomware, I would contain the active spread, preserve evidence, protect identities and recovery systems, and escalate the whole business impact. I would keep containment, eradication and recovery distinct and never claim data theft without supporting evidence.
