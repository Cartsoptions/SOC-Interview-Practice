# SOC Interview Practice - 2026-09-11

## Question 58

### Interview Question

What is a password-spray attack, and how would you investigate suspected password spraying in Microsoft Entra ID or another enterprise identity environment without confusing it with ordinary brute force?

### Interview-Ready Answer

**A password-spray attack tries a small number of common or weak passwords across many user accounts instead of trying many passwords against one account.** The purpose is often to avoid per-account lockout thresholds while finding an account that uses a weak password.

Microsoft Entra ID Protection describes password spraying as a coordinated brute-force pattern targeting multiple identities with common passwords. A current and important Microsoft-specific detail is that the Entra **password spray risk detection fires only when Microsoft has observed the spray and confirmed a successful password validation for a user in the tenant**. Unsuccessful spray attempts alone do not generate that specific Entra risk detection. Microsoft also states that this means the attacker identified the correct password, **not necessarily that the attacker successfully accessed a resource**.

So I would distinguish:

**Observation:** many accounts show related authentication attempts, or Entra raises a password-spray risk detection.

**Hypothesis:** a coordinated password-spray attack is occurring and one or more credentials may have been identified.

**Confirmed compromise:** requires evidence that an unauthorised user actually authenticated to resources or performed malicious post-authentication activity.

As a Tier 1 analyst, I would examine the distribution of attempts across users, source IPs or ASNs, applications, protocols, user agents, timestamps and successful sign-ins. I would compare this pattern with a traditional brute-force attack, which usually concentrates many password attempts against one or a small number of accounts.

If a password-spray detection identifies a user whose password was successfully validated, I would urgently investigate that user's subsequent sign-ins, MFA result, device/client context and access to email, files, applications or administrative resources. Remediation such as password reset, token revocation or account blocking must follow the organisation's authorised identity-response playbook.

### Real-World SOC Scenario

Sentinel or Entra shows authentication activity affecting 80 users over 20 minutes. Each user receives only two or three failed attempts, but the attempts share similar source infrastructure and application/protocol characteristics.

Microsoft Entra ID Protection then raises a password-spray risk detection for one finance user.

My **observation** is a coordinated authentication pattern across many identities and a Microsoft risk detection indicating that the correct password for one account was successfully validated.

My **hypothesis** is password spraying with possible credential compromise.

I would immediately pivot to the affected finance user's successful sign-ins and post-authentication activity. If I then find an unfamiliar successful session, unusual mailbox access or abnormal file activity, the account-compromise hypothesis becomes substantially stronger.

### What I Would Check as a Tier 1 Analyst

- Number of user accounts targeted
- Number of attempts per account
- Time window and frequency
- Source IPs, IP ranges and ASNs
- Applications and authentication protocols
- User-agent or client patterns where available
- Entra password-spray risk detection and affected user
- Failed versus successful sign-ins
- MFA result and authentication method
- Device/browser/client context
- Whether the user recognises the successful activity
- Mailbox, SharePoint, OneDrive, OAuth or administrative activity after authentication
- Similar activity affecting other users
- Legacy authentication exposure where applicable
- Conditional Access and Identity Protection context
- Tier 1 escalation and identity-containment authority

### Tools / Logs

Microsoft Entra sign-in logs and Identity Protection; Microsoft Sentinel; Defender XDR; Defender for Cloud Apps where deployed; Microsoft 365 audit logs; VPN/ADFS or other identity-provider logs where relevant; firewall/proxy telemetry; incident-management records.

### Interview Takeaway

Password spraying spreads a few common password attempts across many accounts to reduce the chance of lockout. I would investigate the cross-user pattern, source and authentication context, and then focus urgently on any account where a password was successfully validated. A correct-password match is serious evidence, but I would still verify whether unauthorised resource access actually occurred.

## Question 59

### Interview Question

What is Microsoft Defender for Endpoint Live Response, and how would you decide between investigating through Live Response and isolating a device during an active incident?

### Interview-Ready Answer

**Microsoft Defender for Endpoint Live Response gives authorised security operations personnel remote shell access to an onboarded device for investigation and response.** Microsoft documents capabilities including running supported investigation commands, downloading files such as malware samples or script output, running approved scripts from the Live Response library, analysing entities and taking or undoing certain remediation actions, depending on platform, permissions and configuration.

Live Response and device isolation solve different problems.

**Live Response is primarily an investigation and controlled-response capability.** I would use it when I need deeper device evidence that is not already clear from the portal, for example to inspect files, processes, services or connections, collect evidence or run an approved investigation script.

**Device isolation is a containment action.** Microsoft Defender for Endpoint isolation disconnects the device from normal network access while retaining the connectivity required for the Defender service to continue monitoring the device. The exact isolation options and support depend on the operating system, Defender configuration and permissions.

As Tier 1, I would not automatically isolate every suspicious endpoint. Isolation can disrupt users and business services, and Microsoft provides special controls for high-value assets because some response actions can have significant operational impact. My decision would depend on the evidence, whether malicious activity is active, the risk of lateral movement or exfiltration, the criticality of the device and my authorised response scope.

I would also not run arbitrary commands or scripts through Live Response. I would use documented commands and approved scripts within the permissions and procedures established by the organisation.

### Real-World SOC Scenario

Defender for Endpoint alerts on a workstation where an unfamiliar executable launched PowerShell and began connecting to external infrastructure. The process has also attempted SMB connections to several internal hosts.

My **observation** is suspicious endpoint execution plus possible lateral-movement activity.

My **hypothesis** is an actively compromised workstation.

If the evidence is strong and the playbook authorises Tier 1 endpoint isolation, I would prioritise isolation to reduce further spread while preserving Defender connectivity. I could then use available portal evidence or Live Response, if authorised and supported, to deepen the investigation and collect additional forensic information.

If the endpoint is a critical server, the evidence is ambiguous, or isolation could have major business consequences, I would escalate the containment decision rather than act outside my authority.

### What I Would Check as a Tier 1 Analyst

- Device identity, operating system and business criticality
- Defender alert and incident timeline
- User associated with the suspicious activity
- Parent and child process chain
- File path, hash, signer and prevalence
- PowerShell or command-line context
- Active network connections and destinations
- SMB/RDP or other lateral-movement indicators
- File, registry, service or scheduled-task persistence
- Whether malicious activity is still active
- Whether Live Response is enabled and supported for the device
- Analyst permissions for Live Response and remediation
- Existing automated response or Action Center activity
- Whether device isolation is supported and available
- VPN/proxy or architecture considerations that could affect isolation
- Device classification as high-value/critical
- Tier 1 isolation authority and escalation requirements

### Tools / Logs

Microsoft Defender for Endpoint device timeline and device page; Defender XDR; Live Response where enabled and authorised; Action Center; Microsoft Sentinel; Windows/Sysmon telemetry; DNS/proxy/firewall data; SMB/RDP evidence; incident-management and change records.

### Interview Takeaway

Live Response helps an authorised analyst investigate and respond directly on an endpoint, while device isolation is a containment action designed to reduce further network impact. I would choose based on evidence, active risk, device criticality and my playbook authority, and I would never run unapproved scripts or isolate critical systems casually.

## Question 60

### Interview Question

A Windows host records a newly installed service. What does System Event ID 7045 mean, and how would you investigate whether the service is legitimate software or malicious persistence?

### Interview-Ready Answer

**Windows System Event ID 7045, generated by Service Control Manager, records that a service was installed in the system.** Microsoft documentation shows useful fields including the service name, service file name/path, service type, start type and service account.

However, **Event 7045 does not mean malware by itself**. Windows services are routinely created by legitimate software installation, endpoint agents, drivers, updates and administration tools.

Attackers can also create or modify Windows services for persistence or privilege escalation. MITRE ATT&CK maps this behaviour to **Create or Modify System Process: Windows Service - T1543.003**. Current MITRE detection guidance recommends correlating service creation or modification with process creation, Registry changes under the Services key, rare service names, unusual executable paths, unsigned binaries and execution under elevated contexts. MITRE's current detection strategy also references Windows Security Event 4697 as a service-creation source where that auditing is available, alongside Sysmon process and Registry telemetry.

For a Tier 1 investigation, I would focus on **who or what installed the service, what executable or driver it points to, where that file is located, whether it is signed and known, its start type and account, and what happened before and after installation**.

An executable in a user-writable location such as a temporary or user-profile directory, a rare service name, an unexpected SYSTEM context, an unsigned file and suspicious network activity would increase concern. An approved vendor installer creating a signed service in the expected program directory during a documented software deployment would support a legitimate explanation.

### Real-World SOC Scenario

The SIEM receives a 7045 event from a finance workstation at 03:10.

The service has a generic name and points to an executable under a user's temporary directory. The service is configured to start automatically.

EDR shows that the executable was dropped shortly before service creation by an unfamiliar process, and the newly installed service later makes an outbound connection to an unusual domain.

My **observation** is that a new Windows service was installed.

My **hypothesis** is service-based persistence, potentially with elevated execution.

I would correlate:

**file creation -> service installation -> service execution -> network activity**

If the service is not approved, the binary is suspicious and the process/network chain supports malicious execution, the persistence hypothesis becomes strong and warrants escalation and authorised containment.

### What I Would Check as a Tier 1 Analyst

- Host and exact 7045 timestamp
- Service name and display name
- Service file name / executable or driver path
- Service type
- Start type
- Service account
- Whether the service name/path is normal for the environment
- File hash, digital signature and prevalence
- File creation time and source process
- Windows Security Event 4697 where enabled and available
- Event 4688 or Sysmon Event 1 process creation where configured
- Sysmon Registry events for relevant service-key changes where configured
- EDR process tree and service execution
- Network activity generated by the service
- Persistence or privilege-escalation behaviour
- Approved software deployment, driver update or administration record
- Similar service creation on other endpoints
- Tier 1 containment and escalation authority

### Tools / Logs

Windows System Event 7045; Windows Security Event 4697 and 4688 where enabled; Sysmon process/Registry telemetry where configured; Defender for Endpoint or another EDR; Microsoft Sentinel; Splunk; Wazuh; file-signature/hash and software-inventory data; DNS/proxy/firewall telemetry; change-management records.

### Interview Takeaway

Event 7045 means a Windows service was installed, not that malware was installed. I would validate the service name, executable path, start type, account, file signer/hash, creating process and resulting behaviour, then compare that evidence with approved software or administration before escalating suspected Windows-service persistence.
