# SOC Interview Practice — 2026-11-10

**Curriculum:** Questions 201–204 | Software supply-chain fundamentals, package-install evidence, Defender XDR hunting, and compromised CI/CD incident response

## Question 201

### Interview Question

A developer installs an approved-looking package from a public registry. Defender for Endpoint then reports that the package manager spawned a shell and connected to an unfamiliar domain. What is a software supply-chain compromise in operational SOC terms, and how would you triage this without assuming every package script is malicious?

### Interview-Ready Answer

A software supply-chain compromise occurs when an attacker interferes with software, a dependency, development tool, build process or distribution channel so malicious or unauthorised content reaches downstream users or systems through a trusted workflow. MITRE ATT&CK distinguishes compromise of software dependencies and development tools as T1195.001 and compromise of the software supply chain as T1195.002.

Package managers legitimately execute lifecycle scripts, compile native modules and contact registries or content-delivery infrastructure. Therefore, a package manager spawning a shell is an investigation lead, not automatic proof of compromise. In a SOC environment, I would identify the device or runner, user or service account, package name and version, configured registry, initiating command, exact child processes, created files, network destinations and whether the package is approved and pinned in the lockfile.

I would compare the observed package with the expected dependency manifest and lockfile, inspect registry and publisher metadata, check whether the package has verifiable signatures or provenance, and correlate endpoint process, file and network evidence. npm documents that packages can define lifecycle scripts such as preinstall, install and postinstall; it also provides signature and provenance verification capabilities, but provenance establishes a verifiable link to source/build information rather than proving that code is safe.

Tier 1 should preserve evidence, identify affected devices/builds and escalate. Blocking a registry, deleting build caches, changing dependency policy or stopping a production pipeline belongs to authorised engineering/incident-response owners unless the playbook explicitly delegates that action.

### Real-World SOC Scenario

An approved developer runs a normal dependency installation. A newly introduced transitive package executes a post-install script, writes an executable into a temporary build directory and connects to a domain absent from the organisation's approved registry/CDN list. The package was introduced by an unreviewed lockfile update.

- **Observation:** A package installation triggered a lifecycle script, file creation and unexpected network activity.
- **Hypothesis:** A malicious or compromised dependency is executing through the trusted package-install workflow.
- **Confirmed Evidence:** Registry/package evidence shows the unexpected dependency, source-control history confirms an unauthorised lockfile change, and endpoint telemetry links its post-install execution to the created payload and network connection.

The verdict is **high-severity true positive — confirmed malicious dependency execution on one developer device; CI use and downstream distribution remain to be scoped**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the Defender alert, process tree, commands, files, hashes, connections and UTC timestamps.
2. Record device/runner, account, project, package manager, registry and install command.
3. Identify direct and transitive package name, version and source.
4. Compare package manifest and lockfile with the last approved commit.
5. Review package lifecycle scripts, publisher, age, download/source context and provenance/signature evidence.
6. Correlate the new files with execution, persistence and network telemetry.
7. Hunt the package/version, hash, script path and behaviour across developer devices and runners.
8. Determine whether any build artefact incorporated the package.
9. Escalate for authorised host, package, registry and pipeline containment.

### Relevant Tools / Logs

Microsoft Defender for Endpoint and Defender XDR, package manifests and lockfiles, npm or other package-registry metadata, source-control and pull-request history, CI/CD logs, software-composition analysis, internal repository/proxy logs, Sentinel or Splunk, DNS/firewall/proxy telemetry and incident records.

### Key Interview Takeaway

A package lifecycle script can be legitimate. I would confirm the dependency, provenance, process/file/network chain and downstream build exposure before declaring a supply-chain incident.

## Question 202

### Interview Question

During `npm ci` on a Windows CI runner, the process tree shows `node.exe` launching a post-install script, followed by `powershell.exe`, creation of a binary under the runner's temporary directory and an HTTPS connection to `updates.example`. How would you interpret this evidence, and what can it prove?

### Interview-Ready Answer

The sequence is suspicious because a dependency installation leads to a shell, a new binary and external communication. However, npm lifecycle scripts can legitimately invoke tools, compile components and download platform-specific files. The reserved `updates.example` name in this interview artefact is not a real indicator.

I would validate whether the post-install script belongs to the expected package and version, whether the command and destination are documented by the package owner, and whether the downloaded file matches an approved hash or signature. I would link the process, file and network records using the strongest identifiers and timestamps available in the deployed telemetry rather than assuming that matching process names alone prove causation.

The process tree proves that the recorded parent/child sequence occurred on the runner. File telemetry can prove that a process created or modified the binary, and network telemetry can prove that a recorded process initiated a connection. Those facts do not alone prove the content was malicious, that secrets were stolen, or that the resulting build was compromised. Confirmation requires package/source evidence, payload analysis, business-owner validation and evidence of unauthorised behaviour.

### Real-World SOC Scenario

The package's published source and approved earlier version contain no post-install network behaviour. The newly installed version was published from an unfamiliar account, its package contents include the observed script, the binary is unsigned and the CI owner denies the destination. The same behaviour appears on two runners after the same lockfile update.

- **Observation:** The install created a repeatable package-to-shell-to-file-to-network chain on CI runners.
- **Hypothesis:** The new dependency version contains a malicious post-install payload.
- **Confirmed Evidence:** Package-content analysis, publisher/version change, owner denial and correlated endpoint evidence establish malicious package execution on two runners.

The verdict is **critical true positive — confirmed malicious dependency execution on CI infrastructure; secret access, build contamination and downstream deployment require immediate scoping**.

### What I Would Check as a Tier 1 Analyst

1. Preserve raw process, file and network events with device and timestamp identifiers.
2. Establish the full ancestry from CI agent to package manager, Node, shell and payload.
3. Confirm package name/version, registry URL, resolved tarball and lockfile entry.
4. Extract the lifecycle script and compare it with approved/source-controlled content.
5. Check file hash, signature, prevalence and safe sandbox/static-analysis results where authorised.
6. Validate destination ownership and whether it is approved for that package.
7. Identify environment variables, files or credential stores the process accessed, where telemetry permits.
8. Scope every runner, developer device, build and artefact using the dependency.
9. Escalate for authorised runner isolation and pipeline suspension.

### Relevant Tools / Logs

Defender for Endpoint process/file/network events, Defender XDR, CI-agent and build logs, package manifest/lockfile and tarball, registry/publisher metadata, source control and pull requests, DNS/proxy/firewall logs, software-composition analysis, malware sandbox/static-analysis tooling and case-management records.

### Key Interview Takeaway

The process chain proves execution and related telemetry proves file/network actions. Maliciousness and downstream impact still require package, owner, payload and build evidence.

## Question 203

### Interview Question

Write a safe first-pass Defender XDR advanced-hunting query to find package-manager or Node processes that directly launch shells or download utilities, and explain what the output can and cannot prove.

### Interview-Ready Answer

I would use `DeviceProcessEvents`, which Microsoft documents as containing process-creation and related endpoint events:

```kusto
DeviceProcessEvents
| where Timestamp >= ago(7d)
| where InitiatingProcessFileName in~ ("npm", "npm.exe", "node", "node.exe")
| where FileName in~ (
    "sh", "bash", "cmd.exe", "powershell.exe", "pwsh.exe",
    "curl", "curl.exe", "wget", "wget.exe")
| project Timestamp,
          DeviceName,
          AccountName,
          InitiatingProcessFileName,
          InitiatingProcessCommandLine,
          FileName,
          FolderPath,
          ProcessCommandLine,
          InitiatingProcessId,
          ProcessId,
          ReportId
| order by Timestamp desc
```

Microsoft documents the projected columns in the `DeviceProcessEvents` schema. This query intentionally avoids undocumented action values and searches both Windows and common Linux process names. It is a narrow behavioural lead: wrappers, renamed binaries, different package managers and indirect descendants can be missed.

A result proves that Defender recorded one of the selected initiating processes directly creating one of the selected child processes. It does not prove that the execution came from a malicious package, that a download succeeded, or that data was stolen. I would inspect the full process ancestry and commands, correlate `DeviceFileEvents` and `DeviceNetworkEvents`, validate the package/build context and tune known approved workflows.

### Real-World SOC Scenario

The hunt returns `node.exe` launching PowerShell on three CI runners within minutes of the same dependency update. Each command references the same package directory, and related network events show connections to an unapproved domain.

- **Observation:** The query finds a repeated Node-to-PowerShell pattern associated with one package update.
- **Hypothesis:** A package lifecycle script is executing an unauthorised payload across CI runners.
- **Confirmed Evidence:** Lockfile/package analysis, raw process events, correlated file/network activity and owner validation confirm the package as the source of malicious execution.

The verdict is **critical true positive — confirmed multi-runner malicious dependency execution; downstream artefacts and credentials remain under investigation**.

### What I Would Check as a Tier 1 Analyst

1. Verify Defender sensor coverage, retention and timestamp consistency.
2. Preserve raw `DeviceProcessEvents` rows behind each result.
3. Inspect complete parent and child command lines and working paths.
4. Expand the hunt to other package managers and indirect descendants where justified.
5. Correlate file writes and network connections to the correct process instances.
6. Compare package/version and lockfile across affected projects.
7. Validate expected build scripts with engineering owners.
8. Hunt the package, behaviour and destinations across endpoints and runners.
9. Document query limitations and telemetry gaps in the escalation.

### Relevant Tools / Logs

Microsoft Defender XDR Advanced Hunting, `DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents`, Defender for Endpoint device timeline, Sentinel where Defender hunting is available, Splunk/Wazuh for equivalent telemetry, CI/CD logs, package records and source-control history.

### Key Interview Takeaway

The query finds direct package/Node-to-shell execution. It is a hunting lead, not a malware verdict; package context and correlated file/network evidence determine meaning.

## Question 204

### Interview Question

You confirm that a malicious dependency executed on four CI runners, read pipeline secrets, modified a release artefact and contacted an external service. One affected artefact was signed and deployed to production before the alert. How would you contain, scope, eradicate and support recovery as Tier 1?

### Interview-Ready Answer

I would classify this as a critical software-supply-chain incident with confirmed CI compromise, credential exposure, artefact tampering and downstream production risk. A valid signature does not make the artefact safe if the authorised build/signing workflow itself was compromised.

I would immediately preserve the package tarball and metadata, manifest/lockfile, source-control changes, CI workflow definitions, runner process/file/network evidence, build logs, caches, artefact hashes, provenance/signature records, deployment history and secret-access evidence. I would build a UTC timeline from dependency introduction through installation, build, signing and deployment.

Under the approved playbook, authorised teams should pause affected pipelines and deployments, isolate or remove compromised runners, block/quarantine the package/version, revoke and rotate exposed CI, registry, cloud and signing credentials, and restrict the malicious infrastructure. High-impact actions require the incident commander and platform/service owners; Tier 1 should not delete evidence or independently rotate production signing keys.

Scoping must cover every repository and lockfile referencing the package; all developer devices and runners that installed it; every build, cache and artefact produced during the exposure window; all secrets available to those jobs; registry publication; and every downstream environment or customer receiving an affected artefact. Secret access establishes exposure, while actual misuse must be proven from identity, cloud, registry or resource logs.

Eradication should remove the malicious dependency, caches and persistence; restore a reviewed and pinned dependency state; rebuild runners from trusted images; rotate exposed credentials; and produce fresh artefacts in a clean pipeline. Recovery should verify source, dependencies, build inputs, hashes, signatures/provenance and deployment state, then monitor for reuse. NIST SSDF groups relevant practices around protecting software from tampering and responding to vulnerabilities, while NIST incident-response guidance supports preserved records, magnitude validation, coordinated containment and secure recovery.

### Real-World SOC Scenario

The response team pauses releases and isolates the runners. Investigation identifies six affected repositories, two production deployments and a registry token used from an unfamiliar address. Clean runners rebuild the applications from reviewed lockfiles; exposed credentials are rotated, affected artefacts are replaced and monitoring finds no renewed activity.

- **Observation:** A malicious package executed on runners, accessed secrets, altered an artefact and communicated externally.
- **Hypothesis:** The attacker may retain credentials, poison additional builds or use deployed artefacts to compromise downstream systems.
- **Confirmed Evidence:** CI/endpoint evidence proves package execution and artefact modification; registry/identity evidence proves one exposed token was misused; deployment records prove two affected releases reached production.

The verdict is **critical true positive — confirmed CI/CD supply-chain compromise with credential misuse and downstream production exposure**.

### What I Would Check as a Tier 1 Analyst

1. Preserve package, source, lockfile, build, runner, artefact, signature/provenance and deployment evidence.
2. Build the dependency-introduction-to-deployment timeline.
3. Escalate for authorised pipeline pause, runner isolation and package/version restriction.
4. Identify every repository, device, runner, cache, build and artefact exposed.
5. Inventory all secrets and identities available to affected jobs and check for actual use.
6. Record every signed or published artefact produced during the exposure window.
7. Scope downstream production systems and recipients without assuming all are compromised.
8. Support removal of the dependency, trusted runner rebuilds and credential rotation.
9. Validate clean rebuilds against reviewed dependencies, hashes and provenance.
10. Monitor for the package behaviour, destinations, credentials and tampered artefacts.
11. Feed lessons into dependency approval, lockfile review, internal registries, least privilege and detection coverage.

### Relevant Tools / Logs

Defender for Endpoint/XDR, CI/CD and runner logs, source-control/audit and pull-request history, package registry and repository proxy, manifests/lockfiles and software bills of materials, artefact repository and signing/provenance records, cloud/identity/secret-store logs, Sentinel/Splunk/Wazuh, DNS/proxy/firewall data, deployment platforms and incident-management records.

### Key Interview Takeaway

A compromised trusted build can produce a validly signed malicious artefact. Contain the package, runners, credentials, pipeline and downstream releases together, then rebuild from reviewed sources in a clean environment.

## Verification Notes

- MITRE ATT&CK T1195.001 covers compromise of software dependencies and development tools. Its detection guidance describes package managers or build tools writing content, executing lifecycle scripts or shells, and making unexpected network connections: https://attack.mitre.org/techniques/T1195/001/
- MITRE ATT&CK T1195.002 and detection strategy DET0309 cover compromised software/update chains and correlate install/write activity with first-run children, signature anomalies and unexpected egress: https://attack.mitre.org/techniques/T1195/002/ and https://attack.mitre.org/detectionstrategies/DET0309/
- npm documents package lifecycle scripts, including preinstall, install, postinstall and prepare. Their existence is legitimate functionality and not proof of maliciousness: https://docs.npmjs.com/using-npm/scripts.html/
- npm documents `npm audit signatures` for registry-signature and provenance verification. npm also states that provenance provides a verifiable link to source code and build instructions that users must assess; it does not state that provenance guarantees safe code: https://docs.npmjs.com/cli/audit/ and https://docs.npmjs.com/generating-provenance-statements/
- Microsoft documents the `DeviceProcessEvents` fields used in Question 203, including `Timestamp`, `DeviceName`, `AccountName`, `FileName`, `FolderPath`, `ProcessCommandLine`, initiating-process fields, process IDs and `ReportId`: https://learn.microsoft.com/defender-xdr/advanced-hunting-deviceprocessevents-table
- Microsoft documents `DeviceFileEvents` for endpoint file events and `DeviceNetworkEvents` for network connections, including process-attribution and destination fields used for correlation: https://learn.microsoft.com/defender-xdr/advanced-hunting-devicefileevents-table and https://learn.microsoft.com/defender-xdr/advanced-hunting-devicenetworkevents-table
- CISA's software-supply-chain guidance recommends package integrity verification, protection of signing keys and defence against repository/distribution compromise: https://www.cisa.gov/sites/default/files/2023-12/ESF_SECURING_THE_SOFTWARE_SUPPLY_CHAIN_DEVELOPERS.pdf
- NIST SP 800-218 SSDF groups practices into Prepare the Organization, Protect the Software, Produce Well-Secured Software and Respond to Vulnerabilities: https://csrc.nist.gov/pubs/sp/800/218/final
- NIST SP 800-61 Rev. 3, finalised in April 2025, recommends preserving incident records/evidence, validating magnitude, coordinating containment, securely recovering and feeding lessons into improvement: https://csrc.nist.gov/pubs/sp/800/61/r3/final
