# SOC Interview Practice — 2026-11-12

**Curriculum:** Questions 209–212 | Risk-based vulnerability prioritisation, scanner validation, Defender XDR vulnerability hunting, and response to exploited public-facing software

## Question 209

### Interview Question

A vulnerability scanner reports a CVSS 9.8 vulnerability on an internet-facing payroll server, while another report shows a CVSS 10.0 vulnerability on an isolated laboratory workstation. Both have patches available. Which should a Tier 1 analyst escalate first, and how would you justify the decision without treating CVSS as the whole risk assessment?

### Interview-Ready Answer

I would not prioritise automatically by choosing the highest CVSS number. CVSS communicates technical severity; FIRST explicitly states that a CVSS Base score is not risk and should not be used alone for patch prioritisation. I would combine severity with evidence about exploitation, exposure, asset importance and the organisation's environment.

For each finding I would validate the affected product/version and asset identity, then check whether the CVE is in CISA's Known Exploited Vulnerabilities catalogue, whether public exploit code or active exploitation is reported, whether the vulnerable service is reachable, what privileges or data it exposes, whether compensating controls exist, and what business harm exploitation could cause. I would also confirm scanner recency and coverage, patch/vendor guidance, remediation deadline, service owner and operational constraints.

On the stated facts, I would normally escalate the internet-facing payroll server first because it is reachable from an untrusted network and supports a sensitive business service. If the workstation's CVE is in KEV, has confirmed exploitation in our environment, or provides a path to highly sensitive systems, its priority could change. CISA recommends prioritising KEV vulnerabilities on internet-facing systems and recording compensating controls where patching is not immediately possible.

Tier 1 should validate and enrich the finding, open or update the approved remediation record, notify the owner and escalate overdue or high-risk exposure. The system owner, vulnerability manager and change authority decide and implement patching, isolation, service shutdown or formal risk acceptance unless the playbook delegates those actions.

### Real-World SOC Scenario

The payroll server exposes the vulnerable application to the internet, the CVE appears in CISA KEV and web-proxy logs show scanning against the affected path. The isolated workstation has no route from untrusted networks and the vulnerable component is not running.

- **Observation:** Two severe scanner findings exist, but their reachability, threat evidence and business impact differ.
- **Hypothesis:** The internet-facing payroll service is more likely to be targeted and has greater immediate operational and data impact.
- **Confirmed Evidence:** Asset inventory, external exposure, KEV status, service configuration and proxy logs confirm the payroll server's applicable and urgent exposure.

The verdict is **priority-one remediation and threat-hunting escalation for the payroll server; the workstation remains a valid finding requiring scheduled remediation and validation**.

### What I Would Check as a Tier 1 Analyst

1. Confirm asset identity, owner, business service, data sensitivity and criticality.
2. Validate product, version, vulnerable component and scanner timestamp.
3. Check internet exposure, network reachability and whether the affected service is running.
4. Check CISA KEV, vendor advisories and credible threat intelligence for exploitation.
5. Review public-exploit availability without treating it as proof of compromise.
6. Look for related alerts, attack traffic, process activity and indicators on the asset.
7. Identify vendor fixes, mitigations and compensating controls.
8. Record priority, rationale, owner, due date and escalation path.
9. Track remediation and require evidence-based validation before closure.

### Relevant Tools / Logs

Tenable, Qualys or Microsoft Defender Vulnerability Management; CISA KEV and vendor advisories; CMDB/asset inventory; firewall, WAF, IDS/IPS, proxy and EDR telemetry; Defender XDR, Sentinel, Splunk or Wazuh; patch/change records and the vulnerability ticketing system.

### Key Interview Takeaway

CVSS describes technical severity, not organisational risk by itself. I would prioritise using exploitation evidence, exposure, applicability, asset value, business impact and compensating controls.

## Question 210

### Interview Question

A credentialed scanner repeatedly flags an old Apache version on a supported Red Hat Enterprise Linux server. The Linux administrator says the vendor backported the security fix without changing to the newest upstream version. How would you determine whether the finding is genuinely vulnerable, already remediated or a false positive?

### Interview-Ready Answer

I would not close the finding based only on the administrator's statement, and I would not insist it is vulnerable based only on the upstream version string. Red Hat documents that it backports fixes into stable package versions; scanners that judge only the upstream version can therefore report false positives.

I would first confirm what the scanner actually detected: asset, port, service, package, source package, installed release, CVE, detection method and scan date. A network banner is weaker evidence than an authenticated package assessment because banners may be hidden, customised or unrelated to the installed package state.

Next I would compare the exact distribution package and release with the applicable Red Hat Security Advisory, CVE page and machine-readable vendor data such as OVAL where available. I would check the package manager's installed-package evidence and change records, confirm that the running service uses the fixed package, and determine whether a restart or reboot is required. I would then rescan using current authenticated checks.

If vendor evidence proves the installed release contains the backported fix and the scanner's logic relied on an upstream-version comparison, I would document a false positive or accepted scanner exception using the organisation's approval process. If the package is fixed on disk but the old vulnerable process is still running, remediation is incomplete. If the evidence remains inconsistent, I would escalate to the vulnerability team or scanner/vendor support rather than guessing.

### Real-World SOC Scenario

The scanner reports the vulnerable upstream version from an HTTP banner. Authenticated package evidence shows the Red Hat release named in the security advisory, but the web service has not been restarted since the update and still maps the old library in memory.

- **Observation:** Banner and package evidence appear to disagree.
- **Hypothesis:** The scanner may be producing a version-based false positive, or the host may be only partially remediated.
- **Confirmed Evidence:** The vendor advisory proves the package contains the fix, while process evidence proves the running service has not loaded it.

The verdict is **not a false-positive closure yet — the package is patched on disk, but service restart and validation are still required**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the scanner plugin/output, CVE, asset, port and detection method.
2. Confirm whether the scan was authenticated and whether credentials succeeded.
3. Identify the exact installed package, release and source package.
4. Compare it with the vendor CVE page, security advisory and OVAL/CSAF data where applicable.
5. Check patch/change records and installation time.
6. Confirm which binary and libraries the running process uses.
7. Determine whether restart or reboot is required.
8. Rescan with current authenticated checks after remediation.
9. Document the evidence before closing, suppressing or creating an exception.

### Relevant Tools / Logs

Tenable or Qualys authenticated scan evidence, Red Hat package-manager inventory, Red Hat Security Advisories/CVE and OVAL data, service/process information, CMDB, change and patch-management records, Defender for Endpoint or Wazuh inventory, SIEM logs and vulnerability exception records.

### Key Interview Takeaway

Version strings are evidence, not a verdict. Validate the distribution package against the vendor advisory, confirm the running service loaded the fix and rescan before closure.

## Question 211

### Interview Question

Write a safe Microsoft Defender XDR Advanced Hunting query to list internet-facing devices with vulnerabilities for which public exploit code is available. Include useful prioritisation context and explain the query's limitations.

### Interview-Ready Answer

I would use the documented Defender Vulnerability Management and `DeviceInfo` tables:

```kusto
let LatestDeviceInfo =
    DeviceInfo
    | summarize arg_max(Timestamp, *) by DeviceId
    | project DeviceId,
              IsInternetFacing,
              ExposureLevel,
              AssetValue,
              SensorHealthState;
DeviceTvmSoftwareVulnerabilities
| join kind=inner (
    DeviceTvmSoftwareVulnerabilitiesKB
    | where IsExploitAvailable == true
    | project CveId,
              CvssScore,
              IsExploitAvailable,
              PublishedDate,
              LastModifiedTime
) on CveId
| join kind=leftouter LatestDeviceInfo on DeviceId
| where IsInternetFacing == true
| project DeviceId,
          DeviceName,
          OSPlatform,
          OSVersion,
          SoftwareVendor,
          SoftwareName,
          SoftwareVersion,
          CveId,
          VulnerabilitySeverityLevel,
          CvssScore,
          IsExploitAvailable,
          CveTags,
          RecommendedSecurityUpdate,
          RecommendedSecurityUpdateId,
          ExposureLevel,
          AssetValue,
          SensorHealthState,
          PublishedDate,
          LastModifiedTime
| order by todouble(CvssScore) desc
```

Microsoft documents the vulnerability, vulnerability-knowledge-base and device fields used here. `CvssScore` is documented as a string, so `todouble()` is used only for numeric ordering. `arg_max(Timestamp, *) by DeviceId` selects the most recent `DeviceInfo` record per device.

The result identifies Defender-assessed vulnerabilities with public exploit availability on devices Defender currently marks internet-facing. It does not prove the exploit works against that exact configuration, that the service is reachable, that the CVE is in CISA KEV, or that exploitation occurred. I would validate application exposure, applicability, vendor guidance, KEV status, sensor health and supporting network/EDR evidence.

This query must run in Defender XDR Advanced Hunting with Defender for Endpoint/Vulnerability Management data. Microsoft states that these TVM tables may be visible in Microsoft Sentinel's schema but are not directly ingested there and return no results unless the organisation builds a custom ingestion path.

### Real-World SOC Scenario

The query returns five devices. One high-value internet-facing server has an exploitable CVE, a healthy sensor and recent inbound requests to the affected service. Two results are retired devices with stale telemetry, and two expose no affected service.

- **Observation:** The hunt returns five vulnerable/internet-facing device records.
- **Hypothesis:** The high-value server may present the most immediate exploitable path, while stale and non-reachable records may require inventory correction or lower priority.
- **Confirmed Evidence:** Current device telemetry, service configuration, network logs and vendor applicability confirm one urgent exposure.

The verdict is **one priority-one applicable exposure, two inventory/sensor-quality issues and two lower-priority findings pending normal remediation**.

### What I Would Check as a Tier 1 Analyst

1. Confirm Defender for Endpoint/Vulnerability Management deployment and data freshness.
2. Validate `IsInternetFacing`, sensor health, asset value and exposure level.
3. Confirm the affected software and service are installed, running and reachable.
4. Check CISA KEV and vendor advisories separately.
5. Correlate WAF/firewall/IDS and EDR activity for exploitation attempts or post-exploit behaviour.
6. Remove or correct stale/duplicate inventory only through the approved asset process.
7. Record the query window, limitations and prioritisation rationale.
8. Escalate actionable findings and track remediation through validation.

### Relevant Tools / Logs

Defender XDR Advanced Hunting, Defender Vulnerability Management, `DeviceTvmSoftwareVulnerabilities`, `DeviceTvmSoftwareVulnerabilitiesKB`, `DeviceInfo`, Defender for Endpoint, CISA KEV, vendor advisories, CMDB, WAF/firewall/IDS telemetry and remediation tickets.

### Key Interview Takeaway

The query creates a prioritised investigation queue, not proof of exploitation. Validate reachability, applicability, threat evidence and telemetry health before acting.

## Question 212

### Interview Question

An internet-facing application with a KEV-listed remote-code-execution vulnerability was not patched before the deadline. WAF logs show crafted requests, the web-server process spawns a shell, a new script appears in the web root and the host makes an unusual outbound connection. How would you contain, scope, eradicate and support recovery as Tier 1?

### Interview-Ready Answer

I would classify this as a critical suspected-to-confirmed exploitation incident, not merely an overdue vulnerability ticket. MITRE ATT&CK T1190 covers exploitation of a public-facing application for initial access. The request pattern alone shows an attempt; the server-to-shell process chain, unauthorised web-root file and outbound connection provide post-exploitation evidence.

I would preserve the vulnerability record, vendor advisory, WAF/reverse-proxy and application logs, raw request details, process tree and commands, new file metadata/hash/content, network connections, authentication activity, cloud/control-plane evidence and UTC timestamps. Where volatile evidence is important, I would escalate for specialist collection before disruptive actions when the response plan and urgency allow.

Under the approved playbook, authorised owners should remove public exposure or block the exploit path, isolate or restrict the host, block confirmed malicious infrastructure, protect evidence and prevent the compromised service identity from reaching other systems. Tier 1 should initiate or request those actions according to authority; it should not independently delete the web shell, rebuild a production server or rotate enterprise credentials without coordination.

Scoping must cover every vulnerable instance, load-balanced node, container/image, account and secret available to the application; all requests from related infrastructure; child processes and persistence; outbound connections; credential use; lateral movement; database or file access; and other systems showing the same file, hash or behaviour. Patching after confirmed exploitation closes the vulnerability but does not remove persistence or stolen credentials.

Eradication and recovery should be specialist-led: remove persistence, revoke/rotate exposed credentials and tokens, correct the vulnerable configuration, patch or upgrade, and rebuild or restore from a trusted source where appropriate. Before returning service, validate application files/configuration, identities, segmentation, WAF controls, logging and the absence of recurring indicators. NIST SP 800-61 Rev. 3 supports preserving incident records/evidence, validating magnitude, coordinated containment and secure recovery.

### Real-World SOC Scenario

Responders remove the application from the public load balancer and isolate the affected node. Investigation finds the same web shell on a second node created through the shared deployment volume, plus a service-account credential used against a database. Both nodes are rebuilt from a trusted image, the credential is rotated and validated traffic is restored under enhanced monitoring.

- **Observation:** Crafted requests are followed by server-side shell execution, a new web-root script and unusual egress.
- **Hypothesis:** The attacker exploited the public application, established persistence and may have accessed credentials or data.
- **Confirmed Evidence:** WAF, process, file and network telemetry establish exploitation and persistence; identity/database logs confirm use of an exposed service credential.

The verdict is **critical true positive — confirmed public-facing application exploitation with multi-node persistence and credential misuse; data impact remains under investigation**.

### What I Would Check as a Tier 1 Analyst

1. Preserve vulnerability, request, application, process, file, network and identity evidence.
2. Build a UTC timeline from exploit request through post-exploitation and credential use.
3. Escalate for authorised exposure removal, host isolation and indicator restriction.
4. Identify every vulnerable instance, node, container/image and shared storage location.
5. Hunt the script/hash, commands, source infrastructure and destinations across the estate.
6. Inventory every application secret, token and service identity exposed to the host.
7. Correlate subsequent authentication, database, cloud and lateral-movement activity.
8. Distinguish attempted exploitation from confirmed execution and confirmed impact.
9. Support persistence removal, trusted rebuild, patching and credential rotation.
10. Validate recovery through rescanning, file/configuration comparison, clean telemetry and monitoring.
11. Track the original vulnerability to verified closure and record why remediation missed its deadline.

### Relevant Tools / Logs

WAF/reverse-proxy and web/application logs, Defender for Endpoint/XDR or another EDR, Sysmon or Linux audit/process/file telemetry where configured, Defender Vulnerability Management/Tenable/Qualys, Sentinel/Splunk/Wazuh, firewall/DNS/proxy, identity and database/cloud logs, CMDB, change records and incident-management evidence.

### Key Interview Takeaway

Once exploitation is confirmed, patching alone is insufficient. Preserve the exploit-to-process-to-file-to-network chain, contain the host and identity paths, scope persistence and credential use, rebuild from trust and validate recovery.

## Verification Notes

- FIRST states that CVSS Base scores describe technical severity and are not risk or a sufficient standalone patch-prioritisation method: https://www.first.org/cvss/v4.0/faq and https://www.first.org/cvss/v4.0/user-guide
- CISA's vulnerability guidance prioritises known-exploited vulnerabilities, especially on internet-facing systems, and recommends documented compensating controls when immediate patching is not possible: https://www.cisa.gov/known-exploited-vulnerabilities-catalog and https://www.cisa.gov/sites/default/files/publications/CISA_CPG_CHECKLIST_12052022.pdf
- NIST SP 800-40 Rev. 4 defines enterprise patch management as identifying, prioritising, acquiring, installing and verifying patches, updates and upgrades: https://csrc.nist.gov/pubs/sp/800/40/r4/final
- Red Hat documents that backported fixes can leave an older upstream version number and that scanners relying only on that number can produce false positives. Red Hat advisories and OVAL data provide product-specific evidence: https://access.redhat.com/security/updates/backporting and https://access.redhat.com/articles/red_hat_vulnerability_tutorial
- Microsoft documents the fields used in Question 211 in `DeviceTvmSoftwareVulnerabilities`, `DeviceTvmSoftwareVulnerabilitiesKB` and `DeviceInfo`: https://learn.microsoft.com/defender-xdr/advanced-hunting-devicetvmsoftwarevulnerabilities-table, https://learn.microsoft.com/defender-xdr/advanced-hunting-devicetvmsoftwarevulnerabilitieskb-table and https://learn.microsoft.com/defender-xdr/advanced-hunting-deviceinfo-table

The query is therefore explicitly a Defender XDR Advanced Hunting query: https://learn.microsoft.com/defender-xdr/advanced-hunting-devicetvmsoftwarevulnerabilitieskb-table
- Microsoft documents vulnerability-remediation requests and tracking; submitting a request does not itself patch devices or apply changes: https://learn.microsoft.com/defender-vulnerability-management/tvm-remediation
- MITRE ATT&CK T1190 covers exploiting weaknesses in public-facing applications for initial access. Detection strategy DET0080 correlates abnormal requests with server errors, child shells or tools and outbound communications: https://attack.mitre.org/techniques/T1190/ and https://attack.mitre.org/detectionstrategies/DET0080/
