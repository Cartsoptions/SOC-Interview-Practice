# SOC Interview Practice — 2026-10-27

**Curriculum:** Questions 161–164 | AWS console authentication, security-group exposure, Microsoft Sentinel CloudTrail hunting, and compromised cloud credentials

## Question 161

### Interview Question

Microsoft Sentinel receives an AWS CloudTrail ConsoleLogin event showing ConsoleLogin=Success and MFAUsed=No for a privileged IAM user from an unfamiliar UK residential IP address. Is this a confirmed account compromise, and how would you triage it?

### Interview-Ready Answer

I would treat it as a high-priority suspicious cloud authentication, but not call it compromise from those fields alone. AWS documents ConsoleLogin as the console sign-in event, responseElements.ConsoleLogin as the sign-in result, and additionalEventData.MFAUsed as whether MFA was used for that sign-in. A successful sign-in without MFA confirms that the account reached the console without MFA; it does not identify the human operator or prove malicious intent.

In a SOC environment, I would validate the AWS account, principal type, ARN or username, source address, user agent, region and time. I would determine whether the identity is a human IAM user, the root user, a federated identity or an assumed role because the available identity fields differ. I would check whether the IP belongs to an approved VPN, administrator location, security service or cloud provider.

I would then review the same principal's CloudTrail activity before and after the login: IAM changes, access-key creation, role assumption, security-group changes, logging changes and access to sensitive services. I would confirm the activity with the user through the approved process. If the user denies it or unauthorised changes follow, I would invoke or request identity containment and escalate.

### Real-World SOC Scenario

The IAM user normally signs in through corporate egress with MFA. The user denies the residential-IP login. Five minutes later, CloudTrail records CreateAccessKey for the same identity.

- **Observation:** A privileged IAM user successfully signed in without MFA from an unfamiliar source and then created an access key.
- **Hypothesis:** An attacker used valid credentials and created an additional credential for persistence.
- **Confirmed evidence:** CloudTrail and user confirmation establish unauthorised console access and access-key creation. How the original password was obtained remains unconfirmed.

The verdict is **high-severity true positive — confirmed unauthorised cloud-account use with additional credentials created**.

### What I Would Check as a Tier 1 Analyst

1. Confirm UTC time, AWS account, EventName, result, MFA value, source address and user agent.
2. Identify UserIdentityType, ARN, principal ID, username and whether the activity used root, IAM, federation or an assumed role.
3. Check source ownership, VPN/proxy context, travel, administrator schedule and approved automation.
4. Review all events for the principal and source before and after the sign-in.
5. Look for CreateAccessKey, user/role/policy changes, role assumption, security-group changes and logging changes.
6. Confirm the user's activity through the approved identity-verification process.
7. Invoke or request authorised credential restriction, session containment and key deactivation when compromise is corroborated.
8. Escalate the timeline, affected accounts/resources, containment status and unknown initial-access method.

### Relevant Tools / Logs

AWS CloudTrail, Microsoft Sentinel AWSCloudTrail, AWS IAM and Identity Center records where applicable, GuardDuty or Security Hub findings, VPN/proxy logs, threat-intelligence enrichment, asset/account inventory and incident case management.

### Key Interview Takeaway

A successful AWS login without MFA is an important observation, not a complete verdict. I would validate the identity and source, review the subsequent API activity and confirm compromise through unauthorised actions or user evidence.

## Question 162

### Interview Question

CloudTrail shows AuthorizeSecurityGroupIngress adding TCP port 22 from 0.0.0.0/0 to the security group attached to a production EC2 instance. Explain what a security group does and how you would decide whether this change created an exploitable exposure.

### Interview-Ready Answer

An AWS security group is a stateful virtual firewall that controls permitted inbound and outbound traffic for associated resources. In operational terms, a rule allowing TCP 22 from 0.0.0.0/0 permits SSH traffic from any IPv4 address at the security-group layer.

That does not automatically prove the instance was reachable from the internet. I would also check whether the instance had a public address, an internet-routable subnet and route, network ACL restrictions, a listening SSH service and any other network or host controls. Conversely, I would not dismiss the change because no login is immediately visible: exposure duration and logging coverage matter.

CloudTrail records EC2 API activity and can establish who made the change, when, from which source and with which request parameters. I would validate the actor, change ticket, automation pipeline and the exact rule. I would correlate VPC Flow Logs, SSH authentication and endpoint evidence for inbound attempts or successful sessions during the exposure window. Network or cloud engineering normally owns the configuration correction; Tier 1 validates the security event and invokes or requests remediation through the playbook.

### Real-World SOC Scenario

The instance has a public IPv4 address and an internet-gateway route. There is no approved change. VPC Flow Logs show inbound connections to port 22, and the Linux authentication log records a successful session from one of those sources.

- **Observation:** An unauthorised rule allowed global IPv4 SSH access to a publicly routable instance.
- **Hypothesis:** The actor intentionally exposed the instance and may have used the opening for remote access.
- **Confirmed evidence:** CloudTrail confirms the unauthorised configuration change, while network and host logs confirm a successful external SSH session. The credential used and the actor's original access path remain under investigation.

The verdict is **high-severity true positive — confirmed unauthorised security-group exposure with successful external access**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the CloudTrail event, actor ARN/principal, access-key ID where present, source address and request parameters.
2. Identify the security group, affected network interfaces, EC2 instances, owners and business criticality.
3. Confirm public addressing, subnet route, internet gateway, network ACLs and whether SSH was listening.
4. Validate change-management, infrastructure-as-code deployment and automation context.
5. Establish the rule's creation and removal times to define the exposure window.
6. Review VPC Flow Logs, SSH/PAM records, EDR and application evidence for access or follow-on activity.
7. Invoke or request removal or restriction of the rule and containment of affected instances within the approved process.
8. Hunt for the same principal, source or rule pattern across accounts and regions.
9. Escalate confirmed access, identity risk and recovery requirements to cloud operations and IR.

### Relevant Tools / Logs

AWS CloudTrail, EC2/VPC configuration, VPC Flow Logs, AWS Config where deployed, GuardDuty/Security Hub, Linux SSH and PAM records, EDR, Microsoft Sentinel or Splunk, change-management and infrastructure-as-code records.

### Key Interview Takeaway

0.0.0.0/0 on port 22 creates broad permission at the security-group layer, but reachability and compromise require additional evidence. I would reconstruct both the control change and what actually reached the instance.

## Question 163

### Interview Question

AWS CloudTrail data is connected to Microsoft Sentinel. Write a safe KQL query to review a suspicious IAM user's console sign-in and high-risk follow-on activity, then explain what the output proves.

### Interview-Ready Answer

I would use a bounded query against the documented AWSCloudTrail table:

```kusto
let lookback = 24h;
let targetUser = "cloud-ops-user";
AWSCloudTrail
| where TimeGenerated >= ago(lookback)
| where UserIdentityUserName =~ targetUser
| extend
    MFAUsed = tostring(parse_json(AdditionalEventData).MFAUsed),
    LoginResult = tostring(parse_json(ResponseElements).ConsoleLogin)
| where EventName in~ (
    "ConsoleLogin",
    "CreateUser",
    "CreateAccessKey",
    "AttachUserPolicy",
    "AuthorizeSecurityGroupIngress",
    "StopLogging"
)
| project
    TimeGenerated,
    EventName,
    EventSource,
    UserIdentityType,
    UserIdentityArn,
    UserIdentityAccessKeyId,
    SourceIpAddress,
    UserAgent,
    AWSRegion,
    SessionMfaAuthenticated,
    MFAUsed,
    LoginResult,
    RequestParameters,
    ErrorCode
| order by TimeGenerated asc
```

Microsoft documents these AWSCloudTrail columns and publishes a console-login example that parses MFAUsed from AdditionalEventData and ConsoleLogin from ResponseElements. The event-name list is an analyst-selected review set, not a Microsoft detection rule or guarantee of maliciousness.

The query proves which matching records were ingested for the named IAM user during the selected period. It does not prove completeness, compromise or success for every API call. I would inspect ErrorCode, raw request/response data and ingestion health. UserIdentityUserName may not identify assumed-role or federated sessions consistently, so investigations should also pivot on ARN, principal ID, access-key ID and session issuer.

### Real-World SOC Scenario

The query returns a successful console login without MFA, followed by CreateAccessKey, AuthorizeSecurityGroupIngress and StopLogging, all from the same unfamiliar address. The account owner denies the activity.

- **Observation:** Sentinel contains a time-correlated sequence of authentication, credential, network-control and logging events.
- **Hypothesis:** A valid cloud account was compromised and used to create persistence, expose an instance and impair visibility.
- **Confirmed evidence:** CloudTrail plus user confirmation establish unauthorised cloud activity. Whether every requested API action succeeded must be checked through error/response fields and current resource state.

The verdict is **critical true positive when the changes are confirmed successful — compromised cloud identity with persistence and defence-evasion activity**.

### What I Would Check as a Tier 1 Analyst

1. Confirm connector health, ingestion latency, retention and the selected UTC window.
2. Review raw records and ErrorCode; do not equate a requested action with success.
3. Pivot on user ARN, principal ID, access-key ID, source, region and session issuer.
4. Compare current IAM, security-group and CloudTrail configuration with the events.
5. Check whether the principal assumed roles or created temporary credentials.
6. Extend the hunt to all accounts and regions available to the SOC.
7. Correlate GuardDuty/Security Hub, VPC Flow Logs and workload telemetry.
8. Record what the query demonstrates separately from hypotheses and visibility gaps.

### Relevant Tools / Logs

Microsoft Sentinel Logs, AWSCloudTrail, AWS CloudTrail Lake or centrally stored trails where deployed, IAM, GuardDuty, Security Hub, AWS Config, VPC Flow Logs, workload EDR and incident case management.

### Key Interview Takeaway

KQL organises the cloud timeline; it does not make the verdict. I would verify raw outcomes, current resource state, identity type and ingestion coverage before escalating.

## Question 164

### Interview Question

An AWS access key belonging to an automation IAM user is used from a new country. CloudTrail then records CreateUser, AttachUserPolicy, CreateAccessKey, StopLogging and high-volume S3 GetObject activity. How would you contain, scope and escalate this incident as Tier 1?

### Interview-Ready Answer

I would treat this as a critical suspected cloud-account compromise and rapidly validate which actions succeeded. MITRE ATT&CK maps use of compromised cloud identities to T1078.004, creation of cloud accounts to T1136.003, creation of additional cloud credentials to T1098.001 and disabling cloud logs to T1685.002.

I would preserve the available CloudTrail records, alert evidence, actor identity, access-key ID, source, user agent, regions, request parameters and resource identifiers. I would determine whether the automation workload or a planned deployment could explain the source and actions. The sequence of unauthorised identity creation, privilege assignment, additional credentials and logging interference would confirm malicious control-plane activity.

Within the approved playbook, I would invoke or urgently request reversible containment: deactivate the compromised long-term access key, restrict the IAM principal's permissions, disable or quarantine newly created identities and credentials, and protect affected resources. I would not assume that deactivating one key invalidates temporary credentials already issued through AWS STS. AWS guidance notes that active temporary credentials may require permission restriction or token-issue-time controls until they expire.

I would scope every account and region, role assumptions, policy changes, network-control changes, new keys/users, CloudTrail configuration and resource access. S3 GetObject is an object-level data event and is not logged by default; I would verify that the relevant data-event logging was enabled before treating the records as complete. High-volume downloads establish access to logged objects but data-breach impact, sensitivity and successful transfer still require evidence and business-owner assessment.

Recovery belongs to authorised cloud/IR teams: restore logging, remove persistence, rotate dependent secrets safely, review infrastructure-as-code and repositories for exposure, rebuild affected workloads where integrity is uncertain, and validate monitoring before closure.

### Real-World SOC Scenario

The automation owner confirms that the workload was inactive. The compromised AKIA-prefixed key created a new administrator, generated a second access key and stopped a trail. S3 data events show successful reads of sensitive finance objects before containment.

- **Observation:** One long-term key performed unauthorised IAM, credential, logging and object-access actions from a novel source.
- **Hypothesis:** The key was exposed in a repository or workload and an attacker established persistence before accessing data.
- **Confirmed evidence:** The owner statement and successful CloudTrail events confirm account compromise, persistence and unauthorised object reads. The exact key-exposure route and whether data left attacker-controlled infrastructure remain under investigation.

The verdict is **critical true positive — confirmed compromised AWS credentials with privileged persistence, logging impairment and sensitive-data access**.

### What I Would Check as a Tier 1 Analyst

1. Preserve all available CloudTrail, GuardDuty/Security Hub, IAM and S3 data-event evidence in protected storage.
2. Confirm access-key ID, owning principal, policies, source, user agent, regions and first/last observed use.
3. Validate which API calls succeeded through error/response fields and current state.
4. Identify created users, attached policies, new keys, assumed roles and temporary sessions.
5. Invoke or request key deactivation, permission restriction and containment of malicious identities under the playbook.
6. Restore and validate logging through authorised cloud owners without overwriting preserved evidence.
7. Scope security groups, compute, storage, secrets, KMS, Lambda and other services touched by the principal.
8. Verify whether S3 data-event coverage was enabled and identify which objects were successfully read.
9. Coordinate with data owners, privacy/legal and IR on sensitivity, exposure and notification decisions.
10. Hunt repositories, deployment pipelines and workloads for the original key exposure, then support safe rotation.
11. Track eradication, recovery, monitoring validation and lessons learned before closure.

### Relevant Tools / Logs

AWS CloudTrail and CloudTrail Lake or central log archive, IAM and STS, GuardDuty, Security Hub, AWS Config, S3 data events and access evidence where enabled, VPC Flow Logs, workload logs/EDR, secrets-management and CI/CD audit records, Microsoft Sentinel or Splunk and incident case management.

### Key Interview Takeaway

Cloud credential containment must address the principal, new persistence and any temporary sessions—not just one access key. I would preserve the control-plane timeline, validate data-event coverage, scope every account and region, and escalate recovery and breach assessment to authorised specialists.

## Verification Notes

- AWS documents CloudTrail console sign-in events with eventName ConsoleLogin, responseElements.ConsoleLogin, additionalEventData.MFAUsed, source address and user-agent information. A successful login without MFA proves the recorded authentication outcome, not malicious intent.
- Microsoft documents the AWSCloudTrail table fields used in Question 163 and publishes an example that parses MFAUsed and ConsoleLogin. The query's event list and 24-hour window are illustrative analyst choices.
- AWS security groups control permitted inbound and outbound traffic for associated resources. A global IPv4 source on TCP 22 permits SSH at that layer but does not independently establish end-to-end internet reachability.
- AWS documents that CloudTrail can identify an EC2 API request, its source address and time. An ongoing trail or CloudTrail Lake event data store is needed for retained records beyond the limited event-history view.
- AWS incident-response guidance supports restricting principal permissions and deactivating or deleting compromised long-term access keys. Deactivation is reversible; deletion is not. Temporary credentials may require separate permission-based containment before expiry.
- S3 object operations such as GetObject are CloudTrail data events. AWS states that trails and event data stores do not log data events by default, so apparent absence is not proof of no object access.
- MITRE ATT&CK currently maps cloud valid-account use to T1078.004, cloud account creation to T1136.003, additional cloud credentials to T1098.001 and cloud-log impairment to T1685.002.
- NIST SP 800-61 Rev. 3, finalised in April 2025, integrates detection, response and recovery with broader CSF 2.0 cybersecurity risk management.
- All identities, addresses, account names, keys and activity in these scenarios are simulated.
