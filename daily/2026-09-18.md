# SOC Interview Practice - 2026-09-18

## Question 73

### Interview Question
A Windows Security alert shows Event ID 1102. What does it mean, and how would you investigate it without assuming that the host is compromised?

### Interview-Ready Answer
Windows Security Event **1102** means **the Security audit log was cleared**. Microsoft documents the account that cleared the log and a Logon ID that can help correlate the action with a logon event such as 4624. Microsoft also recommends monitoring 1102 because manually clearing the Security log is normally uncommon.

Attackers can clear Windows event logs to remove evidence; MITRE ATT&CK maps this behaviour to **T1070.001, Clear Windows Event Logs**. But 1102 alone does not prove attacker activity. Administrators, troubleshooting procedures, lab resets, maintenance or approved scripts can also clear logs.

**Observation:** the Windows Security audit log was cleared.

**Hypotheses:** authorised administration/maintenance, accidental clearing, or deliberate anti-forensics/indicator removal.

**Confirmed malicious activity:** requires corroborating evidence showing the clearing was unauthorised and associated with suspicious activity.

As Tier 1, I would identify the account and session responsible, establish whether the action was approved, and pivot to telemetry that may survive outside the local Security log, such as EDR, SIEM-forwarded events, Sysmon if separately collected, identity, network and central logging evidence. I would preserve available evidence and escalate rather than performing destructive actions outside my authority.

### Real-World SOC Scenario
A finance workstation sends Event 1102 to the SIEM at 02:14. The named account is not expected to perform log maintenance. EDR shows suspicious PowerShell activity immediately beforehand, followed by attempts to connect to internal systems.

**Observation:** the Security log was cleared by an unexpected account.

**Hypothesis:** an attacker may be trying to remove evidence after malicious execution.

I would correlate **account/session -> process activity -> log clearing -> subsequent network/authentication activity**. If no authorised maintenance exists and central/EDR telemetry shows suspicious activity around the clearing, the anti-forensics hypothesis becomes strong.

### What I Would Check as a Tier 1 Analyst
- Host and exact 1102 timestamp
- Account name/domain/SID and Logon ID
- Related 4624/session context where retained centrally
- Approved maintenance, troubleshooting or change records
- EDR process timeline before and after the event
- PowerShell/Sysmon evidence where configured and centrally retained
- SIEM-forwarded Windows events preceding the clear
- Authentication, DNS, proxy and firewall activity
- Whether other Windows logs were also cleared
- Similar 1102 activity on other endpoints
- Evidence preservation and escalation requirements

### Relevant Tools / Logs
Windows Security Event 1102; Microsoft Sentinel/Splunk/Wazuh; Defender for Endpoint or another EDR; centrally collected Windows/Sysmon/PowerShell telemetry where configured; identity, DNS, proxy and firewall logs.

### Key Interview Takeaway
Event 1102 means the Windows Security audit log was cleared. I would treat it as a high-value investigation signal, not automatic proof of compromise, and correlate the responsible account/session with endpoint, SIEM and network evidence to determine whether the clearing was authorised or anti-forensics.

## Question 74

### Interview Question
How does Microsoft Defender for Endpoint automated investigation and remediation work now, and what should a Tier 1 analyst understand about the Action center and automation levels?

### Interview-Ready Answer
Microsoft changed this area recently. **As of 1 September 2026, Automated Investigation and Response (AIR) in Defender for Endpoint no longer runs as a separate investigation experience and cannot be manually triggered.** Microsoft states that AIR detection and response capabilities are included in Defender for Endpoint's default antivirus protection stack and run automatically. For an on-demand investigation, Microsoft currently directs analysts to run a full antivirus scan as needed.

Defender for Endpoint automation levels still determine whether remediation actions are taken automatically or require approval. Microsoft documents examples of remediation actions including quarantining a file, removing a registry key, stopping a process/service, disabling a driver and removing a scheduled task. Pending and completed remediation actions are tracked in the **Action center**, and some completed actions can be undone.

**Observation:** Defender has generated a verdict and/or remediation action.

**Hypotheses:** malicious activity was correctly identified, the action is awaiting approval because of automation policy, or the detection/remediation may be a false positive requiring review.

**Confirmed response state:** comes from reviewing the alert/investigation evidence, Action center status, action source, affected entity and result.

As Tier 1, I would understand the organisation's automation level and approval process, review evidence before approving a pending action, verify completed remediation, and escalate uncertainty or high-impact actions. I would not claim that I can manually start the old Defender for Endpoint AIR investigation workflow because Microsoft removed that capability on 1 September 2026.

### Real-World SOC Scenario
Defender detects a suspicious file on a workstation. The Action center shows a remediation action associated with the device. In one device group, full automation may remediate malicious artifacts automatically; in another configuration, an action may require security-team approval.

My **observation** is that Defender has identified an artifact and generated remediation activity.

My **hypothesis** is that the file is malicious, but I still review the alert evidence, process chain, file reputation/signature, prevalence and user/device context.

If the evidence supports the verdict, I verify the remediation status and scope. If the action is pending and approval is within Tier 1 authority, I follow the playbook; otherwise I escalate. If evidence suggests a false positive, I do not blindly approve destructive remediation.

### What I Would Check as a Tier 1 Analyst
- Alert/incident evidence and affected device/entity
- Defender verdict and detection source
- Device group and automation level
- Action center Pending actions and History
- Action source and remediation status
- File hash, signer, prevalence and process tree
- Whether activity persists after remediation
- Whether the action is reversible
- Business criticality/high-value asset restrictions
- Tier 1 approval/containment authority

### Relevant Tools / Logs
Microsoft Defender XDR; Defender for Endpoint; Action center; device timeline; antivirus/EDR telemetry; Microsoft Sentinel where integrated.

### Key Interview Takeaway
As of 1 September 2026, Defender for Endpoint AIR is no longer a separately triggered investigation experience. Automated detection/response runs in the protection stack, automation settings govern remediation behaviour, and the Action center is where analysts review pending/completed actions and their status.

## Question 75

### Interview Question
Two incidents arrive at the same time: ransomware activity on one user laptop and suspicious authentication against a business-critical production system. How would you prioritise and escalate them as a Tier 1 analyst?

### Interview-Ready Answer
I would not prioritise incidents only by alert severity, arrival order or the name of the attack. I would rapidly establish **scope, likely impact, time-critical nature and available response resources**. Those factors align with current NIST SP 800-61r3 guidance for prioritising incident response.

NIST SP 800-61r3 also states that incidents should be escalated or elevated as needed and that response strategies involve trade-offs. Containment is intended to prevent an incident from expanding and causing additional damage, but the correct action depends on the incident and organisational authority.

**Observation:** two potentially serious security events are occurring concurrently.

**Hypotheses:** the ransomware may be limited to one endpoint or may be spreading; the authentication activity may be unsuccessful probing or may indicate compromise of a critical system.

**Confirmed priority:** requires rapid scoping of business impact, affected assets/identities, active threat behaviour and potential spread rather than guessing from the alert title.

As Tier 1, I would triage both immediately enough to identify life/safety or critical-business impact, whether malicious activity is active, whether lateral movement or data loss is occurring, and whether approved containment is available. I would escalate early when a critical asset, privileged identity, broad scope, destructive behaviour or high business impact is involved.

### Real-World SOC Scenario
EDR reports ransomware-like encryption behaviour on one employee workstation while identity/SIEM telemetry shows repeated suspicious sign-ins to a production finance server using a privileged account.

I would quickly determine whether the workstation is still encrypting or reaching shares and whether the privileged sign-ins succeeded. If endpoint isolation is authorised and the ransomware is active, containment may be urgent. At the same time, a confirmed privileged session on a critical production system could represent greater organisational impact and require immediate elevation to senior incident responders.

The key is not to choose one from the alert labels. I would establish enough evidence to prioritise, initiate only authorised containment, document actions and maintain escalation/handoff for both incidents.

### What I Would Check as a Tier 1 Analyst
- Asset/business criticality and affected users
- Whether malicious activity is active
- Scope: single endpoint/account versus multiple systems
- Successful versus failed authentication
- Privilege level of affected identities
- Evidence of encryption, lateral movement or exfiltration
- Network shares/critical services at risk
- EDR/SIEM confidence and supporting telemetry
- Available authorised containment actions
- Incident severity/escalation matrix and on-call process
- Evidence preservation, timestamps and actions taken
- Recovery/business-continuity implications

### Relevant Tools / Logs
SIEM such as Microsoft Sentinel/Splunk/Wazuh; EDR such as Defender for Endpoint; Windows/Linux and identity logs; firewall/DNS/proxy telemetry; incident/case-management platform; organisational incident-response playbooks; NIST SP 800-61r3.

### Key Interview Takeaway
I prioritise incidents by scope, likely impact, time-critical nature and response constraints, not simply by alert name or arrival order. As Tier 1, I rapidly scope both, contain only within authority, document evidence and escalate critical assets, privileged compromise, destructive activity or expanding incidents early.
