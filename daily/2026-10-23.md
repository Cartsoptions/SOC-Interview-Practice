# SOC Interview Practice — 2026-10-23

**Curriculum:** Questions 153–156 | Password spraying, Microsoft Sentinel identity hunting, Kerberoasting, and DCSync incident response

## Question 153

### Interview Question

Your SIEM reports failed authentication attempts against 35 users from one source during a 20-minute period. Only one or two passwords appear to have been tried per account, and one user later signs in successfully. Is this brute force, password spraying or credential stuffing, and how would you triage it?

### Interview-Ready Answer

I would describe the observed pattern as suspected password spraying: one or a small set of passwords is being tried across many accounts. Traditional online password guessing often concentrates many guesses on one account, while credential stuffing uses previously obtained username-password pairs. I would not claim credential stuffing without evidence that distinct stolen credentials were used.

MITRE ATT&CK defines password spraying as T1110.003 and notes that attackers may throttle attempts to reduce account lockouts and detection. In a SOC environment, I would use the pattern as a hypothesis and then validate the source, protocol, targeted identities, failure reasons and any subsequent success.

For Windows evidence, Event ID 4625 records a failed logon on the computer where the attempt was processed. Event ID 4771 records Kerberos pre-authentication failure on a domain controller when the KDC fails to issue a ticket-granting ticket. These events are useful only when the relevant audit policy, log collection and protocol path produce them; absence from one source does not prove the attempt did not occur.

I would investigate whether the source is a corporate VPN/NAT address, identity proxy, vulnerability scanner, stale service or scheduled task before calling it malicious. A successful sign-in after failures raises priority but still requires validation of the exact user, IP, device, application, authentication result, MFA/Conditional Access outcome and follow-on activity.

### Real-World SOC Scenario

The source is an external residential address not used by corporate VPN infrastructure. Thirty-five enabled accounts receive one failed attempt each, followed by a successful Microsoft 365 sign-in to one account. The user denies the activity, and the same session creates a new inbox rule.

- **Observation:** One external source targeted many accounts with a low number of failures per identity, followed by a success and an unauthorised mailbox change.
- **Hypothesis:** A password spray obtained one valid password and the attacker used the account.
- **Confirmed evidence:** The distributed failure pattern, successful sign-in, user denial and unauthorised inbox-rule creation confirm account compromise. The exact password used, credential source and actor identity remain unconfirmed.

The verdict is **true positive — confirmed account compromise following a password-spray pattern; immediate identity containment and broader scoping are required**.

### What I Would Check as a Tier 1 Analyst

1. Confirm time zone, source address, targeted identities, applications, protocols, result codes and collection coverage.
2. Establish whether the source belongs to VPN, NAT, proxy, scanner, identity provider or another approved service.
3. Compare the number of targeted users, attempts per user, intervals and failure reasons with the normal baseline.
4. Identify successful sign-ins from the source or targeted users before, during and after the failure window.
5. Review MFA, Conditional Access, device, client, location and session/token evidence for any success.
6. Check mailbox, OAuth, authentication-method, role, endpoint and data-access activity after the sign-in.
7. Invoke or request approved session revocation, credential reset, account restriction and malicious-rule removal for compromised identities.
8. Search for the same source, user-agent, targeted-user list and timing pattern across Entra, VPN, AD and application logs.
9. Escalate with confirmed impact, containment status, affected accounts and unresolved initial-access questions.

### Relevant Tools / Logs

Microsoft Entra sign-in and audit logs, Microsoft Sentinel or Splunk, Windows Security Events 4625 and 4771 where applicable, Defender for Identity, VPN/AD FS/RADIUS/application logs, Defender for Office 365, Wazuh-collected Windows event channels where deployed, and case-management records.

### Key Interview Takeaway

Password spraying is a many-accounts, few-passwords pattern. I would validate source and protocol context, search for a successful sign-in and post-authentication activity, and contain only the identities shown to be at risk.

## Question 154

### Interview Question

How would you use Microsoft Sentinel to find a possible Entra ID password spray and then determine whether any targeted account signed in successfully? What does the query prove?

### Interview-Ready Answer

I would run a bounded query against `SigninLogs` in the Sentinel workspace that receives Microsoft Entra sign-in data. The following query identifies IP addresses with failures across several distinct users, then returns all sign-in records from those candidate addresses for analyst review:

```kusto
let lookback = 24h;
let candidateIPs =
    SigninLogs
    | where TimeGenerated >= ago(lookback)
    | where tostring(ResultType) != "0"
    | summarize
        FailedAttempts = count(),
        TargetedUsers = dcount(UserPrincipalName)
      by IPAddress, TimeBin = bin(TimeGenerated, 10m)
    | where FailedAttempts >= 10 and TargetedUsers >= 5
    | distinct IPAddress;
SigninLogs
| where TimeGenerated >= ago(lookback)
| where IPAddress in (candidateIPs)
| project TimeGenerated,
          UserPrincipalName,
          IPAddress,
          AppDisplayName,
          ResultType,
          ResultDescription,
          ConditionalAccessStatus,
          AuthenticationRequirement,
          ClientAppUsed,
          UserAgent,
          Location,
          CorrelationId
| order by IPAddress asc, TimeGenerated asc
```

Microsoft documents these columns in the `SigninLogs` schema. The numeric value zero represents success in Microsoft sign-in log query examples; `tostring()` makes the comparison explicit because `ResultType` is documented as a string in the table reference.

The thresholds are starting points, not universal truth. NAT, VPN concentrators and identity proxies can make many legitimate users share one source address. Attackers can also distribute or slow attempts below thresholds. I would tune against the organisation's authentication architecture and baseline rather than treating the query as a final detector.

The output proves which Entra sign-in records exist for candidate addresses within the selected period. It does not prove that every failure used the same password, that a success belongs to the same attacker, or that the account was compromised. I would correlate device, authentication, user confirmation, audit and post-sign-in evidence.

### Real-World SOC Scenario

The query returns 42 failed sign-ins across 18 users from one external IP. It also shows one successful sign-in to `payroll.user@example.com`. The success used an unfamiliar client and was followed by a new authentication-method registration.

- **Observation:** One source produced a distributed failure pattern and a later success involving one targeted account.
- **Hypothesis:** A password spray succeeded and the attacker attempted to strengthen persistence by adding an authentication method.
- **Confirmed evidence:** The sign-in and authentication-method change are recorded. User denial and audit evidence confirm that the change was unauthorised; reuse of a particular password remains unproven.

The verdict is **true positive — confirmed identity compromise associated with a password-spray pattern**.

### What I Would Check as a Tier 1 Analyst

1. Verify the workspace contains complete and current `SigninLogs` data for the relevant tenant and sign-in types.
2. Review candidate IP ownership, VPN/NAT/proxy context and threat-intelligence enrichment.
3. Inspect failures by account, application, client, interval and `ResultDescription` rather than counting alone.
4. Review every success from the candidate source and every success for targeted users from other sources.
5. Examine Conditional Access, MFA, authentication details, device and session context in the portal.
6. Correlate Entra audit events, mailbox actions, OAuth consent, endpoint telemetry and data access.
7. Confirm user activity through the approved process and record confidence separately from assumptions.
8. Invoke or request authorised identity containment, then verify session revocation and account recovery.
9. Convert the investigation logic into a tuned analytic rule only after baselining and false-positive review.

### Relevant Tools / Logs

Microsoft Sentinel Logs, `SigninLogs`, Entra sign-in and audit portals, Microsoft Defender XDR, Defender for Office 365, VPN/proxy telemetry, Conditional Access information and case management.

### Key Interview Takeaway

KQL narrows the evidence; it does not make the verdict. I would tune the pattern to the environment and prove compromise with successful-authentication and post-sign-in evidence.

## Question 155

### Interview Question

A domain controller records a short burst of Event ID 4769 service-ticket requests from one workstation for many unusual service principal names. Several tickets use RC4 encryption type `0x17`, but no service account has yet been observed logging on elsewhere. Is this Kerberoasting, and how would you investigate it?

### Interview-Ready Answer

Event ID 4769 records a Kerberos service-ticket request on a domain controller. A burst of requests for many service principal names, especially when inconsistent with the user's or device's baseline, is a recognised Kerberoasting indicator. MITRE ATT&CK maps Kerberoasting to T1558.003 and describes adversaries requesting service tickets whose encrypted material can be attacked offline.

I would classify this as suspected Kerberoasting, not confirmed password cracking or account compromise. RC4 encryption type `0x17` can increase concern, but legacy application requirements and account configuration can also produce RC4. Normal Kerberos authentication generates high volumes of 4769 events, so rate, requester, target services, encryption type and historical behaviour must be interpreted together.

I would validate that the requester and source device are expected, identify the requested service accounts and their privileges, and review whether an approved administration, inventory or security tool explains the activity. I would correlate endpoint process evidence for ticket-requesting tools or scripts, directory reconnaissance, suspicious PowerShell and follow-on authentication by the targeted service accounts.

If ticket requests are confirmed unauthorised, I would contain the source under the playbook and escalate. Password cracking happens offline and may leave no direct domain log, so lack of a subsequent logon does not make the activity benign. Identity administrators—not Tier 1—should evaluate service-account password rotation, group-managed service accounts, privilege reduction and removal of unnecessary RC4 support.

### Real-World SOC Scenario

The source is a standard user laptop. EDR shows an unsigned utility enumerating service principal names and requesting tickets. The user denies running it, and the account has no administrative role that explains the requests. No successful use of a targeted service account is yet visible.

- **Observation:** A non-administrative workstation generated anomalous 4769 requests for many SPNs, with correlated unauthorised process activity.
- **Hypothesis:** The attacker collected Kerberos service tickets for offline password cracking.
- **Confirmed evidence:** Unauthorised SPN enumeration and service-ticket collection are confirmed. Successful offline cracking and service-account compromise remain unconfirmed.

The verdict is **true positive — confirmed unauthorised Kerberos ticket collection consistent with Kerberoasting; credential compromise is suspected but not yet proven**.

### What I Would Check as a Tier 1 Analyst

1. Confirm the 4769 events came from domain-controller Security logs and preserve their raw XML/version.
2. Validate requesting user, client address/device, service names, encryption types, status codes and timestamps.
3. Compare request volume and service targets with the user's, device's and environment's baseline.
4. Identify the service-account owners, privileges, supported encryption types and business criticality.
5. Review endpoint process, command-line, script, file and network telemetry on the requesting workstation.
6. Check for preceding LDAP/SPN reconnaissance and later logons or service access by targeted accounts.
7. Search other devices for the same requester, process, command fragments and ticket-request pattern.
8. Invoke or request authorised device and identity containment when unauthorised activity is corroborated.
9. Escalate to Tier 2/identity engineering with affected accounts, exposure, containment and credential-rotation decisions.

### Relevant Tools / Logs

Domain-controller Windows Security Event 4769, Defender for Identity, Microsoft Defender for Endpoint/XDR, Sentinel or Splunk, Wazuh where configured to collect the Security channel, Active Directory account/SPN information, change records and privileged-access inventory.

### Key Interview Takeaway

Anomalous 4769 activity can confirm unauthorised ticket collection, but it cannot prove that an offline crack succeeded. I would investigate requester behaviour and protect high-value service accounts before waiting for misuse.

## Question 156

### Interview Question

Microsoft Defender for Identity raises a DCSync alert showing that a help-desk account on a user workstation requested directory replication from a domain controller. The workstation is not a domain controller or approved identity-sync server. How would you validate, contain and escalate this incident?

### Interview-Ready Answer

I would treat this as a critical suspected credential-access incident. DCSync abuses directory replication operations so an account with sufficient rights can request credential material as though it were a domain controller. MITRE ATT&CK maps it to T1003.006.

The alert alone is not the final verdict. Microsoft notes that Defender for Identity uses identity, device and network-resolution context, and that source attribution must be validated—for example, activity genuinely originating from a domain controller may be expected. I would verify the source IP-to-device mapping at the event time, the requesting identity, the destination domain controller, replication evidence and whether an approved backup, sync, migration or security product explains it.

If a non-DC workstation and unauthorised help-desk identity are corroborated, I would invoke the highest-priority identity/AD incident playbook. Within authority, I would isolate the source endpoint or urgently request isolation, revoke sessions and restrict the affected account, preserve endpoint and identity evidence, and notify Tier 2/IR and the identity team. I would not run destructive cleanup or independently reset domain-wide secrets.

Scoping must assume potentially severe credential exposure while keeping the exact data obtained as an evidence question. I would identify when and how replication rights were granted, which accounts or directory partitions were requested, whether privileged credentials were subsequently used, and whether other endpoints performed similar operations.

Recovery may require credential rotation, privilege removal, trusted rebuilding and domain-wide identity recovery decisions. Rotation of highly sensitive domain credentials, including any KRBTGT recovery procedure, must be planned and executed by authorised AD/IR specialists because sequencing and operational impact matter.

### Real-World SOC Scenario

Network attribution confirms the request originated from the user workstation. Endpoint telemetry shows a credential-dumping tool shortly before the replication request, and directory audit evidence shows the help-desk account received replication rights through an unauthorised access-control change.

- **Observation:** A non-DC endpoint used a help-desk identity to initiate directory replication after an unauthorised privilege change.
- **Hypothesis:** The attacker escalated privileges and used DCSync to obtain domain credential material.
- **Confirmed evidence:** Unauthorised replication rights, tool execution and replication activity are confirmed. The precise credential objects returned, downstream use and original access method require further evidence.

The verdict is **critical true positive — confirmed unauthorised directory replication consistent with DCSync and potential domain-wide credential exposure**.

### What I Would Check as a Tier 1 Analyst

1. Validate alert time, source IP/device resolution, account, destination DC and Defender for Identity sensor health.
2. Confirm the source is not a DC, Entra Connect server, approved backup/sync platform or authorised security tool.
3. Preserve the alert evidence, raw identity/network records, endpoint timeline and relevant directory audit data.
4. Determine how replication rights were obtained and review group, ACL, role and account changes.
5. Examine the workstation for credential theft, privilege escalation, remote access, persistence and lateral movement.
6. Hunt for additional replication operations, affected accounts and use of privileged credentials across the estate.
7. Invoke or request endpoint isolation, session revocation and identity restriction under the critical-incident playbook.
8. Escalate immediately to IR and identity specialists with confirmed evidence, potential domain impact and urgent recovery decisions.
9. Track specialist-led credential rotation, privilege removal, trusted rebuilds and enhanced monitoring through validated recovery.
10. Do not attribute the actor or claim every domain credential was stolen without evidence of the returned data and subsequent use.

### Relevant Tools / Logs

Microsoft Defender for Identity and Defender XDR incident evidence, Defender for Endpoint device timeline, domain-controller and directory-service audit logs, Sentinel or Splunk, firewall/network telemetry, identity and privileged-access records, Active Directory change history and incident case management.

### Key Interview Takeaway

A DCSync alert from a confirmed non-DC source is potentially domain-wide. I would validate attribution quickly, contain the endpoint and identity within authority, preserve evidence and escalate recovery decisions to AD and IR specialists.

## Verification Notes

- MITRE ATT&CK T1110.003 defines password spraying as using one or a small set of passwords against many accounts, often throttled to reduce lockouts and detection.
- Microsoft documents Event 4625 as a failed logon event generated on the computer where the logon attempt was processed. Event 4771 records Kerberos pre-authentication failure on domain controllers when the KDC fails to issue a TGT.
- Microsoft documents `SigninLogs` fields used in Question 154, including `TimeGenerated`, `UserPrincipalName`, `IPAddress`, `AppDisplayName`, `ResultType`, `ResultDescription`, `ConditionalAccessStatus`, `AuthenticationRequirement`, `ClientAppUsed`, `UserAgent`, `Location` and `CorrelationId`.
- Microsoft Sentinel examples compare `ResultType` with zero for successful sign-ins. The query uses `tostring(ResultType)` because the table reference documents the field type as string.
- Detection thresholds in Question 154 are illustrative analyst starting points. They require baselining for VPN, NAT and identity-proxy architecture and should not be presented as Microsoft defaults.
- Event 4769 records Kerberos service-ticket requests on domain controllers. Kerberos service-ticket auditing can be very high volume. MITRE's Kerberoasting detection guidance highlights anomalous ticket volume, unusual service targets and RC4 encryption type `0x17` as signals that require context.
- MITRE ATT&CK T1558.003 describes Kerberoasting as requesting Kerberos service tickets for offline attacks against service-account secrets. Ticket collection does not by itself prove successful cracking.
- MITRE ATT&CK T1003.006 describes DCSync as abuse of directory-replication operations to obtain credential material. Defender for Identity documents DCSync alerts and source attribution context; analysts must verify that the activity did not originate from an authorised DC or synchronisation function.
- Wazuh documents that its Windows agent can collect Windows event channels and that System, Application and Security are monitored by default. Actual visibility still depends on Windows audit policy, Wazuh configuration and ingestion health.
- All users, addresses, devices, account names, thresholds and timestamps in these scenarios are simulated.
