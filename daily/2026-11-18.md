# SOC Interview Practice — 2026-11-18

**Curriculum:** Questions 225–228 | WAF and SQL-injection triage, authenticated BEC investigation, Microsoft Sentinel password-spray hunting, and Linux/Wazuh valid-account compromise

## Question 225

### Interview Question

An Azure Web Application Firewall alert shows repeated SQL-injection rule matches against a public customer portal. Most requests were blocked, but several related requests were logged as matched rather than blocked and the application returned HTTP 200 responses. What does a WAF provide in this situation, and how would you decide whether this is only scanning, a false positive, or a successful attack?

### Interview-Ready Answer

A web application firewall inspects HTTP and HTTPS requests against rules designed to identify and, depending on policy mode and rule action, block suspicious application-layer traffic. In a SOC environment, I would use the WAF as both a preventive control and an evidence source, but I would not treat a signature match, an HTTP 200 response or an attacker-looking payload as proof of exploitation.

Microsoft documents that Azure WAF logs requests that match rules and that a request may or may not be blocked depending on the policy and other rule processing. A block action prevents the request from reaching the origin; a log or match action records the event while processing can continue. I would therefore confirm the policy mode, final action and transaction or tracking identifier for each request before judging exposure.

I would correlate WAF events with reverse-proxy, web-server, application and database logs using time, source IP, URI, request method and a safe representation of the triggering parameter. I would check whether the endpoint should accept that parameter, whether the application produced errors, unusual response sizes or timing, and whether the database recorded unexpected queries, access or exports. An HTTP 200 response only means that the web tier returned a successful HTTP status; it does not prove that injected SQL executed.

OWASP recommends parameterized queries and least-privileged database accounts as primary SQL-injection defenses. A WAF can reduce exposure and buy time, but the application team must correct unsafe query construction rather than rely on signatures alone. I would not create a broad WAF exclusion or disable a rule as Tier 1. If legitimate traffic is affected, I would document a narrow candidate exclusion for the WAF/application owners to test and approve.

### Real-World SOC Scenario

The same source tests several common payloads. WAF logs confirm that most requests were blocked. Three requests reached an application endpoint in detection mode and returned HTTP 200, but application logs show normal validation failures, database logs show no unexpected statement or data access, and the response sizes match normal error pages.

- **Observation:** Repeated SQL-injection signatures targeted a public endpoint; some requests were logged but not blocked.
- **Hypothesis:** The actor attempted SQL injection, or legitimate input triggered the rule.
- **Confirmed Evidence:** WAF and origin logs confirm malicious-looking requests reached the endpoint, but application and database evidence show no successful injection or data access.

The verdict is **confirmed attempted SQL injection with no evidence of successful exploitation; the detection-mode exposure and application control still require remediation review**.

### What I Would Check as a Tier 1 Analyst

1. WAF policy mode, rule ID, final action and transaction identifier.
2. Source IP, user agent, request method, host, URI and timestamp.
3. Whether the request reached the origin server.
4. Web-server and application response status, size, timing and error evidence.
5. Database errors, unusual statements, new sessions, exports or privilege changes.
6. Repeated activity across other endpoints or applications.
7. Threat-intelligence context without treating reputation as proof.
8. Application owner, exposed data and business criticality.
9. Secure-code controls such as parameterized queries and database least privilege.
10. Escalation if exploitation, data access or persistent access is confirmed.

### Relevant Tools / Logs

Azure WAF or another authorised WAF; Microsoft Sentinel or Splunk; reverse-proxy and load-balancer logs; web-server access/error logs; application and database audit logs; EDR; firewall, DNS and identity telemetry; application inventory and change records.

### Key Interview Takeaway

A WAF match is evidence of a suspicious request, not proof of compromise. I confirm whether it was blocked, correlate it with origin and database evidence, and escalate successful exploitation while leaving rule changes and code remediation to authorised owners.

## Question 226

### Interview Question

A finance user receives a payment-change request from a long-standing supplier. SPF, DKIM and DMARC all pass, the display name and domain are correct, and there is no malicious attachment. The writing style and new bank details are unusual. How would you investigate possible business email compromise using Microsoft Defender for Office 365 or equivalent email-security evidence?

### Interview-Ready Answer

Passing SPF, DKIM and DMARC shows that the message was authorised and aligned for the sending domain; it does not prove that the human sender or mailbox is trustworthy. A threat actor who controls a genuine supplier mailbox can send fully authenticated email. BEC may also contain no malicious URL or attachment, so the investigation must combine technical evidence, business context and an independent verification process.

I would preserve the message and examine the envelope sender, header From, Reply-To, return path, Message-ID, authentication results, sending infrastructure, timestamps and conversation history. I would use message trace and, where licensed, Defender for Office 365 Threat Explorer to see delivery action, related messages, campaign or cluster evidence, recipients and URL-click data. Defender documents that Threat Explorer can investigate email, phishing campaigns and supported URL clicks; exact visibility depends on licensing and retention.

I would determine whether other employees received the same change request and whether anyone replied, clicked, disclosed information or initiated payment. I would compare the request with previous supplier communications, but I would not reply to the suspicious thread or use contact details contained in it. Finance or the supplier owner should verify the change through an independently known telephone number or approved vendor-verification process.

If our own Microsoft 365 account might be compromised, I would correlate Entra sign-ins and risk information with Microsoft Purview or Exchange audit evidence. I would look for new or modified inbox rules, external forwarding, sent or deleted messages, delegate changes, unusual mailbox access and suspicious application consent. Microsoft documents `New-InboxRule`, `Set-InboxRule` and `Remove-InboxRule` as auditable rule operations and recommends checking forwarding and mailbox activity when responding to a compromised account.

I would escalate immediately if payment is pending, credentials were entered, sensitive data was disclosed or mailbox compromise is supported. Authorised responders may block or purge related messages, disable or reset an account, revoke sessions, remove malicious rules and coordinate with finance, legal or fraud teams. Tier 1 should preserve evidence and follow the playbook rather than independently change bank details or contact the attacker.

### Real-World SOC Scenario

The email passed authentication because it came from the supplier's genuine Microsoft 365 tenant. The supplier confirms through a known telephone number that the bank change is fraudulent. Message trace shows the same request sent to three employees. Supplier-side investigation later confirms a compromised mailbox and an auto-delete rule hiding replies.

- **Observation:** A genuine supplier mailbox sent an unusual payment-change request with passing email authentication.
- **Hypothesis:** The supplier mailbox or conversation has been compromised for BEC.
- **Confirmed Evidence:** Independent supplier verification rejects the request; message trace confirms wider targeting; mailbox evidence confirms unauthorised access and a malicious rule.

The verdict is **confirmed supplier-mailbox BEC; no internal compromise is assumed until our sign-in, mailbox and user-interaction evidence supports it**.

### What I Would Check as a Tier 1 Analyst

1. Complete headers and alignment of From, Reply-To, return path and Message-ID.
2. SPF, DKIM, DMARC and composite-authentication results.
3. Message trace, delivery action, recipients and related-message evidence.
4. URL, attachment and click evidence where present.
5. Prior supplier conversation and whether the thread was genuinely hijacked.
6. Independent business verification using known contact details.
7. Replies, payments, credential entry or data disclosure by recipients.
8. Entra sign-ins, MFA and risk events for any potentially affected internal user.
9. Inbox rules, forwarding, sent/deleted messages, delegates and mailbox access.
10. Approved containment, fraud escalation and evidence-preservation actions.

### Relevant Tools / Logs

Microsoft Defender for Office 365 Threat Explorer or Real-time detections where licensed; Exchange message trace; Microsoft Purview audit; Entra sign-in and audit logs; Defender XDR/Sentinel; Proofpoint or Abnormal Security evidence where deployed; finance/vendor records; approved WHOIS and reputation services.

### Key Interview Takeaway

Email authentication validates domain use, not the sender's intent or mailbox security. For BEC, I combine headers and message trace with mailbox, identity, user-action and independent business verification before escalating containment and fraud response.

## Question 227

### Interview Question

Microsoft Sentinel receives Microsoft Entra interactive sign-in logs. Write a first-pass KQL hunt for one IP address failing authentication against several users in a short period, then explain how you would decide whether it represents password spraying and whether any account was compromised.

### Interview-Ready Answer

Assuming interactive sign-ins are present in the documented `SigninLogs` table, I would begin with a transparent aggregation whose thresholds are treated as starting points rather than universal truth:

```kusto
let lookback = 1h;
let minimumUsers = 5;
SigninLogs
| where TimeGenerated >= ago(lookback)
| where tostring(ResultType) != "0"
| summarize FailureCount=count(),
            TargetedUsers=dcount(UserPrincipalName),
            Users=make_set(UserPrincipalName, 20),
            Apps=make_set(AppDisplayName, 10)
    by IPAddress, bin(TimeGenerated, 15m)
| where TargetedUsers >= minimumUsers
| order by TargetedUsers desc, FailureCount desc
```

Microsoft documents `IPAddress`, `UserPrincipalName`, `AppDisplayName` and `ResultType` in `SigninLogs`; `ResultType` is a string and `0` represents success. KQL `summarize`, `dcount`, `make_set` and `bin` support this type of aggregation. I would test the query in the actual workspace because connector coverage, duplicate records, table availability and field population vary.

The result identifies IP/time buckets with failures across multiple users. That pattern is consistent with password spraying, which MITRE ATT&CK defines as using one or a small number of passwords against many accounts, but the query does not see the attempted password and does not prove the technique. Corporate proxies, VPN gateways, shared egress, misconfigured applications and security testing can create similar patterns.

I would pivot from each candidate IP into the raw events and examine failure reasons, applications, user agents, client type, location, device details, Conditional Access, authentication requirement, risk information and expected corporate egress. I would search both interactive and relevant non-interactive sign-in telemetry rather than assume one table covers all authentication.

To assess compromise, I would look for subsequent successful sign-ins from the same infrastructure or targeting sequence, then verify MFA outcome, Conditional Access result, unfamiliar device/session evidence, mailbox or cloud activity and the user's confirmation. A successful `ResultType` alone is not proof that an attacker authenticated; it must be placed in session and user context.

### Real-World SOC Scenario

The hunt finds one hosting-provider IP failing against 34 accounts over 15 minutes. Two minutes later the same IP records a successful sign-in for one targeted account, followed by a new inbox rule and access to several email items. The user denies the activity and the address is not an approved VPN or testing source.

- **Observation:** One external IP generated failures across many accounts and then a success for one target.
- **Hypothesis:** A password spray found a valid password and compromised the account.
- **Confirmed Evidence:** The shared source and targeting sequence, successful authentication, unauthorised mailbox rule and email access, and user denial establish account compromise.

The verdict is **confirmed password-spray-related account compromise requiring immediate identity and mailbox response**.

### What I Would Check as a Tier 1 Analyst

1. `SigninLogs` availability, coverage, time range and duplicate-record behaviour.
2. IP address, targeted-user count, application and exact failure reasons.
3. Known VPN, proxy, NAT, penetration-test or corporate egress ranges.
4. Interactive and relevant non-interactive sign-in records.
5. Successful sign-ins after or during the failure sequence.
6. MFA, Conditional Access, risk, device, client and location context.
7. User confirmation and normal working pattern.
8. Mailbox rules, forwarding, email access and cloud audit activity.
9. Other accounts targeted by the same IP or infrastructure.
10. Session revocation, account protection and escalation authority.

### Relevant Tools / Logs

Microsoft Sentinel Logs and incidents; Microsoft Entra `SigninLogs`, relevant non-interactive sign-in tables and audit logs; Defender XDR; Microsoft Purview/Exchange mailbox audit; Conditional Access and Identity Protection evidence where licensed; VPN/proxy inventories; ticketing and user-verification records.

### Key Interview Takeaway

The KQL query finds a many-users-from-one-IP failure pattern; it does not prove a password spray or compromise. I validate shared infrastructure and failure reasons, then require successful authentication plus post-sign-in evidence before declaring account takeover.

## Question 228

### Interview Question

Wazuh reports a successful SSH login to a production Linux server from a new external IP, followed by `sudo` activity and creation of a new local account. The username is valid and no malware alert fired. How would you investigate and escalate the event as a Tier 1 analyst?

### Interview-Ready Answer

I would treat this as a high-priority possible valid-account compromise. A successful SSH login and use of `sudo` can be legitimate administration, but the new source, privileged activity and account creation form a sequence that requires immediate validation. The absence of a malware alert does not reduce the identity and persistence risk because an attacker can use native services and legitimate credentials without deploying malware.

Wazuh can collect operating-system and SSH logs through agents, syslog, monitored files or journald, then decode the records and evaluate them against rules. Its server records generated alerts in `alerts.log` and `alerts.json`. Alert fields and rule IDs depend on the decoder, ruleset, integration and source format, so I would inspect the original event rather than invent or rely on a universal field name.

I would build a timeline from the raw SSH authentication record through the session, `sudo` activity, account creation and any following commands or network connections. I would identify the authentication method, source IP, username, session time, target host and whether a change ticket or approved administrator explains the activity. I would verify the new account, group membership, shell, authorised keys and any changes to `sudoers`, SSH configuration, scheduled jobs, services or startup files through authorised evidence sources.

MITRE ATT&CK maps abuse of legitimate credentials to Valid Accounts, T1078, and malicious use of `sudo` to Sudo and Sudo Caching, T1548.003. Those mappings guide hunting but do not turn ordinary administration into a confirmed incident. I would also search other Linux, VPN, identity, firewall and EDR telemetry for the same account, IP, key fingerprint or sequence.

If the owner cannot validate the session or evidence shows an unauthorised account or key, I would immediately escalate. Within the playbook, authorised responders may restrict the account or key, isolate the host, preserve volatile and disk evidence, rotate exposed credentials and remove persistence after scoping. Tier 1 should not delete the account or reboot a production server without approval because doing so can disrupt service and destroy evidence.

### Real-World SOC Scenario

The system owner confirms that no maintenance was scheduled. Raw SSH evidence shows key-based access from a hosting-provider IP using a dormant administrator account. The session used `sudo`, added a new UID-capable administrative account and installed a new authorised key. Firewall logs show an outbound connection to the same external infrastructure.

- **Observation:** A valid but dormant account authenticated from a new external IP and performed privileged changes.
- **Hypothesis:** Stolen credentials or an SSH key were used to establish privileged persistence.
- **Confirmed Evidence:** Owner denial, dormant-account use, unauthorised account/key creation and related outbound traffic confirm compromise.

The verdict is **confirmed valid-account compromise with privileged persistence; wider key, credential and host impact requires urgent scoping**.

### What I Would Check as a Tier 1 Analyst

1. Raw Wazuh event, decoder/rule context and collection coverage.
2. SSH timestamp, source IP, username, authentication method and session identifier where available.
3. Asset criticality, owner and approved maintenance or change tickets.
4. Account status, last legitimate use and assigned privileges.
5. Exact `sudo` activity and associated command audit evidence where collected.
6. New account, groups, shell, authorised keys and `sudoers` changes.
7. Scheduled jobs, services, startup files and SSH configuration changes.
8. Network connections, file changes, processes and EDR evidence.
9. Same account, IP or key activity across other hosts.
10. Containment authority, evidence preservation and credential/key rotation scope.

### Relevant Tools / Logs

Wazuh alerts and archives where enabled; original Linux authentication logs or journald; SSH, `sudo` and account-management audit evidence; Linux audit framework where deployed; EDR; firewall, proxy, DNS and VPN logs; asset inventory, change records and privileged-access-management records.

### Key Interview Takeaway

Valid credentials and native tools can produce a serious compromise without malware. I reconstruct the raw SSH-to-privilege timeline, validate it with the owner, hunt for persistence and related access, and escalate containment without destroying evidence or disrupting production outside my authority.
