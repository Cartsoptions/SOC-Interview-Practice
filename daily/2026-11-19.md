# SOC Interview Practice — 2026-11-19

**Curriculum:** Questions 229–232 | DNS-tunnelling triage, Windows Active Directory event interpretation, DLP and suspected exfiltration, and compromised third-party VPN access

## Question 229

### Interview Question

A DNS-monitoring alert shows one workstation making thousands of queries to long, apparently random subdomains beneath the same newly observed parent domain. Most responses are `NXDOMAIN`, and the host has little direct web traffic. What does DNS provide in an enterprise environment, and how would you determine whether this is DNS tunnelling, malware using generated domains, or legitimate software?

### Interview-Ready Answer

DNS translates names into records that systems use to locate services. In a SOC environment, DNS telemetry is also a valuable behavioural data source because it shows what domains a host attempted to resolve, when it did so, which resolver handled the request, the query type and the response. It does not normally prove which application initiated the request unless endpoint or enhanced DNS telemetry supplies that context.

The pattern is suspicious but not conclusive. Long unique labels, high query volume, unusual record types, repeated timing and a rare parent domain can be consistent with DNS tunnelling, command and control, or a domain-generation algorithm. Legitimate security products, content-delivery systems, telemetry clients and misconfigured applications can also produce large numbers of unusual or failed queries.

MITRE ATT&CK describes DNS abuse under T1071.004, where adversaries embed command-and-control data within DNS traffic. Its current detection guidance highlights anomalous encoded-looking subdomains and DNS activity initiated by unexpected processes. I would use that mapping to structure the hunt, not as proof that tunnelling occurred.

I would establish a timeline and baseline the host against peers. I would examine query count, distinct subdomains, label length and character patterns, record types, response codes, request timing, parent-domain prevalence and whether other hosts queried the same domain. I would then pivot to EDR, Sysmon or equivalent endpoint telemetry to identify the originating process, command line, file path, signer, parent process and network connections.

If packet capture is available and authorised, Wireshark or another network-analysis tool can help inspect DNS headers, query names, response sizes and timing. I would avoid claiming that encoded-looking text is exfiltrated data unless the traffic can be reliably decoded or correlated with file access, process activity, command execution or verified attacker infrastructure.

Tier 1 may block or sinkhole the domain, isolate the host or request those actions only when the playbook and permissions allow it. I would preserve the queried names and timestamps, but avoid copying sensitive payload content into broadly visible tickets.

### Real-World SOC Scenario

The endpoint is the only corporate host querying the domain. EDR shows an unsigned process in the user's temporary directory issuing the DNS requests every 60 seconds. The subdomain labels change each time, successful TXT responses are followed by local command execution, and the domain is not associated with approved software.

- **Observation:** One host generated high-volume, encoded-looking and periodic DNS queries to a rare domain.
- **Hypothesis:** Malware is using DNS for command and control or data transfer.
- **Confirmed Evidence:** Endpoint process evidence, repeatable DNS timing, TXT responses and follow-on command execution establish malicious DNS-based command and control. The volume alone does not prove that data was exfiltrated.

The verdict is **confirmed DNS-based command and control; data exfiltration remains unconfirmed unless payload or correlated file-transfer evidence establishes it**.

### What I Would Check as a Tier 1 Analyst

1. Source host, user, resolver, timestamps and data coverage.
2. Parent domain, full query names and organisational prevalence.
3. Query volume, distinct-subdomain ratio and timing regularity.
4. Record types, response codes and response sizes.
5. Domain ownership, age and approved-service context where available.
6. Endpoint process, parent process, path, signer and command line.
7. Related file access, scheduled tasks, services or persistence.
8. Other network connections from the same process or host.
9. Packet capture or DNS content where policy and collection allow it.
10. Authorised domain blocking, sinkholing, isolation and wider hunting.

### Relevant Tools / Logs

DNS resolver and protective-DNS logs; Microsoft Sentinel or Splunk; EDR such as Microsoft Defender for Endpoint; Sysmon where configured; firewall, proxy and network-flow telemetry; Wireshark or approved packet-capture tooling; asset inventory and threat-intelligence sources.

### Key Interview Takeaway

DNS anomalies are behavioural leads. I confirm the pattern, identify the process responsible and require correlated endpoint or payload evidence before calling it tunnelling, command and control or exfiltration.

## Question 230

### Interview Question

During an overnight shift, the SIEM shows the following Windows Security events from a domain environment within six minutes:

- Event 4624, Logon Type 10, for an administrator account on a management server.
- Event 4672 with the same Logon ID.
- Event 4720 creating a user named `svc-backup2`.
- Event 4728 adding that new account to the `Domain Admins` group.

How would you interpret this sequence without treating every administrative event as malicious?

### Interview-Ready Answer

I would read the events as a correlated sequence rather than four isolated alerts.

- **4624** records a successful logon on the accessed computer. Logon Type 10 is `RemoteInteractive`, commonly associated with Remote Desktop or Terminal Services.
- **4672** records special privileges assigned to a new logon. Its Logon ID can help correlate it with the related 4624, but privileged administrators can legitimately generate it.
- **4720** records creation of a user object. The Subject fields identify the account that requested creation, while the New Account fields identify the created account.
- **4728** records a member being added to a security-enabled global group. `Domain Admins` is normally a high-impact group, so the target group and added member must be validated.

These events require the relevant advanced audit policies and successful collection from the correct systems. Their presence proves that the recorded actions occurred; it does not establish whether they were authorised.

I would correlate by timestamp, computer, Subject account, Target account, SID and Logon ID where the event provides them. I would verify the administrator's source workstation or IP, the RDP or remote-access path, MFA/VPN evidence if applicable, and whether an approved change or identity-management workflow explains the new service account and membership.

I would then look for what happened after privilege assignment: logons by the new account, Kerberos activity, process creation where audited, remote-service use, access to domain controllers, security-control changes and attempts to clear logs. I would contact the on-call identity or system owner through the approved channel rather than relying on a name such as `svc-backup2`, which an attacker can choose to look legitimate.

If no authorised change exists, this is a critical escalation because the sequence creates a new highly privileged identity. Tier 1 should preserve the event XML and timeline and follow the playbook. Disabling an account or terminating a session must be performed only within delegated authority and with the incident lead aware of service-impact and evidence considerations.

### Real-World SOC Scenario

The administrator is on leave, the source workstation is not an approved management device and no change ticket exists. Ten minutes later, `svc-backup2` authenticates to a domain controller and launches a remote process. The identity owner confirms that no backup account was requested.

- **Observation:** Remote administrative access was followed by creation and privileged-group membership of a new account.
- **Hypothesis:** A compromised administrator session created a persistence account.
- **Confirmed Evidence:** The unapproved source, absent change, owner denial, new Domain Admin membership and subsequent use of the account confirm unauthorised privilege establishment.

The verdict is **confirmed Active Directory account compromise with newly created privileged persistence, requiring critical escalation and domain-wide scoping**.

### What I Would Check as a Tier 1 Analyst

1. Original event XML and whether expected audit policies were enabled.
2. Event time, computer, Subject, Target, SIDs and Logon IDs.
3. 4624 source address/workstation and Logon Type.
4. Correlation between 4624 and 4672 on the same computer.
5. 4720 creator and complete new-account attributes.
6. 4728 group name, member SID and requesting Subject.
7. Approved change, provisioning workflow and account owner.
8. Subsequent logons, process activity and remote administration.
9. Other privilege, policy, security-tool or log-clearing changes.
10. Containment authority, service dependencies and escalation scope.

### Relevant Tools / Logs

Windows Security logs from domain controllers, management servers and targets; Microsoft Sentinel or Splunk; EDR; VPN/RDP gateway logs; Active Directory change and identity-governance records; privileged-access-management evidence; ticketing and change-management systems.

### Key Interview Takeaway

Event IDs tell me what Windows recorded, not whether the activity was approved. I correlate the logon, privilege, account-creation and group-membership events, validate the administrator and change context, then escalate based on confirmed unauthorised use.

## Question 231

### Interview Question

Microsoft Purview DLP alerts that an employee copied a confidential customer-data file to a USB device and later attempted to upload a similarly named file to a personal cloud-storage domain. The user says it was needed for approved work from home. How would you determine whether this is policy-compliant activity, accidental exposure or intentional exfiltration?

### Interview-Ready Answer

DLP identifies data and user activities that match configured policies. It can audit, warn, block with override or block certain endpoint activities depending on policy and configuration. A DLP alert proves that the configured rule conditions were met; it does not by itself prove malicious intent or even that the transfer completed.

Microsoft documents Endpoint DLP coverage for attempts to copy protected files to removable USB devices and upload protected items to restricted cloud-service domains. The alert and activity details must be checked to determine the policy mode, action, override, device and file activity. Licensing, endpoint onboarding, browser support, policy scope and evidence-collection settings affect what is visible.

I would validate the alert rule, sensitivity label or sensitive-information match, file identity, user, device, destination, timestamps, policy action and whether the operation was blocked, overridden or completed. I would not open or distribute sensitive file content unless my role and the investigation process permit it. If evidence collection was configured, access to captured content should follow least privilege and the organisation's privacy and legal rules.

I would correlate DLP with endpoint file events, USB device information, browser or proxy activity, cloud-app logs, email, recent bulk file access and the user's normal pattern. I would check whether the employee had an approved business need, authorised removable media, an approved cloud destination and a current exception. A verbal claim is context, not confirmation; the manager, data owner or documented approval process should verify it.

MITRE ATT&CK maps exfiltration through USB to T1052.001 and transfer to external cloud storage to T1567.002. These mappings describe possible techniques, while intent and completion still require evidence.

If the first copy was blocked and no data left the endpoint, the event may be a prevented policy violation rather than a breach. If a protected file was copied to unauthorised media or uploaded successfully, I would escalate according to data classification, volume, recipients, regulatory impact and evidence of intent. Tier 1 should preserve evidence and coordinate with data protection, HR, legal or insider-risk teams rather than confront the user or seize equipment independently.

### Real-World SOC Scenario

The USB copy was allowed because the policy was in audit-only mode. Endpoint evidence confirms 4,800 customer records were copied. Proxy and browser evidence then confirms a successful upload to a personal cloud account. The manager and data owner deny authorising either destination, and the employee submitted a resignation earlier that day.

- **Observation:** Sensitive data matched DLP rules during USB copying and a personal-cloud upload attempt.
- **Hypothesis:** The user may be moving customer data outside approved controls.
- **Confirmed Evidence:** Completed USB copy, successful cloud upload, unauthorised destinations, data-owner denial and the correlated timeline confirm data exfiltration. Resignation timing increases concern but does not alone prove intent.

The verdict is **confirmed unauthorised data exfiltration requiring immediate escalation to incident response and the organisation's data-protection, legal and insider-risk processes**.

### What I Would Check as a Tier 1 Analyst

1. DLP policy, rule, workload, policy mode and configured action.
2. Whether the activity was audited, warned, overridden, blocked or completed.
3. File name, hash or identifier, classification and sensitive-data match.
4. User, endpoint, time, USB device and cloud destination.
5. File volume and whether other sensitive items were accessed or staged.
6. Endpoint, browser, proxy, cloud-app and email evidence.
7. Approved business need, exception, destination and data-owner confirmation.
8. Similar historical activity and other involved users or devices.
9. Data classification, affected individuals and regulatory implications.
10. Evidence access, privacy limits and escalation to authorised teams.

### Relevant Tools / Logs

Microsoft Purview DLP Alerts and Activity Explorer; Microsoft Defender XDR where DLP integration and licensing permit; Defender for Endpoint; proxy and browser telemetry; cloud-app audit; USB/device-control evidence; file-server and SharePoint/OneDrive audit; Sentinel or Splunk; approved HR, legal and data-owner records.

### Key Interview Takeaway

A DLP alert is a policy match, not a motive verdict. I establish whether sensitive data actually moved, verify authorisation and scope, and escalate confirmed loss through the correct security, privacy and legal channels.

## Question 232

### Interview Question

A third-party support engineer successfully connects through the corporate VPN using a valid account and MFA. Minutes later, IDS and firewall telemetry show the VPN-assigned address scanning internal servers and making RDP and SMB connections outside the vendor's approved support scope. How would you triage, contain and hand over this incident?

### Interview-Ready Answer

A VPN creates an encrypted remote-access path and usually authenticates the user or device. It does not prove that the account, session or connecting endpoint is trustworthy. A stolen session, compromised vendor device, coerced MFA approval or malicious authorised user can still operate through a valid tunnel.

CISA and international partners warn that compromised devices or accounts using VPN services can expose internal resources, particularly where segmentation and least privilege are weak. I would treat the valid login as one piece of evidence and focus on what the session did after connection.

I would first identify the VPN account, source IP, authentication and MFA details, device or posture information where collected, connection time, assigned internal address and session identifier. I would map that internal address to firewall, IDS, DNS and target-host events so that unrelated activity is not mistakenly attributed to the vendor.

I would compare the destinations, ports and timing with the vendor's approved maintenance window and access scope. I would examine whether the IDS showed discovery only or successful sessions, and correlate target-host Windows logs, EDR process trees and file or service changes. Windows 4624 Logon Type 10 supports evidence of RemoteInteractive/RDP access on a destination; Logon Type 3 represents a network logon and can support SMB analysis. Neither proves malicious intent without source, account and activity context.

Because the session is actively reaching systems outside its scope, I would escalate immediately and request or perform authorised session termination, account restriction or network containment. I would coordinate with the vendor-management and system-owner contacts through trusted channels. Blocking only the public source IP may be insufficient if valid credentials or sessions remain usable.

I would preserve the VPN, MFA, firewall, IDS, endpoint and Windows evidence, scope every target reached, and determine whether files, credentials or configurations changed. NIST SP 800-61 Rev. 3 recommends identifying all affected hosts and services during eradication and restoring operations only after entry points and persistence are addressed. Tier 1 supports containment and scoping; account disablement, credential rotation, forensic acquisition and recovery remain governed by the playbook and incident lead.

### Real-World SOC Scenario

The vendor confirms that no maintenance was scheduled and the named engineer is not working. The VPN session used a previously enrolled MFA method, scanned two server subnets, successfully authenticated by RDP to one management server and created a remote service on a file server. EDR records the same account launching credential-access tooling.

- **Observation:** A valid vendor VPN session accessed internal systems beyond the approved support boundary.
- **Hypothesis:** The vendor account, session or endpoint has been compromised and is being used for discovery and lateral movement.
- **Confirmed Evidence:** Vendor denial, out-of-scope access, successful target authentication, service creation and endpoint process evidence confirm malicious use of the remote-access account.

The verdict is **confirmed third-party remote-access compromise with lateral movement; all reached systems, credentials and vendor trust relationships require urgent scoping**.

### What I Would Check as a Tier 1 Analyst

1. VPN username, public source IP, connection time and assigned internal IP.
2. MFA method, result and any session or token identifiers available.
3. Device posture, certificate or managed-device evidence where collected.
4. Approved maintenance window, vendor contact and access scope.
5. Firewall/IDS destinations, ports, actions and successful sessions.
6. DNS, RDP, SMB and target-host authentication evidence.
7. Windows and EDR process, file, service and credential activity.
8. Other sessions or accounts from the same vendor or infrastructure.
9. Data access, configuration changes and persistence.
10. Authorised session revocation, account restriction, isolation and handover.

### Relevant Tools / Logs

VPN concentrator and MFA/identity logs; firewall, IDS/IPS, DNS and network-flow telemetry; Windows Security logs; EDR/XDR; Microsoft Sentinel or Splunk; privileged-access records; vendor-management, asset, change and incident-management systems.

### Key Interview Takeaway

A valid VPN login with MFA does not make subsequent behaviour safe. I map the VPN session to its internal activity, validate vendor scope, contain the active path within authority and hand over a complete evidence-based timeline.
