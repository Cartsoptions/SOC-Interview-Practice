# SOC Interview Practice — 2026-08-19

## Question 7

### Interview Question

What is a SIEM, and how would you use one during a Tier 1 SOC investigation rather than just saying that it collects logs?

### Interview-Ready Answer

A SIEM, or Security Information and Event Management platform, centralises security-relevant telemetry from multiple sources so analysts can search, correlate, detect, investigate and support response to suspicious activity. The important point in an interview is that a SIEM is not simply a storage location for logs. Its value comes from bringing different evidence sources together so activity can be viewed in context.

In a SOC environment, I would use a SIEM to review an alert, identify the entities involved, search related events across a defined timeframe, correlate evidence from sources such as identity, endpoint, firewall, DNS, email and cloud logs, and decide whether the activity is benign, suspicious or requires escalation. Microsoft describes Sentinel SIEM as supporting data collection, threat detection, investigation, response and proactive hunting across multicloud and multiplatform environments.

As a Tier 1 analyst, I would normally work with existing data connectors, detections, dashboards, queries and playbooks rather than independently redesigning SIEM architecture or changing production detection logic without authorisation. I would also remember that a SIEM alert is a starting point for investigation, not proof that an incident occurred.

### Real-World SOC Scenario

A SIEM generates an alert because one user account has repeated failed authentications followed by a successful sign-in and then access to a sensitive server. I would build a timeline around the account, source IP, destination system and authentication events. I would correlate identity logs with Windows Security events, VPN or firewall telemetry, EDR activity and any relevant DNS/proxy data. If the successful sign-in came from expected infrastructure and the activity matches the user's normal work, it may be benign. If the source, timing, endpoint and subsequent activity are abnormal, I would document the evidence and escalate according to the incident playbook.

### What I Would Check as a Tier 1 Analyst

- What detection rule or condition generated the alert
- Alert time range, severity and affected entities
- User, host, IP address, process, domain/URL and other indicators involved
- Raw events that support the detection rather than relying only on the alert title
- Related identity, Windows/Linux, endpoint, firewall, DNS, proxy, email or cloud telemetry
- Whether similar activity exists on other users or systems
- Whether the activity fits an approved administrative or business process
- What is observed, what is only a hypothesis, and what evidence would confirm or disprove it
- Escalation criteria and documentation required by the playbook

### Tools / Logs

Microsoft Sentinel, Splunk, Wazuh or other SIEM platforms; Microsoft Entra sign-in logs; Windows Security logs; Linux authentication logs; EDR telemetry; firewall, DNS and proxy logs; email-security telemetry; threat-intelligence sources; ticketing/incident-management systems.

### Interview Takeaway

A SIEM centralises and correlates security telemetry so analysts can detect and investigate suspicious activity. In a Tier 1 role, I would use it to validate the alert against the underlying evidence, build context across multiple log sources, document what I found and escalate when the evidence meets the organisation's criteria.

## Question 8

### Interview Question

You receive an alert for multiple Windows failed logons. What does Windows Security Event ID 4625 mean, and how would you investigate it without assuming it is a brute-force attack?

### Interview-Ready Answer

Windows Security Event ID 4625 means that an account failed to log on. Microsoft states that the event is generated on the computer where the logon attempt was made and can occur on domain controllers, member servers and workstations. The event contains useful investigation fields such as the account involved, Logon Type, source/network information where applicable, Process Name where available, and Status/Sub Status values that can help explain why authentication failed.

I would not label a single 4625 event as brute force. Failed logons happen for many legitimate reasons, including mistyped passwords, stale credentials, service-account issues, mapped drives, scheduled tasks or application behaviour. Microsoft even documents scenarios where remote WMI activity can create a failed 4625 event as part of normal authentication behaviour. The SOC task is therefore to look for a pattern and context.

For repeated failures, I would examine how many attempts occurred, whether they target one account or many accounts, whether they come from one source or many sources, which Logon Type is present, the failure reason/status, and whether a successful authentication follows. MITRE ATT&CK maps brute-force activity to T1110 and distinguishes password guessing, password spraying and credential stuffing. Those patterns are different: for example, many passwords against one account is not the same pattern as one or a small number of passwords attempted across many accounts.

### Real-World SOC Scenario

A SIEM alert shows 80 Event ID 4625 failures within ten minutes from the same source system. I would first check whether the failures target one account, several accounts or a large user population. I would review Logon Type, source address/workstation information, failure status, destination host and timing. If the events target many accounts with a similar pattern, I would consider password spraying as a hypothesis. If they target one service account after a password change and originate from a known application server, I would investigate a stale service credential instead. If failures are followed by a 4624 successful logon for the same account/source, I would raise the priority and correlate the subsequent activity before concluding compromise.

### What I Would Check as a Tier 1 Analyst

- Event ID 4625 count and timeframe
- Target account(s) and whether privileged/service accounts are involved
- Source IP/workstation and destination host where available
- Logon Type and whether it makes sense for the account and system
- Status/Sub Status or failure reason
- Process Name where present and whether it is expected
- One account with many attempts versus many accounts with a small number of attempts
- Related successful logons such as Event ID 4624 and their timing/context
- Account lockout events or identity-provider signals where relevant
- VPN, RDP, firewall, EDR and Entra/Active Directory evidence that helps explain the activity
- Known maintenance, password changes, scheduled tasks or application/service behaviour

### Tools / Logs

Windows Security Event Log; SIEM such as Wazuh, Splunk or Microsoft Sentinel; Active Directory/domain-controller logs; Microsoft Entra sign-in logs where applicable; VPN/RDP logs; firewall logs; EDR; ticketing and change-management records.

### Interview Takeaway

Event ID 4625 tells me a Windows logon failed; it does not tell me by itself that an attack occurred. I would investigate the pattern, account, source, Logon Type, failure reason and related successful activity, then correlate other telemetry before deciding whether it is user error, an operational issue or a credential attack.

## Question 9

### Interview Question

What is EDR, and how would you investigate an EDR alert for suspicious PowerShell activity on a workstation?

### Interview-Ready Answer

EDR, or Endpoint Detection and Response, provides security teams with endpoint telemetry and detection capabilities so they can investigate suspicious behaviour and take authorised response actions. Microsoft describes Defender for Endpoint EDR as providing near-real-time actionable detections, visibility into the scope of a breach and response capabilities. Its telemetry can include process activity, network activity, user logons, registry changes and file-system activity.

In a SOC environment, I would use EDR to understand what actually happened on the endpoint. For a suspicious PowerShell alert, I would not treat the existence of PowerShell as malicious by itself because PowerShell is a legitimate administrative and automation tool. MITRE ATT&CK maps abuse of PowerShell to T1059.001, so the question is whether the observed execution context is consistent with expected administration or with malicious behaviour.

I would review the device timeline and process tree to identify the parent process, PowerShell command or command-line context where available, user, execution time, child processes, file changes and network connections. Microsoft Defender for Endpoint's device timeline is specifically designed to provide a chronological view of device events and supports process-tree investigation. I would then correlate the endpoint evidence with SIEM, identity, DNS/proxy and threat-intelligence data.

As a Tier 1 analyst, I would follow the incident playbook for escalation and containment. Actions such as isolating a device, quarantining a file or collecting additional evidence may be available in the EDR platform, but I would only perform them if my role and procedure authorise me to do so.

### Real-World SOC Scenario

EDR alerts on PowerShell launched on a finance user's workstation. I would open the process tree and discover whether PowerShell was started by a normal management tool, by the user, by Office, by a script host or by another unusual parent process. I would examine the command context, any child process created, files written and network destinations contacted. If PowerShell was launched by a trusted management platform during an approved change window and the command matches an administrative script, that supports a benign explanation. If it was spawned from a suspicious document process, contacted an unfamiliar external domain and created additional executable content, I would document the chain, correlate the destination and related events, and escalate urgently.

### What I Would Check as a Tier 1 Analyst

- Alert title, severity and detection evidence
- Affected device and user
- Parent process, PowerShell process and child-process relationships
- Command-line or script context where available
- File creation/modification and registry activity associated with the timeline
- Network connections, DNS lookups and external destinations
- Whether the activity matches an approved admin tool, software deployment or change window
- Digital signature/hash/reputation of relevant files where appropriate
- Related alerts on the same device, user or destination
- Similar activity on other endpoints
- Whether containment is authorised and what evidence must be preserved before response

### Tools / Logs

Microsoft Defender for Endpoint or another EDR; device timeline and process tree; Microsoft Sentinel/Splunk/Wazuh; Windows event logs and PowerShell logging where configured; DNS/proxy/firewall telemetry; identity logs; threat intelligence; VirusTotal or other approved reputation services where organisational policy permits.

### Interview Takeaway

EDR gives me endpoint-level visibility to investigate behaviour and support response. For a PowerShell alert, I would focus on execution context, parent/child processes, command activity, files, network connections and related telemetry. PowerShell itself is not proof of maliciousness; the surrounding evidence determines whether the activity is expected or suspicious.
