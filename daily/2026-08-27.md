# SOC Interview Practice — 2026-08-27

## Question 25

### Interview Question

What is cyber threat intelligence, and how would you use an IP address, domain, URL or file hash from a threat-intelligence source during a Tier 1 SOC investigation without treating the indicator as automatic proof of compromise?

### Interview-Ready Answer

Cyber threat intelligence (CTI) is information that provides context about existing or potential cyber threats. It can include reports about threat actors and their tactics, techniques and procedures, as well as tactical indicators such as malicious or suspicious IP addresses, domains, URLs and file hashes. Microsoft Sentinel describes threat intelligence as context that helps security personnel understand unusual activity and notes that indicators can be matched against events in connected data sources to generate detections.

In a SOC environment, I would use threat intelligence to **enrich and prioritise evidence**, not to replace investigation. If an alert contains an IP address or hash that matches a threat-intelligence indicator, the match is an observation. My next step is to validate the indicator's context: source, confidence where available, first/last-seen or validity information, whether it is still relevant, and what activity occurred in our environment.

I would then correlate the indicator with internal telemetry. For an IP address, I would ask which host communicated with it, which process initiated the connection, whether the connection succeeded, how often it occurred and what happened immediately before and after. For a file hash, I would check path, signature, prevalence, process tree and resulting behaviour. A threat-intelligence match increases concern, but it does not by itself prove that the host was compromised because infrastructure can be reassigned, indicators can become stale, shared services can host both benign and malicious content, and context can differ.

As a Tier 1 analyst, I would document the enrichment and evidence, search for the indicator across the environment where appropriate, and escalate based on the combined behaviour and the organisation's playbook. Creating or changing enterprise threat-intelligence feeds, blocking indicators globally or tuning analytics would normally require the relevant authority or senior/security-engineering workflow.

### Real-World SOC Scenario

EDR reports a workstation connecting to an external IP that also appears in the organisation's threat-intelligence data as associated with command-and-control activity. I would not immediately declare the workstation compromised. I would confirm the indicator's validity and source, identify the process responsible for the connection, review DNS/proxy/firewall and EDR telemetry, and determine whether the session was followed by downloads, persistence, credential access or other suspicious behaviour. If multiple endpoints show the same process contacting the same infrastructure and the behaviour aligns with the intelligence context, I would escalate with the correlated evidence and scope the environment for additional matches.

### What I Would Check as a Tier 1 Analyst

- Indicator type: IP, domain, URL, hash or other supported observable
- Intelligence source and reliability/context
- Confidence, validity/expiry and first/last-seen information where available
- Threat or malware association and supporting description
- Whether the indicator is an exact match to the observed artefact
- Internal prevalence: which users, hosts or events contain the indicator
- Process, user and device responsible for the activity
- DNS, proxy, firewall and EDR evidence around the match
- Whether the connection or execution actually succeeded
- File path, signature, hash and process tree for file indicators
- Similar activity on other endpoints/accounts
- Whether the indicator may be stale, reassigned or part of shared infrastructure
- Escalation, containment or blocking authority under the playbook

### Relevant Tools / Logs

Microsoft Sentinel threat intelligence and SIEM telemetry; Microsoft Defender for Endpoint or other EDR; Splunk or Wazuh; DNS, proxy and firewall logs; approved threat-intelligence platforms and reputation services; Microsoft Defender Threat Intelligence where licensed; incident/ticketing records.

### Key Interview Takeaway

Threat intelligence gives me context and indicators that can improve triage and hunting, but an IOC match is not automatic proof of compromise. I would validate the intelligence, correlate it with internal endpoint, identity and network evidence, scope for additional matches and escalate based on the combined behaviour.

## Question 26

### Interview Question

What are HTTP and HTTPS, and how would you use web-proxy or web-security logs to investigate a suspicious download or outbound web connection?

### Interview-Ready Answer

HTTP is a stateless application-level request/response protocol used for interaction with network resources. RFC 9110 defines the shared semantics for HTTP and the `http` and `https` URI schemes. HTTPS uses HTTP semantics over a connection that the client must secure before sending requests for an `https` resource.

In a SOC environment, HTTP/HTTPS knowledge helps me interpret web, proxy and endpoint evidence. Depending on the product and logging configuration, web-proxy or secure-web-gateway telemetry may show the user or device, destination domain or URL, request method, timestamp, response status, bytes transferred, category or reputation and whether access was allowed or blocked. Exact fields vary by platform.

For HTTPS, I would be careful about visibility. Encryption protects the application traffic in transit, so the level of URL, header or content detail visible to a proxy depends on the architecture and whether authorised TLS inspection/decryption is in use. If a proxy only sees a tunnel established with the HTTP `CONNECT` method, I would not assume it can see the full encrypted request path or payload. I would therefore correlate proxy evidence with DNS, firewall and EDR process/network telemetry.

HTTP status codes also need context. A 2xx response indicates that the HTTP request was successfully received/understood/accepted at the protocol level, while 3xx indicates redirection, 4xx a client-side error class and 5xx a server-side error class. A status code does not by itself prove that a downloaded file was malicious or that code executed on the endpoint.

### Real-World SOC Scenario

A user clicks a link in an email and the web-security platform records a request to a newly observed domain followed by a download. I would identify the destination, request/response timing, allow/block action, redirect chain where available and downloaded filename or content metadata if the platform records it. I would then pivot to EDR to confirm which browser or process made the request, whether a file was written to disk, its hash/signature, and whether it executed or spawned child processes. If the proxy shows an allowed request but EDR shows no file creation or execution, I would not claim malware execution without further evidence.

### What I Would Check as a Tier 1 Analyst

- User/device and source IP associated with the web event
- Destination domain, URL or host information available in the platform
- HTTP method such as GET, POST or CONNECT where recorded
- Timestamp and request sequence
- Response-status class and exact status code where logged
- Allow, block, warn or other recorded web-security action
- Redirect chain where available
- Bytes transferred and download/file metadata where available
- TLS inspection/decryption coverage and known visibility limitations
- DNS resolution and firewall connection evidence
- EDR/browser process responsible for the request
- File creation, hash, signature and execution after a download
- Other users/endpoints accessing the same destination
- Reputation/threat-intelligence context and approved-business explanation

### Relevant Tools / Logs

Secure web gateway or proxy logs; Microsoft Sentinel, Splunk or Wazuh; Microsoft Defender for Endpoint or other EDR; DNS and firewall telemetry; email-security evidence; approved threat-intelligence/reputation services; packet capture where authorised and appropriate.

### Key Interview Takeaway

HTTP is an application-level request/response protocol, and HTTPS secures HTTP communication in transit. In a SOC investigation, I would use proxy/web telemetry to understand who accessed what and what the security control recorded, then correlate it with DNS, firewall and endpoint evidence before concluding that a download occurred or malicious code executed.

## Question 27

### Interview Question

What is SMB, and how would you investigate possible lateral movement over SMB or Windows administrative shares as a Tier 1 SOC analyst?

### Interview-Ready Answer

SMB, or Server Message Block, is a network file-sharing protocol used by Windows and Windows Server to access files and other shared resources across a network. Microsoft documents SMB as a client/server protocol in which an SMB client connects to an SMB server that exposes resources such as file shares. Modern direct-hosted SMB commonly uses TCP port **445**.

SMB is heavily used for legitimate administration and business file access, so seeing SMB traffic is not automatically suspicious. In a SOC investigation I would look for context that suggests lateral movement: an unusual source host, a privileged account accessing multiple systems, use of administrative shares, remote file copy, follow-on remote execution, new services or processes, or a pattern that does not match normal administration.

MITRE ATT&CK maps adversarial use of SMB and Windows administrative shares for remote access/lateral movement to **Remote Services: SMB/Windows Admin Shares (T1021.002)**. Windows also provides SMBClient and SMBServer event logs, and additional Windows security/share-access auditing can provide evidence when those audit policies are enabled. I would not assume that one SMB connection proves lateral movement; the hypothesis becomes stronger when SMB access is correlated with authentication and endpoint evidence on the source and destination.

As a Tier 1 analyst, I would validate and scope the activity, document the source, destination, account and shares involved, correlate identity/EDR/network evidence, and escalate according to the playbook. Changing SMB configuration, disabling shares or blocking production systems would generally be an administrator/engineering or authorised incident-response action unless my Tier 1 role explicitly permits it.

### Real-World SOC Scenario

The SIEM shows a workstation making SMB connections to several servers over TCP 445 using a privileged account that is rarely seen from that workstation. Shortly afterward, EDR on one destination records a new executable and a suspicious child process. I would correlate the authentication events, SMB/share-access evidence where available, source and destination EDR timelines and firewall/network logs. If the same account is moving from host to host, copying files and triggering execution on the destinations without an approved administrative reason, I would escalate as suspected lateral movement and help scope all affected systems.

### What I Would Check as a Tier 1 Analyst

- Source and destination hosts/IP addresses
- TCP 445 network activity and timing
- Account used and whether it is privileged
- Whether the source/account normally accesses the destination
- Share names, including administrative shares where logging exposes them
- SMBClient/SMBServer events and share-access auditing where enabled
- Authentication events associated with the connection
- File creation/copy evidence on the destination
- Source and destination EDR process trees
- New services, scheduled tasks or other remote-execution/persistence evidence
- Connections to multiple hosts in a short timeframe
- Firewall/IDS/SIEM evidence and similar activity elsewhere
- Approved software deployment, backup, vulnerability scanning or administrator activity
- Escalation and containment authority

### Relevant Tools / Logs

Windows SMBClient/SMBServer logs; Windows Security/share-access and authentication logs where auditing is enabled; Microsoft Defender for Endpoint or other EDR; Wazuh, Splunk or Microsoft Sentinel; firewall/IDS/network telemetry; Active Directory/identity logs; change-management and software-deployment records.

### Key Interview Takeaway

SMB is a legitimate Windows network file-sharing protocol, commonly using TCP 445. For suspected lateral movement, I would correlate SMB access with the account, source/destination, share activity, authentication and endpoint execution evidence; SMB traffic alone does not prove an attacker moved laterally.

## Verification Notes

- Microsoft Sentinel documentation updated in 2026 describes cyber threat intelligence as information about existing or potential threats and supports indicators such as IP addresses, domains, URLs and file hashes. Sentinel can match imported threat indicators against connected event data to create alerts/incidents.
- Microsoft Sentinel's current threat-intelligence schema uses `ThreatIntelIndicators` and `ThreatIntelObjects`; the legacy `ThreatIntelligenceIndicator` ingestion path ended in 2025. This matters when discussing current Sentinel implementations, although an interview answer should focus on the investigation concept rather than memorising a table name.
- RFC 9110 defines HTTP as a stateless application-level request/response protocol and defines the `http` and `https` URI schemes. For an `https` resource, the client must secure the connection before sending the HTTP request.
- HTTP response-status classes are defined by the first digit: 1xx informational, 2xx successful, 3xx redirection, 4xx client error and 5xx server error. These status codes describe the HTTP response and do not prove malicious execution.
- Microsoft documents SMB as a network file-sharing protocol with client and server roles. Windows records SMB-related events under Applications and Services Logs > Microsoft > Windows > SMBClient and SMBServer.
- Modern direct-hosted SMB uses TCP port 445. Microsoft recommends avoiding SMBv1 on modern networks; current Windows SMB includes signing, encryption and other security features depending on operating-system version and configuration.
- MITRE ATT&CK maps adversarial use of SMB/Windows administrative shares to T1021.002. ATT&CK mapping should follow observed behaviour and does not by itself prove compromise or attribution.
