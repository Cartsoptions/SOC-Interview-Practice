# SOC Interview Practice — 2026-09-07

## Question 46

### Interview Question

What is Zero Trust, and how would you apply Zero Trust principles during a Tier 1 SOC investigation rather than treating Zero Trust as a product?

### Interview-Ready Answer

Zero Trust is a security strategy and architecture that removes implicit trust based only on network location or asset ownership. NIST SP 800-207 explains that Zero Trust focuses on protecting resources and requires authentication and authorization before access is established rather than assuming that something is trustworthy because it is "inside" the network.

Microsoft expresses Zero Trust through three core principles: **verify explicitly**, **use least-privilege access**, and **assume breach**.

In a SOC environment, I would not say "Zero Trust means never trust anyone." I would explain it operationally:

- **Verify explicitly:** evaluate identity, device, location, risk, application and other available signals before granting or continuing access.
- **Use least privilege:** users and workloads should receive only the access they need, for only as long as they need it.
- **Assume breach:** design monitoring and controls as if an attacker may already be present, so we limit blast radius and detect abnormal behavior quickly.

As a Tier 1 analyst, I usually would not design the organisation's Zero Trust architecture. My role is to investigate the evidence produced by its controls. For example, if Conditional Access blocks a sign-in because the device is noncompliant or the session is risky, I would validate the user, device, sign-in source, risk context and post-authentication activity rather than assuming the block alone proves compromise.

### Real-World SOC Scenario

A privileged employee attempts to access a sensitive cloud application from a new unmanaged device.

The access policy blocks the session because the device does not meet compliance requirements.

My observation is that the access request violated policy.

My hypotheses might include:
- legitimate employee using an unmanaged personal device;
- stolen credentials being used from an attacker-controlled endpoint;
- an approved emergency access scenario that was not properly documented.

I would correlate the Entra sign-in, Conditional Access result, MFA evidence, device identity/compliance, source IP, user confirmation and any related Defender XDR or endpoint activity.

If the user denies the attempt and there is additional suspicious identity activity, the compromise hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- User identity and privilege level
- Resource/application being accessed
- Sign-in timestamp and source IP
- Device identity and compliance state where available
- Authentication method and MFA result
- Conditional Access result and relevant policy
- Entra risk detections where available
- Whether the user initiated the access
- Previous and subsequent sign-ins
- Unusual mailbox, file, OAuth or endpoint activity
- Similar access patterns affecting other users
- Whether access was blocked or succeeded
- Tier 1 escalation/containment authority

### Tools / Logs

Microsoft Entra sign-in and audit logs; Conditional Access details; Microsoft Sentinel; Defender XDR; Defender for Endpoint; Defender for Cloud Apps where deployed; Microsoft 365 audit data; firewall/VPN/DNS/proxy telemetry where relevant.

### Interview Takeaway

Zero Trust is a strategy based on explicit verification, least privilege and assuming breach. As a Tier 1 analyst, I would investigate the identity, device, policy and activity evidence produced by those controls rather than treating "inside the network" or a successful authentication as automatic trust.

## Question 47

### Interview Question

What is Microsoft Entra Privileged Identity Management (PIM), and how would you investigate an unusual privileged-role activation as a Tier 1 SOC analyst?

### Interview-Ready Answer

Microsoft Entra Privileged Identity Management, or PIM, is an identity-governance capability for managing, controlling and monitoring privileged access. Microsoft documents PIM as supporting just-in-time and time-bound privileged access, approval requirements, MFA on activation, justification, notifications, access reviews and audit history.

The security value is that a user can remain **eligible** for a privileged role without having that privilege active all the time. When privileged access is needed, the user activates the role for a limited period under the organisation's configured controls.

In a SOC environment, a PIM activation is not automatically suspicious. Administrators legitimately activate roles to perform approved work.

My observation might be:

**A privileged role was activated.**

My hypotheses could include:

- approved administrative work;
- an account that has been compromised and is activating privilege;
- misuse of legitimate administrative access.

I would investigate who activated the role, which role was activated, when, for how long, what justification or ticket information was recorded where configured, whether approval was required, and what the account did after privilege became active.

Microsoft's current PIM audit guidance states that PIM Resource audit logs show role assignment changes, role activations and PIM policy changes. Microsoft also notes that multiple asynchronously processed events can belong to one activation/deactivation cycle, so a single CorrelationId should not always be assumed to represent the entire cycle.

As Tier 1, I would usually investigate and escalate suspicious privileged access. Changing PIM policy, revoking privileged roles or modifying approval settings would normally be an identity/privileged-access administration task unless my playbook explicitly authorises it.

### Real-World SOC Scenario

A normal IT support user activates a Privileged Role Administrator or similarly sensitive role late at night.

The activation is followed by changes to another user's role assignments.

I would first verify whether the user was eligible for that role and whether there was an approved maintenance or emergency-access reason.

Then I would correlate:

**PIM activation → Entra audit activity → privileged changes → sign-in/device context**

If the activation came from an unfamiliar device or location, there is no approved ticket, the user denies initiating it, and privileged changes follow immediately, the compromise or privilege-abuse hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- User/account and normal administrative responsibilities
- Role activated
- Eligibility and activation timestamp
- Activation duration
- Justification and ticket information where configured
- Approval status and approver where applicable
- MFA/Conditional Access context for the activation
- Source IP, device and sign-in activity
- PIM Resource audit history
- Entra audit events after activation
- Role assignments or policy changes performed
- Activity against high-value users/resources
- Other privileged activations by the same user
- Similar activity across privileged identities
- Tier 1 escalation and session/account containment authority

### Tools / Logs

Microsoft Entra PIM Resource audit; Microsoft Entra audit and sign-in logs; Microsoft Sentinel; Defender XDR; Defender for Cloud Apps where deployed; Azure Monitor/Log Analytics where Entra logs are routed; ticketing/change-management records.

### Interview Takeaway

PIM reduces standing privilege by providing controlled, time-bound role activation. A role activation is not automatically malicious, so I would verify who activated the role, why, from where, under what controls and what privileged actions followed, then escalate if the evidence supports account compromise or privilege misuse.

## Question 48

### Interview Question

What is UEBA, and how would you use Microsoft Sentinel User and Entity Behavior Analytics during an investigation without treating every anomaly as malicious?

### Interview-Ready Answer

UEBA stands for User and Entity Behavior Analytics. It uses behavioral baselines and contextual information to help identify activity that is unusual for users, devices, IP addresses, applications or other entities.

Microsoft Sentinel's current UEBA documentation explains that it builds dynamic behavioral profiles and compares current activity with historical, peer-group and organisation-wide behavior. Sentinel can enrich investigations with context such as first-seen activity, unusual volumes, new or uncommon countries or ISPs, and threat-intelligence matches.

A critical SOC point is:

**An anomaly is not the same thing as an incident.**

Unusual activity may be malicious, but it can also result from legitimate role changes, travel, new projects, software deployments or business processes.

I would use UEBA to answer questions such as:

- Is this behavior new for the user?
- Is the volume abnormal?
- Is it unusual compared with the user's peers?
- Did the entity appear from a new country, ISP or device?
- Does the activity correlate with threat intelligence or other alerts?

Microsoft Sentinel stores UEBA investigation data in tables including `BehaviorAnalytics` and `BehaviorInfo`, and identity enrichment in `IdentityInfo`. Exact fields and data depend on enabled connectors and workspace configuration, so I would inspect the real schema rather than assume every environment has the same data.

As Tier 1, I would treat UEBA as prioritisation and investigation context. I would still validate the raw identity, endpoint, network or cloud events before reaching a verdict.

### Real-World SOC Scenario

Sentinel identifies a finance user performing an unusually high volume of cloud-file downloads from a country and ISP not previously associated with that identity.

My observation is:

**The user's behavior deviates from the learned baseline.**

My hypothesis might be:

**The account is compromised and being used for data collection or exfiltration.**

I would first verify whether the user is travelling, working through an approved VPN or performing an authorised bulk-download task.

Then I would correlate Entra sign-ins, MFA, device/session information, SharePoint/OneDrive audit activity, Defender for Cloud Apps, EDR/browser evidence and any other affected users.

If the user denies the activity, the device/session is unfamiliar, and the anomaly is followed by unusual sharing or external transfer, the compromise hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- Entity involved: user, device, IP, application or other object
- UEBA anomaly/behavior description
- Baseline and peer-group context
- First-seen or uncommon-value insight
- Volume deviation
- Country/ISP/device context
- Risk/priority information where available
- Raw events behind the behavior
- User sign-ins and MFA
- Endpoint/browser/process evidence
- Cloud-file, mailbox or application activity
- Business/travel/VPN explanation
- Similar anomalies affecting peers or other users
- Threat-intelligence matches
- Whether activity is ongoing
- Escalation/containment authority

### Tools / Logs

Microsoft Sentinel UEBA; `BehaviorAnalytics`, `BehaviorInfo` and `IdentityInfo` where available; Microsoft Entra sign-ins; Defender XDR/Endpoint; Defender for Cloud Apps; Microsoft 365 audit logs; firewall/DNS/proxy/VPN telemetry; incident-management records.

### Interview Takeaway

UEBA highlights behavior that is unusual for an entity compared with its baseline, peers or the wider organisation. I would use that anomaly context to prioritise and guide investigation, then validate the raw identity, endpoint, cloud and network evidence before deciding whether the behavior is malicious.

## Verification Notes

- NIST SP 800-207 defines Zero Trust Architecture as removing implicit trust based solely on network location or asset ownership and focusing access decisions on protecting resources.
- Microsoft's current Zero Trust guidance uses three core principles: **verify explicitly**, **use least-privilege access** and **assume breach**.
- Microsoft Entra PIM provides just-in-time/time-bound privileged access and can require approval, MFA, justification and ticket information depending on configuration.

- Microsoft Sentinel UEBA builds behavioral profiles and detects deviations from historical, peer and organisation-wide behavior.

Some current behavior-anomaly features are documented as preview functionality in the Microsoft Defender portal.
- UEBA behaviors/anomalies are contextual evidence and do not by themselves prove malicious activity.
