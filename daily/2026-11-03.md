# SOC Interview Practice — 2026-11-03

**Curriculum:** Questions 181–184 | QR-code phishing and credential theft, EDR process-tree triage, Sysmon process/network correlation, and resilient threat-intelligence response using the Pyramid of Pain, MITRE ATT&CK and NIST incident-response guidance

## Question 181

### Interview Question

Microsoft Defender for Office 365 identifies a QR code in an email that claims the recipient must revalidate Microsoft 365 access. The message passed SPF, DKIM and DMARC because it came from a compromised supplier mailbox. The user scanned the code with a phone and says they entered their password. How would you triage and respond?

### Interview-Ready Answer

I would treat this as suspected credential phishing with possible account compromise, not as a harmless message simply because email authentication passed. SPF, DKIM and DMARC help validate sending infrastructure and message integrity; they do not prove that the person controlling an authenticated mailbox is trustworthy. A compromised supplier mailbox can therefore send an authenticated malicious message.

Microsoft Defender for Office 365 can extract URLs from QR codes for detection, and Threat Explorer or Real-time detections can filter messages using the URL Source value `QR code`. Safe Links provides URL scanning and time-of-click verification in supported Microsoft 365 locations. Coverage and resulting telemetry depend on licensing, policy, client and how the URL was opened, so I would verify the actual alert and click evidence rather than assume the phone interaction was recorded.

My first steps would be to preserve the original message and identifiers, confirm the sender and recipients, safely extract the QR destination using the security tooling, and hunt for the same message or URL across the organisation. Because the user reports entering a password, I would immediately inspect Entra sign-in and audit activity, mailbox changes, OAuth consent, MFA-method changes and endpoint/mobile context where available. Under the approved account-compromise playbook, I would escalate and invoke authorised session revocation, credential reset, MFA review and message removal. I would not wait for a malware alert because the primary risk is stolen credentials.

The user report establishes exposure but not successful attacker use. A malicious destination plus credential submission confirms a phishing incident; account compromise requires evidence such as an unauthorised sign-in, session use or post-authentication change. I would also notify the supplier through a trusted, previously known channel because their mailbox may be compromised.

### Real-World SOC Scenario

Threat Explorer finds the QR message in 18 mailboxes. The user confirms entering credentials. Entra records a successful sign-in from unfamiliar infrastructure shortly afterwards, and Exchange audit evidence shows an unauthorised inbox rule. The supplier confirms its mailbox was compromised.

- **Observation:** An authenticated supplier message contains a QR code leading to a Microsoft 365 credential-harvesting page, and the user reports submitting credentials.
- **Hypothesis:** The attacker used the stolen credentials to access the user's account and create persistence or concealment in the mailbox.
- **Confirmed evidence:** The malicious destination, user confirmation, unauthorised sign-in, unauthorised mailbox rule and independent supplier confirmation establish phishing and account compromise.

The verdict is **high-severity true positive — confirmed QR-code phishing and Microsoft 365 account compromise originating from a compromised supplier mailbox; additional data access and payment impact remain to be scoped**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the original email, full headers, message/network identifiers, QR image, extracted URL and delivery action.
2. Review SPF, DKIM, DMARC and composite-authentication results without treating a pass as a benign verdict.
3. Use Defender Threat Explorer or the deployed email-security platform to identify all recipients, deliveries, removals, clicks and related messages.
4. Confirm what the user did: scanned, opened, entered a password, approved MFA, downloaded a file or supplied other information.
5. Review Entra sign-ins, authentication details, risky activity where licensed, audit changes and newly registered authentication methods.
6. Review Exchange mailbox rules, forwarding, delegate changes, sent items and unusual message access.
7. Invoke authorised message removal, session revocation, credential reset, MFA review and account restrictions under the playbook.
8. Contact the supplier through a trusted out-of-band channel and scope other users who communicate with it.
9. Check for follow-on financial requests, OAuth consent, endpoint execution or sensitive-data access before defining the full impact.
10. Escalate a UTC-normalised timeline, confirmed evidence, containment status and remaining uncertainty.

### Relevant Tools / Logs

Microsoft Defender for Office 365 Threat Explorer/Real-time detections and Email entity, Safe Links telemetry where available, Exchange message trace and audit evidence, Microsoft Entra sign-in and audit logs, Defender XDR, Microsoft Sentinel, Proofpoint or Abnormal Security where deployed, mobile/endpoint telemetry, supplier verification and the incident-management platform.

### Key Interview Takeaway

Authenticated email can still be malicious when a real mailbox is compromised. I would establish the QR destination and user action, then pivot immediately to identity and mailbox evidence instead of relying on SPF, DKIM or DMARC as a verdict.

## Question 182

### Interview Question

Microsoft Defender for Endpoint shows `WINWORD.EXE` launching `mshta.exe`, which retrieves remote content, starts PowerShell and is followed by a new DLL plus outbound traffic. What does EDR contribute, and how would you decide whether this is malicious execution rather than legitimate administration?

### Interview-Ready Answer

Endpoint detection and response continuously collects endpoint telemetry and uses it to detect, investigate and respond to suspicious behaviour. In a SOC environment, I would use EDR to reconstruct the process ancestry, command lines, files, accounts, network connections and related alerts on the device. Tier 1 normally validates and scopes the evidence, invokes approved response actions and escalates; security engineering owns policy design and broad sensor configuration.

Microsoft documents `DeviceProcessEvents` as containing process-creation and related endpoint events and `DeviceNetworkEvents` as containing network connections. The schemas include device, account, process, initiating-process, command-line, hash, URL/IP and timestamp context. The precise fields available depend on telemetry and platform coverage.

`mshta.exe` is a legitimate Windows utility, so its presence alone is not malicious. MITRE ATT&CK T1218.005 describes adversaries abusing Mshta for proxy execution and recommends correlating suspicious HTA/script invocation with process spawning, file creation and network retrieval. PowerShell is also legitimate; ATT&CK T1059.001 treats suspicious parents, encoded or otherwise unusual commands and correlated network or child-process activity as stronger evidence than the executable name alone.

I would validate the parent-child chain, full command lines, user, document provenance, URL, downloaded content, hashes, signatures, file locations and outbound destinations. I would check whether an approved macro, software deployment or administrator workflow explains it. If the document led to unauthorised remote retrieval, script execution, payload creation and command-and-control traffic, I would classify it as malicious execution and invoke authorised device isolation and indicator containment while preserving evidence.

### Real-World SOC Scenario

The Word document arrived in the QR-phishing campaign's follow-up email. Defender shows `WINWORD.EXE` spawning `mshta.exe`, which retrieves an HTA from an untrusted domain and launches PowerShell. PowerShell writes an unsigned DLL to a user-writable directory; the DLL's process then connects repeatedly to a rare external address. The user and software owner deny any authorised automation.

- **Observation:** An Office process launches Mshta, followed by PowerShell, payload creation and rare outbound communication.
- **Hypothesis:** A malicious document triggered proxy execution and downloaded or staged a malware payload.
- **Confirmed evidence:** Email provenance, process ancestry, command-line and network correlation, unsigned payload creation, repeated beaconing and owner denial establish unauthorised execution.

The verdict is **critical true positive — confirmed endpoint compromise following malicious-document execution, with behaviour consistent with staged payload delivery and command and control; actor attribution and data exfiltration remain unconfirmed**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the Defender alert, incident, device timeline and complete process tree.
2. Record user, device, timestamps, parent/child processes, command lines, integrity/elevation context and hashes.
3. Identify the document's source, message ID, download origin, Mark-of-the-Web or browser/email provenance where available.
4. Correlate `DeviceProcessEvents`, `DeviceFileEvents` and `DeviceNetworkEvents` around the execution window.
5. Inspect the remote URL, payload path, signature, prevalence and threat-intelligence context without executing the content.
6. Check approved macros, application packaging, administrator activity and change records.
7. Hunt for the document, URL, hashes, filenames and behavioural chain across other devices and recipients.
8. Invoke authorised device isolation, indicator blocking and identity/session containment if compromise is supported.
9. Preserve samples only through approved malware-handling procedures and avoid uploading sensitive files to public services.
10. Escalate scope, business impact, evidence, actions taken and unanswered questions to Tier 2/IR.

### Relevant Tools / Logs

Microsoft Defender for Endpoint and Defender XDR, `DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents`, Microsoft Sentinel, Defender for Office 365, Windows event logs, Sysmon where configured, DNS/firewall/proxy logs, VirusTotal for approved hash or non-sensitive sample analysis and the case-management platform.

### Key Interview Takeaway

EDR turns an isolated alert into an evidence chain. I would judge Mshta and PowerShell by their parent, command, payload, network activity and business context—not by executable name alone.

## Question 183

### Interview Question

You receive the following simplified Sysmon evidence from a Windows workstation. How would you interpret it and what additional evidence would you seek before escalating?

```text
Event ID 1 — Process creation
ProcessGuid: {11111111-2222-3333-4444-555555555555}
Image: C:\Windows\System32\rundll32.exe
ParentImage: C:\Users\alex\Downloads\InvoiceViewer.exe
CommandLine: rundll32.exe C:\Users\Public\update.dll,Start

Event ID 3 — Network connection
ProcessGuid: {11111111-2222-3333-4444-555555555555}
Image: C:\Windows\System32\rundll32.exe
DestinationIp: 203.0.113.10
DestinationPort: 443
```

### Interview-Ready Answer

Microsoft documents Sysmon Event ID 1 as process creation. It can include the full command line, hashes and a `ProcessGUID` designed to support correlation. Event ID 3 records TCP/UDP network connections and links them to a process through `ProcessId` and `ProcessGuid`; network-connection logging is disabled by default and must be enabled in the Sysmon configuration.

The shared `ProcessGuid` links this process-creation record to the connection record despite potential PID reuse. The evidence shows a downloaded executable launching `rundll32.exe` to call the `Start` export in a DLL under a public user-writable path, after which the same Rundll32 process makes an outbound TLS-port connection. The address `203.0.113.10` is a documentation-only placeholder in this practice artefact, not a real indicator.

This is suspicious but not yet a complete verdict. `rundll32.exe` is a legitimate Windows binary and can legitimately load DLL exports. I would validate the downloaded parent's provenance, the DLL's hash and signature, command-line accuracy, user action, file-creation events, process ancestry and network destination in the real telemetry. I would also check whether deployment or diagnostic software explains the sequence.

Confirmation would come from correlated evidence such as an untrusted download, unsigned or malicious DLL, no approved change, repeatable beaconing, related persistence or EDR detection. If Event ID 3 is absent on another host, I would not assume there was no connection until I confirmed Sysmon's configuration and coverage.

### Real-World SOC Scenario

The real destination resolves to a newly registered domain. The DLL is unsigned and was written seconds earlier by `InvoiceViewer.exe`, which was downloaded from a phishing page. Defender identifies the same DLL and behavioural chain on three workstations, and no approved application uses it.

- **Observation:** A downloaded program launches Rundll32 against a DLL in a user-writable location, and the same `ProcessGuid` initiates outbound traffic.
- **Hypothesis:** The downloaded program is using a trusted Windows binary to execute a malicious DLL and establish command and control.
- **Confirmed evidence:** Download provenance, file creation, unsigned payload, cross-host repetition, correlated process/network telemetry and absence of authorised use establish malicious execution.

The verdict is **high-severity true positive — confirmed multi-host malware execution using Rundll32 with outbound command-and-control activity; the content of any transferred data remains unconfirmed**.

### What I Would Check as a Tier 1 Analyst

1. Confirm the events are raw Sysmon records and note the agent, host clock, event channel and collection health.
2. Correlate Event IDs 1 and 3 using `ProcessGuid`, device and time; do not rely only on PID.
3. Review the full command line, parent process, user, integrity level, hashes and signatures.
4. Locate file-creation, image-load, DNS and additional process events where those event types were configured.
5. Establish how `InvoiceViewer.exe` arrived: browser, email, removable media, network share or deployment tool.
6. Enrich the real hash, domain, IP and certificate using approved threat-intelligence sources.
7. Check approved software inventory and change records for legitimate use of the DLL and export.
8. Hunt for the parent, DLL path/hash, Rundll32 command pattern and network destination across the estate.
9. Invoke authorised endpoint/network containment and escalate when malicious execution or active beaconing is confirmed.
10. Document telemetry gaps, especially if Event ID 3 or other required Sysmon event types were not enabled.

### Relevant Tools / Logs

Sysmon Operational log, Event IDs 1 and 3 where configured, Windows event forwarding, Wazuh or Splunk, Microsoft Defender for Endpoint, file and DNS telemetry, firewall/proxy logs, software inventory, threat intelligence and change-management records.

### Key Interview Takeaway

Sysmon's `ProcessGuid` lets me connect execution to network activity. The sequence is suspicious, but I would confirm payload provenance, configuration coverage and business context before stating that Rundll32 was abused.

## Question 184

### Interview Question

A threat-intelligence feed provides a malicious SHA-256 hash, domain and IP for a malware campaign. Your EDR finds no matching hash, but analysts observe the same Office-to-Mshta-to-PowerShell execution pattern, payload locations and beaconing behaviour on several devices using different files and infrastructure. How would you use the Pyramid of Pain, MITRE ATT&CK and the incident-response lifecycle to respond?

### Interview-Ready Answer

I would use the supplied indicators immediately for bounded hunting and blocking where approved, but I would not stop at the hash, domain and IP. The Pyramid of Pain explains that hashes are precise but easy for an adversary to change; IP addresses and domains usually require somewhat more effort; host/network artefacts, tools and tactics, techniques and procedures are progressively harder to replace. RFC 9424 describes the same trade-off and stresses that indicators require assessment, context, deployment and eventual retirement.

The missing hash therefore does not disprove campaign activity. I would hunt for both atomic indicators and the higher-level behaviour: suspicious Office parentage, Mshta remote retrieval, unusual PowerShell execution, payload creation in user-writable locations, recurring beacon patterns and related persistence. ATT&CK provides consistent technique labels—for example T1218.005 for Mshta and T1059.001 for PowerShell—but mapping evidence to ATT&CK does not identify an actor or prove that every matching event is malicious.

At Tier 1, I would validate the detections, preserve the relevant endpoint and network evidence, scope affected users/devices, and invoke approved device, identity, email and network containment. I would promote confirmed hashes, domains, IPs, certificates, paths, mutexes or URI patterns into the organisation's indicator lifecycle with owners, confidence, timestamps and expiry/review dates. I would also recommend behavioural detections around the verified chain because they remain useful when the attacker recompiles payloads or changes infrastructure.

NIST SP 800-61 Rev. 3 frames current incident response around Detect, Respond and Recover, supported by Govern, Identify and Protect, with lessons feeding continuous Improvement. I would keep containment, eradication and recovery distinct: containment limits active access; eradication removes payloads, persistence and compromised access; recovery restores known-good systems and monitors them; improvement updates detections, controls and playbooks.

### Real-World SOC Scenario

The campaign's published hash is absent, but four devices show the same malicious parent-child chain and payload path. Two contact a new domain with the same distinctive URI pattern. EDR isolation stops further communication, and specialist analysis confirms that the new payload is a recompiled variant of the campaign malware.

- **Observation:** Atomic indicators changed, but host and network behaviour closely match the verified campaign pattern.
- **Hypothesis:** The organisation is affected by a variant using changed payloads and infrastructure while retaining the same execution and command-and-control procedure.
- **Confirmed evidence:** Cross-device behavioural correlation, malicious payload analysis, repeated URI/network artefacts and incident-response findings establish campaign-related compromise.

The verdict is **critical true positive — confirmed multi-device compromise by a changed malware variant; behavioural detections succeeded where the original hash did not. Actor attribution remains an intelligence assessment rather than an incident-response fact**.

### What I Would Check as a Tier 1 Analyst

1. Record the intelligence source, publication time, confidence, handling restrictions, indicator type and expiry/review guidance.
2. Search hashes, domains, IPs, URLs and certificates across EDR, SIEM, DNS, proxy, firewall and email telemetry.
3. Hunt for host/network artefacts and the verified process, file and beaconing chain even when atomic indicators do not match.
4. Map confirmed behaviour to ATT&CK without treating the mapping as attribution.
5. Validate false-positive risk and business dependencies before broad blocking.
6. Invoke approved isolation, indicator blocking, message removal and identity/session containment.
7. Scope affected devices, users, persistence, credentials, lateral movement, sensitive-data access and recovery-system impact.
8. Escalate for specialist malware analysis, eradication, trusted rebuilding and monitored recovery.
9. Convert confirmed lessons into behavioural detections, hunting queries, control improvements and playbook updates.
10. Maintain indicator ownership and retire stale or harmful blocks through the organisation's indicator lifecycle.

### Relevant Tools / Logs

Microsoft Defender XDR/Defender for Endpoint, Microsoft Sentinel or Splunk, Wazuh/Sysmon, Defender for Office 365, Proofpoint or Abnormal Security, DNS/firewall/proxy telemetry, threat-intelligence platform, VirusTotal where policy permits, malware-analysis tooling, asset/identity inventories and incident-management records.

### Key Interview Takeaway

Atomic indicators are useful but fragile. I would block and hunt them quickly, then build resilient detections around verified artefacts and TTPs, scope the incident, recover trusted systems and feed the lessons back into detection engineering.
