# SOC Interview Practice — 2026-09-24

## Question 85

### Interview Question

What is a proxy server, and how would a Tier 1 SOC analyst use proxy telemetry during an investigation?

### Interview-Ready Answer

A proxy is an intermediary between a client and a destination service. NIST defines a proxy server as a server that services client requests by forwarding them to other servers. In an enterprise, a forward web proxy commonly sits between users/endpoints and external web services, where it can enforce policy and produce useful evidence about outbound web activity. A reverse proxy is instead positioned in front of servers/applications and handles inbound client requests on their behalf.

In a SOC environment, I would use proxy telemetry to answer questions such as which user or host requested a URL, when it happened, whether the request was allowed or blocked, and what destination/domain was involved. Exact fields depend on the product, so I would verify the organisation's schema rather than invent field names. Proxy evidence is valuable context, but an allowed connection is not proof that malicious content executed on the endpoint, and a blocked request does not automatically mean the incident is finished.

Observation: a web request occurred or was attempted. Hypotheses: normal browsing, an unwanted redirect, phishing follow-on activity, malware command-and-control, or data transfer. Confirmed malicious activity requires correlation with endpoint, identity, DNS, file or other evidence.

### Real-World SOC Scenario

A SIEM alert shows a workstation repeatedly reaching a newly observed domain through the corporate web proxy. I would identify the host/user and timestamps, review the URL/domain and proxy disposition, then correlate with DNS and EDR. If EDR shows an unusual process making network connections to the same destination after a suspicious file executed, the malicious-communication hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- Source host/user and timestamp
- Destination domain/URL and resolved IP where available
- Allowed/blocked disposition and HTTP context provided by the product
- Request frequency and baseline/prevalence
- DNS evidence
- Initiating process from EDR where available
- Related download/file events and hashes
- Threat-intelligence context
- Similar activity from other hosts
- Whether containment/escalation is authorised

### Tools / Logs

Web proxy/Secure Web Gateway telemetry, DNS logs, firewall logs, Microsoft Sentinel, Splunk or Wazuh, Defender for Endpoint or another EDR, and threat-intelligence sources.

### Interview Takeaway

“A proxy intermediates client-server communication. In a SOC I would use its telemetry to understand outbound web activity, but I would correlate proxy evidence with DNS, endpoint and identity data before deciding whether the activity is malicious.”

### Verification Notes

- NIST CSRC Proxy Server glossary: https://csrc.nist.gov/glossary/term/proxy_server
- NIST CSRC Proxy glossary: https://csrc.nist.gov/glossary/term/proxy

## Question 86

### Interview Question

Windows Security Event ID 4625 appears repeatedly on a server. What does it mean, which fields matter, and how would you distinguish attack activity from a configuration problem?

### Interview-Ready Answer

Event ID 4625 records a failed account logon on the computer where the logon attempt was made. Microsoft documents useful investigation fields including the account that failed, Logon Type, Workstation Name, Source Network Address/Port where populated, Authentication Package, Failure Reason, Status and Sub Status. The Status/Sub Status values can materially change the interpretation: for example, Microsoft documents 0xC0000064 as a nonexistent/bad user account and 0xC000006A as a bad password.

I would not label repeated 4625 events as brute force from the Event ID alone. A service using an old password, a scheduled task, a disconnected mapped resource, an expired/disabled account or an application misconfiguration can also generate repeated failures. I would examine the pattern across account, source, target, logon type, rate and failure reason, then correlate with successful logons and endpoint/network activity.

Observation: logon attempts failed. Hypotheses: user error, stale credentials/configuration, enumeration, brute force or another authentication attack. Confirmed attack requires a malicious pattern and supporting evidence.

### Real-World SOC Scenario

A server generates a 4625 every minute for the same service account from the same internal host, shortly after that account's password was changed. That regular cadence and operational context may suggest stale stored credentials rather than an attacker. By contrast, rapidly changing usernames from an unexpected source, or many failures followed by a successful logon, raises the attack hypothesis and requires deeper investigation.

### What I Would Check as a Tier 1 Analyst

- Failed account and domain
- Logon Type
- Failure Reason, Status and Sub Status
- Source Network Address/Workstation Name where populated
- Authentication Package
- Frequency and time pattern
- One account versus many accounts
- Related 4624 successful logons and other authentication telemetry
- Recent password/account changes
- Services, scheduled tasks or applications using stored credentials
- EDR/network activity on the source
- Escalation/containment authority

### Tools / Logs

Windows Security Event 4625 and related authentication events, Active Directory/domain-controller evidence where relevant, Microsoft Sentinel, Splunk, Wazuh, Defender for Endpoint or another EDR, VPN/identity and firewall telemetry.

### Interview Takeaway

“4625 means a logon failed. I would use the account, source, logon type, failure status and timing pattern to determine whether I am seeing user/configuration noise or an authentication attack, then correlate any later success and endpoint behaviour.”

### Verification Notes

- Microsoft Learn Event 4625 reference: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625

## Question 87

### Interview Question

You are shown this Microsoft Sentinel KQL during an interview. Explain what it does and what you would investigate next:

```kusto
SecurityEvent
| where EventID == 4625
| summarize FailedLogons=count() by TargetAccount, Computer
| where FailedLogons > 10
```

### Interview-Ready Answer

I would read it from top to bottom. `SecurityEvent` is the table being queried. `where EventID == 4625` keeps Windows failed-logon events. `summarize FailedLogons=count() by TargetAccount, Computer` counts those events for each account/computer combination. The final `where` keeps combinations with more than ten failures.

Microsoft's own Azure Monitor SecurityEvent examples use `SecurityEvent | where EventID == 4625 | summarize count() by TargetAccount, Computer, _ResourceId` to report Windows failed logins, so the core table/Event ID/operator usage is supported by Microsoft documentation.

The query is useful, but it does not prove brute force and, as written, it has no explicit time filter. In an interview I would say I need to know the query's selected time range and investigate the underlying events rather than treating the threshold as a verdict. I would pivot to source information, Logon Type, Status/Sub Status, authentication package, timing, account distribution and any subsequent successful authentication.

Observation: more than ten failed-logon events exist for an account/computer grouping in the query period. Hypothesis: password attack or configuration problem. Confirmed evidence requires the raw-event pattern and corroborating telemetry.

### Real-World SOC Scenario

The query returns `svc_backup` on `SERVER01` with 240 failures. Rather than immediately escalating it as brute force, I inspect the raw 4625 events. If they occur exactly once per minute from a known backup server after a password rotation, stale credentials become a strong hypothesis. If failures arrive rapidly from an unexpected workstation against several privileged accounts and one later succeeds, attack likelihood rises sharply.

### What I Would Check as a Tier 1 Analyst

- Query time range and threshold rationale
- Raw 4625 events behind the aggregate
- TargetAccount and Computer
- Source address/workstation where populated
- Logon Type, Status/Sub Status and Authentication Package
- Failure cadence and number of distinct accounts/sources
- Related successful logons
- Baseline and authorised automation
- EDR/identity/network evidence
- Whether the query should be refined for the use case

### Tools / Logs

Microsoft Sentinel/Log Analytics KQL, `SecurityEvent`, Windows Security logs, Defender for Endpoint, identity/VPN and firewall telemetry.

### Interview Takeaway

“I can explain what the KQL proves and what it does not. It identifies account/computer groupings with more than ten 4625 failures in the query period; I would then inspect the raw authentication pattern and correlated telemetry before calling it an attack.”

### Verification Notes

- Microsoft Azure Monitor SecurityEvent query examples: https://learn.microsoft.com/en-us/azure/azure-monitor/reference/queries/securityevent
- Microsoft Event 4625 reference: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625

## Question 88

### Interview Question

EDR shows an unusual process making an outbound connection, followed seconds later by creation of an executable in a user-writable directory. How would you investigate possible tool download/Ingress Tool Transfer as Tier 1?

### Interview-Ready Answer

MITRE ATT&CK maps adversary transfer of files or tools from an external system into a compromised environment to T1105, Ingress Tool Transfer. MITRE's current detection strategy describes a useful behavioural chain: an unusual process initiates an external network connection followed by file creation, while also noting that legitimate software updaters must be tuned/allowlisted appropriately.

I would not infer malware solely because a process downloaded an executable. Browsers, package managers, enterprise deployment agents and software updaters legitimately download files. I would identify the initiating process, external destination, newly created file, origin information where available, hash/signature/prevalence and whether the file executed. Then I would correlate parent/child process lineage, persistence, credential activity and further network connections.

In Defender XDR, `DeviceNetworkEvents` contains network-connection telemetry and `DeviceFileEvents` contains file-creation/modification telemetry when Defender for Endpoint supplies those records. I would use the actual schema available in the tenant rather than assume every field is populated.

Observation: network communication was followed by file creation. Hypothesis: legitimate download/update or adversary tool transfer. Confirmed malicious transfer requires contextual evidence such as unauthorised process/destination, malicious file analysis or suspicious execution/follow-on behaviour.

### Real-World SOC Scenario

A script interpreter makes an HTTPS connection to a rare external domain. Seconds later an executable appears under a user's profile and launches, then creates persistence. I would build the timeline: initiating process -> external connection -> file creation -> hash/signature/origin -> execution -> persistence/network activity. If the domain/file is malicious or the execution chain is clearly unauthorised and malicious, I would escalate and perform only authorised containment.

### What I Would Check as a Tier 1 Analyst

- Initiating process, parent, path and command line
- User/device and privilege context
- Destination IP/domain/URL and port/protocol
- File name/path and creation timestamp
- File origin fields where available
- Hash, signer and organisational prevalence
- Whether the file executed and its child processes
- Persistence or credential-access behaviour
- Further DNS/proxy/firewall/EDR activity
- Whether the process is an approved updater/deployment tool
- Similar activity across other endpoints
- Tier 1 containment/escalation authority

### Tools / Logs

Defender for Endpoint/Defender XDR `DeviceNetworkEvents` and `DeviceFileEvents` where available, Microsoft Sentinel, Splunk or Wazuh, Sysmon where configured, DNS/proxy/firewall telemetry, file reputation/sandboxing tools according to organisational policy.

### Interview Takeaway

“Network connection followed by file creation is a useful behavioural chain, not an automatic malware verdict. I would correlate the initiating process, destination, file origin/hash/signature, execution and follow-on behaviour, while ruling out approved software delivery before escalating.”

### Verification Notes

- MITRE ATT&CK T1105 detection strategy DET0060: https://attack.mitre.org/detectionstrategies/DET0060/
- Microsoft Defender XDR DeviceNetworkEvents: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-devicenetworkevents-table
- Microsoft Defender XDR DeviceFileEvents: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-devicefileevents-table
