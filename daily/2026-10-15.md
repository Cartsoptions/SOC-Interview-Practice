# SOC Interview Practice — 2026-10-15

## Question 133

### Interview Question

A Wazuh alert reports repeated SSH authentication failures against an internet-facing Linux server. How would you determine whether this is routine scanning, brute-force activity, password spraying, or a successful compromise?

### Interview-Ready Answer

I would start by explaining that SSH is an encrypted remote-access protocol; the alert tells me that authentication activity crossed a rule threshold, not that the server is compromised. In a SOC environment, I would validate the original authentication events, because a correlation alert is a lead and its meaning depends on the pattern underneath it.

I would establish the time window, destination host, source IPs, targeted usernames, authentication methods and outcomes. Many failures from one source against one or a few accounts is consistent with password guessing or brute force. A small number of attempts against many accounts may be consistent with spraying or username enumeration, although SSH logs normally do not reveal the password attempted, so I would not claim a spray without supporting context. Broad, low-rate failures with no success or follow-on behaviour may be internet scanning, but still merit review if the service should not be exposed.

The critical pivot is whether an authentication succeeded and what happened next. I would search for an `Accepted password` or `Accepted publickey` event involving the same source, account or time window, then correlate sudo, process, file, persistence and network telemetry. A successful login is not automatically malicious; it must be compared with the account owner, source network, change records, normal access patterns and authorised administration. Conversely, an accepted public key proves that the server accepted a configured key, not that the person using it was legitimate.

As Tier 1, I would document the evidence and escalate confirmed success after suspicious failures, privileged follow-on activity, or access to a critical host. Blocking a source or changing SSH controls is an administrative or engineering action unless the playbook delegates it. If Wazuh Active Response is enabled, I would verify the action and its alert rather than assume an IP was blocked merely because an authentication alert fired.

### Real-World SOC Scenario

Wazuh records 240 SSH failures against `web-02` in ten minutes. Most target nonexistent usernames from one source, but a separate source generates three failures and then an accepted login for the valid account `deploy`.

- **Observation:** Authentication failures occurred, and a success event exists for `deploy`; these are separate facts that must be correlated by host, source and time.
- **Hypothesis:** The first source may be automated scanning or brute force. The second pattern may represent successful password guessing, stolen credentials or legitimate administration after mistyped credentials.
- **Confirmed evidence required:** A malicious-compromise verdict needs corroboration such as an unauthorised successful session, account-owner denial, unexpected privilege use, suspicious commands/processes, persistence, file changes or network activity. Failure volume alone does not confirm compromise.

### What I Would Check as a Tier 1 Analyst

1. Validate the raw event times, hostname, source IP/port, target username, authentication method and success/failure result; confirm the sensor and log coverage are healthy.
2. Compare the distribution of sources and accounts, rate and duration, nonexistent versus valid users, and whether any source later succeeded.
3. Check the server's approved exposure, firewall/VPN path and normal administration ranges; treat geolocation and reputation as enrichment, not proof.
4. Correlate accepted sessions with sudo/authentication logs, endpoint or audit telemetry, processes, file changes, cron/systemd changes and outbound connections.
5. Confirm the `deploy` account owner, expected change window, authentication method and usual source; look for the same account or source on other hosts.
6. Preserve the event samples and timeline. Escalate suspicious success or material follow-on activity, and request authorised account, key, firewall or host containment under the runbook.

### Tools / Logs

Wazuh alerts and underlying events, OpenSSH/sshd authentication logs in the systemd journal or distribution-specific files such as `/var/log/auth.log` or `/var/log/secure`, Splunk or Microsoft Sentinel syslog data, firewall/VPN logs, Linux audit or EDR telemetry, asset inventory and change records. `last`/`lastb` may provide supporting wtmp/btmp history when those files are maintained, but they should not replace the primary authentication logs.

### Interview Takeaway

I would not equate an SSH brute-force alert with compromise. I would classify the pattern, pivot to successful authentication and follow-on behaviour, validate business context, and escalate based on corroborated impact.

## Question 134

### Interview Question

At 02:14, a Linux production server records `Accepted publickey for deploy` from a never-before-seen external IP. Minutes later, the account uses sudo and a new cron entry runs a shell script from `/tmp`. How would you investigate and respond?

### Interview-Ready Answer

I would treat this as a high-priority suspected compromise because unusual remote access is followed by privilege use and a plausible persistence mechanism. Public-key authentication is strong when keys are protected, but the log only establishes that sshd accepted a key associated with the account. It does not establish the operator's identity or authorisation.

I would build a precise timeline from the accepted SSH event through session activity, sudo authentication, the cron change, script creation and execution, and any outbound connections. I would validate the actual cron definition, owner, schedule, command and timestamps, hash the referenced script if authorised, and inspect its content safely as data. Cron is legitimate administration, so I would compare the activity with deployment tooling, change records and the account owner's normal behaviour.

I would also determine how access was obtained. That includes reviewing approved keys and recent changes to `authorized_keys`, key fingerprints if the configured logging provides them, account changes and whether the same key/account/source appears elsewhere. I would not assume the key itself was stolen: an exposed automation host, unauthorised key addition or legitimate emergency work are alternative hypotheses.

If the user or change owner cannot validate the activity, or the script contains unauthorised commands or network destinations, I would classify it as a true positive and escalate immediately. Within delegated authority, containment could include restricting the host's network access and disabling or revoking the affected account/key while preserving evidence and avoiding an unplanned shutdown. Engineering or incident-response staff should make higher-impact changes unless the playbook authorises Tier 1.

### Real-World SOC Scenario

The raw logs show a successful key-based login to `prod-api-03`, a successful sudo session, creation of `/tmp/.health.sh`, and a root cron entry invoking it every five minutes. Network telemetry shows repeated outbound connections beginning after the first execution.

- **Observation:** A new-source key login, privilege use, a cron entry, a temporary-directory script and later outbound activity are recorded.
- **Hypothesis:** A valid key or account was abused to obtain remote access, escalate privileges and establish recurring execution.
- **Confirmed evidence required:** Confirm the login/session association, cron definition and owner, script content/hash and execution, sudo activity and network destination. Confirming those behaviours supports compromise; credential theft, data exfiltration and actor attribution require separate evidence.

### What I Would Check as a Tier 1 Analyst

1. Validate timestamps, host, source IP, account, authentication method, session identifiers where available and telemetry time zones.
2. Confirm whether `deploy` should log in interactively, whether the source belongs to an approved automation or administrator, and whether a change ticket covers the activity.
3. Review sudo and audit/EDR evidence for commands, process ancestry, effective user and files created; do not rely on shell history, which can be incomplete or altered.
4. Inspect the relevant user's and system-wide cron locations, plus systemd timers if the evidence points there; record the exact schedule and command before any change.
5. Examine `/tmp/.health.sh` without executing it: ownership, permissions, timestamps, cryptographic hash, content and any referenced payloads or destinations.
6. Correlate DNS, firewall/proxy and host network telemetry; distinguish connection attempts from successful sessions and look for the same indicators on other assets.
7. Check authorised-key and account-change evidence, and scope the same account/key/source across servers.
8. Escalate with a factual timeline, confidence, business impact, current exposure and requested containment. Verify every containment action and record its result.

### Tools / Logs

OpenSSH/sshd and PAM authentication logs, sudo logs, Wazuh, Splunk, Linux auditd or EDR telemetry where deployed, cron files and logs, systemd journal and timer information, file-integrity monitoring, DNS/firewall/proxy/flow logs, asset inventory and change-management records.

### Interview Takeaway

An accepted public key is evidence of authentication, not legitimacy. I would connect the exact session to privilege use, persistence, script execution and network behaviour, then contain and escalate within my authority.

## Question 135

### Interview Question

You receive raw OpenSSH authentication events in Splunk and need a safe first-pass search for hosts and source IPs with repeated failures or any accepted login. What would you search, and how would you interpret the results?

### Interview-Ready Answer

I would first confirm the correct index, retention and log format in that environment. The following is an illustrative first pass for conventional OpenSSH text events; `index=linux_auth` is an example, not a universal value:

```spl
index=linux_auth earliest=-24h
("Failed password" OR "Accepted password" OR "Accepted publickey")
| rex field=_raw "(?<auth_result>Failed password|Accepted password|Accepted publickey).* from (?<src_ip>[0-9A-Fa-f:.]+) port (?<src_port>[0-9]+)"
| stats count(eval(match(auth_result,"^Failed"))) AS failures
        count(eval(match(auth_result,"^Accepted"))) AS successes
        values(auth_result) AS results
        earliest(_time) AS first_seen
        latest(_time) AS last_seen
        by host src_ip
| where failures >= 20 OR successes > 0
| convert ctime(first_seen) ctime(last_seen)
| sort - failures
```

`rex` extracts named fields from `_raw`; `stats` groups by host and source IP and counts matching result types; `where` applies an illustrative triage threshold; and `convert ctime` renders epoch values for readability. I would tune both the parser and threshold to the actual data. The regular expression assumes familiar OpenSSH message text and will miss different formats, localisation, structured events, messages without a `port` token, or upstream transformations.

The query cannot prove brute force or compromise. It aggregates counts and can conceal sequence, usernames and separate sessions. I would inspect the underlying events, add account and session context, check whether failures preceded a success, and correlate privilege, process and network telemetry. I would also avoid treating `successes > 0` as malicious; it deliberately surfaces accepted logins for triage.

### Real-World SOC Scenario

The search returns `prod-api-03 / 203.0.113.50` with 26 failures and one success. Opening the raw events shows that the success was for `deploy`, while many failures targeted unrelated usernames.

- **Observation:** The grouped result contains failures and a success for the same host/source pair in 24 hours.
- **Hypothesis:** The source may have guessed a valid credential, or the aggregate may combine unrelated attempts and an authorised login.
- **Confirmed evidence required:** Raw event order, target accounts, timestamps and authentication methods must establish whether the same sequence is related. Account-owner/business validation and follow-on host activity determine whether the accepted session was unauthorised.

### What I Would Check as a Tier 1 Analyst

1. Verify that recent events exist, the intended hosts are reporting and the search time zone and retention cover the incident.
2. Test the extraction against representative raw events, including IPv4 and IPv6, success and failure records; quantify unmatched events.
3. Open the raw timeline for any result with a success, extract the target user, and distinguish failure-before-success from unrelated aggregated activity.
4. Compare with known scanners, bastions, VPN ranges, administrators and automation, while retaining the underlying evidence.
5. Correlate suspicious accepted sessions with sudo, audit/EDR, file, cron/systemd, DNS and network records.
6. Treat the threshold as a starting point, document blind spots and false positives, and ask detection engineering to tune production content rather than silently changing it.
7. Escalate when the evidence supports unauthorised access or high-risk follow-on behaviour, including the search, time range and raw events in the case.

### Tools / Logs

Splunk Search Processing Language (`rex`, `stats`, `eval`/`match`, `where`, `convert`, `sort`), OpenSSH raw logs, Wazuh alerts, Linux audit/EDR telemetry, firewall/VPN/DNS logs, asset inventory and approved-access records.

### Interview Takeaway

A useful SIEM search creates an explainable lead, not a verdict. I would validate the parser and coverage, inspect raw sequence and account context, and corroborate any successful login with host and network evidence.

## Question 136

### Interview Question

You confirm that an internet-facing Linux server was accessed through SSH using the `deploy` account, sudo was used, a malicious cron job was installed and the host began communicating with an external server. As Tier 1, how would you manage the incident from initial triage through recovery, and how would you use NIST and MITRE ATT&CK without overstating the evidence?

### Interview-Ready Answer

I would declare or recommend a high-severity confirmed host compromise under the organisation's criteria. The evidence shows unauthorised remote access, privileged activity, persistence and external communication on a production server. I would immediately notify the escalation path, preserve the timeline and evidence, and identify service criticality, data exposure and current business impact.

Containment should reduce attacker access while protecting evidence and availability. Under an authorised playbook, that may mean network-isolating the host or tightly restricting its communications, revoking the affected key or disabling the account, and blocking confirmed malicious destinations. Because this is a production server, I would coordinate with incident response and the service owner rather than improvise. I would not simply delete the cron entry, kill processes, reboot or wipe the system: those steps can alert the attacker, destroy volatile evidence or leave other access paths intact.

I would scope horizontally and vertically. Horizontally, I would search other hosts for the account, key/fingerprint if available, source IP, script hash/path, cron command, destination and comparable behaviour. Vertically, I would reconstruct activity on the host: authentication, sudo, process execution, file and account/key changes, persistence, outbound traffic and access to sensitive data. I would determine whether shared credentials or automation secrets require rotation and whether the compromised host was used to reach other systems.

NIST SP 800-61 Rev. 3 places incident response within CSF 2.0 risk management and covers detection, response and recovery outcomes. I would use the organisation's NIST-aligned plan to organise communication, analysis, containment, eradication, recovery and improvement, not as a substitute for the playbook. MITRE ATT&CK can describe the evidenced behaviours: Valid Accounts (T1078), SSH (T1021.004), Unix Shell where shell execution is observed (T1059.004), and Cron (T1053.003). Those mappings help hunting and detection engineering; they do not identify an actor or prove every tactic listed on an ATT&CK page.

After containment and evidence collection, authorised responders should eradicate malicious accounts/keys, jobs, files and other persistence, patch or correct the initial exposure, rotate affected secrets, and normally rebuild a materially compromised server from a trusted image where policy calls for it. Recovery requires validation: approved configuration restored, credentials rotated, sensors/logging healthy, malicious activity absent, application integrity tested and enhanced monitoring in place. The post-incident review should improve SSH exposure, key lifecycle, least privilege, detection logic, evidence retention and the response playbook.

### Real-World SOC Scenario

The service owner denies the 02:14 deployment. Logs and host telemetry correlate the accepted SSH session with sudo, creation and execution of a root-owned cron job, and recurring connections to an unapproved destination. A second server uses the same deployment key but shows no suspicious activity yet.

- **Observation:** Correlated authentication, privilege, persistence and network evidence exists on one server; the key is also authorised on another server.
- **Hypothesis:** The deployment credential or an authorised source system was compromised, persistence was established, and other hosts trusting the same key may be exposed.
- **Confirmed evidence:** The first server is compromised based on the unauthorised session and corroborated privileged persistence/execution. Credential theft, compromise of the second server, data exfiltration and actor identity remain unconfirmed until separately evidenced.

The initial verdict is **true positive — confirmed Linux server compromise**, with urgent scoping of every system that trusts the same credential.

### What I Would Check as a Tier 1 Analyst

1. Open or update the incident with severity, affected service/owner, evidence confidence, business impact and a minute-by-minute UTC timeline.
2. Preserve raw logs, SIEM results, alert metadata, relevant volatile telemetry and hashes according to evidence-handling procedures; record who collected what and when.
3. Trigger the authorised escalation and containment workflow; verify isolation, account/key revocation and network blocks, and record failures or exceptions.
4. Hunt across SSH, sudo, process, file-integrity, audit/EDR, cron/systemd, DNS, proxy/firewall and cloud/identity logs for the account, source, key metadata, commands, hashes and destinations.
5. Identify shared keys, credentials, secrets and trust relationships; check for lateral movement, new users/keys, changed services or timers and access to sensitive data.
6. Keep observation, hypothesis and confirmed evidence separate. Map only observed behaviours to ATT&CK and avoid premature attribution.
7. Hand Tier 2/IR a concise package: timeline, scope, affected assets, confirmed behaviours, remaining hypotheses, containment status, gaps and decisions required.
8. During recovery, verify the trusted rebuild or remediation, secret rotation, application tests, sensor health and absence of recurring indicators; keep heightened monitoring and capture lessons learned.

### Tools / Logs

Wazuh, Splunk or Microsoft Sentinel; OpenSSH/sshd, PAM and sudo logs; Linux auditd/EDR and file-integrity telemetry; cron/systemd configuration and logs; DNS, firewall, proxy and flow records; cloud control-plane and identity logs where applicable; asset/CMDB, change-management, key-management and incident-management systems.

### Interview Takeaway

I would treat the evidence as a confirmed server compromise, contain within delegated authority, preserve and scope before making destructive changes, and give responders a precise handoff. NIST structures the response; ATT&CK labels evidenced behaviours for hunting—it does not supply attribution.

## Verification Notes

- OpenSSH authentication messages and storage differ by distribution and configuration. The systemd journal can be queried with `journalctl`; Debian/Ubuntu commonly use `/var/log/auth.log`, while RHEL-family deployments often use `/var/log/secure`. The answer therefore requires validation of the local source rather than assuming one path.
- Wazuh documents SSH log decoding, authentication-success rule 5715, and correlation of multiple failures for brute-force detection. Wazuh Active Response requires explicit configuration; an ordinary authentication alert does not prove a firewall block occurred.
- Splunk documents `rex` named-field extraction, `stats` aggregation, evaluation functions such as `match`, `where`, and `convert ctime`. The SPL uses an illustrative index and threshold and explicitly identifies format limitations.
- The Linux `last` utility reads wtmp and `lastb` reads btmp. These files may be absent, rotated or incomplete, so their output is supporting evidence rather than definitive proof.
- MITRE ATT&CK supports the mappings used here: Valid Accounts T1078, Remote Services: SSH T1021.004, Scheduled Task/Job: Cron T1053.003, and Command and Scripting Interpreter: Unix Shell T1059.004. Technique mappings describe observed behaviour and do not establish attribution.
- NIST SP 800-61 Rev. 3 was published in April 2025, supersedes Rev. 2, and integrates incident-response recommendations with NIST CSF 2.0 risk management.
