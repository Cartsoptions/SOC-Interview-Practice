# SOC Interview Practice — 2026-11-23

**Curriculum:** Questions 237–240 | WAF and IDS/IPS triage, Entra ID password spraying, Splunk investigation of Linux SSH compromise, and malicious OAuth application consent

## Question 237

### Interview Question

A public customer portal generates a WAF alert for an apparent SQL-injection attempt. The WAF records one request as blocked, a network IDS also alerts, and the application begins returning HTTP 500 errors. How would you determine whether this was a blocked probe, a WAF bypass or successful exploitation, and what do the firewall, IDS, IPS and WAF each contribute?

### Interview-Ready Answer

A network firewall enforces traffic policy using information such as source, destination, protocol, port, connection state and, in some products, application identity. An IDS monitors activity and raises alerts about suspected attacks. An IPS is positioned to attempt prevention, such as dropping traffic or resetting a connection. A WAF focuses on HTTP/S application traffic and evaluates web requests against application-layer rules. Product architecture and configuration determine the exact visibility and enforcement available.

In a SOC environment, I would not treat a WAF `blocked` action as proof that the attack failed completely. It proves that the recorded request matched a rule and the configured action was block. The same actor might have sent other requests, an encoded variation might have bypassed the rule, or the HTTP 500 errors might be unrelated application faults.

I would preserve the WAF event and correlate the timestamp, client IP, host, URI, HTTP method, rule or signature, action, request identifier and upstream destination with reverse-proxy, load-balancer, web-server and application logs. I would check whether the supposedly blocked request appears in the backend logs. I would then look for related requests from the same or nearby infrastructure, different encodings, unusual parameters, authentication events, database errors and new files or processes on the server.

The IDS alert is supporting detection evidence; I would verify whether it observed the same flow and whether the sensor was positioned before or after the WAF. If an IPS or firewall logged a deny, I would distinguish an attempted connection from an established session. Packet capture, where authorised and available, can help confirm the request/response sequence, but encrypted traffic requires an approved decryption point to expose HTTP content.

Tier 1 can collect evidence, scope similar activity and escalate suspected bypass or exploitation. WAF-rule changes, emergency blocks, server isolation and application changes should follow delegated authority because poorly tested changes can disrupt legitimate traffic.

### Real-World SOC Scenario

The blocked request never reached the backend, but the same source sent an encoded variation seconds earlier. The reverse proxy forwarded it, the application log recorded a database syntax error, and EDR later observed the web-service account creating an unexpected script in the web directory.

- **Observation:** The WAF blocked one injection-like request while the application returned errors and another security sensor alerted.
- **Hypothesis:** A related request bypassed the WAF and reached vulnerable application code.
- **Confirmed Evidence:** Backend receipt of the encoded request, correlated database error and unexpected server-side file creation confirm that activity passed the control and affected the host.

The verdict is **confirmed WAF bypass with suspected web-application compromise, requiring urgent application and host investigation; the exact data accessed remains unconfirmed until database and application evidence establishes it**.

### What I Would Check as a Tier 1 Analyst

1. WAF time, client IP, host, URI, method, rule, action and request ID.
2. Whether the WAF was blocking, monitoring or learning for that rule.
3. Reverse-proxy, load-balancer and backend access logs.
4. HTTP status, response size, application and database errors.
5. Related requests, encodings, parameters and source infrastructure.
6. Firewall/IPS action and whether a session was established.
7. IDS sensor position, signature and matching flow.
8. Web-server processes, files, service account and EDR evidence.
9. Authentication, administrative changes and possible data access.
10. Authorised blocking, isolation, rule tuning and escalation.

### Relevant Tools / Logs

WAF, firewall and IDS/IPS logs; reverse proxy and load balancer; web-server, application and database audit logs; EDR/XDR; Microsoft Sentinel or Splunk; DNS and network-flow telemetry; Wireshark or approved packet capture; asset and change-management records.

### Key Interview Takeaway

A control action describes what happened to one observed event. I correlate WAF, network, application, database and endpoint evidence before deciding whether the attack was blocked, bypassed or successful.

## Question 238

### Interview Question

Microsoft Sentinel alerts that one public IP generated failed Microsoft Entra ID sign-ins for 35 users in fifteen minutes. Most failures show error code 50126, but one targeted account later records a successful sign-in. How would you determine whether this is password spraying and whether the successful account was compromised?

### Interview-Ready Answer

Password spraying uses one password or a small set of common passwords against many accounts, often at a rate designed to avoid lockouts. That differs from classic brute force, which commonly tries many passwords against one account. MITRE ATT&CK identifies password spraying as T1110.003.

The pattern is consistent with spraying, but the alert alone does not prove that the later success belongs to the same attack. In Sentinel, I would verify ingestion and query `SigninLogs`, where fields such as `TimeGenerated`, `UserPrincipalName`, `IPAddress`, `AppDisplayName`, `ResultType` and `ResultDescription` can support the investigation. Microsoft documents 50126 as invalid username or password and recommends baselining failures because isolated failures are common.

An illustrative hunting query is:

```kusto
SigninLogs
| where TimeGenerated > ago(1h)
| where ResultType == "50126"
| summarize FailedAttempts=count(),
            TargetedUsers=dcount(UserPrincipalName),
            Users=make_set(UserPrincipalName, 25),
            Apps=make_set(AppDisplayName, 10)
    by IPAddress, bin(TimeGenerated, 15m)
| where TargetedUsers >= 10
| order by TargetedUsers desc
```

The threshold is illustrative and must be tuned to the organisation. I would pivot from the source IP to all failures and successes, then compare the successful sign-in's time, application, authentication requirement, MFA result, device, location, Conditional Access result and session context. Location alone is not proof because VPNs, mobile networks and cloud infrastructure can alter it.

I would check the targeted account's normal pattern and post-authentication activity: mailbox access, file access, application consent, MFA or password changes, inbox rules and additional sign-ins. A successful sign-in from the same IP is stronger evidence, but I would still confirm that the event represents completed authentication rather than an interrupted or policy-blocked attempt.

Tier 1 should escalate a likely successful spray immediately and perform or request authorised account/session containment. Password reset, session revocation, source blocking and Conditional Access changes remain governed actions.

### Real-World SOC Scenario

The successful sign-in came from the spraying IP, used an unfamiliar device and accessed Exchange Online. Minutes later, the account registered a new authentication method and created an external forwarding rule. The user denies the activity.

- **Observation:** One source produced invalid-password failures across many identities followed by a success for one target.
- **Hypothesis:** A common password succeeded against the user and the attacker established access.
- **Confirmed Evidence:** Same-source success, unfamiliar device, user denial, new authentication method and forwarding rule confirm account compromise.

The verdict is **confirmed password-spray compromise requiring session and identity containment, mailbox scoping and a hunt for other successful targets**.

### What I Would Check as a Tier 1 Analyst

1. Alert logic, time window, threshold and data coverage.
2. Source IP, ASN or hosting context and organisational prevalence.
3. Number of targeted users, failures and applications.
4. ResultType, ResultDescription and final sign-in status.
5. Successful sign-ins from the source or targeted accounts.
6. MFA, authentication method and Conditional Access results.
7. Device, user agent, location and normal-user baseline.
8. Password, MFA, mailbox, consent and forwarding changes.
9. Subsequent email, file and application activity.
10. Authorised reset, session revocation, blocking and escalation.

### Relevant Tools / Logs

Microsoft Sentinel `SigninLogs` and `AuditLogs`; Entra ID sign-in, audit, risk and Conditional Access evidence where licensed; Defender XDR; Exchange and Microsoft 365 audit; firewall/proxy; Splunk where Entra data is ingested; identity and incident-management records.

### Key Interview Takeaway

Many accounts failing from one source suggests spraying; a success is not automatically compromise. I correlate authentication completion, MFA, device and post-login actions before reaching a verdict.

## Question 239

### Interview Question

A Splunk alert reports failed SSH authentications against many Linux accounts from one source, followed by a successful login to a dormant support account. The raw Linux fields differ across servers. How would you investigate using the Splunk Common Information Model without inventing field names or assuming that the success is malicious?

### Interview-Ready Answer

Splunk's Authentication data model normalises authentication events from different sources into common fields such as `action`, `app`, `src`, `dest`, `user` and `reason` when the relevant add-ons and field mappings are correctly configured. It does not create missing telemetry, and a search is only reliable if the source data is mapped and complete.

I would first validate that the Linux authentication sources are arriving, timestamps are correct and events are tagged for the Authentication data model. I would compare CIM results with representative raw events so that a parsing or mapping error is not mistaken for an attack.

An illustrative CIM-based search is:

```spl
| tstats count as failures
    dc(Authentication.user) as unique_users
    values(Authentication.user) as users
  from datamodel=Authentication.Authentication
  where Authentication.action="failure"
  by _time span=5m Authentication.src Authentication.dest
| where unique_users >= 10
| rename Authentication.src as src Authentication.dest as dest
| sort - unique_users
```

The threshold must be baselined. I would pivot to the successful event for the dormant account and examine its source, destination, authentication method where logged, time, surrounding failures and whether the source is approved. I would correlate Linux process or audit telemetry, EDR, network connections and file-integrity monitoring. I would specifically look for privilege use, new processes, outbound connections, changes to SSH authorised keys, scheduled tasks and other persistence, but only claim those actions when corresponding evidence exists.

A dormant account successfully used after a spray is high risk, yet legitimate automation, a vulnerability scanner or an authorised administrator could create misleading patterns. I would validate the account owner and change record through a trusted route. Tier 1 should preserve raw events and SPL results, escalate confirmed or strongly suspected compromise, and request containment within playbook authority.

### Real-World SOC Scenario

The source is not approved, the support account owner confirms no login, and Linux audit/EDR evidence shows the session starting a shell, downloading a tool and adding an SSH key. Firewall logs show a new outbound connection from the server.

- **Observation:** A multi-user failure pattern was followed by successful dormant-account access.
- **Hypothesis:** Password spraying obtained valid SSH access and established persistence.
- **Confirmed Evidence:** Owner denial, successful session, executed tool, added authorised key and outbound connection confirm compromise.

The verdict is **confirmed Linux account compromise following password spraying, requiring host and account containment, key removal under authority and wider credential scoping**.

### What I Would Check as a Tier 1 Analyst

1. Data-source health, timestamps, sourcetypes and host coverage.
2. CIM tags, field mappings and representative raw events.
3. Failure count, distinct users, source and target hosts.
4. Successful authentication details and account status.
5. Approved scanners, automation and administrative sources.
6. Account owner, access window and change record.
7. Shell, process, privilege and outbound network activity.
8. SSH-key, scheduled-task and service changes.
9. Similar successes or persistence across other servers.
10. Containment, evidence preservation and escalation authority.

### Relevant Tools / Logs

Splunk Enterprise or Splunk Enterprise Security; Authentication CIM data model and raw Linux authentication data; Linux audit or process telemetry where configured; EDR; Wazuh FIM; firewall, DNS and proxy logs; identity, asset, change and ticketing systems.

### Key Interview Takeaway

CIM makes different authentication sources searchable through common fields, but I verify the mapping against raw logs. The successful login becomes compromise only when account and host evidence confirms unauthorised use.

## Question 240

### Interview Question

A Microsoft 365 user reports accepting a consent prompt for an application called `Document Viewer`. Entra audit data records `Consent to application`, and the app requests delegated access to mail and files plus offline access. How would you determine whether this is a legitimate application, consent phishing or an already active cloud compromise?

### Interview-Ready Answer

OAuth application consent allows an application to receive authorised permissions without learning the user's password. Delegated permissions allow the app to act within the permissions granted in the context of a user. `offline_access` can allow the app to maintain access through refresh tokens, subject to platform controls. The exact permissions a user can grant depend on tenant consent policy; some permissions require administrator consent.

Microsoft describes illicit consent attacks in which an attacker registers an application and persuades a user or administrator to grant access to data. A consent event therefore proves that a grant was recorded, not that the application is malicious or that every requested permission was exercised.

I would preserve the alert and audit event, then identify the application and service-principal IDs, publisher and verification status, owners, creation time, redirect domains, consent actor, consent type, exact permissions and whether the result succeeded. I would verify whether the app is approved and whether its publisher, URLs and business owner match the organisation's records.

I would scope every consenting user and administrator and examine the time during which the grant existed. I would correlate Entra `AuditLogs`, sign-ins, Microsoft 365 unified audit data and Defender for Cloud Apps evidence where licensed. I would look for subsequent application access to mail or files, mailbox searches, downloads, forwarding changes, new app credentials, owner changes or additional consent grants.

If the application is malicious, authorised responders may disable the enterprise application or service principal, revoke the consent grant and sessions or refresh tokens, remove malicious credentials and block further consent. Tier 1 should not delete an application or revoke organisation-wide access without delegated authority because legitimate integrations may depend on it. The affected users and application owners must be scoped, and any original phishing route investigated.

### Real-World SOC Scenario

The application was created recently, has no approved business owner and uses a redirect domain unrelated to the claimed vendor. Three users granted consent after receiving the same message. Audit evidence shows the app reading mail and files, and the publisher confirms it is not their product.

- **Observation:** Users granted an unapproved application delegated access to organisational data.
- **Hypothesis:** Consent phishing gave an attacker persistent access through OAuth tokens.
- **Confirmed Evidence:** Vendor denial, unrelated redirect infrastructure, campaign correlation and recorded mail/file access confirm malicious application activity.

The verdict is **confirmed illicit OAuth consent with active data access, requiring urgent grant and token revocation under authority, user and application scoping, phishing investigation and assessment of exposed data**.

### What I Would Check as a Tier 1 Analyst

1. Alert, consent event, actor, time and result.
2. Application ID, service-principal ID and tenant of origin.
3. Publisher verification, owners, creation time and redirect URLs.
4. Exact delegated or application permissions granted.
5. User versus administrator consent and tenant policy.
6. All consenting users and related phishing messages.
7. Application sign-ins and mail/file activity.
8. New app credentials, owners or additional grants.
9. Approved business owner and integration dependencies.
10. Authorised disablement, consent/token revocation and escalation.

### Relevant Tools / Logs

Microsoft Entra `AuditLogs`, sign-in logs and enterprise-app records; Microsoft 365 unified audit; Defender XDR and Defender for Cloud Apps where licensed; Microsoft Sentinel or Splunk; Defender for Office 365; application inventory, change records and data-owner evidence.

### Key Interview Takeaway

An OAuth consent event is not automatically malicious, but it can provide password-independent access. I validate the app, permissions, consent actor and actual resource activity before scoping and containing it.
