# SOC Interview Practice — 2026-09-03

## Question 40

### Interview Question

A cloud-security alert shows the same user accessing Microsoft 365 from two geographically distant locations within an implausibly short time. How would you investigate possible impossible travel or stolen-session-token activity without assuming the account is compromised?

### Interview-Ready Answer

An impossible-travel or atypical-travel alert is an identity anomaly, not automatic proof of compromise. Microsoft Entra Identity Protection describes atypical travel as sign-ins from geographically distant locations where at least one location is unusual for the user, while Microsoft Defender for Cloud Apps can detect user activity from locations that are too far apart to be physically travelled between in the observed time. These detections deliberately suppress some obvious false-positive patterns such as known VPNs and familiar locations.

In a SOC environment, my **observation** would be that the user's identity activity appears to originate from implausibly distant locations. My **hypotheses** could include credential compromise, stolen/replayed session material, a corporate or personal VPN, mobile/cloud egress changing the visible IP location, or another legitimate routing explanation.

I would therefore build a timeline around both sessions: source IPs, timestamps, applications/resources, device or browser information where available, authentication method, MFA context, session characteristics and what the user did afterwards. I would ask whether the user was legitimately travelling or using an approved VPN and compare the activity with the user's normal baseline.

I would also consider token theft. Microsoft notes that stolen sign-in session tokens can be replayed to access resources without going through the normal authentication process again, and MITRE ATT&CK maps the use of stolen web-session cookies to T1550.004. Token theft can therefore bypass some MFA protections because the attacker is reusing an already authenticated session. Token Protection in Microsoft Entra Conditional Access is designed to reduce replay risk by cryptographically binding supported sign-in session tokens to the device where they were issued.

As Tier 1, I would investigate and escalate suspected account/session compromise. Revoking sessions, marking a user compromised, changing Conditional Access or Token Protection policy, or disabling an account should follow the organisation's authorised identity-response process.

### Real-World SOC Scenario

A finance user normally works in London. Defender for Cloud Apps reports activity associated with London and a distant overseas location within minutes. The overseas session then downloads an unusually large number of SharePoint files.

I would first confirm whether the user is travelling or using a sanctioned VPN and check whether the IPs belong to known corporate/cloud egress infrastructure. I would compare the two sessions' device/browser details, authentication context and applications accessed.

If the user confirms they were only in London, the overseas activity is from an unfamiliar device/session, there is no corresponding legitimate authentication event and the session performs abnormal file access, the stolen-session-token hypothesis becomes much stronger. I would escalate with the identity, cloud-app and data-access evidence and follow the approved session/account containment playbook.

### What I Would Check as a Tier 1 Analyst

- User account and privilege level
- Alert/detection type: atypical travel or impossible travel
- Both timestamps and source IP addresses
- IP ownership and whether either IP belongs to sanctioned VPN/corporate/cloud egress
- Location as supporting context rather than definitive proof
- Application/resource accessed in each session
- Device/browser/client information where available
- Authentication method, MFA context and preceding sign-in events
- Whether the user confirms travel or VPN use
- Whether the same session appears from different device/browser fingerprints
- Post-authentication mailbox, SharePoint, OneDrive or other cloud activity
- Unusual downloads, sharing, OAuth or mailbox changes
- EDR/browser evidence on the legitimate user's endpoint where available
- Similar anomalies affecting other users
- Playbook authority for session revocation, user-risk action, account disablement or credential reset

### Tools / Logs

Microsoft Entra sign-in and risk detections; Microsoft Defender for Cloud Apps anomaly alerts and activity logs; Microsoft Sentinel; Microsoft Defender XDR; Microsoft 365 audit logs; Defender for Endpoint/browser telemetry where available; Conditional Access/Token Protection configuration context; incident-management records.

### Interview Takeaway

Impossible travel is an anomaly that tells me the user's activity appears to come from locations that do not make sense within the time available. I would validate VPN/travel and device context, investigate authentication and post-login behaviour, and consider stolen-session-token replay when activity appears without a normal reauthentication pattern. The alert is the observation; compromise is the hypothesis; correlated identity and cloud activity provides the evidence.

## Question 41

### Interview Question

What is Automated Investigation and Response (AIR) in Microsoft Defender for Endpoint, and how should a Tier 1 SOC analyst work with it now that Microsoft changed the Defender AIR experience on September 1, 2026?

### Interview-Ready Answer

Automated Investigation and Response, or AIR, is Microsoft Defender for Endpoint capability that automatically examines security alerts, expands the investigation to related entities and can perform or recommend remediation actions depending on the organisation's automation settings.

A current interview answer needs to reflect Microsoft's September 1, 2026 product change. Microsoft states that Defender for Endpoint AIR no longer runs as a separate investigation experience and can no longer be manually triggered from Defender for Endpoint alerts/remediations. Its detection and response capabilities are already included in the Microsoft Defender antivirus protection stack and run automatically. For an on-demand Defender for Endpoint investigation, Microsoft currently directs analysts to run a full antivirus scan as needed.

This change does **not** mean analysts stop reviewing automated response. Microsoft Defender XDR's Action Center still tracks pending and completed remediation actions. Depending on automation level and configuration, some actions can be performed automatically while others can require approval. Microsoft also notes that this September 2026 change applies to Defender for Endpoint; AIR capabilities for Defender for Office 365 remain available.

In a SOC environment, I would use AIR as supporting automation rather than treating its verdict as the entire investigation. I would review the original alert, device/user/process evidence, related incidents, what automated actions were taken or are pending, and whether the observed behaviour is consistent with the automation's conclusion. As Tier 1, I would approve/reject remediation only if my role and playbook authorise that decision; otherwise I would document and escalate.

### Real-World SOC Scenario

Defender for Endpoint alerts on a suspicious executable that spawned PowerShell and contacted an external domain. The Defender protection stack automatically investigates and quarantines one file, while another remediation item appears in the Action Center requiring review.

I would validate the device, user, process tree, command-line context, file hash/signature/prevalence and network activity. I would check exactly what Defender already remediated and whether any action remains pending. I would also determine whether the same indicators or behaviour appear on other devices.

If the automated evidence is consistent with malicious execution and the playbook authorises Tier 1 approval of the pending remediation, I could follow that process. If the device is business-critical, the evidence is ambiguous or the action would be disruptive, I would escalate rather than blindly approve automation.

### What I Would Check as a Tier 1 Analyst

- Original Defender alert and incident context
- Device, user and alert timeframe
- Process tree and command line
- File path, hash, signer and prevalence
- DNS/network connections and related domains/IPs
- Files, registry or persistence changes
- Other related Defender alerts/incidents
- Automated investigation findings that are available
- Actions already completed automatically
- Action Center pending actions and their source
- Automation level/device-group configuration context where relevant
- Whether Defender Antivirus is available/configured as required for AIR functionality
- Similar evidence on other endpoints
- Business criticality of the affected device
- Tier 1 authority to approve/reject remediation or isolate a device
- Handoff/escalation details if additional response is required

### Tools / Logs

Microsoft Defender for Endpoint; Microsoft Defender XDR incident/alert evidence; Action Center; Microsoft Defender Antivirus; device timeline/process evidence; Microsoft Sentinel/Splunk/Wazuh where integrated; DNS/proxy/firewall telemetry; Windows/Sysmon evidence where deployed; incident-management records.

### Interview Takeaway

AIR automatically investigates and responds to Defender for Endpoint threats, but as of September 1, 2026 it no longer exists as a separately launched Defender for Endpoint investigation experience. The protection stack runs those capabilities automatically, and the Action Center tracks remediation. I would still validate the underlying evidence and only approve or perform response actions within my authorised Tier 1 role.

## Question 42

### Interview Question

After a security incident has been contained and recovered, what should happen next, and what does a useful post-incident review or lessons-learned process look like from a SOC perspective?

### Interview-Ready Answer

A security incident should not simply be closed when systems are restored. The organisation should capture what was learned and use those lessons to improve cybersecurity risk management, detection, response and recovery.

NIST SP 800-61 Rev. 3 is the current NIST incident-response guidance. Its lifecycle is aligned with CSF 2.0 and explicitly places **continuous improvement** around the incident-response process. NIST explains that lessons learned from activities across the CSF Functions are fed into the Identify-Improvement category, then analysed, prioritised and used to improve all Functions. This means lessons learned are not just a final meeting after a major breach; they are part of an ongoing improvement loop.

From a SOC perspective, I would contribute accurate evidence: the incident timeline, initial detection, what was observed versus assumed, root/initial-access information where known, scope, containment and recovery actions, evidence gaps, alerts that worked, alerts that failed or were noisy, communication/escalation issues and measurable impact. I would avoid claiming root cause if the evidence does not support one.

The output should produce tracked improvements rather than only a narrative. Examples include updating a playbook, tuning or adding a SIEM/EDR detection, improving logging coverage or retention, changing escalation criteria, correcting asset/owner data, improving an identity/network control, updating training, or assigning a vulnerability/remediation action to the appropriate team.

As Tier 1, I might not own these remediation projects, but I can provide the case evidence, identify investigation friction and make practical recommendations through the incident-review process.

### Real-World SOC Scenario

A phishing incident led to credential compromise and suspicious Microsoft 365 access. The account was contained and access restored.

During the review, the team finds that the phishing alert existed but the first analyst could not quickly correlate email, identity and endpoint evidence because the playbook did not specify the required pivots. The team also discovers that a relevant cloud audit source was not retained long enough to answer part of the investigation.

A useful post-incident outcome would therefore include an updated phishing/BEC playbook, a clearer identity-correlation step, improved log retention/coverage, a detection or analytic improvement, and assigned owners/dates for the changes. The incident is not truly improving security unless those actions are tracked to completion.

### What I Would Check as a Tier 1 Analyst

- Final incident classification and evidence-supported scope
- Reliable timeline of detection, investigation, containment and recovery
- Initial access/root cause where genuinely established
- What telemetry or alerts detected the activity
- Which detections were late, noisy or missing
- Evidence/logging gaps and retention issues
- False assumptions or investigation dead ends
- Escalation and communication effectiveness
- Time to detect, triage, contain and recover where measured
- Business/technical impact
- Whether playbooks matched the real investigation
- Needed detection/rule/hunt improvements
- Needed logging, identity, endpoint, email, network or vulnerability-control improvements
- Training/documentation gaps
- Named owners and target dates for improvement actions
- Verification that remediation/improvement actions are actually completed

### Tools / Logs

Incident/ticketing platform; Microsoft Sentinel/Splunk/Wazuh case history; Defender XDR/EDR incident evidence; Microsoft Entra and Microsoft 365 audit evidence; firewall/DNS/proxy/email logs; change-management records; detection-engineering backlog; vulnerability-management and asset-management systems.

### Interview Takeaway

After recovery, I would help turn the incident evidence into measurable improvements. NIST SP 800-61 Rev. 3 treats lessons learned as continuous improvement: analyse what happened, what worked, what failed or was missing, prioritise corrective actions, assign owners and verify the changes are completed. A post-incident review should improve the next investigation, not just document the last one.
