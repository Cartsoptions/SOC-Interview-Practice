# SOC Interview Practice — 2026-09-25

## Question 89

### Interview Question

What is the difference between an IDS and an IPS, and how would a Tier 1 SOC analyst use their alerts during an investigation?

### Interview-Ready Answer

An Intrusion Detection System (IDS) monitors and analyses network or system activity for signs of suspicious or unauthorised behaviour and generates alerts. An Intrusion Prevention System (IPS) also detects suspicious activity but can attempt to stop it. NIST describes an IDS as software/security service that monitors and analyses events for signs of possible intrusion, while an IPS can detect intrusive activity and attempt to stop it before it reaches its target.

Operationally, the important distinction is not simply “IDS alerts, IPS blocks.” Product design and deployment mode matter. In a SOC environment I would verify whether the control was operating in detection-only or prevention mode, what signature/rule fired, which source and destination were involved, whether the traffic was allowed, blocked or reset, and whether the target endpoint shows evidence that the activity succeeded.

Observation: an IDS/IPS rule matched traffic. Hypotheses: genuine attack, benign activity matching a signature, scanning/testing, or a false positive. Confirmed compromise requires corroborating evidence; an alert alone is not proof that exploitation succeeded.

### Real-World SOC Scenario

An IPS alerts on an exploit attempt against an internal web server and reports that the traffic was blocked. I would not close the incident solely because the control says “blocked.” I would verify the action, identify the source/destination and signature, check whether the destination was actually vulnerable, and correlate web-server, WAF, EDR and authentication telemetry for follow-on activity. If no malicious follow-on activity exists and the prevention action is confirmed, the incident may be contained at that control; if suspicious process creation or authentication follows, I would escalate.

### What I Would Check as a Tier 1 Analyst

- IDS versus IPS and actual deployment mode
- Alert/signature/rule and severity
- Source/destination IPs and ports
- Protocol and timestamp
- Allowed/blocked/reset action where the product provides it
- Target asset criticality and vulnerability context
- Repeated attempts or other targets
- WAF/firewall/server/EDR evidence
- Whether exploitation or follow-on activity occurred
- Approved scanner/penetration-test context
- Escalation/containment authority

### Tools / Logs

IDS/IPS telemetry, firewall, WAF, packet capture where authorised, Microsoft Sentinel, Splunk, Wazuh, EDR, web/server logs and vulnerability-management data.

### Interview Takeaway

“IDS primarily detects and alerts; IPS can also attempt prevention. As Tier 1, I would verify what the control actually observed and did, then correlate the target’s telemetry before deciding whether the attempt was blocked, benign or resulted in compromise.”

### Verification Notes

- NIST CSRC IDS glossary: https://csrc.nist.gov/glossary/term/intrusion_detection_system
- NIST CSRC IPS glossary: https://csrc.nist.gov/glossary/term/intrusion_prevention_system
- NIST CSRC IDPS glossary: https://csrc.nist.gov/glossary/term/intrusion_detection_and_prevention_system

## Question 90

### Interview Question

Windows Security Event ID 1102 appears on a critical server. What does it mean, why is it important, and how would you investigate it without automatically declaring malicious log clearing?

### Interview-Ready Answer

Windows Security Event ID 1102 means the Security audit log was cleared. Microsoft recommends monitoring and investigating this event because the Security log normally should not need to be manually cleared. The event includes subject/account information for the account associated with clearing the log, plus a Logon ID that can help correlate to recent logon events such as 4624.

I would treat 1102 as a high-value signal, but not as automatic proof of attacker defence evasion. Legitimate administration, troubleshooting, imaging or maintenance could potentially explain it. I would verify the account, Logon ID, host, timing, change records and surrounding endpoint/process telemetry. I would also determine whether central SIEM/EDR copies of earlier events remain available even though the local Security log was cleared.

Observation: the local Windows Security audit log was cleared. Hypotheses: authorised administration/maintenance or deliberate evidence removal/defence evasion. Confirmed malicious log clearing requires unauthorised context and supporting evidence.

### Real-World SOC Scenario

A production server generates Event 1102 at 02:15. The account is privileged and there is no approved maintenance record. EDR shows an unusual process lineage immediately before the clear event, followed by suspicious remote activity. I would correlate the 1102 Logon ID with authentication evidence, preserve centrally retained telemetry, examine EDR/process/network activity before and after the clear, and escalate because the combination suggests possible defence evasion rather than routine maintenance.

### What I Would Check as a Tier 1 Analyst

- Host and timestamp
- Subject account/SID/domain
- Logon ID and correlated logon events
- Whether the account was authorised to perform the action
- Approved maintenance/change records
- EDR process and command-line telemetry around the time
- Remote administration/RDP/PowerShell evidence
- Central SIEM copies of pre-clear events
- Other log/telemetry gaps
- Similar events on other hosts
- Subsequent persistence, credential or lateral-movement activity
- Escalation/containment authority

### Tools / Logs

Windows Security Event 1102 and correlated authentication/process events, Microsoft Sentinel, Splunk, Wazuh, Defender for Endpoint or another EDR, Sysmon where configured, identity and network telemetry, and change-management records.

### Interview Takeaway

“1102 means the Windows Security audit log was cleared. I would treat it as important but verify who did it, whether it was authorised, what happened immediately before and after it, and preserve/correlate centrally collected evidence before concluding defence evasion.”

### Verification Notes

- Microsoft Learn Event 1102 reference: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-1102

## Question 91

### Interview Question

An interviewer shows you this Microsoft Defender advanced-hunting query. Explain what it is trying to find, what evidence it returns, and why the result is not automatically malicious:

```kusto
union DeviceProcessEvents, DeviceNetworkEvents
| where Timestamp > ago(7d)
| where FileName in~ ("powershell.exe", "powershell_ise.exe")
| where ProcessCommandLine has_any("WebClient", "DownloadFile", "DownloadData", "DownloadString", "WebRequest", "Shellcode", "http", "https")
| project Timestamp, DeviceName, InitiatingProcessFileName, InitiatingProcessCommandLine, FileName, ProcessCommandLine, RemoteIP, RemoteUrl, RemotePort, RemoteIPType
| top 100 by Timestamp
```

### Interview-Ready Answer

This is based on Microsoft’s own Defender XDR advanced-hunting example for PowerShell activity that could involve a download. It unions process and network event data, limits the search to the previous seven days, pivots on PowerShell executables, looks for command-line strings associated with web/download behaviour, projects investigation-relevant columns, and returns up to 100 rows ordered by Timestamp.

I would be careful with the conclusion. The query is a hunting lead, not a malware verdict. Administrators and legitimate automation can use PowerShell and web requests. Also, because it unions two tables, not every projected field is necessarily populated on every returned row. I would inspect the actual process command line, initiating process, user/device, destination, file activity and subsequent behaviour.

Observation: PowerShell-related process/network records match one or more strings in the hunting query. Hypothesis: legitimate administration/automation or suspicious PowerShell download/execution. Confirmed malicious activity requires contextual and correlated evidence.

### Real-World SOC Scenario

The query returns PowerShell activity on a finance endpoint. The command line references an HTTPS URL, the parent is an Office application, and seconds later a new executable appears in the user profile and launches. That chain is substantially more suspicious than PowerShell alone. I would correlate the URL/domain, file hash/signature, process tree, file creation, persistence and further network activity, then escalate if the evidence supports compromise.

### What I Would Check as a Tier 1 Analyst

- Device/user and timestamp
- Full PowerShell command line
- Initiating/parent process and command line
- Whether PowerShell use is expected for the user/device
- Remote URL/IP/port where populated
- File creation/download evidence
- Hash/signature/prevalence
- Child processes and persistence
- EDR alert context
- DNS/proxy/firewall telemetry
- Similar activity across other hosts
- Approved scripts/automation

### Tools / Logs

Microsoft Defender XDR advanced hunting, `DeviceProcessEvents`, `DeviceNetworkEvents`, `DeviceFileEvents` where useful, Microsoft Sentinel, PowerShell/Windows telemetry, DNS/proxy/firewall logs and EDR.

### Interview Takeaway

“I would explain the query as a hunt for PowerShell activity that could involve downloading, not as proof of malware. I would use the result as a pivot into process lineage, destination, file creation and follow-on behaviour.”

### Verification Notes

- Microsoft Defender XDR advanced-hunting query-language example: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-query-language
- Microsoft Defender XDR DeviceEvents/schema guidance: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceevents-table

## Question 92

### Interview Question

You are handling a suspected endpoint compromise. EDR shows malicious execution, the Windows Security log was then cleared, and the host is still communicating with a suspicious external destination. As Tier 1, how would you prioritise triage, evidence preservation, containment and escalation under current incident-response guidance?

### Interview-Ready Answer

I would treat this as an active, high-priority incident because multiple independent signals indicate continuing risk: malicious execution, loss of local audit history and ongoing suspicious communication. My first responsibility is to follow the organisation’s incident-response playbook and escalation matrix, rapidly establish scope and preserve available evidence while ensuring authorised containment is initiated.

Current NIST SP 800-61 Revision 3, finalised in April 2025 and superseding Revision 2, integrates incident response across the six NIST CSF 2.0 Functions rather than presenting the old lifecycle as the sole organising model. For an interview I would therefore avoid claiming that NIST r3 requires a rigid Preparation → Detection/Analysis → Containment → Eradication → Recovery sequence. Operational containment, investigation and evidence preservation can overlap when an incident is active.

As Tier 1, if endpoint isolation is within my authority and the playbook calls for it, I would isolate through the approved EDR mechanism while preserving management/EDR visibility as designed by that product. If isolation requires L2/incident commander approval, I would escalate immediately with the evidence and request containment rather than exceeding my authority. I would preserve central SIEM/EDR telemetry, document timestamps and indicators, scope related identities/hosts, and avoid destructive actions such as deleting files or wiping the endpoint before evidence and response requirements are considered.

Observation: malicious execution, Security-log clearing and ongoing suspicious external communication are present. Hypothesis: active endpoint compromise with possible defence evasion/C2. Confirmed evidence depends on the validated malicious execution and destination/context; the combined signals justify urgent escalation even while full scope is still being established.

### Real-World SOC Scenario

A workstation executes a file confirmed malicious by internal analysis/EDR. Minutes later Event 1102 records Security-log clearing, and EDR continues to show connections to infrastructure confirmed malicious by organisational threat intelligence. I would document the timeline, preserve SIEM/EDR evidence, check affected user/account and nearby hosts, escalate as an active incident and initiate/request approved network isolation. After containment, the response team can determine eradication and recovery actions based on scope, root cause and organisational procedures.

### What I Would Check as a Tier 1 Analyst

- Alert severity/confidence and confirmed malicious evidence
- Device/user and business criticality
- Process tree, file/hash/signature and execution timeline
- Event 1102 account/Logon ID and surrounding activity
- Ongoing network destinations and connection status
- Identity/authentication activity
- Other affected endpoints/users
- Central SIEM/EDR evidence retained before the local clear
- Whether isolation is authorised for Tier 1
- Incident severity/escalation matrix
- Evidence/timeline documentation
- Signs of lateral movement, persistence or credential access
- Business/operational impact of containment

### Tools / Logs

Defender for Endpoint or another EDR, Microsoft Sentinel, Splunk/Wazuh, Windows Security logs, Sysmon where configured, identity, DNS/proxy/firewall telemetry, threat intelligence and the organisation’s incident/ticketing platform.

### Interview Takeaway

“With multiple signals of active compromise, I would not wait for perfect certainty before escalating. I would preserve centrally available evidence, establish immediate scope, and initiate or request containment according to my authority and the playbook, while keeping investigation and business impact in view.”

### Verification Notes

- NIST announcement/final SP 800-61r3, 3 April 2025: https://www.nist.gov/news-events/news/2025/04/nist-revises-sp-800-61-incident-response-recommendations-and-considerations
- Microsoft Learn Event 1102: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-1102
