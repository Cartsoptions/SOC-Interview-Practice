# SOC Interview Practice — 2026-10-28

**Curriculum:** Questions 165–168 | Threat-intelligence validation, Pyramid of Pain, Defender XDR network hunting, and command-and-control incident response

## Question 165

### Interview Question

Your SIEM alerts because twelve endpoints connected to an external IP address contained in a commercial threat-intelligence feed. What does the intelligence match tell you, and how would you decide whether this is a genuine incident?

### Interview-Ready Answer

Cyber threat intelligence is analysed information intended to support a security decision; a feed is one possible source of indicators. An IP match tells me that current telemetry shares an observable with the supplied intelligence. It does not by itself prove that the endpoints are compromised, that the address is still malicious, or that every service hosted behind it is hostile.

In a SOC environment, I would first validate the feed source, confidence, first-seen and last-seen dates, indicator type, reported behaviour, expiry policy and any traffic-light or handling restriction. I would then confirm the raw network events: which devices connected, which process initiated each connection, the direction, destination port, protocol, frequency, bytes transferred and whether the traffic succeeded. Shared hosting, CDNs, VPNs, proxies, security products and reassigned cloud addresses can create misleading IP-only matches.

I would pivot from the IP to stronger context: associated domains, TLS or HTTP artefacts where lawfully available, process ancestry, file hashes, user activity, DNS resolutions and other alerts. If an unauthorised process on several endpoints repeatedly contacts infrastructure that the intelligence specifically associates with command and control, and endpoint evidence shows malicious execution, I would escalate as a confirmed incident. Blocking the IP may be an authorised containment step, but it is not a substitute for finding the process, persistence and initial-access path.

### Real-World SOC Scenario

The twelve connections initially appear serious, but ten devices are approved security scanners using a vendor service hosted on the address. Two finance laptops show a previously unseen executable in a user-writable directory repeatedly contacting the address every five minutes.

- **Observation:** Twelve endpoints matched a threat-intelligence IP; ten have an approved explanation, while two show unusual process-linked beaconing.
- **Hypothesis:** The two laptops may be compromised and using the address for command and control.
- **Confirmed evidence:** EDR confirms unauthorised execution and repeated network activity from the same process; the users and software owner confirm the executable is not approved. The feed match supports context but is not the sole proof.

The verdict is **high-severity true positive for the two laptops; benign true positive for the approved scanner traffic**.

### What I Would Check as a Tier 1 Analyst

1. Record the indicator, intelligence source, confidence, context, handling restrictions and freshness.
2. Confirm the SIEM field mapping and open the raw network events behind the alert.
3. Identify affected devices, users, initiating processes, ports, protocols, frequency and connection result.
4. Check IP ownership and whether a CDN, cloud host, proxy, VPN or approved service explains the traffic.
5. Pivot to domains, DNS, process trees, files, hashes, command lines, persistence and related alerts.
6. Compare the behaviour with the asset role, approved software and normal baseline.
7. Invoke or request authorised isolation or indicator blocking when the evidence justifies containment.
8. Escalate the affected assets, evidence, containment status, false-positive scope and remaining gaps.

### Relevant Tools / Logs

Microsoft Sentinel or Splunk, Defender for Endpoint or another EDR, firewall/proxy/DNS telemetry, threat-intelligence platform, passive DNS and registration context where authorised, asset inventory, software allow-list and incident-management records.

### Key Interview Takeaway

A threat-intelligence match is a lead, not a verdict. I would validate the source and freshness, identify the process and assets behind the traffic, remove legitimate shared-infrastructure explanations and confirm compromise with local behavioural evidence.

## Question 166

### Interview Question

During an investigation, the attacker changes the malware hash, IP address and domain, but each variant still launches from a user-writable directory, creates a scheduled task and beacons over HTTPS. How would the Pyramid of Pain influence your detection and response?

### Interview-Ready Answer

The Pyramid of Pain explains that indicators impose different costs on an adversary when defenders detect and deny them. Hashes sit low because a small file change creates a new hash. IP addresses and domains can also be replaced. Network and host artefacts, tools and especially tactics, techniques and procedures are generally more expensive for an adversary to change.

I would still use the hashes, IPs and domains for immediate scoping and blocking because they are precise and operationally useful while current. I would not build the long-term defence around them alone. The repeated behaviour is more durable: execution from a user-writable path, scheduled-task persistence and non-browser HTTPS communication from the same process chain.

I would preserve the exact indicators and search the estate for them, then give detection engineering a behaviour-focused package: parent/child process relationships, task characteristics, paths, command-line patterns, network cadence and the relevant MITRE ATT&CK techniques. Any rule would be tested against legitimate administration and software-updater behaviour before production use.

The Pyramid is not a severity score and does not mean every higher-level behaviour is malicious. It helps choose detections that remain useful when the attacker rotates infrastructure.

### Real-World SOC Scenario

The first sample is blocked by hash, but a second sample with a new hash runs the next day. Both create similarly named tasks that launch code from the user's profile and make regular HTTPS connections from a non-browser process.

- **Observation:** Static indicators change while the host and network behaviour persists.
- **Hypothesis:** The variants belong to the same intrusion pattern or tool family.
- **Confirmed evidence:** Endpoint and network telemetry confirm the same unauthorised execution, persistence and beaconing sequence across both variants. Attribution to a named actor remains unconfirmed.

The verdict is **confirmed recurring malicious behaviour requiring both immediate IOC containment and durable behaviour-based detection**.

### What I Would Check as a Tier 1 Analyst

1. Preserve all hashes, domains, addresses, file paths, task details and timestamps.
2. Hunt current indicators across endpoint, DNS, proxy and firewall data.
3. Compare parent/child process chains, command lines, task configuration and execution paths.
4. Measure network cadence, destination changes, user agents and protocol characteristics where visible.
5. Map only evidenced behaviours to ATT&CK, such as PowerShell T1059.001, Scheduled Task T1053.005 or Web Protocols T1071.001.
6. Contain affected devices and indicators according to the playbook.
7. Provide the repeated behaviour to detection engineering for testing, tuning and coverage review.
8. Keep incident severity and actor attribution separate from the Pyramid's indicator-cost concept.

### Relevant Tools / Logs

Defender for Endpoint/Defender XDR, Microsoft Sentinel or Splunk, Windows process and task telemetry, Sysmon where configured, Wazuh, firewall/proxy/DNS logs, threat-intelligence platform, malware-analysis results and detection-engineering records.

### Key Interview Takeaway

I would use hashes, IPs and domains for fast scoping, but build more durable detection around the attacker's repeated host, network and ATT&CK-mapped behaviour. The higher levels of the Pyramid generally cost the adversary more to change.

## Question 167

### Interview Question

You receive a suspected command-and-control domain and IP address. Write a Microsoft Defender XDR advanced-hunting query to identify matching endpoint connections and explain what its output can and cannot prove.

### Interview-Ready Answer

Assuming Microsoft Defender for Endpoint is deployed and populating `DeviceNetworkEvents`, I would use a bounded query such as:

```kusto
let lookback = 24h;
let suspectedDomain = "c2-example.example";
let suspectedIP = "203.0.113.50";
DeviceNetworkEvents
| where Timestamp >= ago(lookback)
| where RemoteUrl =~ suspectedDomain or RemoteIP == suspectedIP
| project Timestamp,
          DeviceName,
          ActionType,
          RemoteUrl,
          RemoteIP,
          RemotePort,
          Protocol,
          InitiatingProcessFileName,
          InitiatingProcessCommandLine,
          InitiatingProcessSHA1,
          InitiatingProcessAccountName,
          ReportId
| order by Timestamp asc
```

Microsoft documents `DeviceNetworkEvents` as network-connection and related endpoint telemetry and documents the projected fields. I use `InitiatingProcessSHA1` because Microsoft notes that SHA-256 fields are not always populated in this table. The `.example` domain and `203.0.113.0/24` documentation address are simulated and must be replaced with the authorised investigation indicators.

The output can establish that Defender recorded matching network-related events and can identify devices and initiating-process context. It does not, by itself, prove successful command and control. `RemoteUrl` may contain a URL or FQDN; an IP may be shared or reassigned; an event may represent a blocked attempt; and absence of results may reflect retention, sensor, parsing or telemetry gaps.

I would inspect `ActionType` using the tenant's in-portal schema, open the device timeline and correlate process creation, DNS/proxy/firewall evidence and the intelligence report. I would widen the hunt to related domains, certificates, paths, hashes and behaviour only when supported by evidence.

### Real-World SOC Scenario

The query returns repeated events from one laptop. `powershell.exe`, launched by a document process, is the initiating process; the same device then creates a scheduled task that launches code from the user's profile.

- **Observation:** Defender recorded repeated connections to the supplied indicator from a suspicious process chain.
- **Hypothesis:** The endpoint is attempting or maintaining command-and-control communication.
- **Confirmed evidence:** User denial, unauthorised PowerShell execution, persistence and correlated network telemetry confirm compromise. Whether every connection exchanged commands requires further network or malware evidence.

The verdict is **high-severity true positive — confirmed endpoint compromise with activity consistent with web-protocol command and control**.

### What I Would Check as a Tier 1 Analyst

1. Verify the indicator, time range, licence, retention and Defender for Endpoint sensor coverage.
2. Review `ActionType` and the raw event in the device timeline rather than assuming connection success.
3. Validate device identity, user, initiating process, command line, hash, port and protocol.
4. Correlate `DeviceProcessEvents`, DNS, proxy, firewall and other EDR alerts.
5. Check the domain/IP's current ownership, intelligence context and possible shared-service use.
6. Hunt related devices, users, hashes, paths, scheduled tasks and infrastructure.
7. Isolate or request isolation under the playbook when compromise is corroborated.
8. Document telemetry limitations and the strongest conclusion the evidence supports.

### Relevant Tools / Logs

Microsoft Defender XDR advanced hunting, `DeviceNetworkEvents`, `DeviceProcessEvents`, Defender for Endpoint device timeline, Microsoft Sentinel where integrated, DNS/proxy/firewall telemetry, threat-intelligence platform and asset inventory.

### Key Interview Takeaway

The query finds matching Defender network telemetry and the initiating process; it does not automatically prove C2. I would validate the event action, process chain, threat-intelligence context and endpoint impact before assigning the verdict.

## Question 168

### Interview Question

A finance user opens an unexpected attachment. Defender then records a document process launching PowerShell, PowerShell contacting a rare HTTPS domain every five minutes, and a new scheduled task launching code from the user's profile. How would you use the Cyber Kill Chain, MITRE ATT&CK and NIST incident-response guidance without delaying containment?

### Interview-Ready Answer

I would treat the correlated sequence as a high-severity suspected compromise and begin the approved response immediately. Framework mapping helps organise evidence and scope the investigation; it must not delay containment.

The Cyber Kill Chain provides campaign-stage context. Based only on the available evidence, I can support Delivery through the attachment, execution/exploitation when the attachment causes unauthorised PowerShell execution, Installation or persistence through the scheduled task, and Command and Control through the repeated HTTPS activity. I would not claim Actions on Objectives, such as data theft, without evidence of collection or exfiltration. Reconnaissance and Weaponization may have occurred outside our visibility.

MITRE ATT&CK provides more granular behaviour labels: Spearphishing Attachment T1566.001 for the delivery method, PowerShell T1059.001 for execution, Scheduled Task T1053.005 for persistence/execution, and Web Protocols T1071.001 when evidence supports HTTP/S command-and-control use. ATT&CK mappings describe observed behaviour; they do not identify the attacker or determine the incident verdict.

My Tier 1 priorities would be to preserve the alert and timelines, isolate or request isolation of the endpoint, restrict malicious infrastructure according to policy, identify the affected account and session, and scope the attachment, hash, process chain, task and destinations across the estate. I would escalate immediately to Tier 2/IR with a UTC-normalised timeline, evidence, containment status and uncertainties.

NIST SP 800-61 Revision 3 integrates incident response with CSF 2.0 and places incident-response activity across Detect, Respond and Recover, supported by preparation and continuous improvement. In practice, after containment and specialist-led eradication/recovery, the team should feed the observed behaviours into detection, email controls, hardening and playbook improvements.

### Real-World SOC Scenario

The user confirms opening the attachment but did not run an approved script or create the task. Two additional endpoints received the same message; one has the same process and network sequence.

- **Observation:** Phishing delivery is followed by unauthorised script execution, persistence and periodic outbound communication on two endpoints.
- **Hypothesis:** The attachment established access and the scheduled task maintains malware that communicates over HTTPS.
- **Confirmed evidence:** Email, endpoint and network telemetry plus user confirmation establish unauthorised execution, persistence and repeated communications. Data theft and actor attribution remain unconfirmed.

The verdict is **critical true positive — confirmed multi-endpoint compromise with persistence and activity consistent with command and control**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the original message, attachment metadata, alert evidence and endpoint timelines.
2. Normalise timestamps and link delivery, user execution, process creation, persistence and network events.
3. Validate users, devices, process ancestry, command lines, hashes, paths, task details and destinations.
4. Invoke or request endpoint isolation, indicator restriction and account/session containment under the playbook.
5. Scope every recipient and search the estate for the same attachment, behaviour, task, paths and infrastructure.
6. Investigate credential access, privilege escalation, lateral movement, collection and exfiltration as separate evidence questions.
7. Map only confirmed behaviours to ATT&CK and supported stages to the Cyber Kill Chain.
8. Escalate the timeline, affected assets, containment actions, business impact and evidence gaps to Tier 2/IR.
9. Support specialist-led eradication and trusted recovery without deleting evidence or improvising production changes.
10. Feed lessons learned into email controls, EDR detections, threat intelligence, user guidance and the incident playbook.

### Relevant Tools / Logs

Defender for Office 365, Defender for Endpoint and Defender XDR, Microsoft Sentinel or Splunk, Entra identity logs, Windows process/task telemetry, Sysmon where configured, Wazuh, DNS/proxy/firewall logs, threat-intelligence platform, email trace and incident-management records.

### Key Interview Takeaway

I would use the Kill Chain to understand attack progression, ATT&CK to describe specific behaviours and NIST to structure coordinated response and improvement. None of those frameworks replaces evidence, playbook authority or rapid containment.
