# SOC Interview Practice — 2026-09-28

## Question 93

### Interview Question

What are CVE and CVSS, and why should a SOC or vulnerability team not simply patch vulnerabilities in descending CVSS order?

### Interview-Ready Answer

CVE is a standardized identifier for a publicly disclosed cybersecurity vulnerability. CVSS is a scoring framework for describing vulnerability severity. The important operational distinction is that a CVSS Base score measures technical severity, not an organisation's complete risk. FIRST's CVSS v4.0 guidance explicitly says the Base score should not be used alone to assess risk and recommends adding threat and environmental context.

In a SOC or vulnerability-management environment, I would combine severity with evidence of exploitation, whether the vulnerable product is actually present and exposed, asset criticality, business impact, compensating controls and remediation availability. CISA's Known Exploited Vulnerabilities (KEV) Catalog is particularly important because it identifies vulnerabilities known to be exploited in the wild. NIST's NVD also expanded in 2026 to include SSVC information and continues to include KEV-related enrichment.

Observation: a scanner or inventory identifies a CVE with a severity score. Hypothesis: the vulnerability may create material risk in our environment. Confirmed prioritisation requires environment and threat context, not the Base score alone.

### Real-World SOC Scenario

A scanner reports two vulnerabilities. Vulnerability A has CVSS 9.8 on an isolated internal test asset with strong compensating controls. Vulnerability B has a lower Base score but is on an internet-facing production system and appears in CISA KEV. I would not automatically prioritise A solely because 9.8 is numerically higher. I would validate exposure, affected versions, exploitation status, asset criticality and available mitigations, then follow the organisation's risk-based remediation process. A KEV-listed internet-facing vulnerability would normally demand urgent attention because there is evidence of real-world exploitation, but the final action still follows organisational risk and change procedures.

### What I Would Check as a Tier 1 Analyst

- Exact CVE and affected product/version
- Scanner evidence and false-positive possibility
- CVSS version/vector and Base severity
- CISA KEV status / exploitation evidence
- Internet exposure and attack path
- Asset owner and business criticality
- Existing controls/mitigations
- Patch or vendor mitigation availability
- Related SIEM/EDR exploitation indicators
- Remediation SLA and escalation process
- Validation/rescan after remediation

### Tools / Logs

Vulnerability scanner, CMDB/asset inventory, CISA KEV, NVD/CVE records, vendor advisories, Microsoft Sentinel/Splunk/Wazuh, EDR and firewall/WAF telemetry where relevant.

### Interview Takeaway

“CVE identifies the vulnerability; CVSS describes severity. I would not use the Base score as a complete risk score. I would combine severity with exploitation evidence such as KEV, exposure, asset criticality, controls and business context to prioritise remediation.”

### Verification Notes

- FIRST CVSS v4.0 User Guide: https://www.first.org/cvss/v4.0/user-guide
- FIRST CVSS v4.0 Consumer Implementation Guide: https://www.first.org/cvss/v4.0/implementation-guide
- NIST NVD 2026 update: https://www.nist.gov/itl/nvd
- CISA KEV prioritisation guidance: https://www.cisa.gov/known-exploited-vulnerabilities-catalog

## Question 94

### Interview Question

Windows Security Event ID 4740 appears repeatedly for a user account. What does it mean, and how would you investigate whether the lockout is caused by an attack or stale credentials?

### Interview-Ready Answer

Microsoft documents Event ID 4740 as “A user account was locked out.” It can be generated on domain controllers, member servers and workstations. Useful fields include the account that was locked out and Caller Computer Name, where populated. Microsoft recommends monitoring lockouts of high-value accounts and investigating unexpected caller computers.

I would not call repeated 4740 events a brute-force attack by themselves. Lockouts can be caused by legitimate systems repeatedly using an old password, for example a service, scheduled task or stored credential after a password change. I would identify the affected account and caller computer, establish when the lockouts started, correlate failed-authentication events and check for recent password changes or expected automation. I would also look for suspicious source patterns and any successful authentication or post-authentication activity.

Observation: the account reached the configured lockout condition. Hypotheses: stale credentials/misconfiguration or malicious authentication attempts. Confirmed attack requires supporting authentication, source and behavioural evidence.

### Real-World SOC Scenario

A service account locks every hour shortly after its password was rotated. Event 4740 repeatedly points to the same authorised application server. Correlated failures occur on a regular cadence and there is no suspicious post-authentication activity. Stale credentials in a service or scheduled task become a strong hypothesis. If instead a privileged user is repeatedly locked from an unexpected workstation after rapid failed authentications and that source also shows suspicious endpoint activity, I would escalate as a possible credential attack.

### What I Would Check as a Tier 1 Analyst

- Locked account and whether it is privileged/high value
- Timestamp and recurrence pattern
- Caller Computer Name where populated
- Related failed-authentication events
- Recent password reset/rotation
- Services, scheduled tasks or stored credentials using the account
- Source endpoint EDR telemetry
- Successful authentication around the same period
- Similar lockouts affecting other users
- Approved testing or administrative activity
- Escalation/identity-containment authority

### Tools / Logs

Windows Security Event 4740 and correlated authentication events, Microsoft Sentinel, Splunk, Wazuh, Active Directory/identity telemetry, Defender for Endpoint or another EDR, and change-management records.

### Interview Takeaway

“4740 means an account was locked out. I would use the account, caller computer, timing and correlated authentication evidence to distinguish stale credentials or automation from a credential attack, rather than treating the lockout itself as proof of brute force.”

### Verification Notes

- Microsoft Learn Event 4740: https://learn.microsoft.com/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4740
- Microsoft Windows Server events to monitor: https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/Appendix-L--Events-to-Monitor

## Question 95

### Interview Question

An interviewer shows you this Microsoft Sentinel KQL. Explain what it does and how you would investigate the result:

```kusto
SecurityEvent
| where EventID == 4728
| where SubjectUserName =~ "AutoMatedService"
| where isnotempty(SubjectDomainName)
```

### Interview-Ready Answer

This query is based on Microsoft's current Sentinel migration documentation. It searches the SecurityEvent table, filters for Windows Event ID 4728, then keeps records where SubjectUserName case-insensitively matches `AutoMatedService` and SubjectDomainName is populated.

Microsoft documents Event ID 4728 as “A member was added to a security-enabled global group.” Therefore, the query can help identify global security-group membership additions performed by that specified subject account, assuming the relevant Windows Security events are being collected into SecurityEvent.

I would not say the query detects privilege escalation by itself. It does not restrict the target to Domain Admins or another privileged group, and a group-membership change can be legitimate. I would inspect the target group, member added, account performing the action, time, change ticket and surrounding authentication/endpoint activity. MITRE ATT&CK maps adversary addition of accounts to local or domain groups to T1098.007, Additional Local or Domain Groups, but the ATT&CK mapping becomes relevant only when the behaviour and context support malicious account manipulation.

Observation: Event 4728 records match the specified subject account. Hypothesis: authorised group administration or suspicious account manipulation. Confirmed malicious activity requires evidence that the membership change was unauthorised or part of compromise.

### Real-World SOC Scenario

The query returns an event showing an automation account adding an unfamiliar user to a highly privileged global security group outside the approved change window. I would validate whether the automation account normally performs that action, identify the member and target group, check for a change record, review authentication and EDR activity for the automation account and affected identity, and look for subsequent privileged actions. If the addition is unauthorised, I would escalate promptly and follow the identity-response playbook.

### What I Would Check as a Tier 1 Analyst

- Event ID and timestamp
- SubjectUserName/SubjectDomainName
- Target group
- Member added
- Whether the group grants privileged or sensitive access
- Change ticket/approved automation
- Authentication activity for the acting account
- EDR activity from relevant source systems
- Subsequent privileged actions
- Related 4728/4729/4732/4756 events as appropriate to group type
- Escalation and authorised rollback/containment process

### Tools / Logs

Microsoft Sentinel `SecurityEvent`, Windows Security logs, Active Directory, Defender for Endpoint or another EDR, identity telemetry, Splunk/Wazuh and change-management records.

### Interview Takeaway

“Event 4728 means a member was added to a security-enabled global group. This query narrows those events to a specified subject account, but it does not prove privilege escalation. I would validate the target group, member, authorisation and surrounding identity/endpoint activity before reaching a verdict.”

### Verification Notes

- Microsoft Sentinel ArcSight migration example containing this KQL pattern: https://learn.microsoft.com/en-us/azure/sentinel/migration-arcsight-detection-rules
- Microsoft Audit Security Group Management: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/audit-security-group-management
- MITRE ATT&CK T1098.007: https://attack.mitre.org/techniques/T1098/007/

## Question 96

### Interview Question

A vulnerability scanner reports a critical vulnerability on an internet-facing production server, and threat intelligence says the CVE is in CISA's Known Exploited Vulnerabilities catalog. As Tier 1, what would you do if you also see suspicious requests targeting that server?

### Interview-Ready Answer

I would treat this as more than a routine vulnerability ticket because three risk factors have converged: a potentially affected internet-facing asset, evidence that the vulnerability is exploited in the wild, and suspicious activity against the server. I would validate the scanner finding and affected version, confirm KEV/vendor information, preserve the relevant security telemetry and escalate according to the incident/vulnerability playbooks.

I would not claim exploitation succeeded simply because suspicious requests reached the server. I would determine whether the requests matched the vulnerable path/behaviour, whether the WAF/firewall blocked them, and whether server/EDR/application telemetry shows successful exploitation or follow-on execution. At the same time, I would ensure the vulnerability owner is aware of the urgency so patching or vendor-recommended mitigation can be prioritised through the approved change process.

CISA recommends prioritising remediation of KEV vulnerabilities, particularly on internet-facing systems. CVSS Base severity remains useful, but FIRST explicitly states that CVSS Base measures severity rather than complete risk.

Observation: critical scanner finding, internet exposure, KEV status and suspicious requests. Hypothesis: active exploitation attempt. Confirmed exploitation requires server/application/EDR or other evidence that the attack succeeded.

### Real-World SOC Scenario

A WAF records repeated requests matching the vulnerable application endpoint. The server is confirmed to run an affected version. If the WAF blocked every attempt and server/EDR telemetry shows no suspicious execution, I would document that exploitation has not been confirmed while still escalating the KEV remediation urgently. If an unexpected child process, web-shell artefact or other validated post-exploitation evidence appears, I would escalate as an incident and initiate/request containment according to authority while the response team scopes the compromise.

### What I Would Check as a Tier 1 Analyst

- Exact CVE and vendor advisory
- Confirmed affected version/configuration
- CISA KEV status
- Internet exposure and asset criticality
- Scanner evidence and validation
- WAF/firewall/proxy request details
- Whether prevention controls blocked the request
- Web/application/server logs
- EDR process/file/network activity
- Indicators of successful exploitation or persistence
- Other vulnerable/exposed assets
- Patch/vendor mitigation availability
- Incident and vulnerability-management escalation paths
- Rescan/validation after remediation

### Tools / Logs

Vulnerability scanner, CISA KEV/NVD/vendor advisories, WAF/firewall/proxy logs, web/application logs, Defender for Endpoint or another EDR, Microsoft Sentinel, Splunk/Wazuh, asset inventory and change/ticketing systems.

### Interview Takeaway

“When an internet-facing system is vulnerable to a KEV-listed CVE and suspicious traffic is targeting it, I would urgently combine vulnerability response with incident triage. I would verify whether exploitation actually succeeded, preserve evidence and escalate remediation/containment according to the playbook rather than assuming either that the scanner proves compromise or that a blocked request ends the risk.”

### Verification Notes

- CISA KEV Catalog: https://www.cisa.gov/known-exploited-vulnerabilities-catalog
- CISA Cybersecurity Performance Goals recommend prioritising KEV remediation on internet-facing systems: https://www.cisa.gov/cybersecurity-performance-goals-cpgs
- FIRST CVSS v4.0 User Guide: https://www.first.org/cvss/v4.0/user-guide
- NIST NVD: https://www.nist.gov/itl/nvd
