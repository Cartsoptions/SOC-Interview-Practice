# SOC Interview Practice — 2026-09-08

## Question 49

### Interview Question

What are LOLBins or living-off-the-land binaries, and how would you investigate a trusted Windows binary such as `rundll32.exe` or `regsvr32.exe` being used in suspicious activity?

### Interview-Ready Answer

Living-off-the-land activity is the abuse of legitimate tools or binaries already present in an environment to perform malicious actions. On Windows, trusted Microsoft-signed binaries such as `rundll32.exe`, `regsvr32.exe`, `msiexec.exe` and others can be used legitimately by Windows and administrators, but attackers can also abuse them to proxy execution of malicious code.

MITRE ATT&CK maps this behaviour to **System Binary Proxy Execution — T1218**. Current MITRE detection guidance recommends looking beyond the binary name and examining context such as unusual parent-child relationships, command-line arguments, DLL or script locations, module loads, and network connections.

In a SOC environment, my observation might be:

**`rundll32.exe` or `regsvr32.exe` executed.**

That is not malicious by itself.

My hypotheses could include:

- legitimate Windows/application activity;
- approved administrator or software-installation activity;
- abuse of the signed binary to execute an untrusted DLL, scriptlet or remote payload.

I would investigate the **parent process, full path, command line, file or module being loaded, signer/hash where relevant, network activity and what the process did afterwards**. Windows Security Event ID 4688 can provide process-creation evidence when auditing is enabled, and Sysmon Event ID 1 can provide richer process context where Sysmon is deployed and configured. MITRE's 2026 detection strategies also use Sysmon process creation, module-load and network telemetry to detect anomalous signed-binary proxy execution.

As Tier 1, I would not block or delete a legitimate Windows binary simply because its name appears in an alert. I would validate the execution chain and escalate or contain according to the organisation's playbook.

### Real-World SOC Scenario

EDR alerts on this sequence:

**Microsoft Word → `rundll32.exe` → DLL from a user's Downloads directory → outbound connection**

My observation is that a trusted Windows binary executed a DLL and then network activity followed.

My hypothesis is that `rundll32.exe` may be being abused as a proxy for malicious execution.

I would compare this with legitimate baseline behaviour, inspect the DLL path/hash/signature, review the command line and parent process, then correlate DNS/proxy/firewall and EDR telemetry.

If the DLL is newly downloaded, unsigned or otherwise untrusted, the process chain is unusual, and follow-on persistence or command-and-control activity appears, the malicious-proxy-execution hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- Device and logged-on user
- Binary name and full path
- Parent and child processes
- Windows 4688 or Sysmon Event ID 1 where available
- Full command line where logged
- DLL, scriptlet or payload path
- File hash, signer and prevalence
- Sysmon module-load telemetry where configured
- DNS and network connections
- Proxy/firewall evidence
- Files or registry changes after execution
- Persistence or scheduled-task/service creation
- Whether the behaviour matches approved software installation or administration
- Similar activity on other endpoints
- Tier 1 escalation/containment authority

### Tools / Logs

Microsoft Defender for Endpoint or another EDR; Windows Security Event 4688; Sysmon Event IDs 1, 3, 7 and 22 where configured; Microsoft Sentinel; Splunk; Wazuh; DNS/proxy/firewall telemetry; file reputation/threat-intelligence sources.

### Interview Takeaway

A LOLBin is a legitimate built-in or trusted binary that can be abused to perform malicious actions. I would not judge `rundll32.exe`, `regsvr32.exe` or another signed binary by its name alone; I would investigate the parent-child chain, command line, loaded file, signer/hash, network activity and follow-on behaviour before escalating suspected living-off-the-land execution.

## Question 50

### Interview Question

What is LSASS credential dumping, and how would you investigate an alert that a process attempted to access `lsass.exe` memory without assuming every LSASS access is malicious?

### Interview-Ready Answer

**LSASS — Local Security Authority Subsystem Service — is a Windows security process involved in authenticating users and enforcing local security policy.** Credential-dumping attacks can target credential material held in LSASS process memory.

MITRE ATT&CK maps this to **OS Credential Dumping: LSASS Memory — T1003.001**. Current MITRE detection guidance looks for suspicious process access to `lsass.exe` followed by memory dumping, dump-file creation or other credential-scraping behaviour.

However:

**A process accessing LSASS is not automatically malicious.**

Security products, diagnostic tools and other legitimate processes can interact with LSASS. Microsoft explicitly warns that LSASS-related attack-surface-reduction telemetry can be noisy because many legitimate processes make unnecessary LSASS access calls.

If Sysmon is deployed and configured, **Sysmon Event ID 10 — ProcessAccess** records when one process opens another process. Microsoft notes that this can help detect tools that read LSASS memory, but also warns that ProcessAccess can generate significant logging and should normally be filtered to reduce expected noise.

My investigation would therefore focus on:

**Which process accessed LSASS? Why? With what access? What happened next?**

I would inspect the source process, parent process, file path, signer, hash, command line, access pattern and any dump-file creation or suspicious child activity. I would also look for subsequent credential misuse, privileged authentication, lateral movement or remote-service activity.

Microsoft Defender Attack Surface Reduction includes a rule named **Block credential stealing from the Windows local security authority subsystem**. Microsoft currently recommends LSA protection together with Credential Guard; when LSA protection is enabled, Microsoft states that this ASR rule is not required and does not provide extra protection. Where LSA protection or Credential Guard cannot be used, the ASR rule can help protect LSASS.

As Tier 1, I would not assume an ASR or Sysmon event proves credential theft. I would correlate the process-access evidence with endpoint behaviour and subsequent identity activity.

### Real-World SOC Scenario

EDR reports:

**Unknown executable → access to `lsass.exe` → dump file created in a temporary directory**

Shortly afterwards, the same host authenticates to multiple servers using a privileged account.

My observation is that an unusual process accessed LSASS and a memory-dump-like artefact was created.

My hypothesis is credential dumping followed by credential misuse.

I would validate the source process and dump artefact, check Sysmon/EDR process-access and file-creation telemetry, then correlate Windows authentication, SMB/RDP/remote-service and privileged-access evidence.

If the source process is untrusted, the dump artefact is consistent with credential scraping and abnormal privileged authentication follows, the credential-dumping hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- Device, user and business criticality
- Source process accessing `lsass.exe`
- Parent process and command line
- Process path, hash, signer and prevalence
- Sysmon Event ID 10 where configured
- Access rights/pattern where available
- Dump-file creation and path
- Sysmon Event ID 11 or EDR file telemetry where available
- Related registry or process activity
- Defender/ASR alert and recorded action
- Whether LSA protection/Credential Guard is relevant to the host configuration
- Subsequent Windows authentication activity
- Privileged-account use
- SMB, RDP or other remote-service activity
- Similar LSASS access on other endpoints
- Approved security/diagnostic tooling explanation
- Escalation and containment authority

### Tools / Logs

Microsoft Defender for Endpoint or another EDR; Microsoft Defender ASR telemetry; Sysmon Event IDs 10, 1 and 11 where configured; Windows Security logs; Microsoft Sentinel; Splunk; Wazuh; Active Directory/domain-controller logs; SMB/RDP/network telemetry.

### Interview Takeaway

LSASS credential dumping targets credential material in the LSASS process memory. A single LSASS access event is not proof of credential theft, so I would identify the process, access pattern and dump behaviour, then correlate that with authentication and lateral-movement evidence before escalating.

## Question 51

### Interview Question

As a Tier 1 SOC analyst, how do you decide when to escalate an incident to Tier 2 or incident response, and what information should a good escalation handoff contain?

### Interview-Ready Answer

Tier 1 escalation is not simply **"I do not know what this alert means, so I send it to Tier 2."** A strong escalation should happen when the available evidence meets the organisation's escalation criteria, the incident exceeds Tier 1 authority or complexity, or urgent specialist response is required.

Current UK L1 SOC job descriptions continue to emphasise **monitoring, triage, investigation, escalation and effective handover**. A current Cardiff L1 SOC listing published on 2 September 2026 specifically describes monitoring, triaging and escalating alerts affecting critical systems and stresses continuous coverage through effective handover. Other current UK L1 roles similarly expect analysts to investigate potential incidents and escalate in line with established processes.

In practice, reasons I would escalate include:

- confirmed or strongly suspected malicious activity;
- privileged or high-value accounts/assets involved;
- evidence of lateral movement, credential theft, persistence, data exfiltration or ransomware;
- multiple users/hosts affected;
- material business or customer impact;
- an incident requiring containment or remediation beyond Tier 1 authority;
- uncertainty that cannot be resolved with Tier 1-approved data sources or procedures;
- a severity or service-level threshold defined by the playbook.

A good handoff should let the next analyst **continue the investigation without repeating everything from the beginning**.

I would clearly separate:

**Observations:** what the telemetry actually shows.

**Hypothesis/verdict:** what I think the activity represents and my confidence.

**Actions already taken:** queries, user checks, containment, blocks or other authorised actions.

**Outstanding questions:** what still needs to be determined.

Microsoft Defender XDR and Microsoft Sentinel support incident ownership, severity, status, tags and comments to document investigation progress and reassign incidents during escalation. Microsoft recommends using incident comments/activity history to record findings so other analysts can understand what has already been investigated.

### Real-World SOC Scenario

An L1 analyst receives a Defender XDR incident showing:

**Phishing email → suspicious sign-in → PowerShell execution → SMB connections to two servers**

I validate the email and identity evidence, confirm the PowerShell process tree is abnormal and see follow-on SMB activity.

At this point, the case has moved beyond an isolated phishing alert and may involve credential compromise and lateral movement.

I would escalate with a concise evidence package such as:

**Observed:** phishing delivered to User A at 09:12; suspicious sign-in at 09:26 from IP X; PowerShell launched from Office at 09:31; SMB activity from Host A to Servers B and C at 09:35–09:38.

**Hypothesis:** likely user/endpoint compromise with possible lateral movement.

**Scope so far:** User A, Host A, Servers B and C.

**Actions taken:** message scoped across recipients; endpoint timeline reviewed; source IP and domain checked; no disruptive containment taken because Tier 1 authority does not cover Server B/C isolation.

**Reason for escalation:** suspected multi-stage compromise involving identity, endpoint and lateral movement; containment decisions required.

That handoff is much more useful than writing only **"Suspicious activity, please investigate."**

### What I Would Check as a Tier 1 Analyst

- Alert/incident ID and detection source
- Current severity/priority and business criticality
- Affected users, hosts, IPs, mailboxes and applications
- Reliable timeline with timestamps/time zone
- Raw events supporting the conclusion
- What is observed versus inferred
- Current verdict/hypothesis and confidence
- Scope identified so far
- Privileged/high-value assets involved
- Whether malicious activity is ongoing
- IOCs/TTPs supported by evidence
- Queries and pivots already performed
- User/business validation already completed
- Actions already taken and their results
- Actions specifically not taken and why
- Outstanding questions/gaps
- Exact reason for escalation
- Containment/remediation decision required
- Incident owner, comments and ticket/handoff status

### Tools / Logs

Microsoft Defender XDR incident management and Activity/Comments; Microsoft Sentinel incident management; Sentinel/Splunk/Wazuh; EDR; Entra identity logs; email-security evidence; firewall/DNS/proxy/VPN telemetry; ITSM/ticketing and organisation-specific escalation playbooks.

### Interview Takeaway

As Tier 1, I escalate when the evidence or impact meets the organisation's escalation criteria, the incident exceeds my authority or complexity, or specialist response is needed. My handoff should include a clear timeline, affected entities, evidence, hypothesis, scope, actions already taken, outstanding questions and the exact reason the next tier is needed.
