# SOC Interview Practice — 2026-10-16

## Question 137

### Interview Question

A firewall log shows that a workstation was allowed to connect to an external IP over TCP 443, while a network IDS raises an alert for the same flow. How would you explain the difference between the controls and decide whether the traffic represents a compromise?

### Interview-Ready Answer

A firewall controls traffic according to policy, such as source, destination, port, protocol, connection state and, on some platforms, application or identity context. An `allow` result means the flow matched a rule that permitted it; it does not mean the destination or activity was safe.

An intrusion detection system observes traffic or host activity and generates alerts when a signature, rule or behavioural condition matches. A detection-only IDS normally does not block the flow. An intrusion prevention system is positioned or configured to take preventive action, but whether it actually blocked, reset or merely alerted must be verified from that product's action record and deployment mode. I would not infer prevention from the words IDS/IPS alone.

In a SOC environment, I would correlate the firewall event and IDS alert by timestamp, sensor time zone, internal and external IPs, ports, protocol and any flow/session identifier. I would inspect the exact IDS signature or analytic, severity, matched direction and packet or metadata evidence, then establish which endpoint process initiated the connection. I would compare the destination, Server Name Indication or HTTP host where visible, certificate and proxy/DNS context with the device's normal role and approved software.

The verdict depends on corroboration. A permitted TCP 443 connection from a browser to an approved service may be benign even if a broad IDS rule generated a false positive. A non-browser process making regular connections to a new domain, followed by suspicious file or process activity, would justify escalation. The network alert alone normally cannot prove that an exploit succeeded or that the host is compromised.

### Real-World SOC Scenario

At 09:42, the firewall permits `10.10.20.45:51544` to reach the simulated documentation address `198.51.100.27:443`. The IDS reports a suspicious periodic TLS pattern involving the same endpoints. Endpoint telemetry associates the connections with `updater.exe` from a user-writable directory.

- **Observation:** The firewall permitted a TCP 443 flow, the IDS generated an alert, and endpoint telemetry attributed related connections to a process.
- **Hypothesis:** The process may be unauthorised software or malware using HTTPS-like traffic for command and control; alternatively, it may be a legitimate updater that triggered a broad analytic.
- **Confirmed evidence required:** Process provenance, signature/hash and command line; the destination and connection outcome; supporting DNS/proxy or packet evidence; related file/process activity; and business-owner validation. The firewall action and IDS alert alone do not confirm compromise.

### What I Would Check as a Tier 1 Analyst

1. Validate the firewall action, rule/policy identifier, direction, timestamp, interfaces or zones, source/destination, ports, protocol, byte counts and session result where available.
2. Review the IDS rule name or identifier, description, severity, confidence, matched direction and supporting packet or metadata; check whether the sensor was detection-only or inline prevention.
3. Correlate both records using the full flow tuple and time window, allowing for sensor clock and NAT differences.
4. Identify the initiating endpoint process, path, signer/hash, user, parent process and command line in EDR.
5. Pivot to DNS, proxy, TLS metadata and packet evidence; determine whether a TCP session and application exchange occurred rather than assuming success from an `allow` event.
6. Compare the activity with approved applications, software-update infrastructure, change records and the endpoint's baseline.
7. Search other devices for the same destination, process, domain, certificate or behavioural pattern.
8. Escalate when evidence supports malicious execution, repeated command-and-control-like communication or impact; request blocking or isolation only through authorised procedures.

### Tools / Logs

Firewall and NAT logs, IDS/IPS alerts and packet metadata, Microsoft Defender for Endpoint or another EDR, `DeviceNetworkEvents` and process telemetry, Microsoft Sentinel or Splunk, DNS and proxy logs, Wireshark/PCAP, asset inventory, software allowlists and change-management records.

### Interview Takeaway

`Allow` is a firewall policy decision, not a safety verdict, and an IDS alert is a detection lead, not proof that an attack succeeded. I would correlate the flow with endpoint, DNS, proxy and packet evidence before deciding and escalating.

## Question 138

### Interview Question

DNS monitoring shows one workstation querying a series of long, changing subdomains every minute, including occasional TXT queries. How would you investigate possible DNS tunnelling without treating unusual-looking names as automatic proof?

### Interview-Ready Answer

DNS translates names and supports several record types used by legitimate services. Attackers can also abuse DNS to carry commands or data, but long or high-entropy labels and TXT queries are indicators, not a verdict. Content-delivery networks, security products, cloud applications and domain-validation services can all generate unusual DNS patterns.

I would establish the affected device, user, resolver path, query names, record types, response codes, returned addresses, frequency, regularity and volume. I would measure how many unique subdomains appear under the parent domain, whether labels look encoded, whether queries and responses are unusually large, and whether the pattern is new for that device or application. I would compare it with other hosts: a legitimate enterprise agent may produce the same documented pattern across a managed fleet, while a single outlier process is more suspicious.

The most important correlation is endpoint process context. I would determine which process generated the queries where telemetry allows, inspect its path, signer/hash, parent and command line, and look for related network connections, downloads, persistence or credential activity. I would also check the registered domain and threat intelligence as enrichment, but domain age or reputation alone would not establish intent.

MITRE ATT&CK maps abuse of DNS for command-and-control communication to T1071.004. I would apply that mapping only when the evidence supports protocol abuse; ordinary DNS resolution does not qualify.

### Real-World SOC Scenario

`FIN-LT-022` sends one query approximately every 60 seconds for different labels beneath `sync-service.example`, with a mixture of A and TXT queries. No other corporate endpoint shows the pattern, and EDR associates the traffic with an unsigned executable in the user's profile.

- **Observation:** One host produces regular, unique subdomain queries and occasional TXT requests; endpoint telemetry links them to an unusual process.
- **Hypothesis:** The process may be using DNS for command polling or tunnelling, but legitimate application telemetry or update traffic remains possible.
- **Confirmed evidence required:** Confirmation requires corroborated process and DNS activity showing unauthorised protocol use, such as decoded or otherwise validated command/data exchange, a malicious binary verdict supported by local behaviour, or incident-response analysis establishing the channel. Periodicity and entropy alone remain indicators.

### What I Would Check as a Tier 1 Analyst

1. Confirm the device, user, time range, resolver, complete query name, record type, response code, returned data and query/response sizes where logged.
2. Compare query frequency, interval variance, label length/entropy, unique-subdomain count and parent-domain prevalence against a suitable baseline.
3. Check whether the same pattern appears across approved software or other managed devices.
4. Identify the initiating process where endpoint DNS or network telemetry provides it; review path, signer/hash, parent, command line and first-seen context.
5. Correlate DNS events with subsequent IP connections, proxy/firewall sessions, file activity, persistence and related security alerts.
6. Inspect representative packets or logs safely; do not copy potentially encoded content into an execution environment.
7. Enrich the domain and resolved addresses with approved intelligence, registration and ownership data, treating each as supporting context.
8. Escalate with the observed pattern, baseline comparison, affected assets and evidence gaps; request authorised endpoint isolation or DNS/network blocking if the risk is substantiated.

### Tools / Logs

DNS resolver and protective-DNS logs, Microsoft Defender for Endpoint DNS/network telemetry, Microsoft Sentinel or Splunk, Wazuh or Sysmon when appropriately configured, firewall/proxy logs, Wireshark/PCAP, asset and software inventory, approved threat intelligence and incident-management records.

### Interview Takeaway

I would treat long labels, TXT records and regular timing as investigation signals. The stronger case comes from correlating those DNS patterns with an unexpected process, host behaviour and validated unauthorised communication.

## Question 139

### Interview Question

You are given this simulated packet sequence from a suspected workstation. What can you conclude, what remains unproven, and which Wireshark display filters would you use?

```text
09:42:01.100  10.10.20.45:51544  -> 198.51.100.27:443  TCP [SYN]
09:42:01.132  198.51.100.27:443  -> 10.10.20.45:51544  TCP [SYN, ACK]
09:42:01.133  10.10.20.45:51544  -> 198.51.100.27:443  TCP [ACK]
09:42:01.140  10.10.20.45       -> 198.51.100.27      TLS Client Hello
                Server Name: updates-cloud.example
09:42:01.181  198.51.100.27      -> 10.10.20.45       TLS Server Hello
09:42:01.250  Encrypted Application Data
```

### Interview-Ready Answer

The SYN, SYN-ACK and ACK sequence supports that a TCP connection was established between the two endpoints. The Client Hello shows that the client began a TLS negotiation and offered the displayed server name; the Server Hello and later encrypted application data show that the exchange progressed beyond the initial client request. The capture still does not reveal the encrypted content or prove command and control, malware execution or data exfiltration.

I would also qualify visibility. Server Name Indication is available only when it appears in the captured, parseable handshake; encryption features, capture position, packet loss or protocol differences can limit what is visible. The example IP and domain are explicitly simulated, and `198.51.100.0/24` is a documentation range rather than a real indicator.

Useful Wireshark display filters for this artefact include:

```text
ip.addr == 10.10.20.45 && tcp.port == 443
tcp.flags.syn == 1
tls.handshake.type == 1
tls.handshake.extensions_server_name == "updates-cloud.example"
dns.qry.name == "updates-cloud.example"
```

The first narrows the conversation, the second finds TCP packets with SYN set, the third selects TLS Client Hello messages, the fourth selects a matching visible TLS server name, and the fifth finds matching DNS questions if DNS traffic is present in the capture. Display filters hide nonmatching packets; they do not change the capture. I would use **Follow TCP Stream** only as an analysis view and remember that encrypted application payloads remain unreadable without appropriate session keys and authorisation.

### Real-World SOC Scenario

The same six-packet pattern begins a connection roughly every minute. Firewall logs show the sessions were allowed, and EDR links them to an unknown executable rather than a browser.

- **Observation:** TCP establishment, TLS negotiation metadata, encrypted application data and repeated timing are visible; EDR supplies process attribution.
- **Hypothesis:** The process may be periodically contacting command-and-control infrastructure over HTTPS-like traffic.
- **Confirmed evidence required:** Repetition and TLS metadata support the hypothesis but do not prove it. Confirmation requires process/file evidence, destination validation, related host behaviour, decrypted or otherwise interpretable protocol evidence where lawfully available, or a validated incident finding.

### What I Would Check as a Tier 1 Analyst

1. Verify the capture point, interface, timestamp/time zone, packet loss, snap length and whether the PCAP covers both directions.
2. Confirm the TCP three-way handshake and inspect resets, retransmissions, stream duration and byte directionality.
3. Review TLS version, visible server name, certificate metadata and handshake progression without treating encryption as malicious.
4. Search for preceding DNS queries and compare the returned address with the connection destination.
5. Measure recurrence and interval variance across streams; distinguish a pattern from a single connection.
6. Correlate the flow with firewall/proxy logs and the exact initiating process, user, path, signer/hash, parent and command line in EDR.
7. Compare with approved software and destination ownership; scope the same process/domain/IP pattern across other devices.
8. Preserve the original PCAP and investigation notes, and escalate with separate observations, hypotheses and confirmed findings.

### Tools / Logs

Wireshark and PCAP, firewall/NAT and proxy logs, DNS telemetry, Microsoft Defender for Endpoint `DeviceNetworkEvents` and process evidence, Microsoft Sentinel, Splunk, Wazuh where relevant, certificate and destination intelligence, software inventory and case records.

### Interview Takeaway

The packets prove a TCP connection and show TLS negotiation metadata plus encrypted traffic. They do not reveal intent or payload content, so I would correlate the stream with process, DNS, proxy and endpoint evidence before calling it command and control.

## Question 140

### Interview Question

A finance workstation makes a short outbound TLS connection every 60 seconds to a newly observed domain. DNS queries use changing subdomains, the firewall allows the sessions, an IDS raises a beaconing alert, and Defender for Endpoint attributes the connections to an unsigned executable in a user-writable directory. How would you prioritise, contain, scope and escalate the incident?

### Interview-Ready Answer

I would treat this as a high-priority suspected command-and-control incident because independent data sources converge: periodic communication, unusual DNS behaviour, an IDS analytic and risky process provenance. I would still avoid declaring confirmed C2 solely from periodicity or reputation. Legitimate update and monitoring agents can produce regular encrypted traffic, so the process and host evidence must resolve the hypothesis.

I would create a unified timeline using DNS queries, firewall and IDS events, TLS/packet metadata and Defender endpoint records. In `DeviceNetworkEvents`, documented fields such as `Timestamp`, `DeviceId`, `DeviceName`, `RemoteIP`, `RemotePort`, `RemoteUrl`, `Protocol`, `ActionType`, `InitiatingProcessFileName`, `InitiatingProcessCommandLine`, process path and hashes can support process-to-network correlation. I would interpret `ActionType` using the tenant's in-portal schema reference rather than inventing a value.

I would inspect the executable's origin, signer, hashes, parent, command line, file creation and first-seen context; then look for persistence, downloads, child processes, credential access, discovery and lateral movement. I would hunt across the environment for the domain, resolved IPs, process/hash, path, certificate metadata, DNS pattern and timing behaviour. Threat intelligence would enrich the case, but a clean or unknown result would not outweigh local behavioural evidence.

If the process is unauthorised and the communication chain is corroborated, I would escalate it as a confirmed endpoint compromise with suspected or confirmed command-and-control, depending on the evidence available. Under an authorised playbook, containment may include isolating the endpoint, blocking confirmed malicious domains/IPs or processes and preserving evidence. If Tier 1 lacks those permissions, I would request the actions urgently and record the owner, approval and result. I would avoid deleting the executable or rebooting before evidence needs and higher-tier direction are considered.

MITRE ATT&CK can describe DNS-based communication as T1071.004 and HTTP/S or web-protocol communication as T1071.001 when the observed protocol supports those mappings. The Pyramid of Pain helps prioritise durable detection: an IP address or file hash may change quickly, whereas the combined behaviour—an unsigned user-profile process generating regular TLS sessions and changing DNS labels—is generally harder for an attacker to alter. Neither framework proves attribution.

NIST SP 800-61 Rev. 3 supports risk-based incident analysis, containment, response and recovery. Following containment and higher-tier analysis, recovery should validate removal or trusted rebuilding, persistence eradication, credential/secret rotation where exposure is established, control health and enhanced monitoring.

### Real-World SOC Scenario

The user does not recognise `updater.exe`, and software inventory contains no approved application matching it. EDR shows the file was created shortly before the first connection and launched by a suspicious script process. The same DNS pattern and destination occur on one additional workstation.

- **Observation:** Network and endpoint sources correlate an unauthorised executable with repeated TLS and changing-subdomain DNS activity on two devices.
- **Hypothesis:** The executable is malware using DNS and encrypted web traffic for command and control, with at least two affected endpoints.
- **Confirmed evidence:** The executable is unauthorised and the process-to-network association is corroborated. A confirmed C2 verdict requires validated malicious communication or incident analysis supporting that function; data theft, credential compromise, initial-access method and actor attribution remain separate questions.

The defensible initial verdict is **true positive — confirmed unauthorised execution and endpoint compromise, with suspected command and control and scope expanding to a second device**. I would raise the C2 confidence only as further evidence supports it.

### What I Would Check as a Tier 1 Analyst

1. Set priority using device criticality, user privilege, number of affected assets, connection persistence and observed follow-on behaviour.
2. Preserve the alert records, raw logs, relevant PCAP, endpoint timeline, process/file metadata, hashes and investigation queries.
3. Validate the process-to-network relationship and build a time-normalised sequence across DNS, firewall, IDS/IPS, proxy and EDR sources.
4. Hunt across devices for the process/hash/path, parent and command line, domains and resolved IPs, certificate or TLS metadata, DNS-label pattern and periodic behaviour.
5. Check for persistence, payload delivery, discovery, credential access, lateral movement, privilege escalation and possible collection or exfiltration.
6. Invoke authorised endpoint isolation and indicator blocking, or request them; verify that communication stops and document action results and exceptions.
7. Escalate to Tier 2/IR with the timeline, affected assets, evidence confidence, containment status, telemetry gaps and specific decisions required.
8. Support eradication and recovery by verifying trusted remediation/rebuild, persistence removal, required secret rotation, sensor health and heightened monitoring.
9. Feed lessons into behavioural detections, egress and DNS controls, allowlists, asset inventory and playbooks without relying only on fragile indicators.

### Tools / Logs

Microsoft Defender XDR/Defender for Endpoint advanced hunting and device timeline, `DeviceNetworkEvents`, process and file events, Microsoft Sentinel or Splunk, IDS/IPS and firewall/NAT logs, protective DNS and proxy telemetry, Wireshark/PCAP, Wazuh where deployed, threat intelligence, asset/software inventory and incident-management records.

### Interview Takeaway

I would treat converging network and endpoint evidence as high priority, but separate confirmed unauthorised execution from the still-tested C2 hypothesis. I would contain within authority, scope behaviourally across the estate and give Tier 2/IR an evidence-led handover.

## Verification Notes

- NIST SP 800-41 Rev. 1 defines firewalls as devices or programs that control network-traffic flow between hosts or networks with differing security postures. The publication is older, so it is used here only for stable firewall fundamentals, not current product features.
- NIST SP 800-94 remains final guidance on IDPS fundamentals, but NIST notes its 2007 publication date and that a later Revision 1 draft was retired. The answers therefore use it only for the stable distinction between detection and prevention and require product/deployment verification.
- An allowed firewall record establishes a policy decision for recorded traffic; it does not establish safety or application success. IDS/IPS actions vary by deployment and configuration, so block/reset/prevention must be confirmed from the actual action record.
- Microsoft documents `DeviceNetworkEvents` and the network/process fields named in Question 140. Microsoft directs analysts to the in-portal schema reference for supported `ActionType` values; no undocumented action value is assumed.
- Wireshark documents the display-filter fields used in Question 139: `tcp.flags.syn`, `tls.handshake.type`, `tls.handshake.extensions_server_name` and `dns.qry.name`. Boolean field presence alone is not equivalent to true, which is why the filter uses `tcp.flags.syn == 1`.
- The packet artefact is simulated. `198.51.100.0/24` and `.example` names are reserved for documentation and are not presented as live indicators.
- MITRE ATT&CK supports Application Layer Protocol: Web Protocols T1071.001 and DNS T1071.004. These mappings describe evidenced behaviours and do not prove maliciousness or actor identity.
- NIST SP 800-61 Rev. 3 was published in April 2025 and integrates incident-response recommendations with CSF 2.0 risk management, including analysis, containment, response and recovery considerations.
