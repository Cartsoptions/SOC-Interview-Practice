# SOC Interview Practice — 2026-10-26

**Curriculum:** Questions 157–160 | Linux SSH authentication, `sudo` privilege escalation, Splunk CIM investigation, and SSH-key persistence with compute hijacking

## Question 157

### Interview Question

An internet-facing Linux server records hundreds of failed SSH password attempts against one account, followed by an `Accepted publickey` event for that account from the same source. How would you decide whether this is a brute-force compromise?

### Interview-Ready Answer

I would treat it as high-priority suspected compromise, but the sequence alone does not prove that the password guessing caused the public-key success. The failures and the successful public-key authentication use different methods; an attacker may already possess an authorised private key, or the successful connection may be legitimate activity sharing a NAT or jump-host address.

In a SOC environment, I would first verify time synchronisation, hostname, source address, target account and authentication method from the raw SSH evidence. The location depends on the distribution and logging configuration: systemd systems can expose records through the journal, while traditional syslog configurations commonly route authentication messages to files such as `/var/log/auth.log` or `/var/log/secure`. The SSH service unit may be named `ssh` or `sshd`, so I would not assume one command or path works everywhere.

I would then correlate the successful session with the public-key fingerprint where it is recorded, the account's approved keys, asset owner, VPN/jump-host inventory and change records. Next I would examine session creation, process execution, privilege use, file changes, persistence and outbound connections. A success from an unknown key followed by unauthorised commands is much stronger evidence than authentication text alone.

### Real-World SOC Scenario

The source is not an approved scanner, VPN or jump host. The account owner denies the session. Endpoint telemetry shows the SSH session spawning a shell and downloading an executable into `/tmp`.

- **Observation:** One source generated repeated SSH password failures and then authenticated with a public key.
- **Hypothesis:** The attacker possessed an authorised private key or had added a key earlier; the password attempts may have been reconnaissance or a separate activity.
- **Confirmed evidence:** The user denial, unknown key fingerprint and unauthorised download confirm account misuse. The failed password attempts do not, by themselves, prove how the key was obtained.

The verdict is **true positive — confirmed unauthorised SSH access; initial key acquisition and the relationship to the password failures remain under investigation**.

### What I Would Check as a Tier 1 Analyst

1. Preserve raw SSH/journal records and confirm host time, time zone, source, user, port and authentication method.
2. Check whether the source belongs to an approved VPN, jump host, scanner, administrator or cloud service.
3. Compare the successful key fingerprint, when logged, with the account's authorised-key inventory and change history.
4. Review session-open records, process trees, shell or command telemetry, file writes, `sudo` activity and network connections.
5. Determine whether the account is privileged, shared, service-related or permitted to log in interactively.
6. Search other hosts for the same source, account, fingerprint, filenames, hashes and destinations.
7. Invoke or request authorised account/key restriction and host isolation if malicious follow-on activity is corroborated.
8. Escalate with the evidence, affected host/account, containment status and unresolved initial-access question.

### Relevant Tools / Logs

OpenSSH authentication messages in the systemd journal or distribution-specific authentication logs, SIEM, Linux audit telemetry where configured, EDR process and network evidence, firewall/VPN logs, cloud audit records, authorised-key inventory and case-management records.

### Key Interview Takeaway

An SSH success after failures is a strong lead, not proof of causal compromise. I would distinguish authentication methods, validate the key and source, then confirm impact through session and endpoint evidence.

## Question 158

### Interview Question

Your SIEM shows that a Linux web-operations account used `sudo` to start a root shell and then a new file appeared under `/etc/sudoers.d/`. The user normally restarts services but does not administer access. How would you investigate possible privilege escalation?

### Interview-Ready Answer

`sudo` allows authorised users to execute commands as another user, commonly root. MITRE ATT&CK maps abuse of `sudo` and sudo credential caching to T1548.003. I would treat the root shell plus a sudoers change as suspicious privilege escalation, while verifying whether an approved maintenance task or automation explains it.

I would preserve the original sudo, authentication, audit and endpoint records. Sudo can log accepted or rejected commands through syslog, a log file or a remote logging service, and optional I/O logging can capture terminal input/output. Those details depend on policy and version; their absence does not prove nothing occurred. Common log details can include the submitting user, target user, working directory, terminal and command, but I would validate the actual fields in the organisation's data.

I would correlate the sudo event with login source, parent process, command line, interactive session, file creation and the exact sudoers content. Shell history is useful as a lead but is user-controlled and may be incomplete. A Tier 1 analyst should not edit sudoers or destroy evidence. I would contain or request containment under the playbook, preserve the suspect file and escalate privilege-policy remediation to Linux/IR specialists.

### Real-World SOC Scenario

The account authenticated from an unfamiliar external address. Audit/EDR telemetry shows `sudo` starting a root shell, after which an unauthorised rule granted passwordless execution to the account. There is no change ticket, and the user denies the activity.

- **Observation:** A limited operations account obtained a root shell and a sudoers drop-in was created.
- **Hypothesis:** An attacker used legitimate `sudo` rights or cached credentials to gain persistence with elevated access.
- **Confirmed evidence:** The unauthorised session, root process ancestry, file write and policy content confirm privilege escalation and access-policy manipulation. The original credential-theft method remains unconfirmed.

The verdict is **high-severity true positive — confirmed unauthorised privilege escalation and persistence through sudo policy manipulation**.

### What I Would Check as a Tier 1 Analyst

1. Confirm the source login, user, host, target user, command, working directory, terminal and precise timestamps.
2. Validate whether the activity matches an approved change, automation account or administrator workflow.
3. Correlate sudo records with PAM/SSH evidence, audit events, EDR process ancestry and session telemetry.
4. Preserve the new file, metadata, content, hash and related configuration changes before remediation.
5. Review preceding commands and processes for exploitation, credential access or abuse of cached authorisation.
6. Hunt for additional privileged commands, new accounts/keys, cron or systemd persistence and outbound connections.
7. Invoke or request authorised host and account containment; do not independently edit access policy or delete evidence.
8. Escalate to Tier 2/IR and Linux administration with confirmed scope, business impact and recovery decisions.

### Relevant Tools / Logs

Sudo logs through the configured syslog/journal/file or remote service, PAM and SSH authentication records, auditd where deployed, EDR process/file/network telemetry, SIEM, file-integrity monitoring, `/etc/sudoers` and `/etc/sudoers.d/` evidence, change records and identity inventory.

### Key Interview Takeaway

I would not call every root shell malicious, but an unauthorised sudoers change is strong evidence. My Tier 1 role is to correlate the session and file change, preserve evidence, contain within authority and escalate safe recovery.

## Question 159

### Interview Question

Linux authentication data is normalised to Splunk's CIM Authentication data model. Write a practical SPL search to identify one source producing SSH failures against many users in ten minutes, then explain what the results do and do not prove.

### Interview-Ready Answer

I would begin with a bounded `tstats` search over the CIM Authentication dataset:

```spl
| tstats summariesonly=false count AS failed_attempts
    dc(Authentication.user) AS targeted_users
    values(Authentication.user) AS users
    values(Authentication.dest) AS destinations
  FROM datamodel=Authentication.Authentication
  WHERE Authentication.action="failure"
  BY _time span=10m Authentication.src Authentication.app
| where failed_attempts>=10 AND targeted_users>=5
| rename Authentication.src AS src Authentication.app AS app
| sort 0 - failed_attempts
```

Splunk documents `tstats` searches against `datamodel=Authentication.Authentication` and fields including `Authentication.action`, `Authentication.src`, `Authentication.user` and `Authentication.app`. `dest` is a prescribed Authentication field for the target system. `summariesonly=false` allows matching raw and accelerated data where available, but performance and completeness depend on CIM mapping, permissions, retention and acceleration.

The thresholds are analyst starting points, not Splunk defaults. The search identifies windows with at least ten failure events covering at least five distinct normalised users from one source/application. It does not prove that one password was used, that the source is hostile, that the failures were SSH unless `app` or another mapped field establishes that, or that any account was compromised.

I would inspect the raw events behind each candidate and search for subsequent successes for the same source or targeted users. I would also account for NAT, jump hosts, scanners, PAM integrations and field-normalisation errors. Splunk's documentation warns that `tstats` does not support complex aggregate functions such as `count(eval(...))`, which is why the filter is applied in `WHERE` before aggregation.

### Real-World SOC Scenario

The search finds 64 failures against 18 users from one address with `app=sshd`. Raw events then show a successful key-based sign-in for one targeted account, followed by a root shell and an unauthorised file download.

- **Observation:** The CIM search identifies a many-user authentication-failure pattern from one source.
- **Hypothesis:** The source is attempting password spraying or username enumeration against SSH.
- **Confirmed evidence:** The search confirms normalised failure events and their cardinality. Raw authentication and endpoint evidence confirm one unauthorised session; reuse of a single password remains unproven.

The verdict is **true positive after correlation — suspicious distributed SSH authentication activity with confirmed unauthorised follow-on access**.

### What I Would Check as a Tier 1 Analyst

1. Confirm the time range, index coverage, CIM tags and field mappings for Linux authentication data.
2. Validate that `action`, `src`, `user`, `dest` and `app` represent the source events correctly.
3. Open raw failures and verify message, method, result and source rather than relying only on normalised counts.
4. Check IP ownership, VPN/NAT/jump-host context, approved scanners and the users' normal baseline.
5. Search for successes involving the candidate source and targeted users before and after the window.
6. Correlate successful sessions with process, file, privilege and network evidence.
7. Tune thresholds and grouping to the environment; do not present this example as a universal production rule.
8. Escalate only with clearly separated observations, hypotheses and confirmed evidence.

### Relevant Tools / Logs

Splunk Enterprise or Splunk Cloud, CIM Authentication data model, `tstats`, raw OpenSSH/PAM/journal events, Linux audit and EDR telemetry, VPN/firewall data, asset and identity inventories, and data-onboarding health dashboards.

### Key Interview Takeaway

The SPL is a candidate generator. I would validate CIM mapping and raw SSH evidence, account for shared infrastructure, and use successful-session plus endpoint activity to prove compromise.

## Question 160

### Interview Question

A Linux production server suddenly reaches 100% CPU. EDR shows a miner-like process launched from `/tmp`, an unfamiliar public key was appended to a service account's `authorized_keys`, and the account then authenticated over SSH. How would you triage, contain and escalate this incident?

### Interview-Ready Answer

I would treat this as a high-severity confirmed incident involving persistence and compute-resource abuse. MITRE ATT&CK T1098.004 describes modifying SSH `authorized_keys` for persistent access, and T1496.001 covers abuse of compute resources such as cryptocurrency mining.

I would preserve the process tree, executable, hash, command line, network destinations, authentication records, key material, file metadata and timeline. I would not simply kill the process and delete the key: that may remove visible symptoms while leaving initial access, other persistence or stolen credentials unresolved.

Within the organisation's authority and playbook, I would isolate the server or restrict malicious egress, disable or restrict the affected account/key, and protect service availability with operations/incident-command coordination. I would scope the same key fingerprint, source IP, account, hash, process path, mining-pool destinations and persistence changes across the estate. I would also investigate how the attacker first obtained access, whether secrets or data were accessed and whether lateral movement occurred.

Recovery should be led by authorised IR and system owners: remove persistence, rotate exposed credentials and keys, patch the entry point, rebuild from a trusted image when integrity cannot be established, restore service and validate monitoring before reconnecting. NIST SP 800-61 Rev. 3 places incident response across Detect, Respond and Recover outcomes while also integrating preparation and lessons learned across cybersecurity risk management.

### Real-World SOC Scenario

The key was added outside change control immediately after exploitation of a vulnerable internet-facing service. The same host contacted a known mining-pool endpoint and the process consumed nearly all CPU. Two additional servers contain the same key but have not yet launched the miner.

- **Observation:** An unknown SSH key, unauthorised SSH session, miner-like process and abnormal resource/network activity occur on the same host.
- **Hypothesis:** The attacker exploited the service, established SSH-key persistence and deployed a cryptocurrency miner, with possible spread to other servers.
- **Confirmed evidence:** Unauthorised key modification, access, executable launch, resource consumption and mining-pool communication confirm persistence and compute hijacking. Data theft and the full lateral-movement scope remain unconfirmed.

The verdict is **high-severity true positive — confirmed SSH-key persistence and compute hijacking, with multi-host exposure requiring urgent scoping**.

### What I Would Check as a Tier 1 Analyst

1. Confirm asset criticality, owner, production role, resource impact and whether isolation needs availability coordination.
2. Preserve EDR process/file/network evidence, the executable, hashes, key contents/fingerprint and file metadata.
3. Correlate SSH source, account, method and session time with process launch and configuration changes.
4. Identify the executable's destinations, DNS, parent process, user, persistence and any credential access.
5. Hunt for the same key, account, source, hash, filename, command line and destinations across all assets.
6. Invoke or request authorised isolation, egress blocking and account/key restriction without destroying evidence.
7. Review vulnerable-service, proxy/WAF and application logs to identify the initial access path.
8. Escalate to IR, Linux operations and service owners with affected assets, containment status and integrity concerns.
9. Track trusted rebuild or remediation, credential/key rotation, patching, restoration and post-recovery monitoring.
10. Record what is confirmed separately from open questions about data access, spread and attribution.

### Relevant Tools / Logs

EDR/XDR process, file and network telemetry; OpenSSH, PAM and systemd journal records; Linux audit and file-integrity monitoring where configured; SIEM; DNS/firewall/proxy/WAF and cloud logs; vulnerability and asset data; `authorized_keys` evidence; and incident case management.

### Key Interview Takeaway

Killing the miner is not incident recovery. I would preserve the timeline, contain the host and key within authority, hunt across the estate, investigate initial access and escalate trusted recovery to IR and operations.

## Verification Notes

- Linux authentication evidence varies by distribution and configuration. `journalctl` reads the systemd journal and can filter by unit, but the OpenSSH unit may be `ssh` or `sshd`; file destinations such as `/var/log/auth.log` and `/var/log/secure` depend on syslog configuration.
- An `Accepted publickey` SSH record confirms that the server accepted a key for the account. It does not by itself identify the human operator or prove how the private key was obtained.
- MITRE ATT&CK T1548.003 covers abuse of `sudo` and sudo credential caching. Sudo logging destinations and optional I/O logging are policy-dependent; missing I/O records must not be interpreted as proof that no command ran.
- Shell history is user-controlled and may be absent or altered. It is an investigative lead, not authoritative evidence.
- Splunk documents the CIM Authentication dataset and the `tstats` pattern used here. The sample thresholds are illustrative and require validation against data quality, shared-source infrastructure and normal behaviour.
- Splunk documents that `tstats` does not support complex aggregate functions such as `count(eval(...))`; the example filters failures in the `WHERE` clause instead.
- MITRE ATT&CK T1098.004 describes adding or modifying SSH authorised keys for persistence. T1496.001 describes compute-resource abuse, including cryptocurrency mining.
- NIST SP 800-61 Rev. 3 was finalised on 3 April 2025 and integrates incident response recommendations across the CSF 2.0 functions rather than treating response as an isolated sequence.
- All users, hosts, addresses, keys, thresholds and artefacts in these scenarios are simulated.
