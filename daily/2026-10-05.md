# SOC Interview Practice — 2026-10-05

## Question 109

### Interview Question
What is privilege escalation, and how would you investigate it as a Tier 1 SOC analyst?

### Interview-Ready Answer
Privilege escalation is when an account or process obtains permissions beyond those it previously had. Vertical privilege escalation means gaining higher privilege, while an attacker can also manipulate group or role membership to preserve or expand access. In a SOC environment, I would not treat every administrative change as malicious. I would establish who made the change, what account or group was affected, whether it was approved, and what happened before and after it.

For Windows Active Directory, Microsoft documents Security Event ID 4728 as "A member was added to a security-enabled global group"; 4732 applies to a security-enabled local group and 4756 to a security-enabled universal group. MITRE ATT&CK maps suspicious additions to local or domain groups to T1098.007, under Account Manipulation.

### Real-World SOC Scenario
A normal help-desk account is unexpectedly added to a privileged domain group outside an approved change window. I would verify the initiating account, target member, target group, timing and change approval, then correlate logons and subsequent privileged activity.

**Observation:** A privileged group membership changed.
**Hypothesis:** An attacker or compromised administrator may be escalating or preserving access.
**Confirmed Evidence:** Requires evidence that the change was unauthorised or malicious, such as no approved change plus compromised-account activity or unauthorised privileged actions.

### What I Would Check as a Tier 1 Analyst
- Event ID appropriate to the group type and its Subject, Member and Group details
- Change ticket/approved administration activity
- Initiating account and recent authentication
- Target account and subsequent privileged activity
- Related EDR, SIEM and identity alerts
- Scope: other group/role changes by the same actor
- Escalation/containment according to the playbook

### Tools / Logs
Windows Security logs, Active Directory/domain-controller logs, Microsoft Sentinel, Splunk, Wazuh, Defender XDR/EDR, Entra audit/sign-in telemetry where relevant.

### Interview Takeaway
"Privilege escalation is not proved by one admin event. I validate who changed what, whether it was authorised, and whether identity, endpoint and post-change activity support malicious privilege escalation."

## Question 110

### Interview Question
What does Windows Security Event ID 4720 mean, and what would make it suspicious?

### Interview-Ready Answer
Microsoft documents Event ID 4720 as "A user account was created." The event can identify the Subject that requested account creation and the New Account, including its SID, name and domain. It is an account-management event, not a malware verdict.

A legitimate administrator, provisioning workflow or service can create accounts. Suspicion comes from context: an unexpected creator, unusual time, misleading account name, creation on a sensitive system/domain, rapid enablement or privileged-group addition, or subsequent abnormal logon/activity.

### Real-World SOC Scenario
At 02:14, Event 4720 records a newly created domain user. Minutes later, a group-management event adds it to a privileged group. I would correlate the creator's Logon ID where useful, validate change approval and investigate the creator and new account.

**Observation:** An account was created.
**Hypothesis:** It may be an unauthorised persistence or privilege-escalation account.
**Confirmed Evidence:** Requires corroboration that creation/use was unauthorised or tied to malicious activity.

### What I Would Check as a Tier 1 Analyst
- Subject account, New Account, timestamp and domain
- Creator's authentication/session context
- Whether provisioning/change activity explains it
- Subsequent enablement, password, group-membership and account-change events
- First logon and systems/resources accessed
- Other accounts created by the same actor

### Tools / Logs
Windows Security Event 4720 and related account-management events, domain-controller logs, Sentinel, Splunk, Wazuh, Defender XDR.

### Interview Takeaway
"4720 proves account creation, not compromise. I correlate the creator, approval, subsequent group changes and first use of the account."

## Question 111

### Interview Question
Explain this Defender XDR Advanced Hunting query and its limitations:

```kusto
DeviceLogonEvents
| where Timestamp > ago(24h)
| where LogonType == "Remote interactive"
| summarize Attempts=count(),
            Devices=dcount(DeviceName)
            by AccountName, RemoteIP
| order by Devices desc
```

### Interview-Ready Answer
Microsoft documents DeviceLogonEvents as containing user logons and other authentication events on devices. The query restricts results to the last 24 hours and to Remote interactive logons, which Microsoft describes as RDP/Terminal Services/Remote Assistance or other RDP-client sessions. It groups records by AccountName and RemoteIP, counts matching records, estimates the number of distinct DeviceName values with dcount(), and orders sources/accounts touching the most devices first.

This is a hunting lead, not proof of lateral movement. Legitimate administrators or support infrastructure may use RDP across multiple systems. Also, the query does not by itself distinguish success from failure because it does not filter ActionType. I would inspect the raw events and the supported ActionType values in the Defender portal schema, as Microsoft recommends.

### Real-World SOC Scenario
A non-administrative account appears in Remote interactive events from one remote IP across several servers. I would pivot to raw DeviceLogonEvents, determine event outcomes, check whether the source and account are expected, and correlate endpoint/process/network activity on successfully accessed hosts.

**Observation:** An account/source combination has remote-interactive authentication events across multiple devices.
**Hypothesis:** This could represent lateral movement or unauthorised remote access.
**Confirmed Evidence:** Requires validated successful access and corroborating unauthorised behaviour/context.

### What I Would Check as a Tier 1 Analyst
- Raw ActionType values and FailureReason where relevant
- AccountName, AccountDomain, RemoteIP, DeviceName and LogonType
- Whether the source is an approved jump host/admin system
- Account privilege and normal behaviour
- EDR process/network telemetry after successful sessions
- Related Windows authentication and identity alerts

### Tools / Logs
Defender XDR DeviceLogonEvents, Defender for Endpoint, Sentinel, Windows Security logs, firewall/network telemetry.

### Interview Takeaway
"The aggregation identifies remote-interactive authentication patterns worth investigating. I validate outcome and context before calling it lateral movement."

## Question 112

### Interview Question
A help-desk account logs on remotely to a domain controller, creates a new user, and minutes later that user is added to a privileged domain group. How would you triage this?

### Interview-Ready Answer
I would treat the sequence as high priority because it combines remote access, account creation and privileged group modification. I would not claim compromise from the sequence alone because an authorised administrative workflow could explain it.

I would build the timeline: help-desk authentication -> account creation -> group membership change -> new account use. I would validate whether the help-desk account was authorised to perform these actions and whether a change ticket or approved task exists. I would inspect Event 4720 for the account creation and the group-management event matching the actual group type. For a security-enabled global group, Microsoft documents 4728; local and universal groups use different event IDs.

MITRE ATT&CK T1098.007 covers adding accounts to local or domain groups for persistence/privilege escalation. If evidence indicates unauthorised privileged access, I would urgently escalate and follow the organisation's identity/domain compromise playbook. Containment actions would depend on my authorised role and could require disabling/restricting the suspect account, revoking sessions or removing unauthorised privilege, but I would not perform those actions without playbook authority.

### Real-World SOC Scenario
The help-desk user denies performing the change, no approved ticket exists, and the new privileged account then authenticates to another sensitive server. That combination substantially strengthens the compromise assessment and expands the scope.

**Observation:** Remote authentication, new account creation and privileged-group addition occurred in close sequence.
**Hypothesis:** A compromised help-desk account may be creating a persistent privileged identity.
**Confirmed Evidence:** Examples include user denial plus no authorised change and corroborating unauthorised use of the new privileged account.

### What I Would Check as a Tier 1 Analyst
- Exact timeline and source of the remote logon
- 4720 creator/New Account fields
- Correct group-management event and Subject/Member/Group fields
- Change/ticket approval and expected admin workflow
- Help-desk account's prior authentication and endpoint evidence
- New account's first logons and privileged actions
- Other accounts/groups modified by the same actor
- Related EDR, SIEM, identity and network alerts
- Immediate escalation and authorised containment requirements

### Tools / Logs
Windows Security/domain-controller logs, Defender XDR/Defender for Endpoint, Microsoft Sentinel, Splunk, Wazuh, Entra/identity telemetry where applicable, firewall/network logs.

### Interview Takeaway
"I would correlate the chain rather than judge each event in isolation. Remote admin access followed by account creation and privileged-group addition is high risk; I validate authorisation, scope subsequent use and escalate quickly if the evidence supports compromise."
