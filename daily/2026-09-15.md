# SOC Interview Practice - 2026-09-15

## Question 64

### Interview Question

A Windows alert shows that a new user account was created. What does Security Event ID 4720 mean, and how would you investigate whether the account is legitimate provisioning or attacker persistence?

### Interview-Ready Answer

**Windows Security Event ID 4720 means that a new user account was created.** Microsoft documents that the event is generated when a new user object is created and can occur on domain controllers, member servers and workstations. It is an account-creation observation, not proof of compromise.

MITRE ATT&CK maps adversary account creation to **T1136, Create Account**, with sub-techniques for local, domain and cloud accounts. Current MITRE detection guidance recommends correlating account-creation telemetry such as Event 4720 with process lineage and user context. Attackers may create accounts for persistence or secondary credentialed access, but legitimate onboarding, service-account provisioning and administrative workflows also create accounts.

So I would separate:

**Observation:** a new account was created.

**Hypotheses:** approved user/service provisioning, administrator testing, automation, or unauthorised persistence.

**Confirmed malicious account creation:** requires supporting evidence showing that the account was created without authorisation or was subsequently used for malicious activity.

As Tier 1, I would identify the creator and target account, determine whether the account is local or domain-based, validate the ticket/change or HR/service request, and inspect what privileges or group memberships the new account received. I would then correlate authentication and endpoint/process evidence around the creation and look for subsequent use of the account.

### Real-World SOC Scenario

A domain controller records Event 4720 at 02:20 for a newly created account named `svc-backup2`.

The account was created by an administrator identity, but there is no approved change ticket. Minutes later, the new account is added to a privileged group and authenticates to two servers.

My **observation** is that a new domain account was created and then used.

My **hypothesis** is that a compromised privileged identity may have created a persistence account.

I would correlate:

**creator session -> account creation -> group membership changes -> first authentication -> endpoint/network activity**

If the administrator denies the action, there is no authorised provisioning request and the new account receives unexpected privilege or begins suspicious remote activity, the persistence hypothesis becomes strong and I would escalate.

### What I Would Check as a Tier 1 Analyst

- Host/domain controller and Event 4720 timestamp
- Subject account that created the user
- Target account name and SID
- Whether the account is local or domain-based
- Approved HR, service-account, IAM or change request
- Creator's related successful logon and source context
- New account attributes and expected naming convention
- Group membership or privilege changes after creation
- First successful and failed authentications by the new account
- RDP, SMB, WinRM or other remote activity
- Event 4688 or EDR/Sysmon process evidence where available
- Similar account creation on other systems
- Whether the account was later disabled or deleted
- Business owner confirmation where appropriate
- Tier 1 escalation and containment authority

### Tools / Logs

Windows Security Event 4720; related authentication and account/group-management events; Microsoft Sentinel; Splunk; Wazuh; Defender for Endpoint or another EDR; Sysmon where configured; Active Directory administration/audit evidence; IAM/change-management records.

### Interview Takeaway

Event 4720 means a user account was created. I would not label it persistence from the event alone. I would validate who created the account, whether it was authorised, what privileges it received and what the account did afterwards.

## Question 65

### Interview Question

A user reports clicking a suspicious email link. How would you investigate the incident using Microsoft Defender for Office 365, and what is the difference between Safe Links and Safe Attachments in that investigation?

### Interview-Ready Answer

**Safe Links and Safe Attachments protect different parts of the email attack surface.** In Microsoft Defender for Office 365, Safe Links provides URL protection, including time-of-click checking in supported scenarios. Microsoft states that when a protected user clicks a URL, Safe Links checks it before the website opens and can present a warning if the destination is malicious. Safe Attachments instead uses a virtual environment to detonate and analyse email attachments for malicious behaviour before delivery according to the applicable policy.

That means a user's statement that they clicked a link is only the starting observation. I would determine which message contained the URL, whether Safe Links evaluated the click, the URL/verdict and action available in the Defender evidence, whether the user reached the destination, and what the endpoint and identity did afterwards.

I would not say that Safe Links guarantees no compromise simply because it was enabled. Protection depends on policy, workload, user scope and the specific event. I would also not use Safe Attachments as evidence about a URL unless an attachment was actually involved.

So I would separate:

**Observation:** the user clicked a URL in a suspicious message.

**Hypotheses:** Safe Links blocked the destination; the user reached a benign or malicious page; credentials were entered; a payload was downloaded; or no harmful action followed.

**Confirmed impact:** requires evidence of credential submission, malicious execution, unauthorised authentication or other harmful activity.

### Real-World SOC Scenario

A finance user reports clicking an urgent Microsoft 365 password-expiry link.

In Defender for Office 365, I identify the message and URL/click evidence. The link was delivered in a phishing message and the user says a login page appeared.

My **observation** is that the user clicked the phishing URL and saw a credential page.

My **hypothesis** is credential phishing with possible account compromise.

I would correlate:

**message -> URL/click evidence -> browser/endpoint activity -> Entra sign-ins/MFA -> post-login cloud activity**

If the user confirms entering credentials and Entra then shows an unfamiliar successful session followed by mailbox or SharePoint activity, the account-compromise hypothesis becomes strong. If Safe Links blocked access before the destination loaded and there is no endpoint or identity evidence of impact, that supports a contained event, while I would still scope other recipients and clicks.

### What I Would Check as a Tier 1 Analyst

- Sender, Reply-To, routing and authentication results
- Network Message ID or other message identifier available in the investigation
- Other recipients of the same message
- URL and redirect chain where available
- Defender URL/click evidence and verdict/action
- Safe Links policy coverage for the user/workload
- Whether the user clicked through a warning where policy allows it
- Exact user actions, including whether credentials were entered
- Downloaded files or browser child processes
- Defender for Endpoint process/network evidence
- Entra sign-ins, MFA and device/session context
- Mailbox rules, OAuth grants or cloud activity after the click where relevant
- Safe Attachments verdict only if an attachment was involved
- Similar clicks by other users
- Tier 1 containment/escalation authority

### Tools / Logs

Microsoft Defender for Office 365 Threat Explorer/real-time detections where licensed; Safe Links click/URL evidence; Safe Attachments evidence where applicable; Defender XDR; Defender for Endpoint; Microsoft Entra sign-in/audit logs; Microsoft Sentinel; Splunk/Wazuh where integrated; DNS/proxy/firewall/browser telemetry.

### Interview Takeaway

Safe Links protects URLs and can check them at click time, while Safe Attachments detonates attachments. After a suspicious click, I would trace the message and URL evidence, establish exactly what the user did, and correlate endpoint and identity telemetry before deciding whether the event was blocked, merely attempted, or resulted in compromise.

## Question 66

### Interview Question

A cloud-security alert says a user downloaded or transferred an unusually large volume of files. How would you investigate possible cloud data exfiltration without assuming that every mass download or upload is malicious?

### Interview-Ready Answer

**Data exfiltration is the unauthorised transfer of data out of an organisation or trusted environment.** A large download or upload is an observation, not proof of exfiltration. Legitimate migrations, backups, synchronisation, reporting and user workflows can move large volumes of data.

MITRE ATT&CK maps use of legitimate web services for exfiltration to **T1567, Exfiltration Over Web Service**, including **T1567.002, Exfiltration to Cloud Storage**. Current MITRE detection guidance recommends correlating large file access or staging with unusual outbound HTTPS/API activity and the responsible process or account.

Microsoft Defender for Cloud Apps also documents anomalous file-download detection based on multiple file downloads in a session relative to a learned baseline, and activity policies can be configured to detect mass downloads. Such alerts indicate unusual behaviour and require investigation; they do not prove theft.

So I would separate:

**Observation:** unusually high-volume file access, download or upload occurred.

**Hypotheses:** legitimate business activity, migration/synchronisation, compromised cloud account, insider misuse, or malware-driven staging/exfiltration.

**Confirmed exfiltration:** requires evidence that data left through an unauthorised destination or workflow, or other strong evidence of unauthorised transfer.

As Tier 1, I would identify the user, device/session, files and sensitivity, destination/service, volume and timeframe, and whether the activity matches the user's normal role. I would correlate cloud audit, identity, endpoint, DLP/CASB and proxy/network evidence and escalate quickly where sensitive data, privileged accounts or ongoing transfer are involved.

### Real-World SOC Scenario

Defender for Cloud Apps alerts that a finance user accessed or downloaded thousands of SharePoint files in one session. Soon afterwards, endpoint/proxy telemetry shows a large HTTPS upload to a personal cloud-storage service.

The user normally accesses only a small subset of the finance library.

My **observation** is abnormal high-volume data access followed by an external upload.

My **hypothesis** is staged data exfiltration, possibly from a compromised account or insider activity.

I would correlate:

**identity/session -> sensitive file access -> endpoint staging/archive activity -> external web-service upload -> destination/account context**

If the transfer is to an unauthorised personal service, sensitive files are involved, the user denies the activity or the endpoint shows suspicious staging/tooling, the exfiltration hypothesis becomes strong. I would preserve evidence and escalate according to the incident and data-loss playbook rather than deleting files or blocking accounts outside my authority.

### What I Would Check as a Tier 1 Analyst

- User, role and privilege
- Device, browser/session and source IP
- Cloud service and resource involved
- Number/volume of files and timeframe
- File names/types and data sensitivity where authorised
- Normal baseline for the user/team
- Defender for Cloud Apps alert/policy context where deployed
- Microsoft 365 or SaaS audit activity
- Destination cloud service/account/tenant where visible
- Endpoint file access, staging or archive creation
- Upload process/application
- Proxy/firewall/DNS and outbound volume
- DLP/CASB policy actions
- Entra sign-in/MFA/risk context
- OAuth/app activity where relevant
- Approved migration, backup, sync or business workflow
- Whether the transfer is ongoing
- Similar activity by other accounts
- Tier 1 containment/escalation and legal/privacy handling requirements

### Tools / Logs

Microsoft Defender for Cloud Apps; Microsoft 365 audit; Microsoft Entra; Defender for Endpoint; Microsoft Sentinel; Splunk/Wazuh; secure web gateway/proxy; firewall/DNS; DLP tooling; SaaS audit logs; approved threat intelligence.

### Interview Takeaway

A mass download or upload is a signal, not automatic exfiltration. I would establish who moved what data, from which session/device, to which destination, whether the workflow was authorised and whether endpoint, identity and network evidence supports unauthorised transfer.
