# SOC Interview Practice - 2026-09-17

## Question 70

### Interview Question
What are SPF, DKIM and DMARC, and how would you use their results during a phishing or spoofing investigation rather than treating an authentication failure as automatic proof of a malicious email?

### Interview-Ready Answer
SPF, DKIM and DMARC are complementary email-authentication controls. SPF identifies authorised sending sources for the MAIL FROM/envelope-sender domain. DKIM uses a cryptographic signature to verify signed message content and identifies the signing domain. DMARC uses SPF and/or DKIM results plus alignment with the visible From domain and lets a domain publish handling/reporting policy.

In a SOC environment, I would use these results as evidence, not as a standalone verdict. A message can fail authentication for legitimate reasons such as forwarding or an intermediary modifying a message, and a malicious message can also pass authentication if the attacker controls the sending domain or compromises a legitimate account.

**Observation:** the message has specific SPF, DKIM and DMARC results.

**Hypotheses:** legitimate mail with an authentication/routing issue, direct spoofing, attacker-controlled lookalike domain, or compromised legitimate sender.

**Confirmed phishing/spoofing:** requires broader evidence such as sender/domain context, headers, URLs/attachments, user interaction, reputation, identity and endpoint telemetry.

As Tier 1, I would inspect the Authentication-Results header, compare MAIL FROM, DKIM signing domain and visible From domain, understand DMARC alignment, trace the message and investigate payload/user impact. I would not change DNS authentication records; that is normally an email/security engineering or domain-administration responsibility.

### Real-World SOC Scenario
A finance user reports an invoice email that visually appears to come from a supplier. SPF passes for a third-party sending domain, DKIM passes for that same domain, but DMARC fails because neither authenticated domain aligns with the visible supplier From domain.

**Observation:** SPF/DKIM authentication succeeded for domains that do not align with the visible From domain, so DMARC failed.

**Hypothesis:** the visible supplier identity may be spoofed.

I would then inspect the full headers, Reply-To, URLs/attachments, sending infrastructure, prior legitimate supplier messages and whether other users received the message. If the user entered credentials or opened a payload, I would correlate Entra/identity, browser and EDR evidence. DMARC failure strengthens the spoofing hypothesis but is not my only evidence.

### What I Would Check as a Tier 1 Analyst
- Authentication-Results header: SPF, DKIM and DMARC
- MAIL FROM/envelope-sender domain versus visible From domain
- DKIM signing domain and DMARC alignment
- Reply-To and return path
- Message trace / Network Message ID where Microsoft 365 telemetry is available
- Sender/domain history and approved third-party mail services
- URLs, redirects and attachments using approved analysis processes
- Other recipients and similar messages
- User interaction: click, credential entry, attachment execution
- Entra sign-ins/MFA and mailbox/cloud activity if credentials may be exposed
- Defender for Office 365 / Proofpoint / Abnormal Security evidence where deployed
- EDR, DNS, proxy and firewall evidence for post-delivery impact
- Escalation according to phishing/BEC playbook

### Relevant Tools / Logs
Microsoft Defender for Office 365 and Exchange Online message/header evidence; Proofpoint or Abnormal Security where deployed; Microsoft Sentinel/Splunk/Wazuh where integrated; Entra sign-in/audit logs; EDR; DNS/proxy/firewall telemetry.

### Key Interview Takeaway
SPF checks authorised sending sources, DKIM validates a cryptographic message signature, and DMARC adds alignment with the visible From domain plus policy/reporting. In a SOC investigation I would use authentication results as evidence, then correlate headers, payload, user interaction, identity and endpoint activity before deciding whether the message is malicious.

## Question 71

### Interview Question
A Windows Security alert shows Event ID 4698. What does it mean, and how would you determine whether the scheduled task is legitimate administration or malicious persistence/execution?

### Interview-Ready Answer
Windows Security Event **4698** means **a scheduled task was created**. Microsoft documents fields including the Subject that requested the action, Subject Logon ID, Task Name and Task Content, where Task Content contains the task XML.

A scheduled task is not automatically malicious. Windows, software installers, enterprise management products and administrators create scheduled tasks legitimately. Attackers can also abuse Windows Task Scheduler for execution, persistence or privilege escalation. MITRE ATT&CK maps Windows Scheduled Task abuse to **T1053.005**.

**Observation:** a scheduled task was created.

**Hypotheses:** legitimate OS/application/management activity, administrator automation, or malicious execution/persistence.

**Confirmed malicious task:** requires evidence that the task is unauthorised and/or executes malicious or suspicious content in context.

I would identify the creator, task path/name, trigger, execution command/action, run-as account and surrounding endpoint activity. I would compare it with the host baseline and approved software/change activity. I would not delete or disable the task unless the playbook and my Tier 1 authority permit it, because scheduled tasks can be operationally important.

### Real-World SOC Scenario
A finance workstation records Event 4698 shortly after a suspicious email attachment was opened. The new task has a plausible update-style name but its action launches PowerShell from a user-writable path at logon. EDR shows the same process chain creating a file and then making an unusual outbound connection.

**Observation:** a new scheduled task was created after suspicious user activity.

**Hypothesis:** the task may provide recurring execution or persistence for malicious code.

I would correlate **email/user action -> process creation -> task creation -> task execution -> network/file behaviour**. If the task is absent from the approved baseline, was created by an unexpected process/account and launches suspicious content that produces malicious endpoint/network behaviour, the persistence/execution hypothesis becomes strong.

### What I Would Check as a Tier 1 Analyst
- Host and Event 4698 timestamp
- Subject account/SID and Subject Logon ID
- Task Name/path
- Task Content XML
- Trigger and schedule
- Action/command, arguments and executable/script path
- Run-as/security context
- Related Event 4624/session context where available
- Event 4688 or EDR process creation where available
- Sysmon Event 1/file/registry telemetry where configured
- Event 4702 if the task was subsequently updated
- File hash, signer, path and organisational prevalence
- Network/DNS activity from the task or child process
- Approved software deployment/change records and known baseline tasks
- Similar task creation on other endpoints
- Tier 1 containment/escalation authority

### Relevant Tools / Logs
Windows Security Events 4698, 4702, 4624 and 4688 where enabled; Defender for Endpoint or another EDR; Sysmon where configured; Microsoft Sentinel; Splunk; Wazuh; DNS/proxy/firewall telemetry; software inventory and change-management records.

### Key Interview Takeaway
Event 4698 tells me a scheduled task was created, not that malware definitely established persistence. I would validate the creator, task XML, trigger, action, run-as context and resulting process/network behaviour, then compare it with authorised baseline activity before escalating.

## Question 72

### Interview Question
What is Kerberoasting, and how would you investigate suspicious Kerberos service-ticket requests without assuming that every Event ID 4769 is an attack?

### Interview-Ready Answer
Kerberoasting is a credential-access technique in Active Directory in which an adversary with suitable domain access requests Kerberos service tickets for service principal names (SPNs) and then attempts to crack recoverable ticket material offline to obtain a service account credential. MITRE ATT&CK maps it to **T1558.003, Kerberoasting**.

Windows Security **Event ID 4769** means a Kerberos service ticket was requested. Microsoft states that it is generated on domain controllers when the Key Distribution Center receives a TGS request. Normal Kerberos environments generate many 4769 events, so the event alone does not prove Kerberoasting.

Current MITRE detection guidance recommends looking for anomalous TGS-request patterns, including unusual bursts of service-ticket requests, service accounts/SPNs outside the requester's normal baseline, and RC4 ticket encryption (etype 0x17) where that is anomalous for the environment, while correlating identity and endpoint activity. RC4 is therefore a useful signal in modern environments, not standalone proof of attack.

**Observation:** one or more Kerberos TGS requests occurred.

**Hypotheses:** normal application/service access, administration/testing, or Kerberoasting reconnaissance/credential access.

**Confirmed malicious activity:** requires corroborating evidence such as an abnormal request pattern, unexpected requester/SPNs, suspicious tooling/process activity and/or subsequent credential misuse.

As Tier 1, I would establish the requesting identity, source context, SPNs/service accounts requested, ticket encryption type, volume/timing and baseline. I would escalate suspicious credential-access activity and avoid resetting service accounts or changing Kerberos settings unless authorised, because those actions can affect production services.

### Real-World SOC Scenario
A normal user workstation generates a burst of 4769 events for many service accounts within a few minutes. Several tickets use RC4 (etype 0x17), and the requested SPNs are not normally accessed by that user. EDR also shows an unusual process on the workstation shortly before the requests.

**Observation:** anomalous high-volume TGS requests target multiple service accounts from an unexpected user/device.

**Hypothesis:** Kerberoasting may be underway to obtain service-account ticket material for offline cracking.

I would correlate **user/device -> process activity -> 4769 burst -> requested SPNs/encryption -> later authentication or privilege activity**. If the pattern is outside baseline, the endpoint process is suspicious and later activity shows misuse of a targeted service account, the credential-compromise hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst
- Domain controller and exact time window
- Requesting account and source context available in the event/associated telemetry
- Number and rate of Event 4769 requests
- Service Name/SPN and targeted service accounts
- Ticket Encryption Type, including whether RC4/0x17 is anomalous in this environment
- Ticket Options and result/failure context where relevant
- User/service baseline and legitimate application behaviour
- Whether the requester normally accesses those SPNs
- Related 4624/4648/4672 authentication/session evidence where available
- EDR/Sysmon process activity on the requesting endpoint
- Known admin, scanner or authorised security-testing activity
- Subsequent logons using targeted service accounts
- Privileged group membership and service-account privilege level
- Scope across other users/endpoints/DCs
- Tier 1 escalation and identity-containment authority

### Relevant Tools / Logs
Windows Security Event 4769 on domain controllers; correlated 4624/4648/4672 where available; Defender for Endpoint or another EDR; Microsoft Sentinel; Splunk; Wazuh; Sysmon where configured; Active Directory/SPN and service-account inventory; approved threat-intelligence context.

### Key Interview Takeaway
Kerberoasting abuses legitimate Kerberos service-ticket requests to obtain ticket material that can be attacked offline. Event 4769 is normal Kerberos telemetry, so I would look for anomalous request volume, unusual SPNs/requesters, encryption context and endpoint behaviour, then investigate whether any targeted service account was subsequently misused.

- Microsoft documents SPF as identifying authorised sending sources for the MAIL FROM domain, DKIM as cryptographically signing message elements, and DMARC as using SPF/DKIM plus domain alignment with the visible From domain and policy/reporting. Microsoft also documents that forwarding/intermediaries can legitimately disrupt authentication, so failures require context.
- Microsoft documents Event 4698 as "A scheduled task was created" and exposes Subject, Logon ID, Task Name and Task Content XML. Microsoft recommends monitoring task creation, while MITRE ATT&CK T1053.005 covers adversary abuse of Windows Scheduled Tasks for execution, persistence and privilege escalation.
- Microsoft documents Event 4769 as a Kerberos service ticket request generated on domain controllers. MITRE ATT&CK T1558.003 covers Kerberoasting. MITRE DET0157 highlights anomalous TGS requests, RC4 etype 0x17 where anomalous, bursts of requests and unusual service-account targeting; these are detection signals rather than proof in isolation.
