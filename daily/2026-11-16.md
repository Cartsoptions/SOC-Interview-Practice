# SOC Interview Practice — 2026-11-16

**Curriculum:** Questions 217–220 | Password-spray triage, Entra sign-in evidence, Microsoft Sentinel KQL, and MFA-fatigue account takeover

## Question 217

### Interview Question

Microsoft Sentinel raises an incident after one public IP generates 240 failed interactive Microsoft Entra sign-ins against 85 user accounts in 20 minutes. No single account has more than four failures. What is a SIEM doing in this scenario, and how would you decide whether this is a password spray rather than ordinary user error?

### Interview-Ready Answer

A SIEM centralises security telemetry, applies detection logic and correlation, and gives analysts an incident workspace for investigation. In this scenario, Sentinel is connecting a shared source IP, a short time window and failures across many identities. It is not proving that the IP is malicious or that an account was compromised.

The pattern is consistent with password spraying because an attacker typically tries one password or a small list against many accounts, reducing the failures recorded against any one account and helping avoid lockout thresholds. MITRE ATT&CK describes this as Password Spraying, T1110.003. By comparison, a traditional brute-force attempt usually tries many passwords against one or a small number of accounts.

I would preserve the Sentinel incident and underlying `SigninLogs` events, then validate the source IP, time range, distinct users, applications, failure codes, client applications, user agents, locations, autonomous system and whether the identities follow an automated naming or directory pattern. I would check whether the address belongs to a corporate VPN, trusted proxy, penetration test, identity provider or other shared service that could explain the volume.

I would then look for successful or interrupted sign-ins from the same source, especially successful password validation followed by failed MFA, and inspect each potentially affected user's normal locations, devices, applications and subsequent activity. Microsoft notes that a password-spray risk detection in Entra ID Protection indicates that a spray was observed and a successful credential validation was confirmed; unsuccessful spraying alone does not generate that specific Identity Protection detection. Licensing and telemetry availability must therefore be checked before treating the absence of a risk detection as reassurance.

Tier 1 should document the observation, working hypothesis, enrichment and confidence, then escalate according to the playbook. Blocking an address may be appropriate only through authorised owners and after considering shared VPNs, proxies and rapidly changing attacker infrastructure.

### Real-World SOC Scenario

The IP belongs to a commercial hosting provider, targets accounts alphabetically, uses the same browser signature and produces repeated invalid-credential failures. One targeted account later records a successful password step from the same address but fails the MFA challenge.

- **Observation:** One unfamiliar hosting IP generates low counts per account but a high number of failures across 85 identities.
- **Hypothesis:** The source is conducting a low-and-slow password spray intended to avoid per-user lockout thresholds.
- **Confirmed Evidence:** The cross-account pattern, regular timing, hosting-provider source and repeated authentication characteristics establish an automated spray; a successful password step indicates that one credential may be correct, although MFA prevented a completed sign-in.

The verdict is **high-severity true-positive password spray with one potentially exposed password; completed account takeover is not yet confirmed**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the Sentinel incident, query results and raw sign-in records.
2. Confirm the time window, IP address, distinct users and failure volume.
3. Review `ResultType` and `ResultDescription` rather than treating every non-zero result as an incorrect password.
4. Check applications, client types, device details, locations and user-agent consistency.
5. Enrich the IP with ownership, ASN, VPN/proxy and approved-business context.
6. Search for successful and interrupted sign-ins from the source.
7. Review targeted users for later sign-ins, MFA prompts, mailbox/cloud activity and risky-user evidence.
8. Check for authorised testing, corporate egress or identity-service explanations.
9. Escalate possible credential exposure and authorised containment requirements.
10. Record detection limitations, evidence gaps and tuning opportunities.

### Relevant Tools / Logs

Microsoft Sentinel and `SigninLogs`, Microsoft Entra sign-in and Identity Protection evidence where licensed, Defender XDR/Defender for Cloud Apps where available, Splunk, firewall/VPN/proxy logs, threat-intelligence enrichment, identity inventory and the incident-management system.

### Key Interview Takeaway

A SIEM correlates evidence; it does not create certainty. Password spraying is identified by the many-accounts/few-attempts pattern, but compromise requires evidence of successful credential validation, completed access or malicious follow-on activity.

## Question 218

### Interview Question

During the password-spray investigation, one targeted user has 12 failures, then a sign-in with `ResultType` 0 from the same IP. Conditional Access shows success, but the user says they were not working. Does that prove account compromise, and what Entra evidence would you examine next?

### Interview-Ready Answer

`ResultType` 0 means the recorded sign-in succeeded. It is strong evidence that access was granted, but it does not by itself establish who controlled the session or what happened afterward. I would treat the event as suspected compromise and rapidly correlate identity, device and workload activity.

Microsoft documents `SigninLogs` fields including `IPAddress`, `UserPrincipalName`, `ResultType`, `ResultDescription`, `AuthenticationRequirement`, `AuthenticationDetails`, `AuthenticationMethodsUsed`, `ConditionalAccessStatus`, `DeviceDetail`, `ClientAppUsed`, `AppDisplayName`, `LocationDetails`, risk properties and correlation identifiers. The Authentication Details view shows the sequence of authentication methods, whether each step succeeded and why. I would use those records rather than infer that a generic success necessarily involved a fresh password and MFA prompt; authentication requirements can sometimes be satisfied by existing claims or sessions.

I would compare the successful event with the failed attempts and the user's baseline: source IP and ASN, location, application, client, device ID, operating system, browser, authentication methods, Conditional Access evaluation and risk signals. I would determine whether the source is a trusted VPN or shared service and independently confirm with the user through an established contact method.

Next I would scope what the session did: mailbox access and rules, file access, Teams/SharePoint/OneDrive activity, Azure or Microsoft 365 administrative actions, OAuth consent, authentication-method changes, new devices, role/group changes and additional sign-ins or token use. I would also correlate endpoint telemetry in case phishing or malware exposed the credentials.

If the user denies the event and the evidence shows unfamiliar successful access with suspicious follow-on activity, I would escalate as confirmed or highly likely account compromise. Authorised responders may block the user, reset the password, revoke sessions/tokens, require MFA re-registration and disable compromised devices. Tier 1 should not perform privileged containment outside assigned permissions.

### Real-World SOC Scenario

The successful sign-in comes from the spray IP and an unrecognised Linux browser. Minutes later, the account accesses Exchange Online, creates an external forwarding rule and grants consent to an unfamiliar application. The user denies all activity.

- **Observation:** A successful sign-in follows the spray from the same source and uses an unfamiliar device profile.
- **Hypothesis:** The attacker found the password, completed authentication and established mailbox or OAuth persistence.
- **Confirmed Evidence:** User denial, sign-in evidence, mailbox audit and consent records prove unauthorised access and follow-on changes.

The verdict is **critical true positive — cloud account compromise following password spraying, with mailbox and OAuth persistence**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the complete sign-in sequence and correlation identifiers.
2. Examine authentication steps, methods and Conditional Access results.
3. Compare IP, ASN, location, device, browser, application and client with the user's baseline.
4. Verify the activity independently with the user.
5. Review mailbox, file, collaboration and cloud-administration audit logs.
6. Check inbox/forwarding rules, OAuth grants and authentication-method changes.
7. Search for other users accessed from the same infrastructure.
8. Correlate endpoint evidence for phishing, token theft or malware.
9. Escalate for authorised identity, session, application and device containment.
10. Document what the sign-in proves and what follow-on evidence confirms compromise.

### Relevant Tools / Logs

Microsoft Entra `SigninLogs` and audit logs, Identity Protection where licensed, Microsoft Sentinel, Defender XDR/Defender for Cloud Apps, Exchange and Unified Audit Log evidence, OAuth consent and authentication-method records, endpoint telemetry, Splunk and the incident-management system.

### Key Interview Takeaway

A successful sign-in proves access was granted, not who controlled it. Confirm compromise by combining authentication details, user verification and the session's subsequent actions.

## Question 219

### Interview Question

Write a first-pass Microsoft Sentinel KQL hunt for interactive password-spray candidates where one IP fails against many users and then records a successful sign-in. Explain what the query proves and its limitations.

### Interview-Ready Answer

I would use a transparent investigation query with tunable thresholds rather than present it as a universal production rule:

```kusto
let Lookback = 1d;
let SprayWindow = 15m;
let MinimumFailures = 20;
let MinimumUsers = 10;
let CandidateSprays =
    SigninLogs
    | where TimeGenerated >= ago(Lookback)
    | where IsInteractive == true
    | where tostring(ResultType) != "0"
    | summarize
        FirstFailure = min(TimeGenerated),
        LastFailure = max(TimeGenerated),
        FailedAttempts = count(),
        TargetedUsers = dcount(UserPrincipalName),
        SampleUsers = make_set(UserPrincipalName, 20),
        FailureCodes = make_set(ResultType, 20)
      by IPAddress, WindowStart = bin(TimeGenerated, SprayWindow)
    | where FailedAttempts >= MinimumFailures
        and TargetedUsers >= MinimumUsers;
let SuccessfulSignins =
    SigninLogs
    | where TimeGenerated >= ago(Lookback)
    | where IsInteractive == true
    | where tostring(ResultType) == "0"
    | project
        IPAddress,
        SuccessTime = TimeGenerated,
        SuccessfulUser = UserPrincipalName,
        AppDisplayName,
        ClientAppUsed,
        AuthenticationRequirement,
        ConditionalAccessStatus,
        Location,
        DeviceDetail;
CandidateSprays
| join kind=inner SuccessfulSignins on IPAddress
| where SuccessTime between (FirstFailure .. LastFailure + 30m)
| project
    WindowStart,
    FirstFailure,
    LastFailure,
    IPAddress,
    FailedAttempts,
    TargetedUsers,
    SampleUsers,
    FailureCodes,
    SuccessTime,
    SuccessfulUser,
    AppDisplayName,
    ClientAppUsed,
    AuthenticationRequirement,
    ConditionalAccessStatus,
    Location,
    DeviceDetail
| order by SuccessTime desc
```

Microsoft documents the fields used here. It also publishes a slow-brute-force example that groups failures by IP and counts distinct users, confirming that this is a supported investigative pattern. Thresholds must be tuned to the organisation's population, sign-in volume and trusted egress architecture.

The query proves that Sentinel recorded many failed interactive sign-ins across multiple users from an IP and then a successful interactive sign-in from the same IP within the chosen period. It does **not** prove that:

- The success belonged to one of the accounts targeted in the failed attempts.
- The failures were all invalid passwords; non-zero result codes have different meanings.
- The source is malicious rather than a VPN, proxy, identity provider or authorised test.
- The successful session was controlled by an attacker.
- MFA was freshly completed, or the account performed malicious actions.

I would open the raw records, interpret the failure codes, verify the successful user against the targeted-user evidence, review authentication details and correlate user, device, workload and network activity. A production analytic should include documented exclusions, testing, alert grouping, entity mapping and scheduled review.

### Real-World SOC Scenario

The query returns three candidate IPs. Two are corporate VPN exits with ordinary user mistakes. The third is a hosting-provider address targeting 64 users and followed by a successful sign-in for one of those users, an unfamiliar OAuth consent and mailbox-rule creation.

- **Observation:** Three IPs meet the numerical thresholds.
- **Hypothesis:** At least one may represent a successful password spray.
- **Confirmed Evidence:** Enrichment clears the corporate VPNs; targeted-user validation and post-authentication audit evidence confirm compromise from the hosting-provider IP.

The verdict is **one critical true-positive identity compromise and two benign shared-egress results requiring documented suppression or tuning**.

### What I Would Check as a Tier 1 Analyst

1. Confirm that Entra sign-in logs are connected and retained for the investigation window.
2. Validate the query in the intended Sentinel workspace and inspect raw records.
3. Tune time and count thresholds against normal sign-in volume.
4. Interpret failure codes and remove known benign service behavior.
5. Enrich IPs and maintain approved VPN/proxy/test exclusions.
6. Confirm whether the successful user was actually targeted.
7. Review authentication details, user baseline and subsequent activity.
8. Save relevant results or bookmarks according to the investigation process.
9. Escalate confirmed compromise; send detection changes for authorised testing.
10. Record false-positive causes and a review date for exclusions.

### Relevant Tools / Logs

Microsoft Sentinel Logs and incidents, `SigninLogs`, Microsoft Entra sign-in and audit data, Defender XDR/Defender for Cloud Apps, threat-intelligence and IP-ownership sources, Splunk where Entra data is ingested, and detection-engineering records.

### Key Interview Takeaway

KQL builds an evidence queue, not a verdict. Explain exactly what the query selects, validate the raw events, tune it to the environment and correlate the successful session before declaring compromise.

## Question 220

### Interview Question

A user receives repeated Microsoft Authenticator prompts they did not initiate, denies several, then accidentally approves one. Entra records a successful sign-in from an unfamiliar IP, followed by a new authentication method, SharePoint downloads and an attempted role change. How would you handle this MFA-fatigue incident as Tier 1?

### Interview-Ready Answer

I would treat this as a critical identity-compromise incident because the user confirms approving an attacker-generated prompt and the logs show successful access followed by persistence and potentially high-impact activity. MITRE ATT&CK describes repeated MFA request generation as T1621. An MFA prompt is evidence that an authentication flow reached the additional-factor stage; it does not, by itself, establish how the password or session was obtained.

I would preserve the complete Entra sign-in and audit sequence, authentication details, correlation identifiers, source IPs, device and application information, Conditional Access results, authentication-method registration, directory changes, file access and attempted role modification. I would record the user's account of the prompts, including times and which response was approved, without relying on memory as the only evidence.

Through the approved incident playbook, I would immediately escalate to the identity and incident-response owners for authorised containment. Microsoft documents relevant actions such as blocking the user, resetting the password, revoking refresh tokens or sessions, requiring MFA re-registration and disabling compromised devices. The exact order and execution belong to authorised administrators and must protect emergency-access procedures and business continuity.

Scoping would include all sessions and tokens, additional IPs, registered authentication methods, OAuth grants, enterprise applications, inbox and forwarding rules, role and group changes, SharePoint/OneDrive/Teams and mailbox access, downloads, administrative actions, affected devices and other users receiving prompts from the same infrastructure. I would check whether phishing, password reuse, token theft, help-desk social engineering or endpoint compromise explains the initial access.

Recovery requires restoring the identity to a trusted state, removing unauthorised methods or consent, rotating exposed credentials and secrets, validating device health, reviewing downloaded data and monitoring for renewed token or authentication activity. CISA recommends phishing-resistant MFA; number matching is an interim mitigation for push fatigue rather than equivalent protection. Tier 1 should preserve evidence, maintain the timeline and scope, communicate verified facts and support the authorised response without independently changing enterprise identity controls.

### Real-World SOC Scenario

The user confirms one accidental approval. Audit logs show an attacker-added phone method, 180 SharePoint files downloaded, an external forwarding rule and a failed attempt to add the account to a privileged group. A phishing site visited earlier explains the stolen password; no endpoint malware is found.

- **Observation:** Repeated unsolicited MFA prompts culminate in an approved sign-in and immediate cloud changes.
- **Hypothesis:** The attacker obtained the password through phishing and used MFA fatigue to gain access, add persistence and seek privilege or data.
- **Confirmed Evidence:** User confirmation, authentication records, method registration, audit activity and file-download evidence establish unauthorised access and impact.

The verdict is **critical true positive — MFA-fatigue account takeover with authentication persistence, data access and attempted privilege escalation; wider data exposure remains under assessment**.

### What I Would Check as a Tier 1 Analyst

1. Preserve sign-in, authentication-step, audit and user-report evidence.
2. Build a UTC timeline from the first prompt through all post-access actions.
3. Escalate immediately for authorised account, session and authentication-method containment.
4. Review all active sessions, refresh tokens, source IPs, devices and applications.
5. Identify newly registered methods, OAuth grants, inbox rules and delegated access.
6. Scope file, mailbox, collaboration and administrative activity.
7. Check attempted or completed role, group and Conditional Access changes.
8. Correlate the initial phishing, password reuse or endpoint evidence.
9. Support credential reset, MFA re-registration and trusted device validation.
10. Assess data exposure with file names, sensitivity, volume and destination evidence.
11. Monitor for recurring sign-ins, prompts, tokens and attacker infrastructure.
12. Feed lessons into phishing-resistant MFA, number matching, user reporting and detection coverage.

### Relevant Tools / Logs

Microsoft Entra sign-in and audit logs, authentication-method and risky-user evidence where licensed, Microsoft Sentinel, Defender XDR/Defender for Cloud Apps, Microsoft 365 Unified Audit Log, Exchange, SharePoint, OneDrive and Teams audit evidence, endpoint telemetry, Splunk, phishing/email evidence and the incident-management system.

### Key Interview Takeaway

MFA fatigue becomes confirmed compromise when the attacker obtains an approval and the evidence shows unauthorised access. Contain the identity, sessions, methods and persistence together, then scope data and privilege impact before trusted recovery.
