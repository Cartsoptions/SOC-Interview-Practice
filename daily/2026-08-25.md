# SOC Interview Practice — 2026-08-25

## Question 19

### Interview Question

What is the difference between a true positive, a benign positive and a false positive alert, and how would you decide which one you are looking at in a SOC?

### Interview-Ready Answer

I would define them in operational terms. A **true positive** means the alert accurately identifies genuinely malicious or threat-related activity. A **benign positive** means the detection accurately observed suspicious-looking behaviour, but the behaviour is expected and authorised, such as an approved penetration test, security scan or unusual but legitimate administrator activity. A **false positive** means the alert incorrectly identified non-malicious activity as suspicious because of inaccurate logic, data or another detection problem.

In a SOC environment, I would not classify an alert from the title or severity alone. I would validate the underlying evidence: what triggered the rule, which user/device/IP/process is involved, whether the behaviour actually occurred, whether it is authorised, and whether supporting endpoint, identity or network telemetry shows malicious impact.

Microsoft Sentinel currently distinguishes True Positive – suspicious activity, Benign Positive – suspicious but expected, False Positive – incorrect alert logic, False Positive – incorrect data, and Undetermined when closing incidents. Microsoft Defender XDR similarly distinguishes true positive threats, expected/informational activity and false positives.

As a Tier 1 analyst, I would document why I reached the classification. If the alert repeatedly fires on authorised activity, I would raise the tuning issue through the appropriate process rather than independently weakening a production detection unless that is within my authority.

### Real-World SOC Scenario

A SIEM rule alerts because an internal host performs rapid connections to many systems. My first hypothesis might be scanning. I investigate the source host, account, timing and destination pattern. If I confirm the host belongs to the vulnerability-management team and the activity matches an approved scan window, the detection may be a benign positive: the suspicious-looking activity really happened, but it was authorised. If the rule fired because a parser incorrectly populated the source IP, that may be a false positive caused by inaccurate data. If the same pattern comes from an unauthorised workstation and is followed by exploitation attempts, the alert may be a true positive.

### What I Would Check as a Tier 1 Analyst

- Exact detection logic and evidence that triggered the alert
- User, host, IP, process, domain and timeframe
- Whether the activity actually occurred
- Whether an approved change, scan, penetration test or admin task explains it
- Endpoint, identity, firewall, DNS, proxy and application evidence where relevant
- Similar alerts and historical classification in the environment
- Whether there is evidence of malicious execution, access, persistence or impact
- Whether the issue points to inaccurate data or overly broad detection logic
- Required incident comments and closure classification
- Whether alert-tuning changes require escalation to detection engineering

### Relevant Tools / Logs

Microsoft Sentinel; Microsoft Defender XDR; Splunk; Wazuh; EDR; identity logs; firewall/DNS/proxy logs; change-management records; vulnerability-scanner schedules; incident-management system.

### Key Interview Takeaway

A true positive is genuinely malicious, a benign positive is suspicious-looking but authorised activity, and a false positive is an incorrect alert. I would classify the alert only after validating the underlying evidence and business context, then document the reasoning and escalate tuning issues through the proper process.

## Question 20

### Interview Question

What is Windows Security Event ID 4688, and how would you use it together with Sysmon during an investigation of suspicious process execution?

### Interview-Ready Answer

Windows Security Event ID **4688** records that a new process was created, provided Audit Process Creation is enabled. It can include details such as the new process name, process IDs, creator/parent information and, when the separate command-line auditing policy is enabled, the process command line. Microsoft notes that the command-line field is empty by default unless **Include command line in process creation events** is configured.

Sysmon complements native Windows logging. Sysmon Event ID **1** records process creation with extended context such as the full command line, parent process information, ProcessGUID and configured hashes. Sysmon can also provide additional telemetry such as network connections when those event types are enabled. Sysmon itself does not decide whether activity is malicious; it records telemetry for analysts and detection tools to interpret.

In a SOC investigation, I would use process-creation evidence to answer: what executed, who launched it, what spawned it, with what arguments, and what happened next. I would correlate process creation with file, registry, PowerShell, EDR and network evidence instead of declaring a process malicious from its name alone.

### Real-World SOC Scenario

An alert reports `rundll32.exe` executing on a user workstation. The filename alone is not enough because `rundll32.exe` is a legitimate Windows component. I would inspect Event 4688 and/or Sysmon Event 1 for the executable path, parent process, user, process identifiers and command line where available. If the parent is an Office application, the command line references an unusual DLL from a user-writable directory, and subsequent telemetry shows an external connection, the combined behaviour is more suspicious than `rundll32.exe` by itself.

### What I Would Check as a Tier 1 Analyst

- Whether Audit Process Creation is enabled for 4688 coverage
- New process name and full path
- New process ID and creator/parent process information
- User/security context and logon context where available
- Command line, while confirming whether command-line auditing is enabled
- Sysmon Event ID 1 fields such as ProcessGUID, parent process and configured hashes
- File path, hash, signature and prevalence from EDR where available
- Child processes and subsequent process chain
- PowerShell/script telemetry if scripting is involved
- File or registry changes and persistence
- DNS/proxy/firewall/EDR network activity
- Whether the process chain matches approved software or administration

### Relevant Tools / Logs

Windows Security Event 4688; Sysmon Event 1; Microsoft Defender for Endpoint or other EDR; Wazuh; Splunk; Microsoft Sentinel; PowerShell Operational logs; DNS/proxy/firewall telemetry; file-signature/hash tools.

### Key Interview Takeaway

Event 4688 tells me a process was created when Windows process auditing is enabled, while Sysmon Event 1 can provide richer process context. I would use the parent-child relationship, path, command line, hash and resulting behaviour to judge the activity rather than relying on the executable name alone.

## Question 21

### Interview Question

What is the difference between containment, eradication and recovery during incident response, and what would your role be as a Tier 1 SOC analyst?

### Interview-Ready Answer

I would explain the concepts operationally. **Containment** is about limiting further damage or spread, for example isolating an endpoint, disabling a compromised account or blocking malicious infrastructure when authorised. **Eradication** is about removing the malicious artefacts or root cause, such as removing malware, eliminating persistence, closing the exploited weakness or resetting compromised credentials. **Recovery** is about safely restoring normal operations and verifying that systems and accounts can return to service without the threat reappearing.

I would also note that NIST SP 800-61 Rev. 3, published in April 2025, is the current NIST incident-response publication. It integrates incident response into CSF 2.0 and maps the older Containment, Eradication & Recovery phase primarily across the Respond and Recover Functions rather than requiring organisations to use the older four-phase model unchanged.

As a Tier 1 analyst, my responsibility is normally to validate and scope the incident, collect and preserve relevant evidence, document findings, escalate according to severity and support authorised containment actions. I would not assume I have authority to isolate production systems, disable executive accounts or delete malware unless the organisation's playbook explicitly grants that authority.

### Real-World SOC Scenario

EDR confirms malware execution on a workstation and identifies outbound command-and-control traffic. Immediate containment might involve isolating the endpoint and blocking the malicious destination if authorised. Eradication would involve removing the malware and persistence, addressing the initial access vector and resetting affected credentials where necessary. Recovery would include restoring the workstation or service to a trusted state, reconnecting it under controlled conditions and monitoring for recurrence. My Tier 1 role would be to document the evidence and timeline, identify affected entities, escalate promptly and perform only the response actions authorised by the playbook.

### What I Would Check as a Tier 1 Analyst

- Evidence confirming the incident and affected user/host/account
- Scope: one endpoint or wider activity
- Active malicious processes, persistence and network connections
- Identity compromise and credential exposure
- Business criticality and potential impact
- Containment actions authorised for Tier 1
- Whether isolation, account disablement or blocking requires approval
- Evidence that malicious artefacts/root cause were removed
- Recovery validation and monitoring for recurrence
- Related alerts after restoration
- Required documentation, handoff and lessons/improvement notes

### Relevant Tools / Logs

EDR; SIEM; Windows/Linux logs; identity logs; firewall/DNS/proxy; email-security logs where relevant; vulnerability data; incident-management/ticketing system; organisation-specific response playbooks.

### Key Interview Takeaway

Containment limits damage, eradication removes the malicious cause or artefacts, and recovery restores trusted operations. As Tier 1, I would validate, scope, document and escalate the incident and perform only the containment or response actions that the organisation has authorised me to take.
