# SOC Interview Practice — 2026-10-08

**Curriculum:** Questions 121–124 | Linux remote access, SSH authentication, journal/sudo evidence, and persistence triage.  
**Evidence standard:** Observation → Hypothesis → Confirmed Evidence. Illustrative logs are labelled simulated, not presented as real incident records.

## Question 121

### Interview Question

What is SSH, and how would you use SSH telemetry during a Tier 1 SOC investigation?

### Interview-Ready Answer

SSH (Secure Shell) is a protocol for encrypted remote access and related operations, including remote commands and secure file transfer. In enterprise Linux environments, OpenSSH's `sshd` accepts remote connections and supports authentication methods including passwords and public keys. SSH commonly uses TCP port 22, but a server may be configured to listen on another port. A successful SSH authentication is not proof of compromise, and an open port 22 does not prove anyone logged in.

In a SOC environment, I would use SSH server authentication records to establish the target server, source IP, attempted username, timestamp, authentication method, outcome and whether the access fits an approved administrative workflow. I would correlate this with VPN/bastion logs, EDR or Linux audit telemetry and post-login activity. My Tier 1 responsibility is evidence collection, triage, documentation and escalation; changes to SSH configuration, keys or firewall rules are normally handled by authorised administrators/responders.

**Observation:** SSH activity or a successful login occurred.  
**Hypothesis:** The source or account could represent unauthorised remote access.  
**Confirmed Evidence:** Requires validation of unauthorised identity/session use and supporting host, access-control or user-confirmation evidence.

### Real-World SOC Scenario

A production Linux server records a public-key SSH login at 02:12 from an unfamiliar IP. I would check whether the source belongs to an approved bastion, deployment system or administrator, identify the account/key context and inspect subsequent actions. A scheduled deployment could explain the login; unauthorised commands and file changes could indicate compromise.

### What I Would Check as a Tier 1 Analyst

- Target host, criticality, time and timezone; source IP and port
- Account, authentication method and actual success/failure
- Approved VPN, bastion, deployment or maintenance context
- Key fingerprint where recorded, compared with approved inventory
- Post-login commands, sudo activity, file changes and network connections where available
- Other systems accessed by the same source/account
- Ticket, evidence and playbook escalation authority

### Tools / Logs

OpenSSH/sshd logs, systemd journal (`journalctl`), `/var/log/auth.log` where configured, sudo event logs, auditd/EDR, Wazuh, Splunk, Sentinel, bastion/VPN and firewall logs.

### Interview Takeaway

"SSH provides encrypted remote administration. In a SOC, I validate who accessed which Linux host, from where and how, then correlate authentication with authorised change activity and post-login evidence before deciding whether to escalate."

## Question 122

### Interview Question

How would you investigate suspicious SSH and sudo activity on a Linux server, and why should you not rely on one log file?

### Interview-Ready Answer

Linux authentication logging is distribution- and configuration-dependent; I would not claim that every Linux system has `/var/log/auth.log` or Windows-style universal Event IDs. On a systemd-based Ubuntu server I could inspect the SSH service journal, for example:

```bash
sudo journalctl -u ssh.service --since "2026-10-08 02:00:00" --until "2026-10-08 03:00:00" --no-pager
```

`journalctl` reads the systemd journal; `-u` filters to a unit and `--since`/`--until` select a time window. Ubuntu documents `ssh.service` for OpenSSH. The service name and log availability must be checked on the actual host. On some Ubuntu deployments, authentication events are also in `/var/log/auth.log` when syslog is configured. I would inspect centrally forwarded logs when available.

For privilege activity, I would examine sudo event logs. The sudoers manual documents successful/unsuccessful attempts and fields such as invoking username, TTY, working directory, target user and command. **A sudo event is not necessarily a complete transcript of everything done in the session**: detailed I/O or child-command logging depends on additional configuration.

**Observation:** SSH or sudo records show access or command invocation.  
**Hypothesis:** The activity could be unauthorised privileged access.  
**Confirmed Evidence:** Needs source/account authorisation and independent process, file, session or user evidence.

### Real-World SOC Scenario

An SSH login for a deployment account is followed by a sudo command. I would correlate timestamps and host/account context, check the deployment change ticket and look for unexpected commands or modifications. An approved release might explain both events.

### What I Would Check as a Tier 1 Analyst

- Distro, service name, log retention and ingestion health
- SSH success/failure, username, source IP, method and timestamps
- Sudo invoker, run-as user, recorded command and outcome where available
- Change approvals and whether the account is supposed to have sudo access
- Auditd/EDR process/file evidence and central SIEM copies
- Other related accounts/hosts, timeline and escalation threshold

### Tools / Logs

`journalctl`, sshd and sudo logs, `/var/log/auth.log` where present, auditd, Wazuh FIM, Splunk, Sentinel, EDR, bastion/VPN and change-management records.

### Interview Takeaway

"I would use the system's actual SSH and sudo logging sources, verify their configuration and correlate access with post-login behaviour. A sudo event records a command invocation, not necessarily everything a privileged session did."

## Question 123

### Interview Question

Interpret these **simulated** Linux authentication records. What can you conclude and what would you check next?

```text
Oct  8 02:11:02 app-02 sshd[2145]: Failed password for invalid user admin from 203.0.113.47 port 51421 ssh2
Oct  8 02:12:16 app-02 sshd[2188]: Accepted publickey for deploy from 203.0.113.47 port 51444 ssh2: ED25519 SHA256:EXAMPLE_FINGERPRINT
Oct  8 02:13:05 app-02 sudo: deploy : TTY=pts/0 ; PWD=/home/deploy ; USER=root ; COMMAND=/usr/bin/id
```

### Interview-Ready Answer

The first line records a failed SSH password attempt for an invalid account `admin` from documentation IP `203.0.113.47`. The second records successful public-key authentication to the `deploy` account from the same source IP. The third shows a sudo event in which `deploy` invoked `/usr/bin/id` as root, according to the simulated sudo log. The different usernames and authentication methods matter: **the logs do not prove that a password guess succeeded**. The same source IP might be shared NAT, a bastion or an automation host, and these three records do not by themselves establish that the SSH session and sudo action were operated by the same human.

I would check whether `deploy` is authorised for SSH and sudo, whether the public key fingerprint matches approved key inventory, whether the source IP is an expected jump/deployment host, and what other host activity occurred. I would confirm sudo outcome and the relationship between session and process using additional evidence; an invocation log alone does not prove every downstream action.

**Observation:** Failed invalid-user password attempt, successful public-key login to another account, then sudo invocation.  
**Hypothesis:** A source may have obtained or used deploy access and elevated command execution.  
**Confirmed Evidence:** Requires verification that the key/session or privileged action was unauthorised, with supporting logs or owner confirmation.

### Real-World SOC Scenario

A SIEM correlates these records and raises an SSH-to-sudo alert. If the source is an approved CI/CD runner performing a release, the sequence may be expected. If the key is unrecognised, the owner denies access and new persistence artefacts appear, I would escalate as likely compromise.

### What I Would Check as a Tier 1 Analyst

- Raw log integrity, timestamps and host identity
- Source IP ownership, bastion/NAT context and account baselines
- Accepted key fingerprint versus authorised inventory
- Login/session correlation and sudo outcome
- EDR/auditd process tree, file writes, network activity
- Additional attempts against other users/hosts
- Ticket notes: facts, uncertainty, verdict and escalation reason

### Tools / Logs

Linux sshd/sudo records, journal, SIEM (Splunk/Sentinel/Wazuh), auditd/EDR, VPN/bastion logs, approved key inventory and change records.

### Interview Takeaway

"The records show a failed password attempt for one account, successful key authentication for another, and a sudo invocation. I would not call this a successful brute-force attack without confirming the key, source, authorisation and post-login evidence."

## Question 124

### Interview Question

A Linux production server records a new public-key SSH login for `deploy` from an unfamiliar source. Minutes later sudo is used, and file-integrity monitoring reports a modification to `/home/deploy/.ssh/authorized_keys`. How would you triage it as Tier 1, and would you isolate the server?

### Interview-Ready Answer

I would prioritise this promptly because the sequence could indicate unauthorised remote access followed by SSH-key persistence. MITRE ATT&CK **T1098.004 (SSH Authorized Keys)** describes adversaries modifying `authorized_keys` to maintain access. However, the file can also be changed legitimately during key rotation or deployment; the event chain is not automatically confirmed compromise.

First I would verify the actual successful login and its source, user, method and key fingerprint. I would then identify the sudo actor/command and confirm the FIM alert's target path, change time and the nature of the modification. I would compare the authorised key inventory or a trustworthy previous version with the current file to determine whether an unapproved key was added. I would inspect file-change actor/process evidence from auditd/EDR if collected, correlate the events to the same account/session where possible and validate with the deployment/administrator owner through a trusted channel.

I would preserve logs and FIM evidence, look for additional SSH logins using the newly added key if fingerprint attribution is available, inspect other user `authorized_keys` files and SSH configuration changes, and scope other hosts accessed by the same source or account.

**Observation:** A successful SSH login, sudo event and `authorized_keys` modification occurred in sequence.  
**Hypothesis:** An attacker may have gained access and planted a key for persistence.  
**Confirmed Evidence:** Examples include an unapproved added public key attributable to unauthorised activity, owner denial of the login/change, and corroborating host/identity telemetry. Even then, the scope and impact need investigation.

**Containment decision:** If evidence indicates likely active compromise, I would urgently escalate and request the playbook's appropriate containment, including possible host isolation or SSH access restriction. I would isolate the server myself only if authorised, after considering critical production availability, preservation of evidence and whether remote isolation could disrupt essential services. I would not silently delete keys or restart SSH as an unauthorised Tier 1 action.

### Real-World SOC Scenario

The deployment owner confirms no key rotation was scheduled, the key is absent from approved inventory and EDR/auditd records show an unapproved process modifying `authorized_keys` after the unusual login. I would raise a likely SSH persistence incident, preserve the evidence, scope other systems and seek authorised containment immediately.

### What I Would Check as a Tier 1 Analyst

- Host criticality, SSH source, username, auth method, key fingerprint and login outcome
- Sudo command, actor, timestamps and related session/process context
- FIM old/new file state, added key, permissions and modification actor
- Approved key rotation, CI/CD deployment and change tickets
- Additional `authorized_keys` changes, SSH config and other privileged accounts
- Subsequent logins, outbound network traffic and other hosts accessed
- Evidence preservation, business impact, scope, ticket and authorised containment/escalation

### Tools / Logs

OpenSSH/sshd logs, sudo event logs, Wazuh FIM, auditd/EDR, Splunk, Sentinel, bastion/VPN, firewall/DNS telemetry, key inventory and change-management records.

### Interview Takeaway

"I would investigate the complete SSH → sudo → authorised-key-change chain, verify the new key and change approval, and scope additional access. If the evidence supports persistence, I would urgently escalate for authorised containment while preserving evidence and considering production impact."
