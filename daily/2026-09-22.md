# SOC Interview Practice — 2026-09-22

## Question 79

### Interview Question

Your SIEM alerts on unusual DNS activity from a workstation. What is DNS tunneling, and how would you investigate it without treating unusual DNS as proof of command-and-control?

### Interview-Ready Answer

DNS tunneling is the abuse of DNS traffic to carry data or command-and-control communications, often by encoding information into DNS queries or responses. MITRE ATT&CK maps DNS used for adversary command-and-control to T1071.004. DNS itself is normal and extremely common, so a long or unusual domain name is an observation, not proof of tunneling.

In a SOC environment, I would establish a baseline and correlate the DNS behaviour with the originating endpoint and process. I would look for high-frequency or periodic queries, unusually long or high-entropy subdomains, repeated queries to rare/new domains, unusual record types, unexpected DNS resolvers, and non-standard processes generating DNS. MITRE's current detection guidance specifically highlights anomalous/high-frequency DNS from non-browser or non-system processes and long/frequent subdomains as useful behavioural signals.

I would separate the evidence as follows: Observation: anomalous DNS queries occurred. Hypotheses: legitimate application/update/security tooling, misconfiguration, or DNS-based C2/tunneling. Confirmation requires supporting endpoint/network evidence or verified malicious infrastructure/behaviour.

### Real-World SOC Scenario

A finance workstation begins making frequent DNS requests containing long changing subdomains to one rare external domain. EDR shows that the DNS-related network activity is associated with an unexpected scripting process shortly after a suspicious file execution.

I would correlate endpoint process creation, DNS timestamps, domain age/reputation where available, query pattern and any subsequent network or identity activity. If the process is unauthorised and the DNS pattern is consistent with encoded bidirectional communication or known malicious infrastructure, the DNS-C2 hypothesis becomes strong. I would contain only within my authority and escalate with the evidence.

### What I Would Check as a Tier 1 Analyst

- Source host/user and time window
- Query name, parent domain, record type and response
- Query volume, periodicity, length and entropy patterns
- Rare/new domains and organisational prevalence
- Approved DNS resolver versus direct/external resolver use
- Initiating process where EDR provides it
- Process path, command line, signer/hash and parent process
- Related proxy/firewall/EDR activity
- Threat-intelligence/reputation context
- Similar activity on other hosts
- Tier 1 containment/escalation authority

### Tools / Logs

DNS resolver logs, Microsoft Sentinel/Splunk/Wazuh, firewall/proxy telemetry, Defender for Endpoint or another EDR, Microsoft Defender XDR DeviceNetworkEvents where available, Sysmon where configured, and approved threat-intelligence sources.

### Interview Takeaway

DNS tunneling abuses normal DNS to carry C2 or data. I would not diagnose it from one unusual query; I would correlate query behaviour, domain context and the initiating endpoint process, then look for repeatable communication and supporting malicious evidence.

### Verification Notes

- MITRE ATT&CK T1071.004: https://attack.mitre.org/techniques/T1071/004/
- MITRE DET0400 behavioural DNS-tunneling detection: https://attack.mitre.org/detectionstrategies/DET0400/
- Microsoft Defender XDR DeviceNetworkEvents schema: https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-devicenetworkevents-table

## Question 80

### Interview Question

You see access to C$ or ADMIN$ on a Windows server. How would you investigate possible SMB lateral movement without assuming administrative-share access is malicious?

### Interview-Ready Answer

SMB is used legitimately for Windows file/resource sharing and remote administration. Windows administrative shares such as C$, ADMIN$ and IPC$ are therefore not malicious by themselves. MITRE ATT&CK maps adversary abuse of SMB/Windows Admin Shares for lateral movement to T1021.002.

In a SOC environment, I would determine who accessed the share, from which source, whether that account/source normally performs administration, what files were copied, and whether remote execution followed. Microsoft documents Security Event 5140 as network-share access; it is generated when a network share is first accessed in a session when the relevant auditing is enabled. I would correlate share access with authentication, process/EDR and network evidence rather than relying on one event.

Observation: an administrative share was accessed. Hypotheses: legitimate IT administration/software deployment, security tooling, or attacker lateral movement. Strong confirmation requires evidence such as unauthorised credentials/source plus suspicious file transfer and follow-on remote execution/service/task/process activity.

### Real-World SOC Scenario

A normal employee workstation accesses ADMIN$ on several servers within minutes. The account is not an IT administrator. EDR then shows a binary appearing on one target and suspicious remote execution shortly afterwards.

I would build the timeline: source endpoint/account -> authentication -> SMB/admin-share access -> file transfer -> remote execution/persistence -> onward connections. MITRE's current SMB admin-share detection strategy specifically correlates remote share access with follow-on actions such as remote service creation, scheduled tasks or suspicious process execution.

### What I Would Check as a Tier 1 Analyst

- Source IP/device and user/account
- Target server and business criticality
- Share name such as C$, ADMIN$ or IPC$
- Whether the account/source is an approved administrator or management system
- Event 5140 where Audit File Share is enabled
- Authentication/logon evidence such as 4624/4648 where applicable and available
- EDR process/file timeline on source and target
- Files copied, hashes/signatures and paths
- Remote service, task or process activity after share access
- Firewall/SMB network telemetry
- Similar access across multiple hosts
- Approved change/deployment records
- Tier 1 containment/escalation authority

### Tools / Logs

Windows Security logs, Defender for Endpoint or another EDR, Microsoft Sentinel/Splunk/Wazuh, Sysmon where configured, firewall/network telemetry, Active Directory/identity context, asset inventory and change-management records.

### Interview Takeaway

C$ or ADMIN$ access is not automatically lateral movement. I would validate the account, source, target and administrative context, then correlate SMB access with file transfer and follow-on execution to determine whether the activity is authorised or attacker-driven.

### Verification Notes

- MITRE ATT&CK T1021.002 SMB/Windows Admin Shares: https://attack.mitre.org/techniques/T1021/002/
- MITRE DET0530 multi-event SMB admin-share lateral-movement detection: https://attack.mitre.org/detectionstrategies/DET0530/
- Microsoft Event 5140 documentation: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-5140

## Question 81

### Interview Question

A finance employee receives an email in an existing supplier thread asking for future invoice payments to go to a new bank account. There is no malware attachment. How would you investigate possible Business Email Compromise and respond if a payment may already have been sent?

### Interview-Ready Answer

Business Email Compromise (BEC) is fraud that abuses trusted business communications, often through spoofing, lookalike domains or a genuinely compromised mailbox, to induce actions such as fraudulent payments. It does not require malware, and a message can look convincing because attackers may exploit legitimate email threads or compromised accounts.

I would first treat the payment-change request as suspicious and verify it out-of-band using a previously trusted contact method, not contact details supplied in the suspicious email. The FBI specifically recommends independently verifying changes in account numbers/payment procedures. If money has already been transferred, this becomes time-critical: the financial/finance team and the organisation's fraud/incident process should be engaged immediately; the FBI's public guidance for BEC victims says to contact the financial institution immediately.

Technically, I would determine whether this is display-name/lookalike spoofing or account compromise. For Microsoft 365, I would inspect message headers/authentication, sender/reply-to, message trace/email-security evidence, Entra sign-ins, mailbox audit activity, suspicious inbox/forwarding rules and unusual sent/deleted messages. Microsoft documents suspicious inbox rules and recently added external forwarding as common symptoms of compromised Microsoft 365 email accounts.

Observation: a bank-detail change was requested by email. Hypotheses: legitimate supplier change, spoof/lookalike BEC, or compromised supplier/internal mailbox. Confirmation requires independent business verification plus technical evidence; a fraudulent payment instruction or verified compromised mailbox materially changes severity and response.

### Real-World SOC Scenario

Accounts Payable reports that a supplier email, inside a familiar invoice thread, requested a new bank account. The payment was sent 20 minutes ago. Header analysis shows the message came from the supplier's genuine mailbox, while mailbox evidence later reveals an unauthorised forwarding/inbox rule and suspicious sign-in activity.

I would immediately escalate the potential financial loss through the organisation's incident/fraud procedure so Finance can contact the bank/payment provider while the SOC preserves evidence and investigates the account/thread. I would scope other recipients, fraudulent messages, forwarding rules, sign-ins and downstream actions. Account/token containment would follow the approved identity-response playbook and authority model.

### What I Would Check as a Tier 1 Analyst

- Full message headers, From/Reply-To/Return-Path and authentication results
- Lookalike domain versus genuine compromised mailbox
- Original thread and timing of the bank-detail change
- Independent supplier verification using a known contact channel
- Whether payment was initiated/completed and immediate finance escalation
- Entra sign-in/audit evidence where the affected mailbox is in the tenant
- Suspicious inbox/forwarding rules and external forwarding
- Sent/Deleted Items and unusual mailbox activity
- Other recipients and similar payment-change messages
- Defender for Office 365/Proofpoint/Abnormal Security evidence where deployed
- Evidence preservation and authorised account/token containment

### Tools / Logs

Microsoft Defender for Office 365/Defender XDR where licensed, Exchange Online/message trace and mailbox audit evidence, Entra sign-in/audit logs, Microsoft Sentinel/Splunk, Proofpoint or Abnormal Security where deployed, finance/fraud escalation records and email headers.

### Interview Takeaway

BEC is not just a malicious-link problem. For a payment-change request, I would verify the request independently, determine whether the sender was spoofed or compromised, investigate mailbox and identity activity, and if money may already have moved, escalate immediately so the financial institution can be contacted while the SOC preserves and scopes the technical evidence.

### Verification Notes

- FBI Business Email Compromise guidance: https://www.fbi.gov/how-we-can-help-you/common-frauds-and-scams/business-email-compromise
- Microsoft guidance for compromised Microsoft 365 email accounts: https://learn.microsoft.com/en-us/defender-office-365/responding-to-a-compromised-email-account
