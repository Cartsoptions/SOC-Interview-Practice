# SOC Interview Practice — 2026-11-06

**Curriculum:** Questions 193–196 | Container-runtime triage, Kubernetes audit evidence, Microsoft Sentinel `AKSAudit` hunting, and privileged-pod incident response

## Question 193

### Interview Question

Microsoft Defender for Containers alerts that a process inside a production web pod launched an interactive shell and connected to an unfamiliar external address. The pod is running on a shared Kubernetes worker node. What does container isolation mean here, and how would you triage the alert without assuming the node is compromised?

### Interview-Ready Answer

A container packages an application and its dependencies as an isolated operating-system process environment. Unlike a traditional virtual machine, containers on a node normally share the host kernel. NIST and Kubernetes therefore describe container isolation as useful but weaker than a separate hardware-virtualised machine boundary.

In a SOC environment, I would treat the alert as evidence of suspicious activity in a particular workload, not automatic proof that the attacker escaped to the node. I would establish the cluster, namespace, pod, container, image, service account, node, process ancestry, command, network destination and deployment owner. I would compare the behaviour with the workload's normal purpose: a shell in a debugging or administration image may be expected, while a public-facing web container that never needs a shell is more concerning.

I would then correlate runtime process evidence with Kubernetes audit activity, deployment history, image provenance, application logs, DNS/network telemetry and node-level security evidence. I would check whether the pod was recreated from an approved image or changed through the API, whether an interactive `exec` session occurred, and whether the pod had risky privileges or host mounts.

Within Tier 1 authority, I would preserve the evidence, invoke an approved pod isolation, access restriction or termination action only where supported and authorised, and escalate to the container/platform and incident-response teams. Microsoft documents pod isolation, access restriction and termination as Defender for Containers response actions, but availability depends on licensing, permissions, cluster version, sensor/API access and—for some actions—a supported network-policy enforcer.

### Real-World SOC Scenario

The web pod normally runs only an application process. Runtime telemetry shows that the application spawned `/bin/sh`, which downloaded and launched a miner. The pod then contacted a known mining endpoint. Kubernetes audit logs show no approved interactive session, the image digest matches the approved deployment and node telemetry shows no process or file activity outside the container boundary.

- **Observation:** An unexpected shell and miner process ran inside a production web container and made an external connection.
- **Hypothesis:** The internet-facing application was exploited, leading to in-container code execution; the attacker may attempt cluster or node escalation.
- **Confirmed Evidence:** Process ancestry, network activity, application exploit evidence and owner validation establish compromise of the workload. Current node evidence does not establish container escape.

The verdict is **high-severity true positive — confirmed container workload compromise and cryptomining; node compromise or container escape remains unconfirmed**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the alert, incident, process tree, commands, files, connections and UTC timestamps.
2. Record cluster, namespace, pod, container, image digest, service account and worker node.
3. Compare the process and command with the workload's declared purpose and normal baseline.
4. Review Kubernetes audit evidence for pod creation/update, `exec`, attach, port-forward and identity activity.
5. Verify the image registry, digest, deployment owner and recent CI/CD or manifest changes.
6. Review pod security context, capabilities, host namespaces, service-account token use and volumes.
7. Correlate application, ingress, DNS, firewall and cloud-control-plane logs.
8. Check node EDR/runtime evidence for host-level processes, files, persistence or other affected pods.
9. Invoke authorised pod containment and indicator restrictions while considering service availability.
10. Escalate confirmed workload impact separately from the unproven node-escape hypothesis.

### Relevant Tools / Logs

Microsoft Defender for Containers and Defender XDR where deployed, Kubernetes audit and event logs, container runtime/process telemetry, `AKSAudit` in Microsoft Sentinel, application/ingress logs, image registry and CI/CD records, DNS/firewall telemetry, node EDR/Linux audit logs and incident-management records.

### Key Interview Takeaway

Containers share a host kernel, so a compromised pod creates escalation risk. I would confirm the workload compromise, then use cluster and node evidence to determine whether the attacker crossed the container boundary.

## Question 194

### Interview Question

Kubernetes audit evidence shows a service account creating a pod with `securityContext.privileged: true`, `hostPID: true` and a writable `hostPath` volume mounted from `/`. How would you interpret this event and decide whether it represents authorised infrastructure work or an attempted container escape?

### Interview-Ready Answer

Kubernetes audit events record requests to the API server. Useful fields include the authenticated `user`, request `verb`, `objectRef`, `sourceIPs`, `userAgent`, `responseStatus`, `requestObject`, timestamps and audit ID. The `requestObject` is available only when the audit level records the request body; collection and audit policy must therefore be verified.

The pod specification is highly risky. Kubernetes documents that privileged containers override or undo many kernel hardening controls and receive broad Linux capabilities. `hostPID: true` exposes the host process namespace, while a writable `hostPath` for `/` exposes the node filesystem to the container. Kubernetes warns that writable host mounts can allow an untrusted pod to subvert the host, and MITRE ATT&CK maps escape to the host as T1611.

However, the audit event proves that an API request was made and—if the response code shows success—that the pod was created. It does not prove that the container started, that the service account was compromised, or that the node was modified. Some security, storage and troubleshooting workloads legitimately require elevated access, although that access should be tightly controlled.

I would validate the service account, source IP, user agent, namespace, image, owner, change record, deployment mechanism and response status. I would then correlate scheduler/runtime events, container process activity and node file/process telemetry. If the identity is unauthorised, no approved change exists and the pod reads or changes host resources, I would treat it as a critical incident and invoke authorised containment.

### Real-World SOC Scenario

The request succeeds with HTTP status code 201. The service account normally deploys only to a development namespace, but creates the pod in production from an unfamiliar source. Runtime telemetry shows the container reading `/host/etc/shadow` and writing a cron file under the mounted host root. The platform team denies the change.

- **Observation:** A service account successfully created a privileged production pod with host PID access and a writable mount of the node's root filesystem.
- **Hypothesis:** A stolen or abused service-account credential is being used to escape the container boundary and establish node persistence.
- **Confirmed Evidence:** Unauthorised identity use, successful pod creation, host-file access and host cron modification establish compromise beyond the application container.

The verdict is **critical true positive — confirmed service-account abuse and host-level compromise through a privileged pod; the wider cluster and cloud impact remain to be scoped**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the complete audit event, including `AuditId`, request/response times and raw dynamic fields.
2. Confirm the API response code, request stage and whether the pod was admitted and scheduled.
3. Identify the service account, groups, namespace, role/cluster-role bindings and expected deployment scope.
4. Review `SourceIps` cautiously because forwarded addresses before the final hop may be client supplied.
5. Inspect image, command, security context, host namespaces, capabilities and every volume/mount.
6. Validate image provenance, digest, registry and CI/CD or GitOps records.
7. Check pod start/runtime evidence, `exec` activity and network connections.
8. Examine the node for file changes, processes, persistence, credential access and other affected workloads.
9. Hunt for the same identity, image, source, specification and host changes across the cluster.
10. Invoke authorised pod, service-account and node containment with the platform/IR team.

### Relevant Tools / Logs

Kubernetes API audit logs, `AKSAudit`, cluster events, container runtime logs, Microsoft Defender for Containers, Sentinel or Splunk, RBAC objects, registry/CI/CD records, node EDR and Linux audit/file-integrity telemetry, DNS/firewall/cloud logs and change management.

### Key Interview Takeaway

A privileged pod with host PID and a writable root `hostPath` creates a direct route to host resources. The audit event proves the request; runtime and node evidence determine whether escape or host modification actually occurred.

## Question 195

### Interview Question

AKS Kubernetes audit logs are sent to Microsoft Sentinel's resource-specific `AKSAudit` table. Write a safe first-pass KQL query to find successfully created pods that request privileged mode, host namespaces or a `hostPath` volume, and explain what the results can and cannot prove.

### Interview-Ready Answer

I would start with the documented `AKSAudit` schema and preserve identifying evidence:

```kusto
AKSAudit
| where TimeGenerated >= ago(24h)
| where Stage == "ResponseComplete" and Verb == "create"
| extend Resource = tostring(ObjectRef.resource),
         Namespace = tostring(ObjectRef.namespace),
         ObjectName = tostring(ObjectRef.name),
         Username = tostring(User.username),
         StatusCode = toint(ResponseStatus.code)
| where Resource == "pods" and StatusCode >= 200 and StatusCode < 300
| mv-expand Container = RequestObject.spec.containers
| extend ContainerName = tostring(Container.name),
         Image = tostring(Container.image),
         Privileged = tostring(Container.securityContext.privileged),
         HostPID = tostring(RequestObject.spec.hostPID),
         HostNetwork = tostring(RequestObject.spec.hostNetwork),
         HasHostPath = tostring(RequestObject.spec.volumes) contains_cs '"hostPath"'
| where Privileged == "true"
    or HostPID == "true"
    or HostNetwork == "true"
    or HasHostPath
| project TimeGenerated,
          Username,
          SourceIps,
          Namespace,
          ObjectName,
          ContainerName,
          Image,
          Privileged,
          HostPID,
          HostNetwork,
          HasHostPath,
          StatusCode,
          AuditId
| order by TimeGenerated desc
```

Microsoft documents `TimeGenerated`, `Stage`, `Verb`, `ObjectRef`, `User`, `ResponseStatus`, `RequestObject`, `SourceIps` and `AuditId` in `AKSAudit`. Kusto's `mv-expand` expands the containers array into separate rows, while `contains_cs` performs a case-sensitive substring check for the `hostPath` property in the volume specification.

This is a first-pass hunt, not a complete policy engine. It assumes that audit events were routed to the resource-specific table and that the audit level retained the request body. The `RequestObject` can be omitted or replaced with a size-skipped marker, and generated object names or schema variations can leave some projected values empty.

A returned row proves that Sentinel received an audit record for a successful pod-create request whose recorded specification contains one of the selected risky settings. It does not prove that the pod started, the setting was unauthorised, the identity was compromised or a host escape occurred. I would inspect the raw event and manifest, validate business context, then correlate pod/runtime and node evidence.

### Real-World SOC Scenario

The query returns a production pod created by `system:serviceaccount:dev-tools:builder`. It uses an unapproved public image, privileged mode and a writable root `hostPath`. The raw event shows status 201, and the deployment system has no matching job.

- **Observation:** The hunt finds a successfully created, privileged production pod with a host mount and an unexpected service account/image.
- **Hypothesis:** The service account is compromised or misused to obtain node-level access.
- **Confirmed Evidence:** Raw audit evidence, absent change record, runtime host access and node modifications confirm malicious use.

The verdict is **critical true positive — confirmed unauthorised privileged-pod deployment with host impact; cluster-wide scope is still under investigation**.

### What I Would Check as a Tier 1 Analyst

1. Verify AKS diagnostic settings, resource-specific table routing, retention and ingestion health.
2. Preserve the raw `AKSAudit` records and audit IDs behind every result.
3. Confirm response status, stage, actor, source IPs, namespace and exact object.
4. Inspect the full `RequestObject`; do not rely only on the projected flags.
5. Check init containers, ephemeral containers, all volumes and all security contexts separately.
6. Compare the identity, image and manifest with approved deployment baselines and change records.
7. Correlate scheduling, container start, runtime process and network evidence.
8. Examine the affected node and other workloads for host-level impact.
9. Tune the hunt with known authorised infrastructure workloads rather than suppressing the risk globally.
10. Escalate the query, raw evidence, assumptions and telemetry gaps.

### Relevant Tools / Logs

Microsoft Sentinel Logs, `AKSAudit`, AKS diagnostic settings, Kubernetes audit/events, Defender for Containers, image registry/CI/CD records, RBAC objects, node EDR/Linux audit logs and incident-management records.

### Key Interview Takeaway

The query finds successful pod-create requests with risky recorded settings. It is a hunting lead; the raw manifest, business context and runtime/node evidence establish whether the activity was malicious and whether escape occurred.

## Question 196

### Interview Question

You confirm that a compromised Kubernetes service account created a privileged pod with a writable host-root mount. The pod modified a node cron file, read credentials from the node and contacted an external server. Similar audit activity appears on two more nodes. How would you contain, scope, eradicate and support recovery as Tier 1?

### Interview-Ready Answer

I would classify this as a critical container-platform incident with confirmed service-account abuse, host-level compromise and possible credential exposure across multiple nodes.

My immediate objectives would be to preserve control-plane, runtime and node evidence; stop further attacker access; identify every affected node, pod, identity and credential; and maintain essential service availability. I would escalate immediately to the incident commander, Kubernetes/platform owner, cloud/security team and relevant application owners.

Under the approved playbook, authorised responders could isolate, restrict or terminate malicious pods, restrict the compromised service account/RBAC path, block confirmed infrastructure and isolate or cordon affected nodes. Those actions require platform context: deleting only a pod may allow a Deployment or attacker to recreate it, while abruptly removing nodes can disrupt production. Microsoft documents supported Defender for Containers pod response actions, but the exact action depends on the deployed components and permissions.

I would scope all API actions by the service account, source IPs, user agents and audit IDs; all pods or workload objects it created or changed; every node it touched; and all secrets, cloud identities, registries or data accessible from those nodes. Kubernetes notes that bound service-account tokens have different revocation behaviour from legacy long-lived token Secrets. Token handling must therefore be performed by authorised platform specialists based on token type rather than assuming that one generic reset invalidates everything.

Eradication should remove unauthorised workloads and persistence, revoke or replace exposed identities and credentials, correct excessive RBAC and admission-policy gaps, and rebuild materially compromised nodes from trusted images where policy requires it. Recovery should redeploy approved workloads from verified manifests and image digests, validate node and cluster integrity, restore network policy and monitoring, and heighten detection for recurrence.

NIST SP 800-61 Rev. 3 supports recording response actions, preserving evidence, determining magnitude, coordinating containment, verifying secure recovery and feeding lessons into improvement. MITRE ATT&CK T1611 can label the evidenced escape-to-host behaviour, but it does not identify the attacker or replace incident scoping.

### Real-World SOC Scenario

The platform team blocks further API use by the compromised identity, terminates the malicious workloads and isolates the affected nodes through the approved process. Investigation finds the same cron persistence on three nodes and confirms that one cloud credential was read and later used. Clean nodes are rebuilt and approved workloads are redeployed from signed, verified images. Follow-up monitoring finds no renewed activity.

- **Observation:** A compromised service account created privileged pods on three nodes; the pods modified host files, accessed credentials and communicated externally.
- **Hypothesis:** The attacker intends to maintain node access, steal cloud credentials and expand across the cluster or connected cloud resources.
- **Confirmed Evidence:** Control-plane audit trails, host-file changes, credential access and subsequent credential use establish multi-node compromise and cloud-identity exposure.

The verdict is **critical true positive — confirmed multi-node Kubernetes compromise with host persistence and credential theft; data access and wider cloud impact require continued scoping**.

### What I Would Check as a Tier 1 Analyst

1. Preserve audit, runtime, node, cloud and network evidence with a UTC-normalised timeline.
2. Record cluster, namespaces, nodes, pods, images, service account, RBAC bindings, audit IDs and source IPs.
3. Identify the controller or actor that could recreate each malicious pod.
4. Escalate for authorised pod, identity, network and node containment.
5. Scope every API action and object affected by the compromised service account.
6. Hunt the image, manifest pattern, commands, host paths, cron artefacts and destinations across all nodes.
7. Identify every secret, service-account token, node identity, registry credential and cloud credential exposed.
8. Correlate exposed-credential use across Kubernetes and cloud audit logs.
9. Support specialist-led removal of persistence, credential rotation/revocation, RBAC correction and trusted node rebuilds.
10. Validate restored workloads, image digests, admission controls, network policies, logging and sensor health.
11. Monitor for recreated pods, renewed API use, recurring host changes and cloud activity.
12. Document confirmed access separately from suspected data disclosure, attribution or unobserved lateral movement.

### Relevant Tools / Logs

Kubernetes API audit/events and RBAC objects, Microsoft Sentinel `AKSAudit`, Defender for Containers and Defender XDR where deployed, container runtime/process telemetry, node EDR/Linux audit/file-integrity logs, cloud identity/control-plane logs, registry/CI/CD records, DNS/firewall/proxy telemetry, CMDB/change management and incident case records.

### Key Interview Takeaway

Once a privileged pod changes the host and steals credentials, this is not only a container alert. Contain the workload, identity and affected nodes together, scope every exposed credential, rebuild from trusted sources and verify recovery.

## Verification Notes

- NIST SP 800-190 explains that containers use operating-system-level virtualisation, normally share the host kernel and provide a weaker isolation boundary than hypervisor-separated virtual machines. It also warns that sensitive host mounts can permit host filesystem tampering: https://csrc.nist.gov/pubs/sp/800/190/final and https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-190.pdf
- Kubernetes documents that privileged containers override or undo multiple kernel hardening controls and receive broad capabilities; most workloads should avoid privileged mode: https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/
- Kubernetes warns that `hostPath` mounts create significant security risk and that a writable host mount can let an untrusted pod subvert the host: https://kubernetes.io/docs/concepts/storage/volumes/#hostpath
- Kubernetes Pod Security Standards describe the Privileged profile as unrestricted and capable of bypassing normal isolation; Baseline and Restricted profiles prevent or limit known privilege escalation: https://kubernetes.io/docs/concepts/security/pod-security-standards/
- Kubernetes audit-event documentation defines `auditID`, `stage`, `requestURI`, `verb`, `user`, `sourceIPs`, `userAgent`, `objectRef`, `responseStatus` and `requestObject`. It warns that user-agent and forwarded source-IP information can be client influenced, and request bodies require Request-level logging or higher: https://kubernetes.io/docs/reference/config-api/apiserver-audit.v1/
- Microsoft documents the `AKSAudit` columns used in Question 195, including `AuditId`, `ObjectRef`, `RequestObject`, `ResponseStatus`, `SourceIps`, `Stage`, `TimeGenerated`, `User` and `Verb`: https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/aksaudit
- Microsoft documents that AKS audit levels vary by request and that most core-API write operations are recorded at RequestResponse level. It also recommends sending `kube-audit`, `kube-audit-admin` and `guard` logs to Log Analytics for investigations: https://learn.microsoft.com/en-us/azure/aks/monitor-aks and https://learn.microsoft.com/en-us/azure/aks/secure-aks
- Microsoft documents Kusto `mv-expand` as expanding dynamic arrays/property bags into rows and `contains_cs` as a case-sensitive substring operator. These support the query mechanics in Question 195: https://learn.microsoft.com/en-us/kusto/query/mv-expand-operator and https://learn.microsoft.com/en-us/kusto/query/contains-operator
- Microsoft documents Defender for Containers investigation and supported pod response actions. Pod isolation/access restriction/termination depend on licensing, permissions and component support; isolation/restriction additionally require supported cluster/network-policy conditions: https://learn.microsoft.com/en-us/defender-xdr/investigate-respond-container-threats
- Kubernetes documents that modern bound service-account tokens have bounded lifetimes and that revocation behaviour depends on the binding/token type; legacy token Secrets and TokenRequest tokens must not be treated as one generic credential type: https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/
- MITRE ATT&CK T1611 covers escape to the host and its detection strategy includes privileged containers and host-volume mounts correlated with host-level activity: https://attack.mitre.org/techniques/T1611/ and https://attack.mitre.org/detectionstrategies/DET0219/
- NIST SP 800-61 Rev. 3, finalised in April 2025, recommends preserving incident records/evidence, validating magnitude, coordinating containment, verifying secure recovery and feeding lessons into improvement: https://csrc.nist.gov/pubs/sp/800/61/r3/final
