# SOC Interview Practice — 2026-10-14

## Question 129

### Interview Question

Microsoft Defender for Endpoint raises a high-severity malware alert on a finance laptop and reports that a file was quarantined. The user says they opened an invoice attachment. How would you decide whether this is merely a blocked file or a genuine endpoint compromise?

### Interview-Ready Answer

I would not close the alert just because the file is quarantined. Quarantine is a response outcome for that file; it does not prove that the file never executed, that it created no child processes, or that the device has no persistence or follow-on activity.

I would first validate the alert identity, time, device, user, detection source and remediation status. Then I would reconstruct the sequence in the Defender XDR alert story and device timeline: how the file arrived, where it was written, whether a process started from it, which parent launched it, its command line, children, file or registry changes, network connections and any related alerts. I would record the file's SHA-256 and signer information, but treat reputation as enrichment rather than the verdict. If policy permits VirusTotal, I would search the hash first; I would not upload a confidential attachment to the public service.

Next I would scope the environment for the same hash, filename, URL/domain, sender, command line and behaviours. The decisive distinction is execution and impact. If telemetry shows only a file creation followed by a successful quarantine, with no execution or related activity, I could recommend a prevented-malware verdict after checking telemetry coverage. If the file executed, spawned suspicious processes, established persistence, made unexplained external connections, or affected other assets, I would treat it as a confirmed or strongly suspected incident and escalate.

Any isolation, scan, file blocking, stop-and-quarantine action or evidence collection would be performed only if the runbook and my role allow it; otherwise I would request the authorised responder. I would preserve the timeline, queries, hashes and action results in the case.

### Real-World SOC Scenario

The attachment `Invoice_October.zip` contains `InvoiceViewer.exe`. Defender reports the executable as quarantined at 09:14 on `FIN-LT-044`. The user opened the archive at about 09:12.

- **Observation:** Defender reports a detected file and a quarantine action on one device.
- **Hypothesis:** The control may have blocked the file before execution, or the executable may have run briefly and caused follow-on activity before remediation.
- **Confirmed evidence required:** A process-creation record or process tree showing execution, correlated child processes or network activity, a persistence artefact, or other corroborated endpoint evidence. Conversely, a prevention conclusion requires a successful remediation record, no execution/follow-on evidence in the relevant window, and confidence that endpoint telemetry was healthy.

A clean or unknown reputation result would not outweigh local execution evidence. Similarly, an antivirus name alone would not establish the full incident scope.

### What I Would Check as a Tier 1 Analyst

1. Confirm alert severity, timestamps, device/user, detection source, file path, file hash, signer and remediation/action status.
2. Review the Defender XDR alert story and device timeline before and after the detection; identify the file's parent, whether it executed, and any child processes.
3. Examine command lines, child-process ancestry, file/registry changes, scheduled tasks/services where visible, and network connections initiated by the suspicious process.
4. Check sensor health and telemetry gaps so that “no evidence” is not mistaken for “evidence of no execution.”
5. Hunt for the same hash and higher-value artefacts across devices, email, DNS, proxy and firewall data; search the sender and delivery URL if email was the entry point.
6. Enrich the hash/domain with approved threat intelligence. Search a hash in VirusTotal if policy permits; never upload a sensitive file to its public corpus.
7. If confirmed or materially suspected, preserve the case timeline and escalate with affected assets, observed behaviours, confidence, containment already performed and requested next actions.
8. Under the runbook, request or perform authorised device isolation, antivirus scan, investigation-package collection, file blocking or stop-and-quarantine, then verify the action in the Action center.

### Tools / Logs

Microsoft Defender XDR alert story, Defender for Endpoint device timeline and file/device pages, Defender Action center, Microsoft Sentinel, `DeviceFileEvents`, `DeviceProcessEvents`, `DeviceNetworkEvents`, DNS/proxy/firewall logs, email-security logs, Windows Defender Operational logs, Wazuh-collected Windows/Sysmon telemetry, Splunk endpoint data, approved threat-intelligence sources and VirusTotal hash search.

### Interview Takeaway

“Quarantined” describes an action on a file, not the whole incident. I would prove whether execution and impact occurred, scope the same artefacts and behaviours elsewhere, and escalate or contain only within the runbook and my permissions.

## Question 130

### Interview Question

An EDR process tree shows `OUTLOOK.EXE` spawning `powershell.exe` with an encoded command, followed by `rundll32.exe` loading a DLL from the user's temporary directory and a connection to a newly observed domain. How would you interpret and investigate this chain without jumping straight to a malware verdict?

### Interview-Ready Answer

The chain is high risk because an email client launching encoded PowerShell is unusual, PowerShell can be abused for execution and downloads, and `rundll32.exe` can proxy execution of a DLL. However, process names alone are not proof: PowerShell and `rundll32.exe` are legitimate Windows components, and parent-child relationships can be misread if timestamps or process identifiers are incomplete.

I would validate each process instance using its timestamp, device, user, executable path, signer/hash, full command line and stable process identifier. I would link the PowerShell process to its exact parent and children, then correlate the same PowerShell process instance with its network events. In Defender XDR, `ProcessUniqueId` and `InitiatingProcessUniqueId` are preferable when available because ordinary process IDs can be reused.

I would decode the Base64 content in an approved offline environment as data, not execute it. I would determine what URL, file path or command it references; collect the DLL hash and signer; check whether the domain was contacted successfully; and look for subsequent persistence, credential access, discovery or lateral movement. I would also validate the initiating email or attachment and check whether the same chain appears on other endpoints.

My verdict would be evidence-based. A user opening the message, the exact encoded command downloading a DLL, `rundll32.exe` loading that DLL, and matching network or file telemetry would make the malicious-execution hypothesis much stronger. If the domain is internal, the PowerShell is a signed business automation script, and change records support the chain, I would document and close or tune according to process. If ambiguity remains, I would escalate with the process tree and the evidence needed to resolve it.

### Real-World SOC Scenario

At 10:03:18, `OUTLOOK.EXE` launches `powershell.exe`. At 10:03:21, PowerShell creates `C:\Users\analyst\AppData\Local\Temp\update.dll`; at 10:03:24, `rundll32.exe` references that path; at 10:03:27, endpoint telemetry records an outbound connection associated with the chain.

- **Observation:** The EDR recorded a suspicious parent-child sequence, an encoded command, a temporary-path DLL and outbound network activity.
- **Hypothesis:** A malicious email triggered a PowerShell download-and-execute chain, with `rundll32.exe` used to execute the payload.
- **Confirmed evidence required:** The decoded command and correlated file/process/network records must establish that the same process instance retrieved or created the DLL, that `rundll32.exe` referenced it, and that the relevant connection occurred. A sandbox or malware verdict can support the conclusion but should not replace the local evidence chain.

MITRE ATT&CK mapping is descriptive, not a verdict. The observed PowerShell use may map to T1059.001; additional mappings should be made only when the evidence supports the behaviour.

### What I Would Check as a Tier 1 Analyst

1. Verify the full process ancestry, event times, user/session, executable paths, signatures/hashes, integrity context and command lines.
2. Use stable process-instance identifiers where available, rather than relying only on a PID or a visual tree.
3. Decode the command safely and read its intended actions; never paste or execute it in a production shell.
4. Correlate file creation, the DLL hash/path, the `rundll32.exe` command line and network activity to the correct process instances.
5. Review the destination's DNS resolution, proxy/firewall result, first-seen context and reputation; distinguish an attempted connection from a successful one.
6. Inspect the email/attachment or link that preceded the process chain and search for other recipients or endpoints with the same artefacts.
7. Look for follow-on behaviour: new autoruns or scheduled tasks, new services, credential access, discovery commands, additional payloads and unusual logons.
8. Escalate with a concise timeline, ATT&CK mappings supported by evidence, affected assets, confidence level and recommended authorised containment.

### Tools / Logs

Microsoft Defender XDR alert story and advanced hunting, Defender for Endpoint device timeline, Microsoft Sentinel, `DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents`, email gateway/Defender for Office 365 telemetry, DNS/proxy/firewall logs, Windows Event Logs or Sysmon where configured, Wazuh, Splunk, approved sandboxing and threat-intelligence services.

### Interview Takeaway

I would treat the chain as high priority, but I would prove it by linking exact process instances to command, file and network evidence. Legitimate binaries are context, not a benign verdict; ATT&CK labels explain behaviour, not intent.

## Question 131

### Interview Question

You are asked to use Microsoft Defender XDR advanced hunting to identify PowerShell processes that made network connections during the last 24 hours. How would you write and interpret a safe first-pass query, and what can it not prove?

### Interview-Ready Answer

I would start with a narrow, reviewable query that uses documented advanced-hunting fields and correlates a process instance to network events by device and process unique ID. For example:

```kusto
let lookback = 24h;
let ps =
    DeviceProcessEvents
    | where Timestamp >= ago(lookback)
    | where FileName in~ ("powershell.exe", "pwsh.exe", "powershell_ise.exe")
    | where isnotempty(ProcessUniqueId)
    | project ProcessTime=Timestamp, DeviceId, DeviceName,
              ProcessUniqueId, AccountName, FileName,
              FolderPath, ProcessCommandLine, SHA1;
ps
| join kind=inner (
    DeviceNetworkEvents
    | where Timestamp >= ago(lookback)
    | where isnotempty(InitiatingProcessUniqueId)
    | project NetworkTime=Timestamp, DeviceId,
              InitiatingProcessUniqueId, RemoteIP, RemotePort,
              RemoteUrl, Protocol, ActionType
) on DeviceId, $left.ProcessUniqueId == $right.InitiatingProcessUniqueId
| project ProcessTime, NetworkTime, DeviceName, AccountName,
          FileName, FolderPath, ProcessCommandLine, SHA1,
          RemoteIP, RemotePort, RemoteUrl, Protocol, ActionType
| order by NetworkTime desc
```

The query answers: “Which recorded PowerShell process instances are associated with recorded network events in this period?” It does not answer: “Which results are malicious?” PowerShell is widely used for legitimate administration, and an event's presence does not by itself prove the connection succeeded, delivered a payload or caused compromise. I would interpret `ActionType` using the tenant's in-portal schema reference, then examine the command line, parent process, user, device role, destination, timing and related events.

If the tenant lacks Defender for Endpoint data, the tables may be empty. If hunting from Microsoft Sentinel, I would confirm that the Defender XDR connector is configured to stream the relevant advanced-hunting event tables; connecting incidents and alerts alone is not the same as collecting all raw events. I would also respect retention and telemetry coverage.

### Real-World SOC Scenario

The query returns 86 rows. Most are known management scripts from a signed path, but one row shows `OUTLOOK.EXE` as the initiating parent in the process record, an encoded PowerShell command from a user profile path and a connection to an unapproved external domain.

- **Observation:** The query correlated recorded PowerShell process instances with network-event records.
- **Hypothesis:** One result may represent user-triggered malicious script execution and command-and-control or payload retrieval.
- **Confirmed evidence required:** The process parent/command and related file/network timeline must corroborate the behaviour; DNS/proxy/firewall or endpoint network outcome should show what happened; and any downloaded payload, persistence or follow-on execution should be independently established.

The result is a lead for triage, not a conviction. If `RemoteUrl` is blank, I would pivot on `RemoteIP`; if the network table lacks a record, I would check other network sources rather than assume no connection occurred.

### What I Would Check as a Tier 1 Analyst

1. Confirm the query ran in the intended environment and time zone, and that Defender for Endpoint telemetry and retention cover the period.
2. Validate that `DeviceProcessEvents` and `DeviceNetworkEvents` return recent records before interpreting an empty result.
3. Review the suspicious process's parent by joining or pivoting from `InitiatingProcessUniqueId`, plus its path, signer/hash, account and full command line.
4. Check destination ownership/reputation, DNS, proxy/firewall disposition, bytes or session detail where available, and whether the endpoint event represents connection success or another network action.
5. Search for children, downloaded files, persistence and additional devices using the same command, domain, IP, URL or hash.
6. Compare with approved scripts, software-deployment windows and administrator activity; document the business context used to separate normal automation from suspicious execution.
7. Preserve the KQL, time range, relevant rows and pivots in the ticket, then escalate with observation, hypothesis and confirmed evidence clearly separated.

### Tools / Logs

Microsoft Defender XDR advanced hunting, Microsoft Sentinel where the Defender XDR connector streams the required raw event tables, `DeviceProcessEvents`, `DeviceNetworkEvents`, `DeviceFileEvents`, DNS/proxy/firewall telemetry, change-management records and approved threat intelligence.

### Interview Takeaway

The query correlates exact process instances with network telemetry; it does not label them malicious. I would validate coverage, add parent/command/destination context, and use corroborating evidence before assigning a verdict.

## Question 132

### Interview Question

You confirm that a user opened a malicious attachment, PowerShell downloaded a DLL, `rundll32.exe` executed it, a scheduled task was created for persistence, and the host contacted an external domain. As a Tier 1 analyst, how would you prioritise, contain, investigate and escalate the incident through recovery, and how would MITRE ATT&CK, the Cyber Kill Chain and the Pyramid of Pain help?

### Interview-Ready Answer

I would treat this as a confirmed, high-priority endpoint compromise rather than a single malware alert. There is evidence of execution, persistence and external communication, with a plausible email entry point. I would immediately follow the incident playbook, preserve a factual timeline and notify the designated escalation path.

Containment comes first when continued access poses material risk, but I would act only within delegated authority. Depending on the runbook, that could mean isolating the device through Defender for Endpoint, stopping and quarantining the malicious file where supported, blocking confirmed malicious indicators, and coordinating account containment if identity evidence shows compromise. If I lack permission, I would request these actions urgently and record the request, owner and result. I would avoid shutting down or wiping the device because that can destroy volatile evidence and is normally a higher-tier decision.

In parallel, I would scope the incident across endpoint, email, identity and network data: other recipients, other executions of the same command or hash, the domain/IP/URL, the scheduled-task name and command, abnormal logons, new payloads and possible lateral movement. I would distinguish attempted from successful actions and preserve evidence. The escalation should state what is observed, what is inferred, what is confirmed, what has been contained, what remains exposed, and the decisions needed from Tier 2/IR.

Frameworks help organise the work but do not replace evidence. MITRE ATT&CK describes behaviours such as PowerShell execution (T1059.001) and scheduled-task persistence (T1053.005), helping defenders hunt for the same techniques. The Cyber Kill Chain can communicate the sequence from delivery through execution/installation and command-and-control, while also showing where controls interrupted it. The Pyramid of Pain reminds me to collect and block hashes where useful but also create durable detections for harder-to-change host/network artefacts and behaviours, such as an email client spawning encoded PowerShell followed by a temporary-path DLL. I would not infer a threat actor from a technique match alone.

After containment, authorised responders eradicate the payload and persistence, address the entry point and any compromised credentials, then recover the endpoint from a trusted state. Recovery must be validated: the scheduled task is gone, malicious files/processes and connections do not recur, controls and sensors are healthy, credentials have been reset where required, and monitoring is heightened. Lessons learned should feed email controls, behavioural detections, blocking, user guidance and playbook improvements.

### Real-World SOC Scenario

The investigation confirms the attachment delivery at 10:01, user open at 10:03, PowerShell download at 10:03, DLL execution at 10:04, scheduled-task creation at 10:05 and repeated external connections from 10:06. The same email reached five users, but only one endpoint currently shows execution.

- **Observation:** Correlated email, process, file, persistence and network telemetry exists for one device; five mailboxes received the message.
- **Hypothesis:** The device is compromised and the scheduled task provides recurring execution; other recipients may still be at risk, and credentials or additional hosts may be affected.
- **Confirmed evidence:** The attachment-to-process timeline, decoded command, DLL creation/execution, scheduled-task definition and associated external communication are corroborated. Credential theft, lateral movement and actor attribution remain unconfirmed until separate evidence supports them.

The initial verdict is **true positive—confirmed endpoint compromise**, with scope still under investigation.

### What I Would Check as a Tier 1 Analyst

1. Declare or escalate the incident at the severity required by the runbook; document business context, device criticality, user privilege and evidence confidence.
2. Preserve a timestamped timeline, alert evidence, KQL/SPL searches, process identifiers, command lines, hashes, URLs/domains/IPs, scheduled-task details and response-action results.
3. Under authority, isolate the device and initiate appropriate scan, evidence-collection, file-remediation or indicator-blocking actions; otherwise request them and track completion in the case.
4. Coordinate email containment for all recipients and check whether anyone else clicked, opened or executed the content.
5. Hunt enterprise-wide for the exact hash and indicators, then for higher-value artefacts and behaviours: similar parent-child chains, encoded PowerShell, temporary-path DLL execution, the task name/command and matching network patterns.
6. Review identity telemetry for suspicious logons, token/session anomalies, privilege use and activity after the execution time; recommend account containment only when evidence and playbook criteria support it.
7. Check for additional persistence, payloads, discovery, credential access, lateral movement and exfiltration; clearly mark each as observed, suspected or not evidenced.
8. Escalate to Tier 2/incident response with the current scope, timeline, ATT&CK mappings, containment status, gaps, affected business services and explicit next decisions.
9. During eradication/recovery, verify the authorised team removed persistence and payloads, addressed the delivery path, rebuilt or restored the device from a trusted state where required, and validated normal operation and sensor health.
10. Keep enhanced monitoring in place and feed lessons learned into detections, email controls, blocklists, user awareness and playbook updates.

### Tools / Logs

Microsoft Defender XDR/Defender for Endpoint, Microsoft Sentinel, Defender for Office 365 or another secure email gateway, Entra ID/sign-in telemetry, `DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents`, Windows Event Logs/Sysmon where configured, Wazuh, Splunk, DNS/proxy/firewall logs, case-management system, approved threat intelligence and forensic collection tools used by authorised responders.

### Interview Takeaway

This is a confirmed compromise because multiple evidence sources show execution, persistence and external communication. My Tier 1 job is to preserve facts, reduce risk within authority, scope quickly across controls, and hand Tier 2/IR a defensible timeline—not to overclaim attribution or take unauthorised destructive action.

## Verification Notes

- Microsoft documents that Defender XDR's alert story presents related entities in a chronological process-tree view and that affected entities can expose contextual response actions. [Investigate alerts in Microsoft Defender XDR](https://learn.microsoft.com/defender-xdr/investigate-alerts)
- Defender for Endpoint device investigation can expose the device timeline, file/domain context and response actions including isolation, antivirus scan and investigation-package collection. Action availability depends on subscription, platform, onboarding configuration and permissions. [Investigate devices](https://learn.microsoft.com/en-gb/defender-endpoint/investigate-machines) and [Take response actions on a device](https://learn.microsoft.com/en-us/defender-endpoint/respond-machine-alerts)
- Microsoft documents Stop and Quarantine File as stopping running processes, quarantining the file and deleting persistent data such as registry keys, subject to stated platform, antivirus and permission prerequisites. Because capability and authority vary, the answers make this a runbook-controlled action rather than a universal Tier 1 step. [Take response actions on a file](https://learn.microsoft.com/en-us/defender-endpoint/respond-file-alerts)
- `DeviceProcessEvents` documents `ProcessUniqueId` and `InitiatingProcessUniqueId`; `DeviceNetworkEvents` documents `InitiatingProcessUniqueId`, `RemoteIP`, `RemotePort` and `RemoteUrl`. Microsoft recommends stable process unique IDs where available to avoid PID-reuse ambiguity. [DeviceProcessEvents schema](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table), [DeviceNetworkEvents schema](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-devicenetworkevents-table) and [Advanced hunting query best practices](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-best-practices)
- The Microsoft Sentinel Defender XDR connector can synchronize incidents/alerts and can separately collect raw advanced-hunting events into purpose-built tables. The answer therefore requires validation of connector configuration and table coverage before treating empty results as meaningful. [Stream Defender XDR data to Microsoft Sentinel](https://learn.microsoft.com/en-us/azure/sentinel/connect-microsoft-365-defender)
- MITRE ATT&CK describes PowerShell abuse as T1059.001 and scheduled-task abuse as T1053.005. Technique mappings describe observed behaviour; they do not by themselves establish malicious intent or actor attribution. [PowerShell](https://attack.mitre.org/techniques/T1059/001/) and [Scheduled Task](https://attack.mitre.org/techniques/T1053/005/)
- NIST SP 800-61 Rev. 3, published April 2025, integrates incident response into CSF 2.0 and distinguishes containment, eradication and recovery considerations. It notes that eradication can include eliminating persistence/entry points and that recovery includes restoring normal operation and validating remediation. [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final)
- VirusTotal states that public submissions/queries can enter its dataset and warns against submitting sensitive, confidential or personally identifiable information. The answer therefore recommends hash search first and policy-approved private analysis for sensitive samples. [VirusTotal file upload guidance](https://docs.virustotal.com/reference/files-scan) and [Private Scanning](https://docs.virustotal.com/docs/private-scanning)
- Wazuh documents collection of the Sysmon Operational and Windows Defender Operational channels; actual fields and visibility depend on endpoint configuration. [Wazuh Windows log collection](https://documentation.wazuh.com/current/user-manual/capabilities/log-data-collection/configuration.html)
- David Bianco's Pyramid of Pain distinguishes easily changed hashes/IPs from harder-to-change host/network artefacts, tools and TTPs. It is used here as a detection-prioritisation model, not an incident-severity model. [The Pyramid of Pain](https://detect-respond.blogspot.com/2013/03/the-pyramid-of-pain.html)

Not necessarily.
