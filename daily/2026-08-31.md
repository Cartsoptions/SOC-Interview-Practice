# SOC Interview Practice — 2026-08-31

## Question 31

### Interview Question

A user has granted a newly seen OAuth application access to Microsoft 365 data. What is OAuth consent, what is consent phishing, and how would you investigate the alert as a Tier 1 SOC analyst?

### Interview-Ready Answer

OAuth consent allows a user or administrator to grant an application permission to access resources on the user's or organisation's behalf. In a Microsoft 365/Entra environment, legitimate applications use this model every day. The security problem is **consent phishing**: an attacker tricks a user into authorising a malicious application, which can then access cloud data using the permissions the user granted.

Microsoft explicitly warns that an illicit consent grant can give an external application account-level access to data without the attacker needing an organisational password. That means I would not treat a password reset or MFA challenge as a complete response by itself. I would investigate the application, the permissions granted, who consented, how the consent occurred, and what the application accessed afterwards.

My first observation might be: **a user granted consent to an application**. My hypotheses could include a legitimate new business app, an unwanted app, or a malicious consent-phishing application. To decide, I would review Microsoft Entra audit logs and application-permission activity. Microsoft documents audit activities including `Consent to application`, `Add delegated permission grant`, and app-role assignment activity for application permissions. Where Defender for Cloud Apps/App Governance is licensed and enabled, I would also review the app's publisher/origin, requested permissions, users who authorised it, risk/anomaly information and subsequent application activity.

I would pay special attention to high-impact permissions involving mail, files, contacts or other organisational data, whether the publisher and application are expected, whether the consent request came from a known business workflow, and whether the app accessed unusual volumes of data or performed suspicious mailbox actions. MITRE ATT&CK also covers malicious OAuth application integrations and application-access-token abuse, which reinforces that cloud app consent can provide persistence or data access without a traditional interactive sign-in.

As a Tier 1 analyst, I would document the consent, permissions, affected users and observed app activity and escalate according to the cloud/identity playbook. Disabling an enterprise application, revoking consent or tokens, changing tenant-wide consent policy, or suspending accounts should only be performed if my role and the incident procedure authorise those actions.

### Real-World SOC Scenario

A finance user reports clicking a Microsoft-looking link and approving an application called "Document Viewer". Soon afterwards, the SOC receives an alert for a newly authorised OAuth app with mail permissions.

I would verify the application and publisher, identify the user who consented, review the exact permissions and Entra audit trail, and ask whether the app has a legitimate business owner. I would then investigate the application's activity, especially mailbox or file access, and check the affected user's sign-ins and endpoint/browser timeline around the consent event.

If the app is unknown, the consent originated from a phishing workflow, and the app subsequently accessed large numbers of emails or files, the evidence supports escalation as an illicit consent-grant incident. If the app is an approved enterprise integration with documented ownership and expected permissions, that supports a legitimate explanation.

### What I Would Check as a Tier 1 Analyst

- Application name, application/service-principal identity and publisher/origin
- User or administrator who granted consent
- Time of the consent event and surrounding sign-in/browser activity
- Microsoft Entra audit activity such as `Consent to application` or delegated/app-role permission grants
- Exact permissions/scopes granted and whether they fit the application's business purpose
- Whether admin consent was involved
- Business owner, change/request record and whether the application is approved
- Users who have authorised the same app
- Mail, file or other Microsoft 365 activity performed by the application
- Unusual data-access volume or suspicious email/mailbox actions
- Defender for Cloud Apps/App Governance risk or anomaly evidence where licensed
- Related phishing email, URL, identity and endpoint evidence
- Escalation and authorised remediation requirements

### Relevant Tools / Logs

Microsoft Entra audit logs and Enterprise Applications; Microsoft Defender for Cloud Apps/App Governance where licensed; Microsoft Defender XDR advanced hunting where available; Microsoft Sentinel/Splunk/Wazuh when relevant cloud logs are ingested; Defender for Office 365 for the phishing delivery path; EDR/browser telemetry; Microsoft 365 audit data; incident/change-management records.

### Interview Takeaway

OAuth consent is how users or administrators authorise applications to access cloud data on their behalf. In a SOC investigation, I would verify who granted the consent, what permissions the app received, whether the app is legitimate and what it did afterwards. A suspicious consent grant can provide access even without a stolen password, so I would treat password reset or MFA alone as insufficient and escalate authorised app-consent remediation through the playbook.

## Question 32

### Interview Question

You receive a Windows alert that a new scheduled task was created. What does Security Event ID 4698 mean, and how would you investigate whether the task is legitimate administration or persistence?

### Interview-Ready Answer

Windows Security Event ID **4698** records that a scheduled task was created when the relevant auditing is enabled. Microsoft documents useful fields including the account that requested the task creation, the task name and the task-content XML. On newer Windows versions, later event versions can also include client and parent process identifiers that can help with correlation.

A scheduled task is not malicious by itself. Windows and enterprise applications legitimately use Task Scheduler for maintenance, updates and administration. However, attackers can also abuse Task Scheduler for execution and persistence. MITRE ATT&CK maps this behaviour to **Scheduled Task/Job: Scheduled Task (T1053.005)** under Execution, Persistence and Privilege Escalation.

My observation would be: **a new scheduled task was created**. My hypothesis might be legitimate software/administration or malicious persistence. I would inspect who created it, the task name and path, its trigger, run-as account, executable/script or arguments contained in the task definition, and the process that created it where telemetry is available. I would then correlate with Event 4688/Sysmon/EDR process activity, file hash/signature and the events immediately before and after creation.

I would also look for related task lifecycle events where the environment collects them: 4699 for deletion, 4700 for enablement, 4701 for disablement and 4702 for an updated scheduled task. These are supporting events, not mandatory evidence in every environment.

As Tier 1, I would document and escalate a suspicious task. I would not delete or disable a task on a production system unless the playbook and my authority explicitly allow it, because legitimate scheduled tasks can be business-critical and evidence may need to be preserved.

### Real-World SOC Scenario

A workstation generates Event 4698 shortly after a user opens an unexpected attachment. The new task has an unusual name, runs at user logon and launches a script from a user-writable directory.

I would correlate the task-creation time with the EDR process tree and Windows process events. If the parent process traces back to the attachment, the referenced script is low-prevalence or suspicious, and the task later launches that script followed by an outbound connection, the combined evidence strongly supports malicious persistence.

If instead the task was created by an approved software-management agent, points to a signed vendor binary and matches a documented deployment, that supports a legitimate explanation.

### What I Would Check as a Tier 1 Analyst

- Event ID 4698 timestamp and affected host
- Subject/account that requested task creation
- Task name and Task Scheduler path
- Task-content XML or equivalent task definition
- Trigger: logon, startup, time-based or other condition
- Run-as/security context and privilege level
- Executable/script path and command arguments
- Client/parent process identifiers where the event version provides them
- Event 4688, Sysmon Event 1 or EDR process tree around creation
- File hash, signature, prevalence and path of referenced binaries/scripts
- Related 4699/4700/4701/4702 task events where collected
- Network, DNS, file and registry activity when the task executes
- Approved software deployment, maintenance or administrative context
- Similar task creation on other endpoints
- Escalation/containment authority and evidence-preservation requirements

### Relevant Tools / Logs

Windows Security Event 4698 and related scheduled-task audit events; Event 4688; Sysmon where deployed; Microsoft Defender for Endpoint or other EDR; Wazuh, Splunk or Microsoft Sentinel; Task Scheduler operational evidence where collected; PowerShell logs; file-signature/hash and software-inventory data; DNS/proxy/firewall telemetry.

### Interview Takeaway

Event 4698 tells me a scheduled task was created; it does not tell me the task is malicious. I would investigate who created it, what it runs, when and under which account it runs, the creating process and the resulting endpoint/network behaviour, then compare that with approved administration before escalating suspected persistence.

## Question 33

### Interview Question

A security tool alerts that a user or endpoint uploaded an unusually large volume of data to a cloud-storage service. How would you investigate possible data exfiltration without assuming that every large upload is malicious?

### Interview-Ready Answer

Data exfiltration is the unauthorised transfer of data out of an organisation or security boundary. A large cloud upload can be an important signal, but it is not automatically exfiltration because legitimate backups, collaboration, migrations, developer workflows and approved file transfers can also move large amounts of data.

MITRE ATT&CK maps adversarial use of services such as Dropbox, Google Drive, OneDrive, MEGA and other cloud storage for stealing data to **Exfiltration Over Web Service: Exfiltration to Cloud Storage (T1567.002)**. In a SOC environment, I would therefore treat the upload alert as an observation and build the context required to determine intent and impact.

I would establish the user and device, cloud service, amount of data, timeframe, source files or repositories where telemetry provides them, process/application responsible, destination account or tenant where visible, and whether the activity matches the user's normal job. I would correlate endpoint, secure-web-gateway/proxy, DNS, firewall and cloud-app activity. Microsoft Defender for Cloud Apps can detect anomalous or mass file-download/share patterns and can surface unusual application data usage; exact detections and governance controls depend on connected apps, licensing and configuration.

I would also investigate what happened before the transfer. For example, did an unusual process stage or archive files, did the user access large numbers of sensitive documents, was there a recent risky sign-in, did a new OAuth app gain access, or did tools such as a command-line cloud-sync utility appear? I would not claim exfiltration merely because bytes were uploaded; I would look for evidence that sensitive organisational data was transferred to an unauthorised destination.

As Tier 1, I would document scope, sensitivity and supporting evidence and escalate under the data-loss/incident-response playbook. Blocking a cloud service, suspending a user, isolating a host or changing DLP/session policy should be performed only when authorised because these actions can have significant business impact.

### Real-World SOC Scenario

A proxy/EDR alert shows a finance workstation uploading several gigabytes to a personal cloud-storage service late at night. The user does not normally use that service.

I would identify the responsible process and user session, verify whether an approved business workflow explains it, review the files or sensitivity context where authorised telemetry provides that information, and correlate the upload with file-access, archive creation, cloud-app, identity and network activity.

If the timeline shows a new executable or cloud-sync tool collecting files from sensitive shares, creating an archive and uploading it to an unauthorised personal cloud account, that strongly supports exfiltration and requires urgent escalation. If the upload is a documented migration performed by an approved administrator to a sanctioned tenant, that supports legitimate activity.

### What I Would Check as a Tier 1 Analyst

- User/account, device and privilege/business role
- Cloud service/domain and whether it is sanctioned or normally used
- Upload volume, timing, duration and deviation from normal baseline
- Process/application responsible for the transfer
- Destination account/tenant or URL context where available
- Files, folders, sensitivity labels or data classification where authorised telemetry exposes them
- File-access and archive/staging activity before the transfer
- EDR process tree and command-line context
- DNS, proxy, firewall and network connection evidence
- Defender for Cloud Apps/Purview DLP or other data-security alerts where deployed
- Recent sign-in, OAuth-consent or identity anomalies
- Similar transfers from other users/hosts
- Approved backup, migration, collaboration or administration context
- Evidence that the transfer actually completed
- Incident severity, legal/privacy/business escalation path and authorised containment

### Relevant Tools / Logs

Secure web gateway/proxy; firewall/DNS/network telemetry; Microsoft Defender for Endpoint or other EDR; Microsoft Defender for Cloud Apps where licensed; Microsoft Purview DLP where deployed; Microsoft Sentinel/Splunk/Wazuh; cloud-service audit logs; identity/Entra sign-ins; file-access telemetry; incident/ticketing records.

### Interview Takeaway

A large cloud upload is a signal, not automatic proof of data exfiltration. I would establish who transferred the data, from which device and process, what data was involved, where it went, whether the destination and workflow were authorised, and what endpoint/identity activity preceded it. Confirmed unauthorised transfer of sensitive data would require urgent escalation through the data-loss and incident-response playbook.

## Verification Notes

- Microsoft Entra documentation defines consent phishing as tricking users into granting permissions to malicious cloud applications, allowing the application to access legitimate cloud services and user data.
- Microsoft Entra audit guidance documents permission-related activities including `Consent to application`, `Add delegated permission grant`, and application-role assignment events for service principals.
- Microsoft Defender for Cloud Apps/App Governance documentation updated in August 2026 documents OAuth app policies and anomaly detections including malicious OAuth app consent and suspicious application activity. Availability depends on licensing, connected apps and configuration.
- Microsoft Defender for Office 365 guidance on illicit consent grants notes that a malicious external application can retain account-level data access without the attacker having an organisational password; password reset or MFA alone is therefore not a complete remediation for the application grant itself.
- MITRE ATT&CK Cloud Application Integration (T1671) covers OAuth application integrations used for persistence, and Steal Application Access Token (T1528) includes abuse of OAuth authorisation to obtain application access tokens.
- Microsoft documents Windows Security Event 4698 as `A scheduled task was created` and lists Subject, Task Name and Task Content among its investigation fields. The Audit Other Object Access Events subcategory also includes 4699, 4700, 4701 and 4702 for scheduled-task lifecycle changes.
- MITRE ATT&CK Scheduled Task/Job: Scheduled Task (T1053.005), last modified 12 May 2026, covers abuse of Windows Task Scheduler for execution, persistence and privilege escalation.
- MITRE ATT&CK Exfiltration to Cloud Storage (T1567.002), last modified 12 May 2026, describes adversaries transferring stolen data to cloud-storage services such as Dropbox, Google Drive, OneDrive and similar platforms.
- Microsoft Defender for Cloud Apps documentation updated in 2026 describes detections/policies for mass or anomalous file activity and monitoring unusual application data usage. Exact telemetry and response options depend on connected services and configuration.
