# SOC Interview Practice — 2026-09-30

## Question 101

### Interview Question

What is password spraying, and how is it different from a traditional brute-force attack?

### Interview-Ready Answer

Password spraying is an authentication attack in which an attacker tries one password, or a small set of commonly used passwords, across many accounts rather than trying many passwords against one account. MITRE ATT&CK tracks it as T1110.003 under Brute Force. The operational reason this matters is that spreading attempts across many accounts can reduce the chance of triggering per-account lockout thresholds.

In a SOC environment, I would look for the pattern, not just a single failed login: one source or related sources generating authentication failures across many different accounts in a short period, repeated failures with similar timing, and any successful authentication that follows the failures. I would also check whether the source is expected, whether the targeted accounts are privileged, whether MFA was challenged or satisfied, and whether the activity is external or internal.

Observation: multiple authentication failures occurred. Hypothesis: the pattern may be password spraying. Confirmed evidence requires the distribution across accounts, source/timing context and supporting identity telemetry; a few failed logins alone do not prove an attack.

### Real-World SOC Scenario

A SIEM alert shows the same external IP generating failed authentication attempts against 40 user accounts over ten minutes. One account later authenticates successfully from that IP. I would prioritise the successful account, review the sign-in context and MFA result, check subsequent activity, scope other targeted users and escalate according to the identity-compromise playbook.

### What I Would Check as a Tier 1 Analyst

- Number of distinct targeted accounts and failure count
- Source IP(s), geolocation/context and known corporate/VPN infrastructure
- Time window and repetition pattern
- Failure reasons and authentication protocol/logon type where available
- Any successful authentication following the failures
- MFA and conditional-access results where available
- Privilege/sensitivity of targeted accounts
- Post-authentication activity and other affected users
- Escalation/containment authority under the playbook

### Relevant Tools / Logs

Microsoft Entra sign-in logs where applicable, Windows Security authentication events, Microsoft Sentinel, Splunk, Wazuh, VPN/SSO logs, firewall/proxy telemetry and identity-provider logs.

### Key Interview Takeaway

“Password spraying targets many accounts with a small number of passwords. As Tier 1, I would identify the cross-account pattern, prioritise any successful sign-in, correlate identity and network evidence, and follow the playbook for containment and escalation.”

### Verification Notes

- MITRE ATT&CK T1110.003 Password Spraying: https://attack.mitre.org/techniques/T1110/003/
- MITRE DET0487 describes detection using authentication failures across multiple accounts and includes Windows Security 4625/4771 among relevant data sources: https://attack.mitre.org/detectionstrategies/DET0487/

## Question 102

### Interview Question

What does Windows Security Event ID 4625 tell you, and how would you use its fields during an investigation?

### Interview-Ready Answer

Microsoft documents Event ID 4625 as “An account failed to log on.” It records a failed logon attempt and can include the account targeted, logon type, failure reason, Status/SubStatus, workstation and source network information depending on the authentication path and available data.

I would not treat 4625 as proof of an attack. Failed logons can result from mistyped passwords, stale service credentials, disabled accounts or legitimate configuration problems. I would use the fields to understand who failed to authenticate, from where, how, why and whether the event is part of a larger pattern. Microsoft notes, for example, that 0xC0000064 can indicate a bad/non-existent username and repeated occurrences can be a user-enumeration signal; 0xC000006A indicates a bad password. I would interpret Status/SubStatus using Microsoft documentation rather than memorising or guessing codes.

Observation: an authentication attempt failed. Hypothesis: repeated or patterned failures may indicate attack activity. Confirmed evidence requires correlation across accounts, sources, timing and any subsequent successful authentication or malicious behaviour.

### Real-World SOC Scenario

A domain controller records many 4625 events from one source against different usernames. I would group failures by source and target, review the Status/SubStatus and logon type, then search for successful 4624 events or identity-provider sign-ins from the same source. A later success on a targeted account would raise urgency substantially.

### What I Would Check as a Tier 1 Analyst

- Target account/domain
- Timestamp and affected host
- Logon Type
- Failure Reason, Status and SubStatus
- Source Network Address/Workstation Name when populated
- Volume and number of distinct targeted accounts
- Related successful logons
- Account privilege and normal sign-in baseline
- VPN/Entra/EDR/network evidence for the same source

### Relevant Tools / Logs

Windows Security Event 4625 and related authentication events such as 4624 where appropriate, Microsoft Sentinel, Splunk, Wazuh, Active Directory/domain-controller logs, Entra sign-in logs, VPN and firewall logs.

### Key Interview Takeaway

“4625 means a logon failed; it does not mean an attacker was present. I use the account, source, logon type and documented failure codes, then correlate the pattern and look for any successful authentication.”

### Verification Notes

- Microsoft Learn Event 4625: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625

## Question 103

### Interview Question

You have normalised authentication data in Splunk with fields `src_ip`, `user` and `action`. Explain what this SPL is trying to show and what it does not prove:

```spl
index=auth action="failure"
| stats count AS failures dc(user) AS distinct_users values(user) AS users BY src_ip
| sort - distinct_users
```

### Interview-Ready Answer

The search filters the chosen authentication index to events whose normalised `action` is `failure`. The `stats` command then groups results by `src_ip`, counts the failure events, calculates the distinct number of users targeted with `dc(user)`, and returns the observed user values. Finally, it sorts the results so sources targeting the greatest number of distinct users appear first.

Splunk officially documents `stats` as an aggregation command and `dc()`/`distinct_count()` as returning the count of distinct values. The important qualification is that `src_ip`, `user`, `action` and even `index=auth` are example normalised fields/index names for this interview artefact; real field names depend on the organisation's data model, add-ons and ingestion pipeline.

Observation: a source has authentication failures against multiple users. Hypothesis: a high distinct-user count may be consistent with password spraying. Confirmed evidence requires validating the raw events, time window, source context, failure reasons and any later success. This search alone does not prove password spraying because a proxy, VPN concentrator, misconfigured application or other shared infrastructure could create a similar aggregation.

### Real-World SOC Scenario

The result shows one external IP with 120 failures across 55 accounts, while most sources target only one or two users. I would pivot to the raw events, narrow the time window, inspect failure reasons, identify whether the IP belongs to approved infrastructure, and search for successful logins from that source or against those users.

### What I Would Check as a Tier 1 Analyst

- Raw events behind the aggregation
- Search time range
- Whether field extraction/normalisation is correct
- Distinct users versus total failures
- Source IP ownership and expected infrastructure
- Authentication failure reasons
- Successful logins from the same source
- MFA/identity-risk evidence where available
- Subsequent endpoint/cloud activity for any successful account

### Relevant Tools / Logs

Splunk SPL, identity/authentication logs, Windows Security logs, Microsoft Entra sign-in logs, VPN/SSO logs, firewall telemetry and threat-intelligence context.

### Key Interview Takeaway

“This SPL helps surface sources failing against many distinct accounts, which is useful for spray triage. I would validate the raw events and context and then look for successful authentication; the aggregation is a lead, not proof of compromise.”

### Verification Notes

- Splunk `stats` command: https://help.splunk.com/en/splunk-enterprise/spl-search-reference/9.2/search-commands/stats
- Splunk documents `dc()`/`distinct_count()` as counting distinct field values: https://help.splunk.com/en/splunk-cloud-platform/search/spl2-search-reference/statistical-and-charting-functions/aggregate-functions

## Question 104

### Interview Question

Your SIEM detects failed sign-ins against dozens of users from one external IP. Ten minutes later, one targeted user successfully signs in from the same IP. As Tier 1, how would you triage and escalate this possible password-spray compromise?

### Interview-Ready Answer

I would raise the priority because the combination of broad failures followed by a success on a targeted account is more concerning than failures alone. I would still avoid declaring compromise until I validate the evidence.

First, I would confirm the failed-sign-in pattern: number of accounts, source IP, time window, authentication method and failure reasons. Then I would investigate the successful sign-in: whether the user normally signs in from that source/location, whether MFA was involved and what the identity platform recorded, whether the device/session is known, and whether conditional-access or risk signals exist. I would then review post-authentication activity for unusual mailbox, cloud, endpoint, privilege or lateral-movement behaviour as relevant to the environment.

I would scope the source IP and targeted users across the SIEM and identity platform. If the successful sign-in is inconsistent with the user's baseline or there is corroborating malicious activity, I would escalate as likely account compromise and follow the organisation's authorised containment process, which may include session revocation, credential reset, account restriction or other identity actions by the appropriate responder. I would not claim that Tier 1 can perform those actions unless the playbook grants that authority.

Observation: many accounts failed from one source and one targeted account later succeeded. Hypothesis: password spraying may have obtained valid credentials. Confirmed evidence could include an anomalous successful session plus unauthorised post-login activity, user confirmation that the sign-in was not theirs, or other corroborating identity/endpoint evidence.

### Real-World SOC Scenario

The targeted user confirms they were not signing in, the source is not corporate infrastructure, and the successful session is followed by unusual cloud activity. I would preserve the timeline and indicators, escalate urgently, scope other targeted accounts and follow the identity-compromise playbook for containment and recovery.

### What I Would Check as a Tier 1 Analyst

- Failed-authentication pattern and distinct users
- Successful sign-in details for the targeted account
- Source IP ownership/reputation and expected VPN/proxy infrastructure
- MFA and conditional-access results where available
- User/device/location baseline and user confirmation where appropriate
- Session and post-login activity
- Privilege level of the account
- Other users with successful sign-ins from the same source
- Related endpoint, email and cloud alerts
- Ticket timeline, evidence preservation and escalation threshold
- Authorised containment actions in the playbook

### Relevant Tools / Logs

Microsoft Sentinel or Splunk, Microsoft Entra/other IdP sign-in logs, Windows authentication logs, Defender XDR/EDR, Microsoft Defender for Office 365 where email is relevant, VPN/firewall/proxy logs, Wazuh and threat-intelligence sources.

### Key Interview Takeaway

“Failures across many users suggest spraying; a later success on a targeted account materially raises the risk. I would validate that success, check MFA and post-login behaviour, scope other users, and escalate or contain according to the identity-compromise playbook and my authority.”

### Verification Notes

- MITRE ATT&CK T1110.003 Password Spraying: https://attack.mitre.org/techniques/T1110/003/
- MITRE DET0487 detection strategy: https://attack.mitre.org/detectionstrategies/DET0487/
- Microsoft Learn Event 4625: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625
