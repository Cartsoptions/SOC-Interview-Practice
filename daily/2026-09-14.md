# SOC Interview Practice - 2026-09-14

## Question 61

### Interview Question

A workstation suddenly begins connecting to many internal IP addresses and ports over a short period. What is network service discovery or port scanning, and how would you investigate whether the activity is legitimate administration or attacker reconnaissance?

### Interview-Ready Answer

**Network service discovery is the process of identifying hosts, open ports and services that are reachable on a network.** Administrators, vulnerability scanners, asset-discovery platforms and troubleshooting tools perform this legitimately. Attackers can also use the same behaviour after gaining access to learn what systems and services are available for lateral movement or exploitation.

MITRE ATT&CK maps this behaviour to **Network Service Discovery, T1046**. Current MITRE detection guidance recommends looking for behavioural patterns such as rapid or sequential connections to many destination IPs or ports, the responsible process, and whether the source is an approved scanner or administrative system.

So I would separate:

**Observation:** one endpoint is probing multiple hosts or services.

**Hypotheses:** approved vulnerability scanning, asset discovery, troubleshooting, misconfiguration, or attacker reconnaissance.

**Confirmed malicious discovery:** requires supporting evidence showing that the scanning is unauthorised and linked to suspicious endpoint, identity or follow-on activity.

As a Tier 1 analyst, I would identify the source device and process, quantify the destinations and ports, determine whether the pattern is horizontal, vertical or mixed, and compare the source with the organisation's list of approved scanners. I would then correlate EDR, firewall, IDS/IPS, NetFlow or PCAP evidence and look for activity that preceded or followed the scan.

I would not call a scan malicious purely because tools such as Nmap, vulnerability scanners or scripted connection tests are visible. The business context and surrounding telemetry matter.

### Real-World SOC Scenario

The SIEM detects one finance workstation connecting to TCP 445, 3389, 22 and 5985 across dozens of internal systems within several minutes.

The finance workstation is not an approved vulnerability scanner or IT-administration device.

EDR shows an unfamiliar process started shortly before the connection burst, and the same account later attempts authentication to two discovered servers.

My **observation** is high-volume internal service probing from an unexpected endpoint.

My **hypothesis** is attacker reconnaissance after endpoint compromise.

I would correlate:

**source process -> network scan pattern -> discovered services -> authentication attempts -> possible lateral movement**

If the source process is suspicious, the host is not authorised to scan and follow-on authentication or remote-service activity appears, the malicious discovery hypothesis becomes strong and I would escalate.

### What I Would Check as a Tier 1 Analyst

- Source host, user and business role
- Whether the source is an approved scanner, monitoring platform or admin device
- Source process and parent process
- EDR or Sysmon process evidence where available
- Number of unique destination IP addresses
- Number and type of destination ports
- Scan rate and timeframe
- Whether the pattern targets many hosts on one port, many ports on one host, or both
- Firewall, IDS/IPS and NetFlow evidence
- PCAP or Wireshark evidence where available and authorised
- Whether connection attempts succeeded or were blocked
- Services exposed on the destination systems
- Authentication attempts after discovery
- SMB, RDP, SSH, WinRM or other remote-service activity afterwards
- Approved vulnerability scan or change window
- Similar scanning from other endpoints
- Tier 1 escalation and containment authority

### Tools / Logs

Microsoft Defender for Endpoint or another EDR; Microsoft Sentinel; Splunk; Wazuh; firewall logs; IDS/IPS; NetFlow; Sysmon Event 1 and network telemetry where configured; Wireshark/PCAP where available; asset inventory; vulnerability-scanner schedules and change-management records.

### Interview Takeaway

Network service discovery identifies reachable hosts, ports and services. I would not treat scanning as automatically malicious. I would identify the source process and endpoint, compare it with approved scanning activity, analyse the destination pattern and correlate any authentication or lateral-movement behaviour before escalating.

## Question 62

### Interview Question

What does Windows Security Event ID 4672 mean, and how would you investigate a special-logon alert without assuming that every 4672 event represents privilege escalation?

### Interview-Ready Answer

**Windows Security Event ID 4672 means that sensitive privileges were assigned to a newly created logon session.** Microsoft documents privileges that can appear in this event, including `SeDebugPrivilege`, `SeBackupPrivilege`, `SeImpersonatePrivilege`, `SeLoadDriverPrivilege` and others.

A critical interview distinction is that **4672 shows privileges assigned to the logon token. It does not by itself prove that those privileges were actually exercised, and it does not automatically prove privilege escalation.**

Many legitimate highly privileged sessions generate Event 4672. Microsoft specifically recommends focusing monitoring on accounts other than expected built-in principals such as LOCAL SYSTEM, NETWORK SERVICE and LOCAL SERVICE, and on administrative accounts that do not normally receive the listed privileges.

Event 4672 contains a **Logon ID** that Microsoft says can be correlated with other events such as **Event 4624**, which records a successful logon. I would use that correlation to understand how the session was created and what the account did afterwards.

So I would separate:

**Observation:** sensitive privileges were assigned to a new logon session.

**Hypotheses:** normal SYSTEM/service activity, legitimate administrator logon, unexpected privileged authentication, or account misuse.

**Confirmed privilege misuse or escalation:** requires evidence showing an unexpected account gained or used privileges and then performed suspicious privileged actions.

### Real-World SOC Scenario

A workstation generates Event 4672 for a normal help-desk user who does not usually perform local administrative work.

The event includes sensitive privileges such as `SeDebugPrivilege` and `SeImpersonatePrivilege`.

Using the Logon ID, I correlate the event with a nearby Event 4624 and determine that the account successfully logged on interactively to the device. EDR then shows an unfamiliar elevated process accessing another security-sensitive process shortly afterwards.

My **observation** is that the help-desk user's logon session received sensitive privileges.

My **hypothesis** is unexpected privileged access or privilege escalation.

I would verify whether the user was temporarily authorised for admin work, whether group membership changed, how the session authenticated, which elevated processes ran, and what privileged actions followed.

If the privilege assignment is unexpected and is followed by suspicious process, credential-access or security-control activity, I would escalate.

### What I Would Check as a Tier 1 Analyst

- Host and Event 4672 timestamp
- Security ID, account name and account domain
- Logon ID
- Exact privileges listed
- Whether the account is SYSTEM, NETWORK SERVICE, LOCAL SERVICE or an expected administrator
- Related Event 4624 using the same Logon ID
- Logon Type and source context from the related authentication event
- Account's normal role and privilege baseline
- Recent privileged-group membership changes
- Event 4688 or EDR process activity after logon
- Process integrity/elevation context where available
- Credential-access or LSASS-related alerts
- Service, scheduled-task, Registry or security-control changes
- Remote access such as RDP, SMB or WinRM
- Approved administration/change ticket
- Similar unexpected 4672 events elsewhere
- Tier 1 escalation and containment authority

### Tools / Logs

Windows Security Events 4672 and 4624; Event 4688 where process auditing is enabled; Defender for Endpoint or another EDR; Microsoft Sentinel; Splunk; Wazuh; Sysmon where configured; Active Directory or Entra identity evidence; change-management records.

### Interview Takeaway

Event 4672 means sensitive privileges were assigned to a new logon session. It does not prove those privileges were used or that privilege escalation occurred. I would correlate the Logon ID with the successful logon, check whether the account normally receives those privileges and investigate the privileged activity that followed.

## Question 63

### Interview Question

An EDR alert shows `powershell.exe` or `pwsh.exe` using `-EncodedCommand`. What does that mean, and how would you investigate encoded or obfuscated PowerShell without assuming that Base64 encoding is automatically malicious?

### Interview-Ready Answer

**PowerShell's `-EncodedCommand` parameter accepts a Base64-encoded command string.** Microsoft documents this as a legitimate way to submit commands that contain complex quoting or nested syntax. In Windows PowerShell 5.1 and modern `pwsh`, the encoded command is represented as Base64 over a UTF-16LE command string.

That creates an important SOC distinction:

**Base64 encoding is not encryption, and `-EncodedCommand` is not automatically malware.** Legitimate deployment, automation and administration tools can use encoding. Attackers also use encoding and other obfuscation to make commands harder to read and to evade simple detections.

MITRE ATT&CK maps encoded, compressed or otherwise concealed content to **Obfuscated Files or Information, T1027**. Its current behavioural detection guidance recommends correlating obfuscated command lines with suspicious parent processes, process creation, encoded or compressed artefacts and follow-on activity.

As Tier 1, I would inspect and safely decode the command content for analysis where the organisation's tooling or procedure supports it, but I would **not execute the decoded command on the production endpoint**.

Where Windows PowerShell **Script Block Logging** is enabled, Microsoft documents **Event ID 4104** in the `Microsoft-Windows-PowerShell/Operational` log. Script Block Logging records the content of script blocks processed by PowerShell and can therefore provide much better visibility than the encoded command line alone. Logging coverage must be verified because this policy is not something I would assume is enabled everywhere.

In Microsoft Defender XDR Advanced Hunting, the `DeviceProcessEvents` table contains process-creation telemetry and fields such as `ProcessCommandLine` when Defender for Endpoint supplies the data. I would use the actual available schema rather than assume every environment has identical telemetry.

### Real-World SOC Scenario

EDR shows:

**Outlook -> powershell.exe -EncodedCommand ... -> external network connection**

The user had opened an attachment minutes earlier.

My **observation** is that Outlook launched PowerShell with an encoded command.

My **hypothesis** is malicious script execution triggered by the phishing attachment.

I would inspect the parent-child process chain, recover or decode the encoded content safely, check Event 4104 if Script Block Logging is enabled, identify any files or Registry changes and correlate DNS/proxy/firewall activity.

If the decoded content downloads or launches an untrusted payload, the execution chain is unusual and suspicious network or persistence activity follows, the malicious-execution hypothesis becomes strong.

If the command instead belongs to an approved enterprise-management workflow and all surrounding activity matches the expected baseline, that supports a benign explanation.

### What I Would Check as a Tier 1 Analyst

- Device and logged-on user
- `powershell.exe` versus `pwsh.exe`
- Parent and initiating process
- Full command line where available
- Whether `-EncodedCommand` or another obfuscation technique is present
- Safely decoded command content without executing it
- PowerShell Script Block Logging coverage
- Event ID 4104 where Script Block Logging is enabled
- Event 4688 or Sysmon Event 1 where configured
- Defender XDR `DeviceProcessEvents` process telemetry where available
- File creation and downloaded payloads
- File hash, signer and prevalence
- Registry, scheduled-task or service persistence
- DNS, proxy and firewall activity
- Child processes launched by PowerShell
- Whether the user recently opened an email attachment or link
- Approved administration/deployment automation
- Similar encoded PowerShell across other endpoints
- Tier 1 containment and escalation authority

### Tools / Logs

Defender for Endpoint and Defender XDR Advanced Hunting; Microsoft Sentinel; Splunk; Wazuh; Windows Security Event 4688 where enabled; PowerShell Operational Event 4104 where Script Block Logging is enabled; Sysmon Event 1 and related telemetry where configured; DNS/proxy/firewall logs; Defender for Office 365 or other email-security evidence.

### Interview Takeaway

`-EncodedCommand` means PowerShell received a Base64-encoded command. It is not automatically malicious and Base64 is not encryption. I would inspect the parent process, safely decode the content without executing it, check Script Block Logging or EDR process telemetry and correlate files, persistence and network behaviour before deciding whether the PowerShell activity is malicious.

- MITRE ATT&CK maps network service discovery and port/service scanning to **T1046**. Current detection strategy **DET0376**, last modified 12 May 2026, recommends correlating process creation with rapid or sequential network probing and maintaining allowlists/context for approved tools such as Nmap or vulnerability scanners.
- Microsoft documents **Event ID 4672** as `Special privileges assigned to new logon`. The event is generated when sensitive privileges are assigned to a new logon session and includes a Logon ID that can be correlated with events such as **4624**. Microsoft recommends focusing monitoring on unexpected accounts or sensitive privileges rather than treating all 4672 events as malicious.
- Event 4672 represents privileges assigned to the logon token. It does not by itself demonstrate that the privileges were exercised or prove privilege escalation.
- Microsoft PowerShell documentation confirms that both Windows PowerShell and modern `pwsh` support **`-EncodedCommand`** using a Base64 representation of a UTF-16LE command string. This feature has legitimate administrative uses.
- Microsoft documents **PowerShell Script Block Logging Event ID 4104** in the `Microsoft-Windows-PowerShell/Operational` log when Script Block Logging is enabled. The policy records the content of processed script blocks.
