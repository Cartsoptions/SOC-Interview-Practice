# SOC Interview Practice — 2026-09-02

## Question 37

### Interview Question

What is MFA fatigue or MFA push bombing, and how would you investigate repeated MFA prompts followed by a successful sign-in?

### Interview-Ready Answer

MFA fatigue, sometimes called MFA push bombing, is an attack pattern where an adversary repeatedly triggers MFA requests in the hope that the user eventually approves one. MITRE ATT&CK maps this behaviour to **T1621 — Multi-Factor Authentication Request Generation**. The attacker may already know or have guessed the password, but still needs the second factor.

In a SOC environment, repeated MFA prompts are the **observation**. My hypotheses could include an attacker generating prompts, a broken application/session causing repeated challenges, or legitimate user retry behaviour. I would not treat a later successful sign-in as automatic proof of compromise until I correlate the identity evidence.

I would review the user's sign-in events around the timeframe, source IPs and locations as context, device information where available, authentication method, MFA result, whether the user says they initiated the sign-in, and what happened after the successful authentication. I would also check for repeated failures, unusual applications/resources, new devices, session anomalies and related endpoint or mailbox activity.

Microsoft Authenticator number matching is designed to reduce accidental approval of push notifications by requiring the user to match a number shown on the sign-in screen. Microsoft currently enables number matching for Authenticator push notifications. As Tier 1, I would investigate and escalate suspected compromise; changing authentication policy, revoking sessions or disabling an account should follow the organisation's authorised identity-response process.

### Real-World SOC Scenario

A user reports receiving ten Microsoft Authenticator prompts they did not initiate. Minutes later, Entra logs show a successful sign-in from an unfamiliar IP.

I would build a timeline of the failed sign-in attempts, MFA challenges and final success. I would confirm whether the user approved any prompt, compare the source IP/device/application with the user's normal activity and check what the account accessed afterwards.

If the user confirms they did not initiate the sign-in and the successful session is followed by suspicious mailbox rules, OAuth consent, unusual downloads or other identity activity, that would strongly support account compromise and require escalation.

### What I Would Check as a Tier 1 Analyst

- User account and privilege level
- Number and timing of MFA prompts/challenges
- Failed and successful sign-in events
- Source IP and geolocation as supporting context
- Device/browser/client information where available
- Application/resource being accessed
- Authentication method and MFA result
- Whether the user initiated or approved the request
- New or unfamiliar device/session activity
- Conditional Access or Identity Protection signals where available
- Post-authentication mailbox, file, OAuth or endpoint activity
- Similar MFA prompt patterns affecting other users
- Playbook authority for session revocation, password reset or account disablement

### Tools / Logs

Microsoft Entra sign-in logs; Microsoft Sentinel; Microsoft Defender XDR; Defender for Cloud Apps where deployed; Microsoft 365 audit logs; EDR/browser telemetry; incident-management records.

### Interview Takeaway

MFA fatigue is repeated MFA-request generation intended to pressure a user into approving access. I would correlate the prompt pattern, sign-in source, authentication result, user confirmation and post-login activity before deciding whether the account is compromised.

## Question 38

### Interview Question

What is Kerberoasting, and how would you investigate suspicious Kerberos service-ticket activity such as Windows Security Event ID 4769?

### Interview-Ready Answer

Kerberoasting is a credential-access technique against Active Directory service accounts. An authenticated domain user can request Kerberos service tickets for accounts associated with Service Principal Names (SPNs). An attacker can then attempt to crack the ticket material offline to recover a service-account password. MITRE ATT&CK maps this technique to **T1558.003 — Kerberoasting**.

Windows Security Event ID **4769** records a Kerberos Ticket Granting Service (TGS) service-ticket request and is generated on domain controllers. Microsoft notes that Windows Server 2016 and later can show an updated 4769 event after the January 14, 2025 or later security cumulative update, with additional encryption-related fields.

In a SOC environment, 4769 events are extremely common and are not malicious by themselves. I would look for anomalous patterns such as one account requesting many service tickets in a short period, requests for unusual service accounts/SPNs, activity from an unexpected client address, and encryption behaviour that differs from the organisation's baseline. MITRE's current Kerberoasting detection guidance specifically highlights anomalous 4769 bursts and RC4-encrypted TGS requests as useful signals. However, RC4 alone is not proof of Kerberoasting because legacy applications or account configuration can still cause legitimate RC4 usage.

I would correlate the requesting account, source host, Service Name/SPN, ticket encryption type, timing and volume with endpoint/process evidence and the account's normal behaviour. As Tier 1, I would document and escalate suspected credential-access activity; changing service-account passwords or Kerberos settings would normally be handled by identity/AD administrators under an approved response plan.

### Real-World SOC Scenario

The SIEM detects one normal user account requesting service tickets for dozens of SPN-backed service accounts within a few minutes. Several requests use RC4, and the activity originates from a workstation that does not normally perform directory administration.

I would verify the 4769 events on the domain controller, identify the requesting account and client address, list the Service Names targeted and compare the request volume with the user's baseline. I would then inspect EDR/Sysmon/4688 evidence from the source workstation for suspicious tooling or scripts and correlate related logon events.

If the burst of unusual TGS requests is accompanied by suspicious process activity and there is no approved administration or scanning explanation, that would strongly support a Kerberoasting hypothesis and require escalation.

### What I Would Check as a Tier 1 Analyst

- Event ID 4769 timestamp and domain controller
- Requesting account and account privilege
- Client Address/source host
- Service Name/SPN and service account targeted
- Number of service tickets requested in the timeframe
- Whether the requested services are normal for that account/host
- Ticket Encryption Type and supported-encryption context
- RC4 usage versus the organisation's normal Kerberos baseline
- Related 4624/4648/4672 authentication events where useful
- 4688/Sysmon/EDR process activity on the source workstation
- PowerShell or suspicious executable activity
- Similar TGS-request bursts from other users/hosts
- Approved admin, monitoring or security-testing activity
- Escalation and credential-remediation authority

### Tools / Logs

Windows Security Event ID 4769 on domain controllers; Microsoft Sentinel; Splunk; Wazuh; Defender for Endpoint or other EDR; Windows Event ID 4688; Sysmon where deployed; Active Directory/service-account inventory.

### Interview Takeaway

Kerberoasting abuses legitimate Kerberos service-ticket requests to obtain material that can be cracked offline. I would not treat 4769 or RC4 as proof by themselves; I would look for abnormal TGS-request volume, unusual SPNs or sources and supporting endpoint evidence before escalating.

## Question 39

### Interview Question

What is ransomware, and how would you investigate and respond to a suspected ransomware incident as a Tier 1 SOC analyst?

### Interview-Ready Answer

Ransomware is malicious activity that encrypts or otherwise makes data or systems unavailable, commonly to extort payment. MITRE ATT&CK maps file/data encryption for impact to **T1486 — Data Encrypted for Impact**. Modern ransomware incidents may also include credential theft, lateral movement and data exfiltration before encryption, so seeing encrypted files can represent a late stage of a broader compromise.

In a SOC environment, I would first validate the alert and determine scope: which hosts/users are affected, whether encryption is active, what process is responsible, what files or shares are being changed and whether other endpoints show the same behaviour. I would look for precursor activity such as suspicious PowerShell, credential abuse, remote-service activity, unusual administrative tools, file staging or data exfiltration.

CISA's #StopRansomware guidance recommends determining impacted systems and isolating them promptly, while also examining EDR/AV/IDS/IPS and logs for earlier-stage evidence. Microsoft Defender for Endpoint provides device-isolation actions, but response capabilities depend on licensing, permissions and platform support. As Tier 1, I would only isolate a device, disable an account or block infrastructure if the incident playbook explicitly authorises that action; otherwise I would escalate immediately with clear scope and evidence.

I would also preserve evidence and avoid actions that could unnecessarily destroy forensic artefacts. Recovery decisions, restoration from backups, enterprise-wide containment and communications are coordinated incident-response/business-continuity activities rather than unilateral Tier 1 actions.

### Real-World SOC Scenario

EDR raises alerts on a workstation for high-volume file modifications and unusual file extensions. A ransom note appears, and the same account has recent SMB activity to several file servers.

I would identify the encryption process, user and host, determine whether activity is still ongoing and search the SIEM/EDR for the same process/hash/behaviour elsewhere. I would correlate SMB, authentication, scheduled-task/service, PowerShell and network activity to establish how far the incident has spread and whether lateral movement or data exfiltration occurred before encryption.

If the playbook authorises workstation isolation, I would isolate affected endpoints while coordinating escalation. Critical servers or domain controllers would require additional approval because indiscriminate isolation can cause major business impact.

### What I Would Check as a Tier 1 Analyst

- Affected user(s), endpoint(s), server(s) and business impact
- Whether encryption is active or completed
- Process responsible for encryption
- Parent/child process tree and command line
- High-volume file modifications or unusual extensions
- Ransom-note creation
- Files/shares/directories affected
- EDR alerts and antivirus detections
- SMB/RDP/remote-service activity
- Authentication and privileged-account activity
- Scheduled tasks/services/persistence
- PowerShell or script execution
- DNS/proxy/firewall/C2 activity
- Evidence of staging or data exfiltration before encryption
- Similar behaviour across other hosts
- Backup/recovery status as reported by authorised teams
- Tier 1 containment authority and escalation path
- Evidence preservation and incident documentation

### Tools / Logs

Defender for Endpoint or another EDR; Microsoft Sentinel/Splunk/Wazuh; Windows Security and Sysmon logs where deployed; firewall/DNS/proxy telemetry; SMB/RDP and identity logs; antivirus; file-server audit data; backup/incident-response platforms where available.

### Interview Takeaway

Ransomware is an impact technique that can be the final stage of a larger intrusion. I would validate encryption, identify the responsible process, scope affected systems, look for precursor lateral movement or exfiltration, preserve evidence and execute only authorised containment while escalating urgently.
