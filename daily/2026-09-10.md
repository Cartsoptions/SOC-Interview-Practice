# SOC Interview Practice — 2026-09-10

## Question 55

### Interview Question

What is a DCSync attack, and how would you investigate suspected DCSync activity in an Active Directory environment as a Tier 1 SOC analyst?

### Interview-Ready Answer

**DCSync is an Active Directory credential-access technique that abuses directory-replication permissions so an account can request replication data in a way that imitates legitimate domain-controller replication.** MITRE ATT&CK maps DCSync to **OS Credential Dumping: DCSync — T1003.006**. Microsoft Defender for Identity also has a **Suspected DCSync attack (replication of directory services)** detection, and Microsoft security-posture guidance recommends removing unnecessary DCSync replication permissions from accounts that should not have them.

In a normal Active Directory environment, replication between authorised domain controllers is legitimate. Therefore, the observation I would care about is not simply that replication occurred, but that **replication-related activity appears to originate from an unexpected account or non-domain-controller source**.

A useful Windows evidence source can be **Security Event ID 4662, “An operation was performed on an object,”** when **Audit Directory Service Access** and the appropriate SACLs are configured. Microsoft explicitly notes that 4662 is generated only when the relevant SACL exists and the performed operation matches it, so I would never claim that the absence of 4662 proves DCSync did not occur. MITRE’s current DCSync detection strategy also uses 4662 together with replication-protocol/network context and expected domain-controller source information.

My investigation would focus on the requesting identity, the source host, whether that source is an authorised domain controller or replication service, whether the account legitimately holds replication permissions, and what happened before and after the replication activity. If Microsoft Defender for Identity generated a DCSync alert, I would treat it as strong detection evidence but still validate the entities, timeline and surrounding endpoint/authentication activity before escalation.

### Real-World SOC Scenario

Microsoft Defender for Identity or the SIEM alerts on suspected directory-replication activity from a normal employee workstation rather than a domain controller.

The requesting account is a privileged service account, but the asset inventory shows that the workstation is not an authorised replication source.

My **observation** is abnormal replication-related activity involving a privileged account and an unexpected source host.

My **hypothesis** is that the account may be abusing DCSync-capable permissions to obtain Active Directory credential material.

I would correlate:

**identity/sign-in → source workstation process activity → replication evidence → subsequent privileged authentication or lateral movement**

If the source is not an authorised DC, the account has replication rights it should not normally exercise from that host, endpoint evidence is suspicious, and subsequent privileged activity appears, the DCSync hypothesis becomes much stronger and warrants urgent escalation.

### What I Would Check as a Tier 1 Analyst

- User/service account involved and privilege level
- Source workstation/IP and whether it is an authorised domain controller or replication system
- Destination domain controller(s)
- Defender for Identity DCSync alert details where deployed
- Windows Security Event ID 4662 where the required auditing/SACL coverage exists
- Directory-replication permissions on the account, especially unnecessary replication rights
- Whether the activity matches legitimate AD administration, backup, identity-sync or recovery tooling
- Authentication events before and after the replication activity
- EDR/Sysmon process activity on the source host
- RPC/network evidence related to directory replication where available
- Similar replication activity from other non-DC hosts
- Subsequent privileged authentication, SMB, RDP or other lateral movement
- Scope across high-value identities and systems
- Tier 1 escalation and containment authority

### Tools / Logs

Microsoft Defender for Identity; Microsoft Defender XDR; Windows Security Event 4662 where configured; Active Directory auditing and permission review; Microsoft Sentinel; Splunk; Wazuh; Defender for Endpoint or another EDR; Sysmon where deployed; firewall/network telemetry; identity and domain-controller logs.

### Interview Takeaway

DCSync abuses Active Directory replication permissions to request directory credential data. I would not diagnose it from one event alone; I would validate the requesting account, source host, replication permissions, Defender for Identity/SIEM evidence and supporting endpoint or network activity, with special concern when replication originates from a non-domain-controller system.

## Question 56

### Interview Question

What does Windows Security Event ID 1102 mean, and how would you investigate an audit-log-clearing alert without assuming every log clear is malicious?

### Interview-Ready Answer

**Windows Security Event ID 1102 means that the Windows Security audit log was cleared.** Microsoft states that this event is generated whenever the Security audit log is cleared and includes subject information such as the account SID/name/domain and Logon ID associated with the action.

Microsoft’s monitoring guidance says this event should typically be uncommon and recommends investigating why it occurred. However, **1102 does not by itself prove attacker activity**. An authorised administrator, troubleshooting process, system-maintenance workflow or other legitimate action could clear a log, although routine manual clearing of Security logs is generally unusual.

An important current ATT&CK detail is that **Clear Windows Event Logs is now T1685.005**, under **Disable or Modify Tools**, in the current 2026 Enterprise ATT&CK content. Older material may still reference the previous T1070.001 mapping, so in an interview I would use the current identifier and avoid relying on outdated technique numbering.

As Tier 1, I would first identify **who cleared the log, on which host and when**. I would correlate the 1102 subject Logon ID with recent authentication evidence where possible, review process-creation/EDR telemetry around the event, and check whether the action was authorised. MITRE’s current detection strategy for Windows event-log clearing correlates 1102 with elevated/process activity and other evidence rather than treating 1102 as a standalone compromise verdict.

I would also remember an important logging principle: if logs are centrally forwarded to a SIEM or another remote repository before an attacker clears the local log, the remote copies can preserve evidence that is no longer present on the endpoint.

### Real-World SOC Scenario

Sentinel alerts that the Security log was cleared on a finance workstation at 02:40.

Event 1102 identifies the account associated with the clear. There is no approved maintenance ticket for that endpoint.

EDR shows an unfamiliar process running with elevated privileges shortly beforehand, followed by the log-clear event and then a suspicious outbound connection.

My **observation** is that the Security audit log was cleared.

My **hypothesis** is defence impairment intended to hide earlier activity.

The hypothesis becomes stronger when the action is unauthorised and is surrounded by suspicious privilege, process and network evidence. If the clear is instead linked to documented maintenance by an authorised administrator and the surrounding activity is expected, that supports a benign explanation.

### What I Would Check as a Tier 1 Analyst

- Host and exact timestamp of Event 1102
- Subject account SID/name/domain in the event
- Subject Logon ID and related authentication context
- Whether an approved maintenance/change record exists
- Account privilege and normal administrative duties
- Windows Event 4688 or EDR/Sysmon process activity before the clear
- PowerShell or native-tool activity around the same timeframe where logged
- Privilege-elevation and logon evidence
- Whether other logs were cleared or logging was disabled
- Central SIEM/collector copies of events that pre-date the clear
- File deletion or other anti-forensic behaviour where telemetry exists
- DNS/proxy/firewall/EDR activity after the clear
- Similar 1102 events on other endpoints
- Whether malicious activity was already under investigation on the host
- Tier 1 escalation/containment authority

### Tools / Logs

Windows Security Event 1102; Windows 4688 where enabled; Sysmon/EDR telemetry where deployed; Microsoft Sentinel; Splunk; Wazuh; Defender for Endpoint; PowerShell logs where configured; central Windows Event Forwarding/SIEM data; firewall/DNS/proxy telemetry; change-management records.

### Interview Takeaway

Event ID 1102 means the Windows Security audit log was cleared. I would identify the account and Logon ID, validate whether the action was authorised, correlate process/authentication/network evidence around it and use centrally retained logs where available before deciding whether it represents legitimate administration or defence impairment.

## Question 57

### Interview Question

What is DNS tunnelling, and how would you investigate suspected DNS-based command-and-control or exfiltration as a Tier 1 SOC analyst?

### Interview-Ready Answer

**DNS tunnelling abuses DNS queries and responses to carry data or command-and-control information through the DNS protocol rather than using DNS only for ordinary name resolution.** MITRE ATT&CK maps DNS-based command-and-control to **Application Layer Protocol: DNS — T1071.004**.

DNS itself is essential and extremely noisy, so **an unusual DNS query is not automatically a tunnel**. Current MITRE detection guidance recommends looking for behavioural patterns such as unusually frequent queries, long or encoded-looking subdomains, unexpected processes generating DNS traffic, anomalous query patterns and DNS activity to suspicious infrastructure.

For Windows endpoints, **Sysmon Event ID 22** records DNS queries issued by a process whether the query succeeds or fails, provided Sysmon is deployed and configured. Sysmon Event ID 3 can add network-connection context when that high-volume event type is enabled. At the DNS-server layer, Microsoft Windows Server provides DNS Analytical logging that records DNS activity, but **DNS Analytical logs are not enabled by default**. Microsoft Sentinel’s Windows DNS Events via AMA connector depends on those analytical events, so I would always check actual logging coverage before claiming a data source should contain evidence.

As Tier 1, I would correlate **DNS pattern + responsible process + destination infrastructure + endpoint behaviour**. Long subdomains or TXT queries may be interesting, but they are not proof on their own because legitimate applications, CDNs, security products and service-discovery mechanisms can generate unusual DNS patterns.

### Real-World SOC Scenario

A SIEM detection reports hundreds of DNS queries from one workstation to the same external domain every few seconds.

The queried names contain long, changing subdomains. Sysmon Event 22, where deployed, shows that the queries are being generated by an unexpected script interpreter rather than a browser or normal system process.

EDR also shows the same process reading local files before the DNS burst.

My **observation** is high-frequency, unusual DNS activity from an unexpected process.

My **hypothesis** is DNS-based command-and-control or data tunnelling.

I would correlate the process tree, DNS query pattern, domain reputation/ownership, query timing and endpoint/file activity. If the same process repeatedly reads data and generates anomalous DNS queries to untrusted infrastructure, the tunnel/exfiltration hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst

- Source host and user
- Querying process where endpoint telemetry provides it
- Sysmon Event 22 coverage where deployed
- Query domain, subdomain length and variation
- Query frequency and periodicity
- DNS record types and response patterns
- Number of unique subdomains
- Domain age/reputation/threat-intelligence context where approved
- Whether the organisation normally communicates with the domain
- Other hosts querying the same domain
- Windows DNS Analytical logs where enabled
- Sentinel Windows DNS Events via AMA coverage where configured
- EDR process tree and command/script context
- File access or staging before the DNS activity
- Network/firewall/NSM evidence
- Legitimate software, security-agent, CDN or service-discovery explanation
- Whether suspicious activity continues after DNS resolution
- Tier 1 escalation/blocking authority

### Tools / Logs

DNS resolver/server logs; Windows DNS Analytical events where enabled; Sysmon Event 22 and Event 3 where configured; Microsoft Sentinel; Windows DNS Events via AMA where deployed; Splunk; Wazuh; Defender for Endpoint or another EDR; firewall/NSM/PCAP; Wireshark; approved threat-intelligence and domain-reputation sources.

### Interview Takeaway

DNS tunnelling uses DNS to carry command-and-control or other data. I would not diagnose it from one strange domain or long query; I would correlate query frequency and structure, the responsible process, domain context, endpoint behaviour and other network evidence before escalating suspected tunnelling or exfiltration.
