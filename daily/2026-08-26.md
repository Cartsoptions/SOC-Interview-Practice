# SOC Interview Practice — 2026-08-26

## Question 22

### Interview Question

What does Windows Security Event ID 4624 mean, and how would you investigate a suspicious successful Remote Desktop logon without assuming that every successful logon is malicious?

### Interview-Ready Answer

Windows Security Event ID **4624** means that a logon session was successfully created on the destination computer. The important SOC detail is the **Logon Type**, because it explains how the session was created. Microsoft documents, among others, Logon Type 2 as Interactive, Type 3 as Network, Type 5 as Service and Type 10 as RemoteInteractive, which is used for Remote Desktop/Terminal Services sessions.

In a SOC environment, a 4624 event is an observation that authentication succeeded; it does **not** prove compromise. I would investigate whether the account, source, destination, time and Logon Type are expected. For a suspicious Type 10 event, I would review the New Logon account, Source Network Address where populated, workstation/source context, authentication package, Elevated Token where applicable and the Logon ID. I would then correlate the session with VPN/firewall/RDP telemetry, identity data and endpoint activity after the logon.

MITRE ATT&CK maps adversarial use of Remote Desktop Protocol to **Remote Services: RDP (T1021.001)**. That mapping is useful if the evidence supports RDP-based lateral movement, but the presence of a Type 10 logon by itself does not prove adversarial activity.

### Real-World SOC Scenario

A SIEM alert shows a successful 4624 Logon Type 10 to a finance server at 02:15. The source address is an internal workstation not normally used by the account. I would confirm whether the user or support team had an approved reason to connect, correlate preceding failed/successful authentication and VPN activity, and inspect the destination server's EDR/process timeline after the logon. If the session is followed by unusual PowerShell, credential access or lateral movement, I would escalate urgently. If it matches an approved maintenance window and expected admin tooling, that supports a legitimate explanation.

### What I Would Check as a Tier 1 Analyst

- Event ID 4624 timestamp and destination host
- New Logon account, domain and Logon ID
- Logon Type and whether it fits the expected access method
- Source Network Address and workstation information where populated
- Authentication Package and Logon Process
- Elevated Token / privilege context where available
- Whether the account is privileged, dormant or unusual for the target
- Related 4625 failures, VPN/RDP gateway and firewall activity
- EDR/process activity after the successful logon
- Approved change, support or maintenance context
- Similar logons on other systems and escalation criteria

### Relevant Tools / Logs

Windows Security Event Log; Wazuh, Splunk or Microsoft Sentinel; Active Directory/domain-controller logs; VPN/RDP gateway logs; firewall telemetry; Microsoft Defender for Endpoint or other EDR; change-management/ticketing records.

### Key Interview Takeaway

Event ID 4624 tells me a Windows logon succeeded. I would use the Logon Type, account, source, destination and post-logon behaviour to decide whether it is expected or suspicious; for RDP, Logon Type 10 is particularly relevant, but a successful remote logon is evidence to investigate, not proof of compromise.

## Question 23

### Interview Question

On a Linux server, where would you look for evidence of suspicious SSH authentication, and how would you investigate repeated failures followed by a successful login?

### Interview-Ready Answer

On Linux, the exact log location depends on the distribution and logging configuration. On Ubuntu systems, authentication-related evidence is commonly available in **`/var/log/auth.log`**, and systems using systemd may also expose relevant service events through the system journal. I would not assume every Linux distribution stores authentication logs in the same file.

For SSH, I would investigate the username, source IP, timestamps, whether authentication failed or succeeded, the authentication method where recorded, and whether the account normally uses SSH from that source. I would then correlate the successful login with `sudo`/privilege activity, process execution, file changes and outbound network connections. MITRE ATT&CK maps adversarial use of SSH for remote access/lateral movement to **Remote Services: SSH (T1021.004)**, but legitimate administrators also use SSH, so context is essential.

As a Tier 1 analyst, I would normally analyse the logs in the SIEM or approved host-log source rather than modifying SSH configuration. Changes such as disabling an account, changing `sshd` policy or blocking an address would follow the organisation's response authority and playbook.

### Real-World SOC Scenario

A Linux server records dozens of failed SSH authentication attempts for an administrative account from one external IP, followed by a successful login. I would compare the successful event with the failures, determine whether the source is expected, check whether the account normally allows remote SSH, and review post-login activity. If the session is followed by unexpected `sudo` use, new persistence, file downloads or outbound connections, I would escalate as possible account compromise. If the source belongs to an approved administrator and the failures were caused by a known key/password issue, that may explain the pattern.

### What I Would Check as a Tier 1 Analyst

- Distribution and actual authentication logging source
- Failed and successful SSH events and timeframe
- Username/account privilege and whether the account should use SSH
- Source IP and source reputation/context
- Authentication method where recorded
- Whether the success follows repeated failures
- `sudo`/privilege escalation and session activity after login
- New processes, files, persistence or configuration changes
- DNS/firewall/proxy/EDR or host network telemetry where available
- Similar activity on other Linux hosts
- Approved admin/change context and containment authority

### Relevant Tools / Logs

Ubuntu `/var/log/auth.log` where applicable; systemd journal where configured; Wazuh, Splunk or Microsoft Sentinel; EDR/XDR for Linux where deployed; firewall/network telemetry; SSH server logs; change-management and ticketing records.

### Key Interview Takeaway

For suspicious Linux SSH access, I would first identify the system's actual authentication log source, then correlate failures, the successful login, source/user context and post-login behaviour. SSH is a legitimate administration protocol, so the evidence after authentication is critical to deciding whether the session is malicious.

## Question 24

### Interview Question

Explain the TCP three-way handshake, and show how you would use packet or firewall evidence to distinguish an attempted connection from an established TCP session during a SOC investigation.

### Interview-Ready Answer

TCP establishes a connection by synchronising sequence numbers between both peers. In the normal three-way handshake, the client sends **SYN**, the server responds **SYN-ACK**, and the client returns **ACK**. RFC 9293 explains that the SYN exchange and acknowledgements synchronise the initial sequence numbers, and that the server's SYN and ACK can be combined, producing the three-message handshake.

In a SOC environment, this helps me interpret network evidence rather than simply memorise SYN/SYN-ACK/ACK. If I see repeated SYN packets with no SYN-ACK, I have evidence of connection attempts but not a completed TCP handshake. If I see SYN, SYN-ACK and the final ACK, the TCP session was established at the transport layer. That still does **not** prove that the application transaction succeeded or that the traffic was malicious; I would examine what followed, such as TLS, HTTP or another application protocol, plus endpoint/process context.

I would also be careful with SYN-scan behaviour. A scanner can send SYN, receive SYN-ACK and then reset rather than complete a normal application session. Therefore, I would evaluate packet flags, timing, repetition, destinations and subsequent payload/application traffic rather than assuming that every SYN-ACK means a normal user connection.

### Real-World SOC Scenario

A firewall alert reports thousands of connection attempts from one source to many destination ports. In a packet capture I see repeated SYNs, with some targets replying SYN-ACK and the source immediately sending RST instead of proceeding into normal application traffic. That pattern is consistent with scanning as a hypothesis. I would correlate source reputation, target scope, firewall/IDS alerts and whether any full sessions or exploit traffic followed before escalating.

### What I Would Check as a Tier 1 Analyst

- Source/destination IP addresses and ports
- TCP flags: SYN, ACK, RST and FIN
- Whether the full SYN → SYN-ACK → ACK handshake completed
- Timing, repetition and number of destination ports/hosts
- Whether a reset occurs immediately after SYN-ACK
- Whether application-layer traffic follows the handshake
- Firewall/IDS action and connection state
- Endpoint process responsible for the connection where available
- Whether the traffic matches an approved scanner or monitoring tool
- Related DNS, proxy, EDR and threat-intelligence context

### Relevant Tools / Logs

Wireshark or other approved packet-capture tooling; firewall logs; IDS/IPS; NetFlow/network telemetry; Splunk, Microsoft Sentinel or Wazuh; EDR process/network telemetry; DNS/proxy data.

### Key Interview Takeaway

The TCP three-way handshake is SYN, SYN-ACK, ACK. In a SOC investigation, I use it to determine whether I am seeing only connection attempts or an established transport-layer session, then I correlate subsequent application and endpoint evidence before deciding what the traffic means.

- Microsoft documents Windows Security Event ID 4624 as a successful logon session created on the destination computer. The Logon Type field identifies the access method; Type 2 is Interactive, Type 3 is Network, Type 5 is Service and Type 10 is RemoteInteractive/Remote Desktop.

- Wireshark documentation illustrates the normal SYN, SYN-ACK, ACK sequence and notes that a rejected connection can instead return RST.
