# SOC Interview Practice - 2026-09-21

## Question 76

### Interview Question
A user reports that they approved an unfamiliar Microsoft 365 application consent prompt. What is OAuth consent phishing, and how would you investigate it as a Tier 1 SOC analyst?

### Interview-Ready Answer
OAuth consent phishing is an attack in which a user is tricked into granting a malicious or attacker-controlled application permissions to cloud data or services. Unlike classic credential phishing, the attacker may not need the user's password: the user can authorise the application through a legitimate identity-provider consent screen. Microsoft documents that malicious apps can gain access to cloud services and user data after consent is granted.

I would not treat every unfamiliar enterprise application as malicious. I would first establish which application was consented to, who consented, which permissions/scopes were granted, whether admin consent was involved, the publisher/application context, and what the application accessed afterwards. A verified publisher is useful context but is not, by itself, proof that an application is safe.

**Observation:** a user granted consent to an unfamiliar application.

**Hypotheses:** legitimate business app, mistaken consent, or malicious consent phishing.

**Confirmed compromise:** requires evidence that the application is malicious/unauthorised and/or that its granted permissions were abused to access data or perform actions.

### Real-World SOC Scenario
A finance user reports approving an app that claimed it needed Microsoft 365 access to view a shared document. The application requested mail-related permissions. Soon afterwards, cloud audit evidence shows unusual mailbox access through the application.

I would correlate **phishing message/link -> user consent -> application/service principal -> permissions -> sign-in/token/application activity -> mailbox or file access**. If the app is unauthorised and the permissions are followed by suspicious access, I would escalate as a cloud identity/application compromise and follow the approved playbook for revoking consent/tokens or disabling the app where authorised.

### What I Would Check as a Tier 1 Analyst
- User and time of consent
- Application ID, display name and publisher context
- Permissions/scopes granted and whether they are delegated or application permissions
- Whether user or admin consent was involved
- Entra audit/sign-in and enterprise-application evidence
- Microsoft 365/Defender XDR activity after consent
- Mailbox, SharePoint/OneDrive or Graph activity consistent with the permissions
- Original phishing email/link and other recipients
- Whether other users consented to the same application
- Existing organisational approval for the application
- Tier 1 authority for revocation, disablement or escalation

### Tools / Logs
Microsoft Entra ID, enterprise applications/app registrations, Entra audit and sign-in logs, Microsoft Defender XDR/Defender for Office 365 where licensed, Microsoft 365 audit, Microsoft Sentinel/Splunk where integrated, email gateway and proxy/DNS evidence.

### Interview Takeaway
“Consent phishing can give a malicious OAuth application authorised access without stealing the user's password. I would validate the app, consented permissions, user/admin consent and post-consent cloud activity, then revoke or escalate only according to the organisation's response authority.”

### Verification Notes
Microsoft Entra documentation confirms that consent phishing can trick users into granting malicious OAuth apps access to legitimate cloud services and data. Microsoft has also documented real campaigns in which OAuth app permissions were abused for mailbox access and phishing. No claim here assumes that consent alone proves compromise.

## Question 77

### Interview Question
What does Windows Security Event ID 4776 mean, and how would you investigate repeated failures without calling every 4776 event a brute-force attack?

### Interview-Ready Answer
Windows Security Event ID **4776** records credential validation using **NTLM authentication**. Microsoft documents that it appears on the computer authoritative for the credentials: for a domain account that is normally a domain controller; for a local account it is the local computer. The event can record successful or failed validation. Microsoft also notes that the event identifies the **Source Workstation**, but does not provide the destination computer being accessed.

So 4776 is not a generic “failed login” event and is not automatically brute force.

**Observation:** NTLM credential validation attempts occurred.

**Hypotheses:** normal application/service authentication, stale stored credentials, user password mistakes, misconfiguration, password guessing/spraying, or compromised credentials.

**Confirmed attack:** requires a pattern and corroborating evidence showing the attempts are unauthorised or malicious.

I would establish whether the event succeeded or failed, identify the account and source workstation, examine frequency and account distribution, and correlate with logon, endpoint, identity and network telemetry. A repeated failure from one workstation after a password change could be a service or scheduled task using stale credentials; many accounts being tested from one unexpected source would be more concerning.

### Real-World SOC Scenario
A domain controller records hundreds of failed 4776 events from one employee workstation against many domain accounts over a short period.

My observation is a burst of failed NTLM credential validations. My hypothesis is password spraying or automated credential guessing, but I would first rule out a legitimate authentication service or misconfiguration. I would correlate **source workstation -> accounts attempted -> timing/failure pattern -> endpoint process -> successful authentication or follow-on activity**. If EDR shows suspicious tooling and one account later authenticates successfully from the same source, the attack hypothesis becomes much stronger.

### What I Would Check as a Tier 1 Analyst
- Success/failure status and error code
- Account name and domain
- Source Workstation
- Number of accounts and attempts per account
- Time window/rate and baseline
- Whether a password was recently changed
- Services, scheduled tasks or applications that may hold stale credentials
- Related authentication/logon evidence where available
- EDR process activity on the source workstation
- Network/firewall evidence
- Any subsequent successful authentication
- Similar activity elsewhere and Tier 1 escalation authority

### Tools / Logs
Windows Security Event 4776, related Windows authentication/logon events where available, Active Directory/domain-controller logs, Defender for Endpoint or other EDR, Microsoft Sentinel, Splunk, Wazuh, firewall and identity telemetry.

### Interview Takeaway
“4776 records NTLM credential validation. I would not call it brute force from the Event ID alone; I would analyse the account/source pattern, success or failure, error context and endpoint activity, remembering that 4776 gives the source workstation but not the destination system.”

### Verification Notes
Microsoft’s Event 4776 documentation confirms that it is generated for NTLM credential validation, can represent success or failure, occurs on the authority for the credentials, and exposes Source Workstation rather than the destination computer.

## Question 78

### Interview Question
A server records a successful Windows logon with Logon Type 10 from an unusual workstation. How would you investigate possible RDP lateral movement without assuming every remote logon is malicious?

### Interview-Ready Answer
Windows Security Event **4624** records a successful logon. Microsoft documents **Logon Type 10 (RemoteInteractive)** as a remote logon using Terminal Services/Remote Desktop. That tells me a remote interactive session occurred; it does not by itself prove lateral movement.

RDP is a legitimate administrative technology. MITRE ATT&CK maps adversary use of RDP with valid accounts to **T1021.001, Remote Desktop Protocol**, under Lateral Movement.

**Observation:** a successful RemoteInteractive logon occurred.

**Hypotheses:** legitimate administration/support, expected user remote access, or attacker lateral movement using valid credentials.

**Confirmed malicious lateral movement:** requires evidence that the session was unauthorised and associated with compromise or malicious follow-on actions.

I would establish the account, source address/workstation context available in the event/environment, destination asset, time, whether the account normally uses RDP, and what happened during and after the session. I would correlate the destination’s endpoint timeline, process creation, file/service/task changes and network activity. I would also investigate the source host because it may be the previously compromised pivot system.

### Real-World SOC Scenario
A production server records a successful 4624 Logon Type 10 for a finance user at 03:00 from an internal workstation the user does not normally use. Minutes later, EDR records an unusual administrative process and a new remote connection to another server.

The observation is a successful RDP session. The hypothesis is lateral movement using compromised credentials. I would correlate **source endpoint -> account authentication -> RDP session -> destination process activity -> further remote connections**. If the user denies the session, the source endpoint is compromised and malicious actions occur on the server, the lateral-movement hypothesis becomes strong.

### What I Would Check as a Tier 1 Analyst
- 4624 timestamp, account/SID and Logon ID
- Logon Type 10 / RemoteInteractive
- Source network/workstation context available in the environment
- Destination server criticality
- Whether RDP use is normal and authorised for the account
- MFA/RD Gateway/VPN evidence where applicable
- EDR timeline on both source and destination hosts
- Process creation, file transfer, service/task creation and PowerShell activity after logon
- Additional SMB/RDP/WinRM/SSH connections
- Account privilege and recent credential-risk indicators
- Approved maintenance/change window
- Whether the activity is ongoing and Tier 1 containment authority

### Tools / Logs
Windows Security Event 4624, Windows/Terminal Services telemetry where collected, Defender for Endpoint or another EDR, Microsoft Sentinel, Splunk, Wazuh, firewall/VPN/RD Gateway logs, identity telemetry and network evidence.

### Interview Takeaway
“4624 Logon Type 10 tells me a successful Remote Desktop/Terminal Services session occurred. I would validate the account, source, destination and business context, then correlate endpoint and network behaviour on both sides before concluding that it was lateral movement.”

### Verification Notes
Microsoft documents 4624 Logon Type 10 as RemoteInteractive, used for Terminal Services/Remote Desktop. MITRE ATT&CK T1021.001 documents adversary use of RDP and valid accounts for lateral movement. RDP itself remains legitimate, so correlation is required.
