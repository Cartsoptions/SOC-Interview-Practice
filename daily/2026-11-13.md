# SOC Interview Practice — 2026-11-13

**Curriculum:** Questions 213–216 | Malware triage, Wazuh/Sysmon process evidence, Pyramid of Pain detection strategy, and coordinated malware-outbreak response

## Question 213

### Interview Question

Microsoft Defender for Endpoint raises an alert for a low-prevalence unsigned file named `invoice_viewer.exe` in a user's Downloads folder. A VirusTotal hash lookup shows detections from only a small minority of engines. The user opened it after receiving a supplier-themed email. How would you decide whether this is malware without treating the alert or detection ratio as the verdict?

### Interview-Ready Answer

I would explain that malware triage is the controlled process of collecting enough endpoint, file, delivery and behavioural evidence to decide whether an object is benign, unwanted, suspicious or malicious and what response is justified. A low detection ratio is neither proof of malware nor proof of safety. New, targeted, packed or uncommon files may have limited reputation, while legitimate administrative or commercial tools can trigger heuristic detections.

I would preserve the Defender alert and file identifiers, then establish the device, user, file path, SHA-256/SHA-1, first and last seen times, organisational and global prevalence, signer and certificate status, source URL or email, and whether the file executed. Microsoft documents that the Defender file page can show incidents, alerts, file names, first/last seen information, device prevalence, VirusTotal ratio and Defender Antivirus determination. I would examine the device timeline and process tree for the file's parent, children, command lines, files, registry changes, persistence, network connections and security-control tampering.

I would use a hash lookup before considering a file upload. VirusTotal states that a hash search retrieves an existing report without uploading the file, and warns against submitting or querying confidential, sensitive or personally identifiable information. Any sample collection or submission would therefore follow the organisation's authorised malware-analysis procedure. I would not execute the sample on a production workstation; deeper static or dynamic analysis belongs in an approved sandbox or specialist environment.

I would also investigate the delivery path in Defender for Office 365, Proofpoint or the available email gateway: original message, headers, attachment hash, sender history, related recipients, delivery action and user interaction. If the file executed, I would correlate the endpoint and email timelines and hunt the hash, names, paths, parent-child pattern and network indicators across the estate.

Tier 1 should record a reasoned verdict, preserve evidence and initiate or request containment according to the playbook. Microsoft Defender for Endpoint supports actions such as device isolation and collecting an investigation package, but availability depends on onboarding, platform and permissions; I would not claim or perform an action outside my assigned authority.

### Real-World SOC Scenario

The email gateway confirms delivery of the attachment to four users. On one device, `outlook.exe` launches `invoice_viewer.exe`; the file then starts hidden PowerShell, creates a scheduled task and connects to an unfamiliar domain. The same file is absent from approved software inventory and has no valid signer.

- **Observation:** A low-prevalence unsigned file was delivered by email and executed, but the initial multi-engine detection ratio is inconclusive.
- **Hypothesis:** The file is a loader using PowerShell and task scheduling for execution and persistence.
- **Confirmed Evidence:** Email evidence establishes delivery, endpoint telemetry links the file to hidden PowerShell and task creation, and network telemetry confirms communication with infrastructure identified as malicious through approved intelligence sources.

The verdict is **high-severity true positive — malicious loader execution confirmed on one device; three additional recipients and any related infrastructure require scoping**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the alert, file hashes, path, size, timestamps and detection name.
2. Confirm whether the file was written, opened and executed, and by which user.
3. Review signer/certificate information, prevalence and trusted software inventory.
4. Inspect the complete process tree, commands, created files, registry changes and persistence.
5. Correlate network, DNS, proxy and firewall activity.
6. Trace the email or download source and identify every recipient/device.
7. Perform a hash lookup before any authorised sample submission.
8. Hunt the hash and higher-value behavioural indicators across the estate.
9. Escalate for authorised device, file, account and email containment.
10. Record what is observed, what remains hypothetical and what evidence confirms the verdict.

### Relevant Tools / Logs

Defender for Endpoint and Defender XDR device timeline/file page, Defender for Office 365 or Proofpoint, VirusTotal hash lookup, `DeviceProcessEvents`, `DeviceFileEvents` and `DeviceNetworkEvents` where available, Sentinel/Splunk/Wazuh, DNS/firewall/proxy logs, software inventory and incident records.

### Key Interview Takeaway

A detection ratio is context, not a verdict. I would connect delivery, execution, process, persistence and network evidence, use safe hash-first enrichment, and contain only through the approved playbook.

## Question 214

### Interview Question

Wazuh ingests the following Sysmon sequence from a finance workstation shortly after a user opens an emailed document: Event ID 1 shows `winword.exe` starting hidden PowerShell with an encoded command; Event ID 11 records a new DLL under the user's roaming profile; another Event ID 1 shows `rundll32.exe` loading that DLL; and, where network-event logging is enabled, Event ID 3 shows `rundll32.exe` connecting externally. How would you interpret the sequence without assuming that PowerShell or `rundll32.exe` is automatically malicious?

### Interview-Ready Answer

I would treat this as a high-risk execution chain that requires validation, not as four independent alerts. Microsoft documents Sysmon Event ID 1 as process creation, Event ID 11 as file creation and Event ID 3 as network connection; Event ID 3 is disabled by default and only exists when the Sysmon configuration enables it. Wazuh can collect the `Microsoft-Windows-Sysmon/Operational` channel, but useful visibility still depends on the endpoint's Sysmon configuration and collection health.

PowerShell and `rundll32.exe` are legitimate Windows components. The suspicious meaning comes from context: an Office application launches hidden encoded PowerShell, a DLL appears in a user-writable location, and a signed Windows utility loads that DLL and communicates externally. MITRE ATT&CK maps PowerShell abuse to T1059.001 and malicious proxy execution through Rundll32 to T1218.011.

I would preserve the raw XML/JSON events and normalised Wazuh records, confirm timestamps and device identity, decode the PowerShell content in a safe analysis environment, and verify the document, DLL path, hashes, signer, file origin and user activity. I would correlate scheduled tasks or other persistence, DNS/proxy/firewall records, Defender or antivirus detections, and any related email evidence. The process sequence proves the recorded execution relationship and file/network activity; it does not by itself prove the decoded content was malicious or that data was stolen.

If the DLL is confirmed malicious or the decoded command retrieves/executes an unauthorised payload and the network destination is corroborated, I would escalate as a true-positive malware incident. If owner validation and signed-file analysis show an approved business automation with expected destinations, I would document the benign explanation and consider detection tuning through the authorised process.

### Real-World SOC Scenario

The decoded PowerShell downloads the DLL from a newly registered domain. The DLL is unsigned, has no organisational prevalence and creates a scheduled task. Defender records the same process chain and the proxy confirms repeated outbound callbacks.

- **Observation:** Office-to-encoded-PowerShell-to-DLL-to-Rundll32-to-network activity occurred in close sequence.
- **Hypothesis:** A malicious document initiated a staged loader that established persistence and command-and-control communication.
- **Confirmed Evidence:** Safe decoding identifies the download action, file and signer evidence confirm the unauthorised DLL, and endpoint plus proxy telemetry establish execution, persistence and callbacks.

The verdict is **critical true positive — document-delivered malware with PowerShell execution, Rundll32 proxy execution, scheduled-task persistence and confirmed outbound communication**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the original Wazuh/Sysmon events and UTC timeline.
2. Verify Event IDs, endpoint identity, sensor health and Sysmon configuration coverage.
3. Review parent/child processes, command lines, users and integrity levels.
4. Decode encoded content only in an approved analysis environment.
5. Hash and validate the document and DLL; inspect signer and prevalence.
6. Correlate file creation, task/registry persistence and subsequent execution.
7. Correlate DNS, proxy, firewall and EDR network telemetry.
8. Trace the original email and identify related recipients.
9. Hunt the behavioural chain across Wazuh, Defender, Sentinel or Splunk.
10. Escalate for authorised containment and specialist malware analysis.

### Relevant Tools / Logs

Wazuh manager/dashboard and archives where enabled, Microsoft-Windows-Sysmon/Operational, Sysmon Event IDs 1, 11 and conditionally 3, Defender for Endpoint/XDR, Windows Task Scheduler evidence, Defender for Office 365/Proofpoint, Sentinel or Splunk, DNS/proxy/firewall and incident-ticket evidence.

### Key Interview Takeaway

PowerShell and Rundll32 are not malicious by name. The parent-child sequence, encoded content, user-writable payload, persistence and network behaviour determine the verdict.

## Question 215

### Interview Question

Your SOC blocks one malicious file hash, but the attacker changes the file and returns with a new hash while using the same document-to-PowerShell-to-Rundll32 execution pattern and similar callback behaviour. How would you use the Pyramid of Pain and MITRE ATT&CK to improve detection without discarding precise indicators?

### Interview-Ready Answer

I would keep the confirmed hash because it remains a precise indicator for finding or blocking that exact sample, but I would not make the defence depend on hashes alone. The Pyramid of Pain is a threat-intelligence model that orders indicators by the operational cost imposed on an adversary: hashes are easy to change, followed broadly by network indicators and artifacts, while tools and tactics, techniques and procedures are harder to replace. The model does not say that lower-level indicators are useless; it helps explain their durability and how to layer them.

I would convert the incident evidence into several detection layers:

- Exact sample hashes and attachment names for immediate retrospective search.
- Domains, IP addresses and URLs, with expiry/review dates because infrastructure changes.
- Host and network artifacts such as the unusual DLL location, scheduled-task characteristics, parent-child relationships and callback pattern.
- Tool behaviour such as Office spawning hidden encoded PowerShell and Rundll32 loading a user-profile DLL.
- ATT&CK-mapped techniques such as PowerShell T1059.001, Rundll32 T1218.011 and Scheduled Task T1053.005.

I would test these against legitimate administrative baselines and require multiple correlated signals where a single behaviour is noisy. For example, PowerShell alone is common, but Office spawning hidden encoded PowerShell followed by a new user-profile DLL and an external connection is much higher confidence. I would document required telemetry and exclusions, validate the detection against known test data, and send tuning or engineering changes to the authorised detection owner.

This approach also helps hunting. I would use the precise indicators to find known exposure quickly, then hunt the behavioural chain to identify changed payloads. ATT&CK describes adversary behaviour; it does not provide a severity score or prove that a particular event is malicious.

### Real-World SOC Scenario

The hash rule catches the first attachment but misses two repacked variants. A correlated behaviour rule identifies all three because each variant uses the same Office-to-PowerShell chain, writes a DLL beneath the user profile, establishes task persistence and calls back with a consistent timing pattern.

- **Observation:** Exact hashes change, while the execution and persistence pattern remains stable.
- **Hypothesis:** The attacker is cheaply repacking the loader while retaining the same operating method.
- **Confirmed Evidence:** Endpoint and network timelines from all three samples show the same behavioural chain despite different hashes.

The verdict is **a valid hash control with insufficient resilience; retain it and add tested behaviour-based detection and hunting mapped to the observed ATT&CK techniques**.

### What I Would Check as a Tier 1 Analyst

1. Preserve every confirmed hash and associated case context.
2. Separate known-bad indicators from unverified leads.
3. Record IP, domain and URL age, ownership and confidence.
4. Extract stable host, process, persistence and network artifacts.
5. Map only observed behaviours to the correct ATT&CK techniques.
6. Compare the pattern with legitimate software and administrator baselines.
7. Hunt historical data for both exact indicators and the behaviour chain.
8. Identify telemetry gaps across EDR, Sysmon, Wazuh, SIEM and network controls.
9. Escalate detection changes for authorised testing, tuning and deployment.
10. Add review/expiry dates so stale indicators do not remain unquestioned forever.

### Relevant Tools / Logs

Defender XDR/Endpoint, Wazuh and Sysmon, Microsoft Sentinel or Splunk, DNS/proxy/firewall telemetry, Defender for Office 365 or Proofpoint, approved threat-intelligence platforms, MITRE ATT&CK and incident/detection-engineering records.

### Key Interview Takeaway

Use hashes for speed and precision, then add artifact- and behaviour-based detections that cost the attacker more to evade. The Pyramid of Pain guides durability; ATT&CK describes the observed behaviour.

## Question 216

### Interview Question

During the same shift, Defender detects the document-delivered loader on one laptop, Wazuh reports the same persistence behaviour on six more endpoints, DNS logs show repeated callbacks, and a file server records unusual access by one affected user's account. How would you manage the malware outbreak as Tier 1, use the Cyber Kill Chain to explain what happened, and support the NIST incident-response lifecycle?

### Interview-Ready Answer

I would declare or escalate this as a high-severity multi-host incident because the evidence shows execution, persistence, command-and-control activity and possible credential or data impact. I would not treat it as seven independent antivirus tickets.

The Cyber Kill Chain is useful for communicating the sequence: supplier-themed delivery, user execution/exploitation, payload installation, command-and-control callbacks and actions on objectives such as file-server access. Lockheed Martin describes seven stages — reconnaissance, weaponisation, delivery, exploitation, installation, command and control, and actions on objectives. The mapping is an analytical aid; missing visibility at one stage does not prove the stage did not occur, and containment should not wait for every stage to be reconstructed.

I would preserve the original emails/documents, hashes, endpoint alerts and process trees, Wazuh/Sysmon records, persistence artifacts, DNS/proxy/firewall events, sign-in and file-server audit evidence, and a UTC timeline. I would identify every affected user, device, IP, hostname, payload, task, domain and account action while clearly separating confirmed compromise from exposure-only recipients.

Under the approved playbook, I would initiate or request isolation of confirmed hosts, block confirmed malicious infrastructure and files, disable or restrict compromised identities, and remove malicious email from additional mailboxes. Microsoft documents that Defender for Endpoint can isolate a device while retaining its connection to Defender and can collect an investigation package, but those actions require onboarding, supported platforms and appropriate permissions. Business-critical systems and identity actions require coordination with authorised owners.

Scoping would include devices with the same process/persistence behaviour, all email recipients, related network callbacks, use of affected accounts, file-server and cloud access, lateral movement, and any privileged sessions or secrets exposed to infected systems. A file-server access event proves that the account accessed a resource; it does not by itself prove exfiltration. I would check objects accessed, volume, timing, destination activity and business context.

NIST SP 800-61 Rev. 3 frames incident response around Detect, Respond and Recover, supported by broader preparation and continuous improvement. Responders should contain affected systems and identities, eradicate malware, persistence and entry points, and recover through trusted restoration or rebuilding, credential rotation, validation and enhanced monitoring. NIST also recommends identifying all affected hosts and services so weaknesses can be remediated rather than cleaning only the first detected endpoint.

Tier 1 should preserve evidence, maintain the case timeline and affected-asset list, perform approved hunts, request authorised containment, communicate confirmed facts and uncertainty, and escalate eradication/recovery to the responsible incident, endpoint, identity, network and business owners.

### Real-World SOC Scenario

Seven endpoints are confirmed compromised. Two additional email recipients received but did not execute the file. The affected account accessed a sensitive file share, but proxy and DLP evidence show no confirmed outbound transfer. After authorised containment, responders remove the persistence, rotate exposed credentials and rebuild the compromised systems from trusted images.

- **Observation:** The same delivery and behaviour chain appears across seven endpoints, with callbacks and subsequent file-server access.
- **Hypothesis:** The malware may have harvested credentials, spread through shared access or prepared data for theft.
- **Confirmed Evidence:** Email, endpoint, Wazuh, DNS and identity/file-server logs confirm seven compromises and account use; available network/DLP evidence does not yet confirm exfiltration.

The verdict is **critical multi-host malware incident with confirmed execution, persistence, command and control and account misuse; data exfiltration remains unconfirmed and under investigation**.

### What I Would Check as a Tier 1 Analyst

1. Open or escalate one coordinated incident and maintain a UTC master timeline.
2. Preserve email, file, process, persistence, network, identity and file-access evidence.
3. Separate confirmed-compromised devices from exposed-only recipients.
4. Escalate for authorised host, identity, email and network containment.
5. Hunt the hashes, paths, commands, scheduled-task behaviour, domains and callback pattern.
6. Identify every account, token, share and secret available to affected devices.
7. Correlate authentication, file access, cloud activity, lateral movement and egress.
8. Map the evidence to Cyber Kill Chain stages without treating the model as proof.
9. Support specialist eradication, trusted rebuilding and credential rotation.
10. Validate recovery through clean scans, absence of persistence/callbacks and heightened monitoring.
11. Record detection gaps, delayed decisions and lessons for continuous improvement.

### Relevant Tools / Logs

Defender for Endpoint/XDR and Defender for Office 365, Wazuh/Sysmon, Microsoft Sentinel or Splunk, DNS/proxy/firewall, Entra/Active Directory and file-server audit logs, DLP where deployed, VirusTotal hash lookup, approved malware-analysis platforms, incident-management records, MITRE ATT&CK, Cyber Kill Chain and NIST SP 800-61 Rev. 3.

### Key Interview Takeaway

Manage an outbreak as one coordinated incident. Preserve the delivery-to-execution-to-persistence-to-command-and-control chain, contain hosts and identities through authorised owners, distinguish access from proven exfiltration, and validate trusted recovery.
