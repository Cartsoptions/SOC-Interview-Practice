# SOC Interview Practice — 2026-10-22

**Curriculum:** Questions 149–152 | Defender malware alerts, safe file triage, process-tree hunting, and ransomware containment and recovery

## Question 149

### Interview Question

Microsoft Defender for Endpoint reports that `invoice_viewer.exe` was detected and quarantined on a finance laptop. The alert is marked remediated. Would you close it, and how would you decide whether this was prevention or an incident?

### Interview-Ready Answer

I would not close the case solely because the file was quarantined or the alert says remediated. Quarantine is a response action against the detected file; I still need to determine whether the file executed before remediation, created child processes, changed the system, contacted other infrastructure or reached other devices.

In a SOC environment, I would first confirm the alert source, detection time, affected device and user, file path, hash, signer, first-seen time and action status. I would check the Defender Action center to verify that quarantine or another remediation action actually completed. Microsoft documents quarantine, process stopping and other remediation actions, but the action taken against one entity does not establish that the whole incident has been contained.

I would reconstruct the device timeline around the detection. The difference between prevention and compromise is evidence: if the file was blocked before execution and there is no related activity, it may be a prevented attempt. If it executed, spawned a script interpreter, wrote files, established persistence or made suspicious network connections, I would treat it as an incident even if the original file was later quarantined.

I would also avoid automatically restoring or excluding the file because a business user says it is legitimate. Microsoft warns that exclusions reduce protection; a disputed detection should go through the approved false-positive and file-submission process. Tier 1 should collect evidence, classify and escalate. Endpoint/security administrators normally approve exclusions, restoration or wider policy changes.

### Real-World SOC Scenario

The Action center confirms that Defender quarantined `invoice_viewer.exe` at 10:08. Device telemetry shows it executed at 10:06, spawned `powershell.exe`, created a second executable in the user's profile and contacted a newly observed domain. No approved software or change record explains the sequence.

- **Observation:** The original file was quarantined after execution; correlated process, file and network activity occurred first.
- **Hypothesis:** The file acted as a loader that launched a second-stage payload and attempted external communication.
- **Confirmed evidence:** Execution and unauthorised follow-on activity are confirmed. Malware family, persistence, credential access, data theft and full device scope remain unconfirmed until separately evidenced.

The verdict is **true positive — confirmed unauthorised execution and endpoint compromise; quarantine removed one file but did not prove full containment**.

### What I Would Check as a Tier 1 Analyst

1. Confirm alert source, severity, device, user, detection name, file path/hash, signer and first/last-seen details.
2. Verify the remediation state in the Action center rather than relying on an alert summary alone.
3. Determine whether the file was written, blocked, quarantined, executed or stopped, and place those events in timestamp order.
4. Review the process tree, parent/child command lines, file writes, registry or scheduled-task changes and network connections.
5. Check device criticality, user privilege, sensor health and whether the host is online, isolated or still communicating.
6. Hunt across the estate for the hash, file name/path, signer, domains, URLs and behavioural sequence.
7. Establish user actions and file origin, such as email, browser download, removable media or software deployment.
8. Invoke or request authorised isolation, scanning, file blocking and evidence collection when the risk justifies it.
9. Escalate with confirmed facts, hypotheses, scope, remediation status, evidence locations and decisions required.
10. Close only after the incident scope and recovery criteria are satisfied, not merely because the original file is quarantined.

### Relevant Tools / Logs

Microsoft Defender XDR incident and device timeline, Defender for Endpoint file page and Action center, `DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents` and `DeviceEvents` where available, Microsoft Sentinel or Splunk, email/proxy/DNS logs, software inventory, change records and case management.

### Key Interview Takeaway

Quarantine is an entity-level remediation action, not proof that execution never occurred or that the endpoint is clean. I would validate the action, reconstruct what happened before it and scope all follow-on behaviour.

## Question 150

### Interview Question

During malware triage, a SHA-256 search returns 18 detections in VirusTotal, while the file has a valid digital signature and is common on ten corporate devices. How would you assess it safely, and how does the Pyramid of Pain affect your detection strategy?

### Interview-Ready Answer

I would treat the VirusTotal result, signature and prevalence as evidence to interpret, not as competing automatic verdicts. A multi-engine detection ratio is useful reputation context, but it does not prove that every detection is correct or that the file behaved maliciously in our environment. A valid signature establishes a signing relationship and file integrity after signing; it does not guarantee that the software is safe, authorised or uncompromised. Prevalence can reduce or increase suspicion, but widespread software can still be abused.

I would begin with a hash lookup rather than uploading the file. VirusTotal documents that reports can be retrieved by MD5, SHA-1 or SHA-256. I would not upload a confidential, customer or internally developed sample to the standard service without policy approval. VirusTotal states that its Private Scanning workflow must be used to keep a submitted item private; this means the analyst must understand the organisation's data-handling rules before submitting bytes.

Safe static triage would include file type and size, exact path, hashes, signer and certificate status, version metadata, compile timestamp as weak context, strings/imports where approved, first/last seen, internal/global prevalence, known names, source and associated alerts. I would not execute the sample on my workstation. Dynamic analysis belongs in an approved sandbox or specialist workflow.

I would then connect the file to behaviour: which parent launched it, what command line ran, what children it created, whether it wrote files or persistence and which destinations it contacted. The process and network evidence is generally more durable than a hash alone.

David Bianco's Pyramid of Pain orders indicators from hash values through addresses, domains, host/network artefacts and tools to tactics, techniques and procedures. A file hash is valuable for immediate scoping and blocking but is trivial for an adversary to change. Behavioural detection such as an unusual document application spawning encoded PowerShell and a suspicious network chain is harder to evade because the attacker must change more of the operation.

### Real-World SOC Scenario

The signed file is a legitimate remote-management utility, but finance users are not authorised to run it. It appears for the first time on the affected laptop, was launched by an unexpected script and connects to an external tenant not used by the organisation.

- **Observation:** The binary is signed and known, but its path, parent, user population and destination are inconsistent with approved use.
- **Hypothesis:** An attacker is abusing a legitimate tool for remote access or persistence.
- **Confirmed evidence:** Unauthorised installation and execution are confirmed by software policy and endpoint telemetry. Malicious operator intent, initial access and data theft require further evidence.

The verdict is **true positive — unauthorised execution of a legitimate remote-management tool, requiring incident investigation; the signature and VirusTotal ratio do not override local behaviour**.

### What I Would Check as a Tier 1 Analyst

1. Record all hashes, names, paths, size, file type, signer, certificate chain and version metadata.
2. Compare internal prevalence, first/last seen and affected-device roles with approved software inventory.
3. Perform a hash-only reputation lookup first; check scan date, vendor labels, relationships and behavioural context.
4. Do not upload file contents unless classification, privacy and organisational policy permit it; use an approved private workflow when required.
5. Review file origin, download/referrer evidence, email delivery, user action and deployment/change records.
6. Correlate parent/child processes, command lines, persistence, service/task creation, file writes and network destinations.
7. Distinguish malicious files from legitimate tools used maliciously and from genuine false positives.
8. Scope and block the hash where justified, but add behaviour-, tool- and TTP-focused detection so a recompiled or renamed sample is still visible.
9. Escalate disputed detections through the documented submission and exception process; do not create an exclusion independently.

### Relevant Tools / Logs

Defender for Endpoint file page, device timeline and advanced hunting; VirusTotal hash reports and approved private-scanning workflow; digital-signature and certificate information; Sentinel/Splunk; software inventory/allowlist; proxy/DNS/email logs; approved static-analysis or sandbox tooling; case management.

### Key Interview Takeaway

Reputation, signatures and prevalence are contextual signals. I would make the verdict from local execution evidence and business authorisation, use hashes for rapid scope, and build more durable detections around artefacts, tools and TTPs.

## Question 151

### Interview Question

Defender shows the following simulated process sequence on `FIN-LT-022`. How would you interpret it, what KQL would you use to retrieve the process evidence, and what can the artefact prove?

```text
10:06:14  explorer.exe
  └─ WINWORD.EXE                 C:\Users\Ayo\Downloads\Invoice.docm
       └─ powershell.exe         -NoProfile -EncodedCommand <redacted>
            └─ rundll32.exe      C:\Users\Ayo\AppData\Local\Temp\stage.dll,Start
```

### Interview-Ready Answer

The chain is high risk because a document application launches PowerShell with an encoded command, which then launches `rundll32.exe` against a DLL in a user-writable temporary directory. Each program can have legitimate uses, so process names alone do not prove malware. The strength comes from the unusual parent-child relationships, command-line context, file location and any corroborating file or network activity.

MITRE ATT&CK maps adversary abuse of PowerShell to T1059.001 and suspicious use of `rundll32.exe` to execute a DLL to T1218.011. These mappings describe observed behaviours and help with hunting; they do not identify the actor or prove that every PowerShell or Rundll32 execution is malicious.

I would run a scoped query in Microsoft Defender XDR Advanced Hunting:

```kusto
let targetDevice = "FIN-LT-022";
let startTime = datetime(2026-10-22 09:55:00);
let endTime = datetime(2026-10-22 10:20:00);
DeviceProcessEvents
| where Timestamp between (startTime .. endTime)
| where DeviceName =~ targetDevice
| project Timestamp,
          DeviceName,
          AccountName,
          FileName,
          FolderPath,
          ProcessCommandLine,
          SHA1,
          InitiatingProcessFileName,
          InitiatingProcessFolderPath,
          InitiatingProcessCommandLine,
          InitiatingProcessSHA1,
          ProcessId,
          InitiatingProcessId,
          ReportId
| order by Timestamp asc
```

Microsoft documents `DeviceProcessEvents` as process-creation and related telemetry populated by Defender for Endpoint. The projected columns are documented fields. I use SHA-1 because Microsoft notes on several device schemas that SHA-256 fields are often not populated; a separate SHA-256 can still be collected from the file page when available. `ReportId` must be combined with device and timestamp context rather than treated as a globally unique event number.

The query can prove what Defender recorded during the selected period: process names, command lines and initiating-process relationships. It cannot by itself decode the redacted payload, prove that `stage.dll` is malicious, establish successful network communication or confirm user intent. I would pivot to file, network, registry, logon and email/browser evidence.

### Real-World SOC Scenario

The query reproduces the chain. File telemetry shows that `WINWORD.EXE` wrote `stage.dll`, network telemetry shows PowerShell connected to an unapproved domain immediately before Rundll32 started, and the user confirms opening the emailed document. No approved automation explains it.

- **Observation:** A macro-enabled document led to encoded PowerShell, a DLL write and Rundll32 execution, with a correlated external connection.
- **Hypothesis:** The document delivered a staged payload that used PowerShell and Rundll32 for execution or defence evasion.
- **Confirmed evidence:** The document-to-script-to-DLL execution chain and unauthorised network activity are confirmed. Malware family, persistence, credential access, lateral movement and attribution remain unconfirmed.

The verdict is **true positive — confirmed malicious-looking document execution chain and endpoint compromise, requiring containment and broader scoping**.

### What I Would Check as a Tier 1 Analyst

1. Validate device identity, user, timestamps/time zones and process identifiers.
2. Preserve complete command lines and original telemetry; do not decode or execute unknown content on a production workstation.
3. Retrieve the document and DLL hashes, paths, signer status, first/last seen and prevalence through approved tooling.
4. Correlate `DeviceProcessEvents` with file writes, network connections, registry changes, scheduled tasks/services and security-control events.
5. Trace the document's origin through email or browser/proxy telemetry and determine other recipients/downloads.
6. Hunt for the same parent-child chain, DLL path/hash, domains, command fragments and behavioural sequence across the estate.
7. Check for credential access, privilege escalation, persistence, discovery, lateral movement, collection and exfiltration.
8. Invoke or request authorised isolation and evidence collection, then escalate with the timeline, scope and remaining gaps.
9. Use ATT&CK mappings as behavioural labels, not as proof of actor identity or a substitute for the incident verdict.

### Relevant Tools / Logs

Microsoft Defender XDR Advanced Hunting and device timeline; `DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents`, `DeviceRegistryEvents` and `DeviceEvents` where available; Defender for Office 365 or browser/proxy logs; Sentinel/Splunk; VirusTotal hash lookup; approved sandbox/static-analysis tools; case management.

### Key Interview Takeaway

I would judge the complete execution chain, not a single process name. The KQL retrieves documented process evidence; corroborating file, network and business context turns a suspicious chain into a defensible incident verdict.

## Question 152

### Interview Question

Several users report renamed or unreadable files on a shared drive. Defender shows rapid file modifications on two laptops, a ransom note appears, and one host attempted to disable recovery features. As Tier 1, how would you prioritise, contain, scope, escalate and support recovery?

### Interview-Ready Answer

I would treat this as a critical suspected ransomware incident with active business impact. A ransom note and rapid unauthorised encryption provide strong evidence of encryption for impact; attempted disabling of recovery features increases urgency. I would immediately invoke the ransomware playbook and notify the incident lead rather than waiting to identify the malware family.

Containment must be rapid but authorised. I would isolate affected endpoints through EDR or request immediate isolation, and I would ask the infrastructure/storage owner to protect the shared service according to the recovery plan. I would not improvise by powering off every system, deleting files or disconnecting backups without IR direction because that may destroy evidence, interrupt critical services or affect recoverability.

Microsoft Defender for Endpoint supports device isolation, antivirus scanning and investigation-package collection subject to licensing, platform support and permissions. Isolation retains connectivity to the Defender service, but VPN and service-connectivity considerations must be understood. I would verify every submitted action in the Action center and record failures or offline devices.

I would scope by device, user, process/hash, command line, file extension, ransom-note name, network share, account, remote session, service/task, destination and time pattern. I would check whether a privileged or service account performed changes, whether the same indicators or behaviours appear elsewhere and whether backup systems or domain services were accessed.

MITRE ATT&CK maps confirmed encryption for operational disruption to T1486, Data Encrypted for Impact. Evidence that recovery mechanisms were disabled or removed supports T1490, Inhibit System Recovery. These are behaviour mappings, not malware-family or actor attribution.

NIST SP 800-61 Rev. 3 integrates incident response with CSF 2.0 and emphasises Detect, Respond and Recover activities supported by preparation and risk management. For recovery, authorised teams should eradicate persistence, rebuild or remediate from a trusted state, rotate exposed credentials, validate clean backups before restoration, test services, restore in a controlled order and maintain heightened monitoring. Paying a ransom, negotiating or making legal/regulatory notifications is an executive/legal decision, not a Tier 1 action.

### Real-World SOC Scenario

The same user account authenticated to both laptops shortly before encryption began. One laptop ran an unknown executable from a temporary directory; the second received a remote process shortly afterwards. The shared drive is affected, but offline backups are reported intact and have not yet been used.

- **Observation:** Two endpoints and shared data show active unauthorised encryption; a recovery-inhibition attempt and cross-device account activity are present.
- **Hypothesis:** The first laptop may be the initial execution point, and the account or remote-management path may have enabled spread to the second device and share.
- **Confirmed evidence:** Encryption impact on the two endpoints/shared drive is confirmed. The initial-access method, account compromise, lateral-movement mechanism, data theft, backup integrity and actor identity remain unconfirmed until separately evidenced.

The verdict is **critical true positive — confirmed encryption-for-impact incident with suspected lateral spread; immediate coordinated containment and recovery activation are required**.

### What I Would Check as a Tier 1 Analyst

1. Declare/escalate under the ransomware playbook and record incident ownership, severity, business services and decision makers.
2. Build a UTC-normalised timeline from first suspicious execution through account activity, remote access, recovery inhibition and encryption.
3. Invoke or request isolation of affected endpoints and verify the action; identify offline or unsupported devices requiring another approved containment route.
4. Coordinate with storage/network teams to limit further access to affected shares while preserving evidence and business-critical availability decisions.
5. Preserve EDR timelines, process/file/network evidence, ransom notes, hashes, affected extensions, logon/audit records and investigation packages.
6. Scope users, privileged/service accounts, endpoints, servers, shares, backup systems, remote-management tools and related network destinations.
7. Check for prior credential access, privilege escalation, security-control tampering, persistence, discovery, lateral movement, staging and exfiltration.
8. Do not assume encryption means data theft; investigate exfiltration separately and communicate only supported impact.
9. Hand Tier 2/IR a concise timeline, affected assets, containment status, evidence confidence, business impact, gaps and urgent decisions.
10. Support recovery validation: trusted rebuild/remediation, credential rotation, backup integrity testing, controlled restoration, service-owner testing, sensor health and monitoring for recurrence.
11. Feed lessons into segmentation, privileged access, backup protection, EDR coverage, detection content and response exercises.

### Relevant Tools / Logs

Microsoft Defender XDR/Defender for Endpoint device timelines, advanced hunting, device isolation and Action center; Sentinel or Splunk; Windows security/audit and file-server logs; identity, VPN/RDP, firewall, DNS and proxy telemetry; backup/storage consoles; Wazuh where deployed; CMDB, change management and incident case records.

### Key Interview Takeaway

For active ransomware, I would escalate and contain immediately within authority, preserve evidence, scope accounts and infrastructure, keep encryption and exfiltration as separate findings, and support recovery only from a validated trusted state.

## Verification Notes

- Microsoft documents that the Defender for Endpoint device investigation experience provides device timelines, exposure context and response actions. Supported response actions vary by product plan, platform and permissions.
- Microsoft documents quarantine, process stopping and other remediation actions and records completed or pending actions in the Action center. A remediated entity does not by itself prove that no execution or follow-on activity occurred; that conclusion requires timeline evidence.
- Microsoft warns that antivirus exclusions reduce protection and recommends using them sparingly. The answers therefore route disputed detections through approved review/submission rather than instructing Tier 1 to create an exclusion.
- Microsoft documents the Defender file page as showing file attributes, associated incidents/alerts, organisation prevalence, first/last seen information, VirusTotal detection ratio and Microsoft Defender Antivirus detection.
- VirusTotal documents hash-based file-report retrieval using MD5, SHA-1 or SHA-256. VirusTotal also states that its Private Scanning form must be used to keep uploads private. The answers therefore recommend hash lookup first and prohibit unapproved upload of sensitive samples.
- The Pyramid of Pain is David Bianco's indicator model: hashes, IP addresses, domains, host/network artefacts, tools and TTPs rise in the cost imposed on an adversary when defenders detect and deny them. It is a detection-durability model, not an evidence-confidence score.
- Microsoft documents `DeviceProcessEvents` as process-creation and related telemetry populated by Defender for Endpoint. The KQL in Question 151 uses documented columns and deliberately avoids relying on undocumented `ActionType` values.
- The `ReportId` field is a repeating counter and requires device and timestamp context for unique-event interpretation. The query is scoped to one device and a bounded time period.
- MITRE ATT&CK T1059.001 describes adversary abuse of PowerShell; T1218.011 covers suspicious Rundll32 proxy execution; T1486 covers data encrypted for impact; and T1490 covers disabling or removing recovery mechanisms. These mappings label evidenced behaviours and do not establish attribution.
- NIST SP 800-61 Rev. 3 was finalised on 3 April 2025 and supersedes Rev. 2. It integrates incident-response recommendations into CSF 2.0. NIST SP 800-61 Rev. 2 is withdrawn and is not used as the current incident-response authority.
- All identities, devices, file names, domains, timestamps, hashes and process artefacts in these scenarios are simulated. The encoded command is intentionally redacted and should not be executed.
