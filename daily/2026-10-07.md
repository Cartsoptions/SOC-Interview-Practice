# SOC Interview Practice — 2026-10-07

## Question 117

### Interview Question

What is defense evasion, and how would you investigate it as a Tier 1 SOC analyst?

### Interview-Ready Answer

Defense evasion is attacker behaviour intended to reduce, bypass, or interfere with security visibility and controls. In a SOC, I would not treat every security-tool or logging change as malicious because authorised maintenance, policy deployment, and troubleshooting can produce similar events. I would establish what changed, who or what changed it, whether it was authorised, and what activity occurred immediately before and after.

Current MITRE ATT&CK includes Disable or Modify Tools (T1685), with sub-techniques covering Windows Event Log changes and log clearing. The practical SOC lesson is to correlate control impairment with identity, process, endpoint, and network evidence rather than use the control-change event as a verdict.

Observation: a logging or security control changed.
Hypothesis: an attacker may be reducing visibility before or after malicious activity.
Confirmed Evidence: the change is shown to be unauthorised and/or is corroborated by malicious activity around the same time.

### Real-World SOC Scenario

A workstation stops forwarding expected security telemetry shortly after an unusual privileged login. I would verify agent/service health and approved maintenance, then inspect identity, endpoint, process, and network evidence around the gap. If the telemetry loss follows unauthorised privileged activity or a process that altered a security control, I would escalate promptly.

### What I Would Check as a Tier 1 Analyst

- Affected host, user, timestamp, and control
- Change/maintenance records and known platform issues
- Privileged logons and process activity before the change
- SIEM ingestion/agent health versus true host-side logging impairment
- EDR, network, identity, and other independent telemetry
- Other hosts showing the same pattern
- Playbook escalation/containment authority

### Tools / Logs

Microsoft Sentinel, Defender XDR/Defender for Endpoint, Windows Event Logs, Splunk, Wazuh, Sysmon where deployed, identity logs, firewall/proxy/DNS telemetry, and change-management records.

### Interview Takeaway

"Defense evasion is behaviour intended to reduce or bypass security visibility or controls. As Tier 1, I verify whether the change is authorised, correlate it with surrounding identity/process/network evidence, scope the impact, and escalate when the evidence supports malicious impairment."

## Question 118

### Interview Question

What does Windows Security Event ID 1102 mean, and does it prove an attacker cleared logs?

### Interview-Ready Answer

Microsoft documents Security Event ID 1102 as "The audit log was cleared." It is generated when the Windows Security audit log is cleared. The event includes the account that cleared the log, and its Logon ID can help correlate the action with a recent logon such as Event 4624.

Event 1102 proves that the Security audit log was cleared; it does not by itself prove malicious intent. Microsoft recommends monitoring and investigating this event because manually clearing the Security log is normally uncommon.

MITRE ATT&CK's current model maps Windows event-log clearing under Disable or Modify Tools: Clear Windows Event Logs (T1685.005).

Observation: the Security audit log was cleared.
Hypothesis: an attacker may be removing evidence.
Confirmed Evidence: requires context showing the action was unauthorised or associated with malicious activity.

### Real-World SOC Scenario

Event 1102 appears on a server at 02:10 under an administrator account. I would correlate the account and Logon ID, determine the source/session, check the approved change window, and pivot to EDR/SIEM/network telemetry that may survive outside the cleared local log. If the administrator denies the action and suspicious privileged/process activity precedes the clear, priority rises substantially.

### What I Would Check as a Tier 1 Analyst

- Account Name, Account Domain, Logon ID, computer, and timestamp
- Correlated successful logon/session evidence
- Approved maintenance/change records
- EDR process telemetry and command line where available
- Central SIEM copies of events preceding the clear
- Other logs or hosts affected
- Post-clear activity and evidence gaps

### Tools / Logs

Windows Security Event 1102, Windows Event Logs, Sentinel/Log Analytics, Splunk, Wazuh, Defender for Endpoint/XDR, Sysmon where deployed, identity and network telemetry.

### Interview Takeaway

"1102 means the Windows Security audit log was cleared. I treat it as a high-value investigation event, but not automatic proof of an attacker; I identify the actor/session, validate authorisation, and reconstruct the surrounding activity from independent telemetry."

## Question 119

### Interview Question

Explain this Microsoft Log Analytics / Sentinel KQL query:

```kusto
WindowsEvent
| where Provider == "Microsoft-Windows-Security-Auditing"
| where EventID == 1102 or EventID == 4719
| extend DescriptionMessage = iff(EventID == 1102, "Audit log was cleared", "System audit policy was changed")
| take 100
```

### Interview-Ready Answer

This is a Microsoft-published example for the WindowsEvent table. It selects events from the Microsoft-Windows-Security-Auditing provider, keeps Event ID 1102 or 4719, creates a readable DescriptionMessage, and returns up to 100 matching records.

Microsoft documents 1102 as the Security audit log being cleared and 4719 as the system audit policy being changed. Microsoft recommends monitoring 4719, especially on high-value assets, because audit-policy changes should be planned.

The query is useful for finding potentially important logging/auditing changes, but it does not prove defense evasion. It also uses take 100 without ordering, so I would not describe it as an exhaustive or chronological incident timeline.

Observation: matching audit-policy/log-clear events exist.
Hypothesis: logging visibility may have been deliberately impaired.
Confirmed Evidence: requires raw-event and contextual correlation showing unauthorised malicious change.

### Real-World SOC Scenario

The query returns a 4719 event followed by 1102 on the same critical server. I would inspect the raw records, affected audit subcategory/change, actor/session, approved changes, and independent EDR/SIEM/network telemetry. I would also determine whether 4719 reflects a genuine effective policy change rather than assuming intent from the event alone.

### What I Would Check as a Tier 1 Analyst

- Raw 1102/4719 events and timestamps
- Account/Logon ID and affected host
- For 4719: category, subcategory, and change details
- Change-management context and host baseline
- Events before the log clear retained centrally
- EDR/process and network evidence
- Similar activity on other assets

### Tools / Logs

Microsoft Sentinel/Log Analytics WindowsEvent, Windows Security logs, Defender XDR/Endpoint, Splunk, Wazuh, Sysmon where deployed, change records, and network telemetry.

### Interview Takeaway

"The query surfaces Windows audit-log clears and audit-policy changes. It is a triage lead, not a compromise verdict; I pivot to the raw events and correlate actor, authorisation, endpoint, and network evidence."

## Question 120

### Interview Question

A domain controller records Event 4719 changing audit policy. Minutes later, Event 1102 shows the Security audit log was cleared. The same administrator account had an unusual remote logon shortly beforehand. How would you triage this?

### Interview-Ready Answer

I would treat the sequence as high priority because the correlation suggests possible defense impairment: unusual privileged access, audit-policy change, then Security-log clearing. I would still avoid declaring compromise until I validate the events and authorisation.

First I would reconstruct the timeline and correlate the administrator's authentication/session with the 4719 and 1102 records. For 4719 I would inspect which audit category/subcategory changed and whether Success or Failure auditing was added or removed. For 1102 I would identify the account and Logon ID responsible for clearing the Security log.

Next I would check approved change activity and verify the administrator's expected behaviour. I would preserve and pivot to centrally retained SIEM data, EDR telemetry, identity logs, and network evidence because local evidence may have been removed.

MITRE's current ATT&CK detection strategy for Windows event-log clearing explicitly correlates elevated activity with log clearing and can use Event 1102 plus process telemetry. NIST SP 800-61 Rev. 3 is the current NIST incident-response guidance and integrates incident response into CSF 2.0 risk management.

Observation: unusual privileged logon, audit-policy change, and Security-log clear occurred in sequence.
Hypothesis: a compromised privileged account may be impairing logging to hide subsequent or prior activity.
Confirmed Evidence: examples include the administrator denying the actions, no approved change, process/EDR evidence of unauthorised log manipulation, or malicious activity correlated around the logging changes.

### Real-World SOC Scenario

If the administrator denies the session, no approved change exists, and EDR shows an unexpected process under that privileged context immediately before the log clear, I would escalate urgently as a likely privileged compromise with defense impairment. I would scope other systems touched by the account and preserve remote/central evidence. Any containment action would follow the organisation's playbook and my Tier 1 authority.

### What I Would Check as a Tier 1 Analyst

- Source, outcome, and context of the administrator's remote logon
- 4719 category, subcategory, and exact audit-policy change
- 1102 actor, domain, Logon ID, host, and timestamp
- Approved change/maintenance records
- Centrally retained pre-clear logs
- EDR process tree/command line and security-control events
- Other systems accessed by the administrator
- Network, DNS/proxy/firewall, and identity evidence
- Scope, evidence preservation, and escalation/containment authority

### Tools / Logs

Windows Security 4719/1102 and authentication logs, Microsoft Sentinel, Defender XDR/Endpoint, Splunk, Wazuh, Sysmon where deployed, firewall/proxy/DNS telemetry, identity logs, and change-management records.

### Interview Takeaway

"I would investigate the chain, not each alert in isolation. An unusual privileged logon followed by audit-policy change and Security-log clearing is high risk. I validate authorisation, preserve central evidence, reconstruct the activity from independent telemetry, scope the privileged account, and escalate quickly when the evidence supports defense impairment or compromise."
