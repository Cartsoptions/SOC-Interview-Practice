# SOC Interview Practice — 17 August 2026

## Question 1: What is a firewall, and how would you use firewall information as a SOC analyst?

### Interview-Ready Answer
In a SOC, I would describe a firewall as a security control that enforces network traffic rules between systems or network zones. As a Tier 1 analyst, I may not be the person designing the firewall policy, but firewall logs are important evidence during an investigation. If an alert shows repeated connections from a suspicious external IP to an internal server, I would review whether the firewall allowed or denied the traffic, the source and destination IPs, ports/protocols, timestamps, and whether the activity matches expected business traffic. I would then correlate that evidence with SIEM, endpoint, authentication, DNS, proxy, or other available telemetry before deciding whether the activity is benign, suspicious, or needs escalation.

### Real-World SOC Scenario
A SIEM alert shows repeated inbound attempts against a public-facing server. I would use firewall telemetry to determine what was targeted and whether any traffic was permitted. A blocked connection alone does not prove compromise; an allowed connection alone does not prove malicious activity. Both are observations that need correlation.

### What I Would Investigate
- Source and destination IP addresses
- Destination port/protocol and direction of traffic
- Allow/deny action and applicable rule, where available
- Frequency and timing of connections
- Reputation/context of the source IP
- Related endpoint, authentication, DNS, proxy, IDS/IPS or application events
- Whether there is evidence of successful access or follow-on activity

### Relevant Tools / Logs
Firewall logs, SIEM, EDR, IDS/IPS, DNS logs, proxy logs and authentication logs.

### Key Interview Takeaway
A SOC analyst uses firewall telemetry as one source of evidence and correlates it with other data before concluding that an incident occurred.

## Question 2: You see many Windows failed-logon events. What would you do first?

### Interview-Ready Answer
I would not immediately label repeated failed logons as a brute-force attack. I would first establish what the events actually show. On Windows, Security Event ID 4625 represents a failed logon and is generated on the computer where the access attempt occurred. I would review fields such as the account, logon type, source/workstation or network information when present, failure status/substatus, authentication details, timestamps and the number/distribution of attempts. I would then correlate the failures with successful logons and other identity or endpoint evidence.

A pattern of many passwords attempted against one account may be consistent with password guessing, while a small number of common passwords attempted across many accounts may be consistent with password spraying. Those are hypotheses until the surrounding evidence supports them.

### Real-World SOC Scenario
The SIEM produces an alert for 100 failed logons. If they all come from one expected service using an expired credential, that is very different from attempts against many employee accounts from an unusual external source. The alert starts the investigation; it does not provide the conclusion.

### What I Would Investigate
- Target account(s)
- Source host/IP when available
- Logon type
- Failure reason/status and substatus
- Attempt count and time pattern
- Whether one account or many accounts are targeted
- Successful logons around the same period
- Known service accounts, scheduled tasks or expected administrative activity
- Identity, VPN, EDR and network telemetry where available

### Relevant Tools / Logs
Windows Security logs, SIEM, identity-provider logs, Active Directory/domain-controller telemetry, VPN logs and EDR.

### Key Interview Takeaway
Event ID 4625 means a logon failed; it does not by itself prove an attack. Investigate the pattern and correlate evidence before classifying it.

## Question 3: What is a SIEM, and how would you actually use one during a shift?

### Interview-Ready Answer
On the job, I would think of a SIEM as the place where security telemetry from multiple systems is collected and searched so analysts can detect and investigate activity across the environment. During a Tier 1 shift, I might start with an alert, inspect the underlying events, identify the affected user or host, expand the time range, search for related activity, and correlate endpoint, authentication, firewall or other logs. The goal is not simply to close alerts; it is to determine what the available evidence supports and escalate when the scope, severity or uncertainty requires it.

### Real-World SOC Scenario
Suppose a SIEM alert flags suspicious authentication activity for a user. I would review the events that triggered the rule, compare source locations/IPs and timestamps, check whether there are successful authentications, and look for related endpoint or network activity. If evidence suggests account compromise, I would follow the organisation's incident process and escalate with the relevant evidence rather than making unsupported assumptions.

### What I Would Investigate
- Why the detection rule fired
- User, host, IP and timestamp context
- Related events before and after the alert
- Successful versus failed activity
- Endpoint/network/identity correlation
- Whether the behaviour has a legitimate explanation
- Evidence needed for escalation and documentation

### Relevant Tools / Logs
SIEM platforms such as Wazuh or Splunk; Windows/Linux logs; EDR; firewall; DNS; proxy; VPN and identity-provider telemetry depending on the environment.

### Key Interview Takeaway
A SIEM helps centralise and correlate evidence, but an analyst still has to investigate the underlying events and distinguish observations from conclusions.

## Verification Notes
- Microsoft documentation confirms Windows Security Event ID 4625 represents a failed logon and is generated where the logon attempt occurred. Microsoft also documents fields such as logon type, process/network information and failure information as useful investigation context.
- MITRE ATT&CK identifies Brute Force as T1110, Password Guessing as T1110.001, Password Spraying as T1110.003 and Credential Stuffing as T1110.004. Password spraying uses a small set of passwords across many accounts, whereas password guessing can involve repeated guesses against accounts.
- The investigation guidance above deliberately treats alerts and individual log events as observations requiring correlation rather than proof of compromise.
