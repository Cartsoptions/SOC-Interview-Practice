# SOC Interview Practice — 2026-11-05

**Curriculum:** Questions 189–192 | Secure-web-proxy investigation, OAuth consent phishing, Microsoft Sentinel `AuditLogs` hunting, and full malicious-application containment and recovery

## Question 189

### Interview Question

A secure web proxy records that a user visited a newly registered website and downloaded a file over HTTPS. The proxy action is `allowed`, but Microsoft Defender for Endpoint later reports suspicious execution from the user's Downloads folder. Explain what a proxy contributes in this situation and how you would investigate.

### Interview-Ready Answer

A forward web proxy sits between users and external web services. Depending on its design and policy, it can mediate outbound HTTP/HTTPS access, apply URL or content controls, authenticate users, record destinations and enforcement actions, and sometimes inspect permitted TLS traffic. An `allowed` action means that the observed request was permitted by that proxy policy; it does not mean the site or downloaded content was safe.

In a SOC environment, I would use the proxy evidence to establish the user or device, timestamp, requested URL, destination, category, action, response, user agent and transferred object information that the deployed product actually records. I would verify whether TLS inspection was active for that flow because visibility may be limited when traffic is not decrypted. CISA recommends preserving proxy logs and, where possible, URI parameters because web-proxy evidence helps identify initial-access, payload and command-and-control infrastructure.

I would correlate the proxy event with browser history or download telemetry, Defender process and file events, DNS and firewall activity, email or chat provenance, and the actual file hash and signature. An allowed download is only an observation. Confirmation requires evidence that the file reached the endpoint and executed or caused unauthorised activity.

Tier 1 should preserve and correlate the evidence, invoke approved endpoint or indicator containment, and escalate. Proxy policy design, certificate deployment, TLS-inspection exceptions and broad category changes belong to network/security engineering because they can have privacy and business-impact implications.

### Real-World SOC Scenario

The proxy records an allowed download named `SecureViewer.iso`. Defender shows the browser writing that file, the user mounting it, and `viewer.exe` launching PowerShell followed by a rare outbound connection. The user says the link arrived in an unsolicited support message, and no approved application matches the file.

- **Observation:** The proxy allowed an HTTPS download from a newly registered site, and endpoint telemetry shows the corresponding file on disk.
- **Hypothesis:** The website delivered a malicious file that initiated endpoint compromise.
- **Confirmed Evidence:** Download-to-file correlation, user execution, unauthorised PowerShell activity, outbound communication and absence of approved software establish malicious execution.

The verdict is **high-severity true positive — confirmed malware delivery through an allowed web-proxy session followed by endpoint execution and outbound activity; the encrypted network content alone did not establish the verdict**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the raw proxy event and confirm timestamp, user/device attribution, URL, destination and action.
2. Establish whether TLS inspection applied and what request, response or file metadata was actually visible.
3. Correlate the proxy event with DNS, firewall, browser and endpoint telemetry.
4. Confirm whether the object was downloaded, written, opened and executed.
5. Review the file hash, signature, prevalence, path and approved-software inventory.
6. Examine the complete process tree, command lines, child processes and network connections.
7. Identify the link's source, such as email, chat, search result or advertising redirect.
8. Hunt for the URL, domain, hash and execution chain across other users and devices.
9. Invoke authorised device isolation, indicator restriction or content removal under the playbook.
10. Escalate confirmed scope, actions, business impact and proxy-visibility limitations.

### Relevant Tools / Logs

Secure web gateway/proxy logs, Defender for Endpoint and Defender XDR, `DeviceFileEvents`, `DeviceProcessEvents` and `DeviceNetworkEvents` where available, DNS/firewall logs, browser or download telemetry, Microsoft Sentinel or Splunk, threat intelligence, software inventory and case-management records.

### Key Interview Takeaway

An allowed proxy event proves that the control permitted the request—not that the content was benign. I would correlate the web session with endpoint file creation, execution and follow-on behaviour.

## Question 190

### Interview Question

A Microsoft 365 user receives a message offering a document-conversion service. The link opens a genuine Microsoft consent page, and the user grants an unfamiliar application delegated `Mail.Read` and `Files.Read` permissions. The user says they never entered their password on a suspicious site. How would you investigate possible consent phishing?

### Interview-Ready Answer

OAuth consent allows an application to request authorised access to protected data without receiving the user's password. Delegated permissions allow the application to act within the granted scope on behalf of the signed-in user. Consent phishing abuses this legitimate flow: the user authenticates to the real identity provider but authorises a malicious or deceptive application.

The absence of password submission therefore does not make the event harmless. Microsoft documents that delegated `Mail.Read` allows an application to read the signed-in user's mailbox, while the risk of any grant depends on the exact permission, app purpose, publisher, consent type and user context. Microsoft also warns that consent itself is not automatically malicious; defenders should investigate new grants, suspicious app names or publishers, unnecessary permissions and high-profile users.

I would preserve the message and consent URL, identify the application ID and service-principal object ID, determine who granted consent, record the exact delegated scopes, and review whether the app is verified, known and approved. I would search Entra audit logs for `Consent to application`, examine related app changes and users, and review Defender for Cloud Apps or resource-level activity for what the application subsequently did.

A consent grant proves authorisation, not abuse. Confirmation requires evidence that the application is unauthorised or malicious and that it obtained or used inappropriate access. Within Tier 1 permissions, I would escalate immediately and invoke the approved malicious-app playbook. Revoking consent, disabling the service principal, revoking user sessions or changing tenant consent policy requires the appropriate identity/security authority.

### Real-World SOC Scenario

The app uses a generic name, has an unverified publisher and is absent from the approved application inventory. Entra records the user's consent, and Defender for Cloud Apps shows the app accessing mailbox and file activity shortly afterwards. Four other users received the same lure.

- **Observation:** A user granted an unfamiliar OAuth application delegated access to mail and files through a legitimate Microsoft consent page.
- **Hypothesis:** The application is using consent phishing to obtain persistent access without stealing the user's password.
- **Confirmed Evidence:** Unapproved application identity, excessive permissions, campaign evidence and subsequent app-attributed mailbox/file access establish malicious use.

The verdict is **critical true positive — confirmed consent-phishing campaign with malicious OAuth application access; the precise data viewed or removed must be scoped from downstream activity logs**.

### What I Would Check as a Tier 1 Analyst

1. Preserve the lure, sender, message identifiers, consent URL and delivery/click evidence.
2. Record application ID, service-principal object ID, display name, publisher and verification status.
3. Review `Consent to application` activity, initiating user, result, target and correlation ID.
4. Identify exact delegated/application permissions and whether admin or user consent was involved.
5. Compare the requested permissions with the application's stated business purpose.
6. Identify every user who granted consent or received the lure.
7. Review app-attributed mailbox, file, Graph and cloud activity after consent.
8. Examine the user's sign-ins and account changes for separate credential compromise.
9. Invoke authorised app, grant, session and message containment under the playbook.
10. Escalate confirmed data access separately from unproven exfiltration or disclosure.

### Relevant Tools / Logs

Microsoft Entra audit and sign-in logs, Microsoft Purview Audit, Defender for Cloud Apps/App Governance where licensed, Defender for Office 365, Defender XDR, Microsoft Sentinel, Graph and workload activity logs, enterprise-application inventory and incident-management records.

### Key Interview Takeaway

Consent phishing can succeed on a legitimate Microsoft page without stealing a password. I would investigate the application, exact permissions, affected users and downstream resource activity.

## Question 191

### Interview Question

Microsoft Entra audit logs are connected to Microsoft Sentinel. Write a safe first-pass KQL query to find application-consent activity from the last seven days, and explain what the results can and cannot prove.

### Interview-Ready Answer

I would start with documented `AuditLogs` columns and preserve the dynamic evidence instead of assuming a fixed position for every nested property:

```kusto
AuditLogs
| where TimeGenerated >= ago(7d)
| where OperationName == "Consent to application"
| project TimeGenerated,
          OperationName,
          Result,
          ResultDescription,
          Identity,
          InitiatedBy,
          TargetResources,
          AdditionalDetails,
          CorrelationId
| order by TimeGenerated desc
```

Microsoft documents `AuditLogs` as the Sentinel/Log Analytics table for Entra directory activity. `OperationName`, `Result`, `ResultDescription`, `Identity`, `InitiatedBy`, `TargetResources`, `AdditionalDetails`, `CorrelationId` and `TimeGenerated` are documented columns. Microsoft also documents `Consent to application` as the audit activity for a user granting consent to an application.

This query returns recorded consent operations within the selected period. The `InitiatedBy`, `TargetResources` and `AdditionalDetails` values are dynamic objects, so I would inspect their raw contents before writing environment-specific parsing. This avoids silently depending on array positions or property layouts that may vary between operation versions.

The results do not prove that an application is malicious, that its tokens were used, or that data was accessed. I would inspect the exact application, actor, permissions and result; correlate events by `CorrelationId`; compare the app with the approved inventory; and search downstream application/resource activity. I would also verify connector health, ingestion delay and retention before treating absence as evidence that no consent occurred. Microsoft notes that corresponding audit entries can be delayed.

### Real-World SOC Scenario

The query returns five successful consent events for the same unfamiliar application. Raw `TargetResources` and modified-property details show mail and file permissions; the users received the same lure, and subsequent cloud activity is attributed to the app.

- **Observation:** Sentinel contains successful `Consent to application` audit events for several users and one unfamiliar application.
- **Hypothesis:** A coordinated consent-phishing campaign persuaded users to authorise malicious access.
- **Confirmed Evidence:** Common lure, unauthorised application, inappropriate scopes and subsequent app activity establish malicious consent abuse.

The verdict is **critical true positive — confirmed multi-user malicious application consent and use; each user's downstream data impact still requires individual scoping**.

### What I Would Check as a Tier 1 Analyst

1. Verify Entra diagnostic settings, connector health, workspace, retention and ingestion delay.
2. Preserve complete raw events before flattening dynamic fields.
3. Review result, initiating identity, target application and correlation ID.
4. Inspect modified properties for consent type and permission scopes.
5. Compare application and publisher information with the approved inventory.
6. Identify all users and administrators associated with the app.
7. Correlate `Add service principal`, delegated-permission and app-role assignment activity where relevant.
8. Search Defender for Cloud Apps, Graph, Exchange, SharePoint and OneDrive activity for subsequent use.
9. Document what the query proves and which telemetry gaps remain.
10. Escalate with the query, raw evidence, app identifiers, users, permissions and containment recommendation.

### Relevant Tools / Logs

Microsoft Sentinel, the `AuditLogs` table, Entra audit logs, Microsoft Purview Audit, Defender for Cloud Apps/App Governance, Defender XDR, Microsoft Graph activity, Exchange/SharePoint/OneDrive audit evidence and enterprise-application inventory.

### Key Interview Takeaway

The query finds consent events, not malicious applications. I would preserve the dynamic audit evidence and correlate permissions, app identity and downstream activity before reaching a verdict.

## Question 192

### Interview Question

You confirm that six users granted a malicious OAuth application access to mail and files. The application subsequently read messages and accessed SharePoint documents, while the original lure remains in other mailboxes. How would you contain, scope, eradicate and support recovery as Tier 1?

### Interview-Ready Answer

I would treat this as a critical multi-user cloud incident involving malicious application persistence and confirmed data access. My immediate objectives would be to stop further authorisation and token use, preserve the evidence, identify every affected user and resource, and remove the original lure.

Microsoft's current application-investigation playbook recommends examining consent, permissions, application/service-principal activity, owners and related identities. For containment, disabling the compromised or malicious application is a common strategy, but Microsoft advises balancing security and business impact. Microsoft also documents revoking application permissions and user sign-in sessions through authorised administrative procedures.

I would escalate to identity, Microsoft 365, legal/privacy and incident-response owners. Under the approved playbook, authorised specialists could disable the service principal, revoke the malicious consent grants, revoke affected users' sessions and remove campaign messages. Password resets may be appropriate if separate credential compromise exists, but a password reset alone does not remove an OAuth consent grant.

Containment may not invalidate every already-issued access token immediately. Microsoft notes that disabling a malicious OAuth application denies new token and refresh-token requests while existing access tokens can remain valid until expiry, and session revocation can take several minutes. Monitoring must therefore continue after containment.

I would scope what the app actually accessed using Graph, Exchange, SharePoint, OneDrive, Purview and Defender for Cloud Apps evidence. `Mail.Read` or `Files.Read` permission establishes potential capability; resource audit events establish observed access. Data exfiltration, external disclosure or misuse must not be claimed without supporting evidence.

Eradication and recovery should include removing unauthorised grants or app objects according to specialist guidance, checking for additional owners/credentials/roles, reviewing affected accounts, validating legitimate integrations, restoring business access where needed and monitoring for renewed consent. NIST SP 800-61 Rev. 3 supports recording response actions, preserving evidence, verifying incident magnitude, executing secure recovery and producing an after-action report.

### Real-World SOC Scenario

Identity administrators disable the malicious service principal and revoke its grants. Security operations remove the lure and revoke affected sessions. Audit evidence identifies 240 messages and 18 SharePoint files accessed by the app, but shows no outbound sharing or mail sending. Monitoring finds no renewed consent after recovery.

- **Observation:** Six users granted the app mail/file permissions, and resource logs show subsequent mailbox and SharePoint access.
- **Hypothesis:** The attacker used OAuth tokens to collect sensitive organisational information and may attempt further fraud or phishing.
- **Confirmed Evidence:** Consent, app-attributed resource activity and campaign correlation establish malicious access to specified messages and files.

The verdict is **critical true positive — confirmed multi-user consent-phishing incident with malicious mailbox and SharePoint access; external disclosure or exfiltration remains unconfirmed without additional evidence**.

### What I Would Check as a Tier 1 Analyst

1. Preserve consent, app, service-principal, user and resource activity records with UTC timestamps.
2. Record application IDs, object IDs, publisher, permissions, owners, credentials and affected users.
3. Identify every lure recipient, click, consent event and related application.
4. Escalate for authorised service-principal disablement and grant revocation.
5. Revoke affected sessions and reset credentials only where the playbook and evidence require it.
6. Remove or quarantine campaign messages across the organisation.
7. Scope mailbox, Graph, SharePoint, OneDrive and other workload activity by the app.
8. Check for mail sending, forwarding, external sharing, file download and privilege/owner changes.
9. Monitor for residual token use, re-enabled applications, restored objects or renewed consent.
10. Support specialist-led eradication, business validation and secure restoration of legitimate access.
11. Document confirmed access separately from suspected disclosure or exfiltration.
12. Feed lessons into consent policy, publisher verification, user training, detections and the incident playbook.

### Relevant Tools / Logs

Microsoft Entra audit/sign-in logs, Microsoft Sentinel, Microsoft Purview Audit, Defender for Cloud Apps/App Governance, Defender for Office 365, Defender XDR, Microsoft Graph activity logs, Exchange/SharePoint/OneDrive audit evidence, application inventory, ticketing and legal/privacy escalation channels.

### Key Interview Takeaway

Contain both the malicious application and its grants, then prove impact from resource activity. A password reset alone is not sufficient, and permission scope is not the same as confirmed data access.
